## 二、逐项证据

### P1 【3.1.1】自然语言自动分解为层次化节点，识别核心主题与分支逻辑

> 原文：「研究如何通过大语言模型（如GPT、Claude等）将用户输入的自然语言（关键词、句子或段落）自动分解为层次化的思维导图节点，并识别核心主题与分支逻辑。」（段 034）

**证据**：`backend/app/agent/tools.py:10095` `_generate()` 是唯一生成入口，机制为三段：

- 骨架：`_skeleton_outline()`（`tools.py:3455`）从材料目录/图谱概念清单里定一级分支；覆盖率 <60% 不拼（`_skeleton_plan` `tools.py:1871`、`_cap_plan:1894`）。
- 结构：一次调用只写 `id/label/层级`，不写正文。
- 说明：`_fill_details()`（`tools.py:5633`）按节点数切两半并发，只写 `detail`。
- 工具注册按意图分组：`_ALLOWED_BY_INTENT`（`tools.py:16253`），`create` 只有 `mindmap_generate`。

**判定 A**。计划书说的"分解 + 识别核心主题与分支逻辑"落在骨架与结构的接缝上，且比原文更进一步（材料带目录时按章节、无目录时按图谱概念）。用例：`tests/test_skeleton.py`、`test_detail_round.py`、`test_single_call_generate.py`。

**差在哪**：无实质偏差。唯一保留项是"结构合理性"没有系统评测——那是 P21 的事，不是这一条没做（`docs/FEATURES_AND_OWNERS.md` F01 已注明）。

### P2 【3.2.1】文本输入

> 原文：「支持文本、语音、图像（如手绘草图）甚至PPT输入」（段 037）

**证据**：`backend/app/ingestion/router.py:34` `POST /api/ingestion/text` → `service.py:106` `parse_text()`（空串显式 422，不返回空 Source）；长文本在 `_intake`（`tools.py:7127`）里自动变成材料而非主题。

**判定 A**。**差在哪**：无。

### P3 【3.2.1】语音输入

**证据**：`backend/app/ingestion/asr.py:53-55` 端点 `dashscope.aliyuncs.com` + 模型 `qwen-audio-3.1-asr-flash`；`asr.py:50` `MAX_SLICE_SECONDS = 300` 自动切片；`asr.py:293` `transcribe_audio()`；入口 `ingestion/router.py:56-58`，前端 `frontend/src/audio/recorder.ts` + `components/VoicePress.vue`。

**判定 B**。做到了什么：文本 + 句级时间戳写进 `Source.sentences`。

**差在哪**（三条，都在代码里写明）：

1. **格式窄**：`AUDIO_SUFFIXES = {".wav"}`（`service.py:88`），`router.py:70-71` 对 mp3/m4a/aac/amr/ogg 直接 422 并要求转 WAV。计划书只说"语音"，未限定格式，交付面比承诺小。
2. **依赖云端**：需 `DASHSCOPE_API_KEY`，缺凭证时整条路 422，没有本地降级（`docs/RESEARCH-ASR-LOCAL.md` 是调研，不是实现）。
3. **时间戳没接到引用**：`SourceRef` 只支持字符区间（`FEATURES_AND_OWNERS.md` F07 未做项）。

### P4 【3.2.1】图像（手绘草图）输入

**证据**：`vision_pdf.py:142-159` 单图走 OpenAI 兼容 `image_url` + base64 data URL，与 PDF 逐页同一条路；`CONCURRENCY = 8`（`vision_pdf.py:60`）；`IMAGE_SUFFIXES = {".png",".jpg",".jpeg",".webp",".gif",".bmp"}`（`service.py:93`）；不可用时 `VisionUnavailable`（`vision_pdf.py:97`）→ 422，不返回空正文。

**判定 B**。**这里是"真给模型看画面"，不是"文件名当图片"**——`router.py:72-73` 的提示语反证了这一点（SVG 被拒的理由是"模型拿到的是 XML 而不是画面"）。

**差在哪**：

1. 模型输出的是 **Markdown 文本**（草图按层级还原成缩进列表、截图提标题正文、图表转表格），**不识别节点间关系**、无来源标注、无人工修正入口（F06 未做项）。
2. SVG 不收。计划书举的例子是"上传一张产品设计草图"——位图可满足，矢量稿不可。

### P5 【3.2.1】PPT 输入

**证据**：`.pptx` 在 `DOCUMENT_SUFFIXES`（`service.py:78-80`）→ `_parse_office_source()`（`service.py:284`）走 Docling 非版式流水线；`.ppt` 在 `LEGACY_RENDER_SUFFIXES`（`service.py:83`）→ `_parse_legacy_rendered_source()`（`service.py:321`）经 LibreOffice 转 PDF 后复用视觉提取。

**判定 B**。**差在哪**：

1. `.ppt`（97–2003 二进制）依赖系统级 LibreOffice（约 1.5GB）。`docker-compose.yml` 里 `WITH_OFFICE: ${WITH_OFFICE:-0}`，**容器镜像默认不带**——同一份代码在 systemd 部署能处理 `.ppt`，在容器部署不能。这是"部署形态决定功能成立与否"，计划书没有这层区分。
2. 计划书期望的"AI 自动关于此 PPT 的思维导图"成立，但**页码级定位没有**（`SourceSpan.page` 只记总页数），点引用回不到原页（F05 未做项）。

### P6 【3.2.2】自动布局（树/流程/鱼骨）+ 颜色图标 + 偏好学习与个性化推荐

> 原文：「AI根据内容主题自动设计导图布局（如树状图、流程图、鱼骨图），并适配颜色、图标等视觉元素。」「研究用户偏好学习，实现个性化风格推荐。」（段 040-041）

**证据**（分派点只有一处，`frontend/src/canvas/layout/index.ts:66-72`）：

- 树：`layout/tidy.ts`（四种朝向）；流程：`layout/flow.ts`（dagre 分层 TB、判定菱形更大、回退边虚线）；鱼骨：`layout/fishbone.ts`（主骨横贯、六类斜插、头在右是几何定死）。
- 配色：`tools.py:1939` `_fill_branch_colors()`、`1981` `_palette_fill()`；导入侧色值归一化 `importing/colors.py:126-158`。
- 图标：`normalize_icon()` 按 Unicode 类别挡掉"把字当图标"；`tools.py:2025` `_strip_plan_icons()`。
- 偏好：`prefs/service.py:59-95`（A/B/C 三类键）＋ `prefs/style.py:360 observe()` / `540 summarize()` / `604 refresh()`（8 个结构参数的中位数画像）。

**判定 B**（三个子项分档：布局 **A**、颜色图标 **A**、风格定制 **B**、"偏好学习" **B**）。

**差在哪**：

1. **主题预设/字体/主色前端不渲染**。`Theme.preset` 只存在于契约（`api/types.ts:404`、`api/schema.d.ts:2620`）与 `contract-check.ts:22` 的注释里；`styles.css` 里没有 preset 分支，字体只有一行固定的 `font-family`（`styles.css:11`）。所以"五套主题、三种字体、主色"是**契约里有、界面没有**——这一类属于"做了不生效"。
2. **"偏好学习"不是模型学习**：显式写入 + "近 3 次一致才提一条建议"的规则（`prefs/service.py:30-33` 记录了 06:02/06:04 两个相反要求的实测依据）。统计画像（`style.py`）只在排序/提示词层加分，开关 `MINDMAP_PROFILE_RERANK` 默认关。协同过滤与 Bandit 都没有（缺多用户与曝光记录）。

### P7 【3.3.1】外部知识库集成 + 自动填充/验证

> 原文：「连接行业数据库（如学术论文、百科）、企业文档或用户个人知识库，自动填充或验证节点内容。示例：用户输入"碳中和"，AI自动关联政策、技术路径、企业案例等分支。」（段 044-045）

**证据**：五源在 `knowledge/external.py:348-355`（中文维基 API / arXiv / OpenAlex / Crossref / 快百科 URL）；个人库 `knowledge/library.py:205 ingest()`、`456 prune()`（保留 90 天 / 200 份）；材料自动入库 `knowledge/remember.py`；没材料时先联网（`tools.py:893 external_knowledge_off_reason()`、`922 external_knowledge_enabled()`）。

**判定 B**。**差在哪**：

1. **"验证"只到逐字命中**：`optimization/source_refs.py` 判的是"这句话出自那里"，**不判来源可靠、不判事实正确**（`optimization/service.py:45-49` 把理由写死了）。
2. **企业文档与权限没有**：五源全是公网只读源；个人库只有只读入口，写侧（删除/重新导入）没做。
3. **"碳中和 → 政策/技术路径/企业案例"这类定向分支靠外部检索的偶然命中**，不是知识库里的结构化关联。实测外部检索覆盖率 97.2%（`docs/PROJECT-STATUS.md:133`），但那是"能拿到 ≥1 条"，不是"三分支都有"。
4. 部署侧还有个坑：`docker-compose.yml` 把外部代理默认改成 `none`，容器里默认直连；`external.py:196` 的代码缺省值是作者本机 Clash 地址。

### P8 【3.3.2】逻辑纠错与冲突检测

> 原文：「AI识别思维导图中的逻辑矛盾、冗余节点或缺失环节，提出优化建议（如"分支A与分支B存在因果关系，建议添加连接线"）。」（段 047）

**证据**（这条比 `FEATURES_AND_OWNERS.md` 里的旧记录做得多，旧记录说"前端 0 次调用"已过期）：

- 后端：`optimization/service.py:461 check()`（单子节点 / 达深度上限 / 同级重复标签 / 引用核验）、`479 suggest()`、`185 _SUGGESTION_OF_CODE`、`207 NOT_SUGGESTED`。
- 前端**真有界面，且入口追到了按钮**：`components/StructureCheck.vue:218` `@click="check.runFull(sources.readySources)"`（面板内重检按钮）、`components/ChatDock.vue:547` `structure.checkAfterGenerate()`（生成落地后自动体检）、`components/ChatDock.vue:561` `structure.runFull(sources.readySources)`（对话框侧手动入口）、`stores/structure.ts:185-240`（`run()` / `checkAfterGenerate()` / `runFull()`）、`api/client.ts:379/397/476`（check / suggest / repair 三个函数）。面板渲染规则见 `StructureCheck.vue` 文件头（`warn`/`error` 展开、info 折叠、原码可查、`ATTENTION_LIMIT=6`）。

**判定 B**。**差在哪**（三条，都对得上计划书的原句）：

1. **"分支A与分支B存在因果关系，建议添加连接线"做不到**。`optimization/service.py:52-62` 把原因写清了：`relations`（跨节点关系）**界面上根本不渲染**（`frontend/src/mindmap/edits.ts` 原话：用户看不到那条残留关系，也没法删），所以这类建议"做了用户也看不见结果"。前置条件是先把 `relations` 画出来，不是补一个检测函数。
2. **"逻辑矛盾"检测没有**。现有 NLI 判的是"节点论断与**引用原文**是否相反"，不是"图内两个节点互相矛盾"；且默认关。实测反例：24 条真实引用有 4 条被误判成相反。
3. **只对树生效**：`stores/structure.ts:190-198` 对鱼骨/流程直接返回 `unsupported` 并给一句人话，理由是后端 `check()` 签名只认 `MindMapContent`，传过去会 500。三种图型里两种进不去体检。

### P9 【3.4.1】多人实时协作中的 AI 辅助

> 原文：「在团队协作场景下，AI扮演"协作者"角色：自动整合多用户输入、解决冲突提议、记录讨论轨迹。」（段 050）

**证据**：**零**。全仓 `yjs|CRDT` 只命中 `docs/`；`room|presence` 在 `backend/app/**` 与 `frontend/src/**` 里零业务命中（`optimization/service.py:553` 的 `room` 是"剩余额度"变量名）；`WebSocket` 唯一出现是 `ingestion/router.py:91` 的注释（语音转写内部用），不是协作通道。界面上的"模型协作"（`AgentPanel.vue:396-400`）指人机，不是人人。

**判定 C（完全没做）**。现有 `version` 乐观锁只能防覆盖，不能合并并发编辑 —— 那不是实时协作。依赖关系：F18（AI 汇总多人输入）没有协作事件可喂。

## 三、三件必须纠正

排序标准：**答辩/验收时最容易被问穿，且纠正成本最低**。不是"最严重"，是"最该先改"。

### 第一件：`<3 秒 / <5 秒` 两条指标（P19、P21）

**为什么是这件**：它是唯一**物理不可达**的承诺（D 档），且原文在两处重复（段 089、段 113），验收阶段（第五阶段"对照预期成果指标进行验收评估"）必然逐条对表。实测 41.0–139.5 秒，差 14–46 倍——这不是"再优化一下"能补的距离，因为瓶颈是 `节点数 × 0.35 秒` 的模型输出量。

**代价**：改两句话。改完立刻自洽，且能拿首帧 0.1s 这个实测数字去支撑新口径。

## 四、两件该改计划书

标准：**实现比计划书更对**，且能给出可直接替换的原句。

### 第一件：向量库（P18）—— Milvus/Pinecone → SQLite 缓存 + numpy

**原句**（段 085）：

> 数据预处理：将思维导图样本转换为向量格式，存入 Milvus/Pinecone。

**问题**：这句话在 2C2G 单机目标下是**负优化**，有实测：查询慢 8–19 倍（179 ms vs 9.5–21.6 ms）、常驻 +119 MB、拖进 19 个依赖包（约 75 MB）、且 Milvus Lite 官方不支持 Windows（本机是未承诺组合）。而它想解决的问题（ANN 索引）在几千条向量这个规模上不存在——Milvus 用的 FLAT 内部也是暴力扫。

**替换句**：

> 数据预处理：将思维导图节点与材料块转换为 1024 维向量（`text-embedding-v3`），以 `(文本指纹, 模型名)` 为键缓存在本机 SQLite 中；检索用归一化向量的余弦矩阵乘完成。在 3652 节点规模下实测单次检索 9.5–21.6 ms。本期不引入独立向量数据库：同规模下 Milvus Lite 查询 179 ms、常驻内存 +119 MB，而 ANN 索引在数千条量级无收益。复评门槛（历史节点 ≥50 万 / 单次查询 ≥500 节点 / 并发 ≥10 QPS）与实测数据见 `docs/OPTIMIZATION-CROSS-MAP.md`。

**顺带的收益**：这句话改写后，"为什么不用 Milvus"从"我们简化了"变成"我们量过"。答辩时这是加分项，不是欠账。

### 第二件：前端 PUML 渲染（P15）—— viz.js/plantuml-encoder → 服务端导出

**原句**（段 076，节选）：

> 基于pluml-encode和viz.js 处理puml代码

**问题**：这不是技术选型差异，是**语法层面的不可能**。`viz.js` 只接受 **DOT** 语言，不接受 PlantUML 语法；`plantuml-encoder` 只做 URL 压缩编码，**出图需要 PlantUML 服务端（JVM）**。两个库组合起来无法在浏览器内把 PUML 渲染成图。仓库对此有专门记录（`docs/ARCHITECTURE_ADDENDUM.md`），把理由写在了留下的那一天。

**替换句**：

> PlantUML 采用"服务端生成 + 下载"形态：后端按图型（树 / 流程 / 鱼骨）输出 `.puml` 文本，与 Markdown / OPML / JSON 并列，共四种导出格式；JSON 是唯一的无损格式。不在浏览器内渲染 PUML：`viz.js` 只认 DOT 语法，`plantuml-encoder` 仅做压缩编码、出图依赖 JVM 服务，两者组合无法完成前端渲染。导出实现见 `backend/app/export/service.py`，逐字节回归用例 `tests/test_export.py::ByteIdenticalTest`。

**为什么这两件，不是 Docker/K8s**：K8s 那条确实是过度设计（2C2G 单机、`docs/DOCKER.md` 自己说明容器化是为可选形态、现有生产仍走 systemd），但它的偏差性质是"规模不匹配"，属于 B 档正常收缩；而上面两条是**计划书的技术判断本身不成立**，不改会在答辩现场被直接指出来。K8s 的处置建议写在 P19：把"Kubernetes"改成"单机容器化（可选形态）+ systemd（生产形态）"，并注明 compose 尚未真机验证。

### 6.3 我今天在这里避开的两个坑

用户提到的两次误判（grep 不到 `Dockerfile` 就判"没做"、grep 到 `image` 就以为"图片当材料"），本质是同一个错误：**把"检索工具的命中情况"当成"实现的事实"**。这次我用三条方法对冲：
