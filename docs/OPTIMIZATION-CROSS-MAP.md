# 跨图参照：节点向量索引实测，以及为什么没装 Milvus

> 2026-11-19，本机（2C2G / Windows / Python 3.13）实测。
> 复现：`cd backend ; python scripts/measure_cross_map.py --embed --ab`。
> 结论先行：**"跨图参照"这个功能有真增量（+43 条建议、抽检 10 条全成立），
> 但它需要的不是向量数据库，是 embedding 缓存 + 一次矩阵乘。**

---

## 0 一句话结论

| 问题 | 答案 |
|---|---|
| 优化建议的瓶颈是"检索引擎"吗 | **不是**。全库 3652 个节点，numpy 暴力扫一次 15–60 ms，比一次 `suggest()` 的模型层（1.4 s）小两个数量级 |
| Milvus Lite 在这个规模上是负优化吗 | **是**。查询慢 10–19 倍、常驻内存 +119 MB，而它省下的那部分（暴力扫 → ANN）在这个规模上不存在 |
| 那该做什么 | 做 `cross_map`（本文件第 4 节），向量缓存进已有的 `chunk_vectors`，检索用 numpy |
| 什么时候才该换 Milvus | 见第 7 节的三个门槛，现在一个都没到 |

---

## 1 先量：四类候选各有多少

判断"装不装"的前提是"装完有没有用"。所以第一步不是接引擎，是把现有图库跑一遍。

**样本**：库里 24 张图 + `runs.candidate` 里 68 份生成结果，去掉 22 张画布回归基线
（节点标签是「第二条分支」「A 侧交付面」这类占位文本，见
`scripts/measure_cross_map.py` 的 `FIXTURE_TITLES`），**真图 58 张、3652 个节点**。

| # | 候选类型 | 数量 | 说明 |
|---|---|---|---|
| ① | 语义冗余（图内节点对余弦 ≥ 0.85） | **3775 对** | 其中 **3528 对跨分支**——规则层只看同级，完全看不见 |
| | 其中同级、规则层也应报却没报 | **247 对** | `_near_reason` 是编辑距离判据，这 247 对一个都没抓到 |
| ② | 矛盾（`annotate_nli` 可判的引用） | **1319 条** | 但本机 NLI 未启用（无模型目录），contradiction **恒为 0** |
| ③ | 缺失环节（兄弟完备性差异） | **101 处** | 其中同一父节点下 ≥3 个兄弟的 92 处 |
| ④ | 现状：`suggest(model=off)` | **77 条 / 58 张图** | 13 张图有建议，45 张图 0 条 |

三个必须先说清的前提：

1. **① 不接近 0，而且规则层的盲区比它的覆盖面大得多**。3528 : 247 ≈ 14 : 1——
   规则层能看见的那一小块（同级标签的编辑距离）根本没有覆盖"语义冗余"这件事。
   这推翻了"图本来就没问题，所以加什么都是 0 条"这个假设。
2. **② 的口径与需求对不上**。用户要的是"图内节点互相矛盾"，而 `annotate_nli`
   判的是"节点论断与**引用原文**是否相反"——它有 `source_refs` 才工作，没有引文
   的节点它一次都不看。本机 1319 条可判引用里，NLI 未启用所以一条结论都没有。
   要做"图内矛盾"得另写判据，而那是 LLM 的活（见第 5 节的 24 条模型层建议：
   人工抽检真 9 / 边界 6 / 假 9）。
3. **③ 的 101 处不等于 101 个"缺失环节"**。"五个兄弟有子节点、一个是叶子"在
   很多图上是**正常**的（"其他"类分支本来就该是叶子）。它只说明"这里有差异可看"，
   与 ① 的"差异真实存在"是同一级别的信号，都需要人判。

## 2 选型：三个都测了，三个都不该用

`docs/ARCHITECTURE.md` 的部署目标是 **2C2G 单机**。三个候选在这个约束下的样子：

| | 部署形态 | 2C2G 能不能跑 | 结论 |
|---|---|---|---|
| **Milvus Lite** | `pip install milvus-lite`，单文件 | 能跑（实测） | 见下：**慢 10 倍、+119 MB** |
| **Milvus Standalone** | docker compose + etcd + MinIO | 跑不动（官方最低 8 GB） | 出局 |
| **Pinecone** | 云 | — | 数据出境 + 按量计费，与"单机自托管"的目标冲突；而且它解决的问题（亿级向量的 ANN）这里不存在 |

### 2.1 Milvus Lite 的三个数（1000 条 × 1024 维，FLAT / COSINE）

| 指标 | 数值 |
|---|---|
| 写入 1000 条 | **688 ms** |
| 打开库 | 506 ms |
| 查询 top-10（首次 / 之后） | **186 ms / 179 ms** |
| 进程常驻内存增量 | **+119 MB**（207 → 326 MB） |
| 依赖体积 | `pymilvus` 拖进 **19 个包**（faiss-cpu 16.6 MB、grpcio 5.6 MB、pandas 10.7 MB、pyarrow 29 MB…），装完约 75 MB |

内存那条在 2C2G 上是硬约束：Docling 常驻约 350 MB、语音峰值约 250 MB、NLI
（如果启用）再 +140 MB。再加 119 MB 意味着"开了跨图参照就不能同时开别的重模块"。

### 2.2 它能不能用，与它在 Windows 上跑不跑得起来是两件事

Milvus 官方只支持 Linux / macOS。本机（Windows 11 / Python 3.13）上
`milvus-lite 3.2.2 + pymilvus 3.0.3` **能启动、能写入、能查询**——但这是
未承诺的平台组合，把它写进 `requirements.txt` 等于把一个"官方不支持的组合"
变成部署前提。这一条本身就够劝退，不需要再看性能。

### 2.3 API 兼容性：这一点 Milvus 做得对

`MilvusClient` 那一套（`create_schema` / `prepare_index_params` / `insert` /
`search`）在 Lite 与 Standalone 上是同一份代码，LOCAL 与 remote 只差 `uri`。
所以"将来迁移要重写"这个担心**不成立**——真要迁移只是换个 uri。

结论因此更清楚：**不装的理由不是"API 不好"，是"这个规模上它更慢、更占内存"。**

## 3 暴力扫 vs Milvus 查询

同一批 1000 条向量，同一个 top-10：

| 实现 | 单次查询 | 相对 |
|---|---|---|
| numpy `queries @ matrix.T` | **9.5–21.6 ms** | 1× |
| Milvus Lite（FLAT/COSINE） | **179 ms** | **8–19× 慢** |

规模放大到全库 3652 个节点：numpy 一次约 **15–60 ms**（一张 40 节点的图做 40 次
query，一次矩阵乘搞定）。而 Milvus Lite 用的是 FLAT 索引——**它内部也是暴力扫**，
只是多了一层 gRPC 序列化与进程边界。在"几千条"这个量级上，ANN 索引的收益本来就
是 0，额外开销却是实的。

**明说：暴力扫已经够快，Milvus 在这一步是负优化。**

## 4 落成了什么

### 4.1 新增模块 `app/optimization/cross_map.py`

判据与前三层不同：

```
check()     这张图**内部**有没有结构问题    词面判据，0.5 ms
模型层      同一父节点下有没有语义重复      一次 LLM 调用，1.4 s
本模块      同类图里这个节点别人怎么写的    一次检索 + 一次矩阵乘
```

具体比三件事：**参照图的子树更深**（这里是叶子）、**参照图的正文更长**
（210 字 vs 77 字）、以及**命中了几张图**（跨图投票，单张图的偶然差异不报）。

### 4.2 向量存哪：复用 `chunk_vectors`，不新增表

`knowledge/vector_cache.py` 是按 `(text_hash, model)` 存的纯缓存，键是文本本身。
节点 label 与材料块共用一张表**没有语义问题**（都是"这段文本 → 这个向量"），
收益是跨图参照还能命中材料检索已经算过的向量。

改动的边界因此很小：`vector_cache.py` **一行没动**（只 import 它的
`text_hash` / `get_vectors` / `put_vectors` / `pack` / `unpack`）。

### 4.3 成本闸

| 场景 | 耗时 | 说明 |
|---|---|---|
| 新图 40 个节点补向量 | **2.85 s**（4 批，71 ms/条） | 这是**真成本**，也是这一层的主要开销 |
| 历史库 1075 个节点**现算** | 约 75 s | 所以历史侧**只读缓存**，不现算 |
| 矩阵乘（3652 历史 × 40 查询） | 15 ms | 可以忽略 |
| 一次体检（缓存全热） | **105 ms/图** | 58 张图合计 6.1 s |
| 一次体检（规则层基线） | 0.5 ms/图 | 对比用 |

所以同步路径上的策略是：

- **新图节点补向量**（封顶 `MAX_QUERY_NODES = 40`），第一次约 3 s，之后命中缓存；
- **历史节点只读缓存**——历史库是几十次生成攒下来的，在 `/suggest` 里现算它等于
  让一个按钮点下去等一分多钟；
- 预热入口 `prime_history()`，由脚本或保存路径调用。

**代价说清楚：库里一张图都没保存过时，这一层返回空列表。** 这是设计选择。
它的实测表现是"冷启动 0 条 → 预热后 43 条"。

### 4.4 开关与出口

```
MINDMAP_OPTIMIZATION_CROSS_MAP=1    # 默认关
```

关闭时连 `numpy`、数据库、`cross_map` 模块都不进 import 图。`suggest()` 也接受
显式参数（`use_cross_map=True/False`），`/suggest` 可以带 `map_id` 把当前图自己
从历史里排除。

建议的 `kind` 是 **`cross_map`**，与 `expand` / `add_detail` 分开——动作指引可能
一样，但依据来自别的图，用户要能单独识别、单独关掉。`evidence` 的格式是
`"<map_id>#<节点标签>"`，跳转入口需要的两样东西都在里面。

## 5 A/B：加索引前后

### 5.1 建议条数

| | 条数 | 有建议的图 |
|---|---|---|
| A　`check()` + 规则层建议 | **77** | 13 / 58 |
| B　A + `cross_map` | **120**（+43） | 18 / 58 |
| C　A + 模型层（`use_model=True`） | **101**（+24） | 19 / 58 |

### 5.2 人工抽检

**模型层的 24 条**（逐条判，判据是"把这两个合成一个，读者会丢掉一个独立信息点吗"）：

| 判定 | 条数 | 例子 |
|---|---|---|
| 成立 | 9 | 「主题与观点的关系校验」↔「辨析主题与观点的关系」 |
| 边界 | 6 | 「模型一词的两层含义」↔「模型是输入到输出的映射」（后者是前者的一层） |
| **不成立** | **9** | 「理论基础」↔「定义与基本概念」；「铁路节能」↔「高速铁路节能发展」 |

精确率 37.5%（严格）/ 62.5%（含边界）。典型失败形态是**目标 vs 手段**：
「节能减排与能效提升」↔「碳中和与碳达峰目标」被报成近义，而模型的理由自己写着
"前者是目标，后者是实现该目标的手段"。

**跨图参照的候选**（238 条候选，按类型分层抽 9 条）：

| 判定 | 条数 | 说明 |
|---|---|---|
| 成立 | 8 | 「Python 库与框架」detail 逐字相同、只是参照图把它展开了；「模型方法与软件工具」h1 ← h3 |
| 边界 | 1 | 「无监督学习」自己已有 72 字说明，参照图 detail 为空但是展开了 |
| 不成立 | 0 | — |

差别在于**判据的性质**：模型层判"这两句话是不是一件事"（语义判断，会错），
跨图参照判"这个节点在别的图里有没有 detail / 有没有子节点"（客观差异，不会错）。
后者更弱（"差异存在"不等于"你该改"）但更准。

### 5.3 延迟与内存

| | 延迟 | 内存 |
|---|---|---|
| A　规则层 | 0.5 ms/图 | 0 |
| B　+ 跨图（缓存热） | **105 ms/图** | 常驻 +约 40 MB（3652 × 1024 × 4 B 的 float32） |
| B　+ 跨图（新图补向量） | **2.9 s/图** | — |
| C　+ 模型层 | **1.4 s/图** | 0（远程） |
| Milvus Lite | 179 ms/次查询 | **+119 MB** |

**这一格是本次最该看的地方**：跨图参照的 2.9 秒里有 2.85 秒是 embedding，
15 毫秒是检索。把检索换成 Milvus 能把 15 ms 变成 179 ms，**对总耗时的影响是 5%**，
方向还是反的。

## 6 数据集本身的两个坑（会直接影响推荐质量）

1. **62% 的跨图候选是"同一主题的多个版本互相参照"**。全库 238 条候选里 148 条的
   参照物与当前图**标题完全相同**——那是"你上次写得更细"，不是"别人的写法"。
   所以 `cross_map` **排除同名图**，代价是"上一版"不能当参照。
2. **库里混着画布回归基线与一次保存冲突测试的产物**。有一个 57 节点的
   「触发器拦住事件时保存的标题」其实是「机器学习的主要方向」的另一份拷贝，
   它在历史库里当参照物时给出的建议是对的（那边 detail 确实更长），但这说明
   **历史库的质量直接等于建议的质量**。生产库不会有这些，开发库有。

## 7 自评：Milvus 解决的问题，这个规模本来就不存在

**是。** 三个数摆在一起就很清楚：

```
3652 个节点的暴力扫          15 ms
Milvus Lite 同规模查询       179 ms      ← 慢 12 倍
一次 embedding（40 节点）    2850 ms     ← 比两者大两个数量级
```

用户的原话是"存入 Milvus/Pinecone，让 AI 提建议更准"。实测下来：

- **"更准"来自跨图参照这个判据**（+43 条，抽检 9/9 成立），不来自检索引擎；
- **"更慢"来自 embedding**，而 Milvus 一点都不碰它；
- **"更占内存"来自 Milvus 自己**（+119 MB），在一个还要跑 Docling 的 2C2G 机器上。

也就是说：装 Milvus 的唯一效果是**把 15 ms 变成 179 ms 并多吃 119 MB**，
而建议条数与准确率一个字节都不会变。这不是"暂时用不上"，是**用反了**。

### 什么时候它才会变成必要的

三个门槛，**任何一个**到了才需要重新评估：

| 门槛 | 数量级 | 为什么是这个数 |
|---|---|---|
| 历史节点总数 | **≥ 50 万**（约 8000 张 60 节点的图） | 暴力扫是 O(n)，15 ms @ 3652 节点 → 2 s @ 50 万节点。在此之前 numpy 都比 ANN 快，因为 FLAT 也是暴力扫 |
| 单次体检的查询节点数 | **≥ 500** | 矩阵乘的另一维。现在封顶 40，是为了控制 embedding 成本而不是检索成本 |
| 多用户并发体检 | **≥ 10 QPS** | numpy 每次查询要占满一个核 15 ms；进程内单例可以串行，多用户时才需要独立的检索进程 |

在 2C2G 单机上，第一条到之前，暴力扫就是正确答案。

**而如果哪天 embedding 变成本地小模型（或生成流程顺手把节点向量写了），
第一条门槛会提前到——那时该换的仍然不是 Milvus Lite，而是"把向量放进已有的
SQLite 缓存 + 一个 numpy 矩阵"。**

## 8 复现

```bash
cd backend
python scripts/measure_cross_map.py            # ①③④ + ②的可判样本量（不联网）
python scripts/measure_cross_map.py --embed    # ①，需要 MINDMAP_EMBEDDING_* 凭证
python scripts/measure_cross_map.py --ab       # A/B 条数与延迟
python scripts/measure_cross_map.py --index    # 与 Milvus Lite 对比（需要单独装 pymilvus）
```

`--index` 在没装 `pymilvus` 的环境里会跳过并说明原因——**它没有进
`requirements.txt`**：为一个实测更慢的实现拖进 19 个包（约 75 MB）不划算。
要复现那三个数，在 `backend/data/` 下建一个临时 venv 装 `pymilvus milvus-lite`
再跑同一个脚本即可（`pymilvus 3.0.3` + `milvus-lite 3.2.2` 是本次实测的版本）。
