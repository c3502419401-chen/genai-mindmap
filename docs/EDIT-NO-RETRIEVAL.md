# 改图该查时查不查：5 组说法的实测与裁定

2026-11-26。`9c2ebcf` 把 `edit` / `expand` 的检索从"没说"改成"**默认不要检索**"，
判据放在提示词层（`app/agent/service.py::_RAG_INTENT_RULES`）。那位 agent 自己记下的
代价是：

> 模型可能在该查时也不查，表现为改图后引用为空。

建议的兜底是：goal 里出现「材料 / 原文 / 引用 / 出处」时，把检索指令提到最前面。

**这一件的判据是"有没有发生"，不是"会不会发生"。** 下面是实测。

---

## 一、结论

| 观测 | 结果 |
|---|---|
| 5 组"该查"的说法，**没查的** | **0 / 5** —— 每组都发了 1–2 次 `rag_query` |
| 3 组"不该查"的说法，查了的 | **0 / 3** |
| "改完之后引用为空" | 5 / 5 —— **但这不是"没查"的证据**（见第三节） |
| 兜底 | **不做**。加它等于给一个不存在的问题加代码 |

一句话：**收窄之后那个"合法口子"是通的**，该查的都查了；而"引用为空"这个症状
的成因在别处，不在检索。

## 二、怎么测的

`scripts/measure_edit_retrieval.py`，真发 `POST /api/agent/runs/stream`（`intent=edit`）：

```
图      mindmaps.c1d30b17「注意力机制的核心思想」，136 节点，6 条一级分支
材料    library_sources.attention-37973.md（Attention Is All You Need，42,526 字）
身份    先 GET /api/auth/me 领一张游客 cookie（没有它一律 401）
判据    事件流里有没有 tool_start name=rag_query；以及产物候选树上的 source_refs
```

5 组"该查"的原话（节点名取自真图，不是我编的说法）：

| # | goal | 查了几次 | 耗时 | 落地产出 |
|---|---|---|---|---|
| 0 | 把「自注意力与跨序列对齐」这一支按材料补充一下 | **2** | 27.0 s | 136 → 145 节点（确实补了 9 个） |
| 1 | 「相似度打分与权重分配」下面这几条的引用要和原文对上 | **3** | 31.0 s | 136 节点（只改措辞） |
| 2 | 把「多头并行捕捉多类关系」这段改成材料里的说法 | **1** | 13.6 s | 136 节点 |
| 3 | 按原文核对一下「查询、键与值的三元结构」这几条说得对不对 | **2** | 20.5 s | 136 节点 |
| 4 | 把材料里的原文补进「加权求和生成上下文向量」这几条 | **2** | 22.0 s | 136 节点 |

耗时取自 `runs` 表的 `created_at → updated_at`（同一次运行的墙钟），不是脚本自己
掐的表——那个数含 HTTP 与落库，读库这一份才是用户等到的时间。

3 组对照（不该查）：`把「注意力机制的核心思想」这个标题改短一点` 3.1–3.8 s（0 次）、
`把「多头并行捕捉多类关系」改名成「多头并行」` 3.5–4.6 s（0 次）、`把标题改短一点`
25.4–37.4 s（0 次，但发了 3–50 次 `update_node` —— 它在挨个节点改，不是检索）。
**对照组的 0 次是对的**：它们证明判据不是"凡是 edit 都算没查"。

`rag_query` 的实参也印证了它查的是对的东西，例如第 3 组：

```
{"question": "查询、键与值的三元结构：查询与键做相似度计算得到注意力权重，归一化后对值加权求和", "top_k": 8}
{"question": "缩放点积注意力 除以键向量维度的平方根 防止梯度消失 softmax", "top_k": 8}
```

## 三、"引用为空"这条判据本身不成立

5/5 组改完之后 `source_refs` 都是 **0 条**，包括查了 3 次的那一组。原因不是检索，
是**模型能走的那条编辑层写不了引用**：

```
contracts/ops.py::UpdateChanges   source_refs 在契约里（原生编辑、导入用）
agent.tools.EditChange            模型看到的那一层，没有这个字段
```

契约里那句注释写得很清楚——编辑路径再开一个引用入口，等于多一条能凭空造引用的路。
所以：

- `edit` 之后引用恒为空，**与查没查无关**；
- "改完引用为空" 这个症状真正指向的是"这条路径没有把检索结果落成引用"的能力缺口，
  不是一个检索缺失；
- 想让它有引用，要改的是编辑层的契约（谁能写、写之前怎么逐字校验），不是提示词。

`tests/test_edit_retrieval_scope.py::test_the_edit_layer_cannot_write_refs_so_empty_refs_is_not_evidence`
钉着这一条：哪天 `EditChange` 能写引用了，那句"改完引用为空说明没查"才重新变成可疑信号。

## 四、裁定

**不加兜底。** 判据是 ≥2/5 才加，实测 0/5。加代码的代价不只是那几行——一条
"goal 里有这几个字就先检索"的规则会让「引用要和原文对上」这类说法**永远**先花
3–7 秒，而它今天已经在做这件事了（模型自己认得出）。

留在代码里的东西只有一个：`_RAG_INTENT_RULES` 那三句话**不动**，并且有一条用例
（`test_keywords_do_not_change_the_instruction_and_that_is_the_verdict`）钉住
"关键词不改变指令"——将来谁要加兜底，会先被它拦一下，然后按这份文档重跑一遍再决定。

## 五、可复现

```
cd backend
python scripts/measure_edit_retrieval.py                     # 5 组该查 + 3 组对照（约 3 分钟）
python scripts/measure_edit_retrieval.py --ask 0 3           # 只跑其中两组
python scripts/measure_edit_retrieval.py --save scripts/_edit_retrieval.json
```

**不花游客配额**：这台机器的 `run-backend.bat` 没有 `MINDMAP_FREE_TIER_API_KEY`，
`generation/quota.py::enabled()` 因此是 False（`free_quota` 表实测 0 行）。花掉的是
模型 token 与墙钟。
