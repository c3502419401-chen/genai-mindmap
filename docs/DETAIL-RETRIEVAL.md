# 第三段（写说明）的证据：每个节点在自己那一章内检索

`MINDMAP_DETAIL_RETRIEVAL=1` 走这条路，不设就是现状。**默认关**：它是 A/B 的一臂，
也要多付 N 次检索（N = 待补说明的节点数）。它依赖 `MINDMAP_SECTION_SLICE=1`——那条路
先给出"哪一章"，这条路才谈得上"章内"；没有章时**静默退回**原来的证据，prompt 与
`data` 逐字节不变。

## 一、它替换的是第三段的哪一列

```
                      A（现状）                            B（本开关）
① 骨架（_plan_ask）     不变                                不变
② 结构（按章切）        每章一次调用，只给它这一章的原文        同左（一个字都没改）
③ 说明（_fill_details） 每组证据 = 整支片段（按支分组时，约 2,000 字/组）
                        或整份材料（全塞时，14,120 字）
                        ↓                                  ↓
                      两半各带**同一份**全部证据             每个节点只拿**它自己那一章**里
                                                          命中的 2–3 段（450–700 字/段）
                                                          块跨节点去重，两半各渲染自己那份
```

一级分支（章标题）那一层没有变：它的说明要概括"这一章在讲什么"，证据只能是整章
——`chapter.prompt_text`（8,000 字上限）在第二段已经给过一次，cost 已经付过。

## 二、范围是怎么限定的：不用过滤候选块，而是把**来源**切成这一章

`search_parent` / `search_multi` **没有**范围参数（`SourceFilter` 只按元数据筛来源，
不认偏移）。两条路都试过，选的是第二条：

| 做法 | 代价 |
|---|---|
| 先取更深的池子（如 `top_k=12`）再按 `章首 ≤ start < 章末` 过滤 | 被剔掉的候选仍占着 `top_k` 的名额；池子要挖多深取决于别的章有多像，**结果不可预期** |
| **把来源裁成这一章再检索**（`_chapter_source`） | 命中落在本章内是**构造保证**；坐标是章内相对的，`+chapter.start` 平移回全文口径 |

第二种还顺带守住了引用口径：平移之后 `quote` 仍逐字等于 `原文[start:end]`
（`tests/test_detail_retrieval.py::test_blocks_stay_inside_their_chapter_and_quote_is_exact`）。

检索入口是新加的 `knowledge.service.search_exact_blocks`：父块粒度、**不重排**、
不查库。不重排不是省事——`knowledge/rerank.py` 的注释点名了这类调用方
（"标题定位""关键词跳到某章"），重排的默认值是按自然语言问法评估出来的，在字面
检索上是**静默的负收益**，而 `MINDMAP_RERANK` 是全局开关（`rag_query` 要走它），
不能为一个调用方翻。

## 三、query 长什么样（实跑取样）

`label` 为主；**同一章内** label 重复时才补父 label（跨章重名不算重名——范围本来就
不同）。父与子同名时不拼（"一句话结论 一句话结论"只是把同一个词发两遍）。

```
s1              → 1 已经落地的两件事
s2-1            → 递归切块
s2-1-3          → 重叠吸附到句首
s3-1            → 实测数据
s9-1-2          → 2G总账余量400~600MB
s10-1-1         → 报错像权限实为事务类型
```

## 五、数据回答了什么

**引用条数与覆盖率没有动，而且不可能由这一段动。** 引用是**第二段**的产物：

```
_slice_one → _slice_refs（在 [章首, 章末) 内定位模型抄的 quote，写 start/end）
           ↑ SECTION_SLICE_REF_RULES："凡是内容出自这一章，就必须给这个节点挂一条 source_refs"
_fill_details → _with_details（只写 detail 一个字段）
           ↑ DETAIL_ONLY_*_RULES："不要新增或改动引用"
```

第三段既不写也不改 `source_refs`，所以 37/33 → 38/38 是结构那一轮的采样波动，
不是这条路的贡献。同样的话对"覆盖率"成立：`Σ(引用并集) / 14,120` 的两个输入都来自
第二段，这一段只可能是 0 变化。

**真正动的是输入侧与"证据到位"这件事：**

- 输入 token **−18~19%**（26.8k → 21.8k）：第三段的两半原来各带整份 14,120 字，
  现在各只带自己那半节点的章内块（约 7.4k 字）；
- 每个节点手里的证据从"整份材料里自己找"变成"这一章命中的 2–3 段，编号指到块"，
  块并集覆盖全文 **94–98%**；
- 代价是墙钟 **+4~6s**（检索本身 2.7–11.4s，主要是块向量冷启动与 MaaS 往返）
  与 60 次本地检索。

**detail 均长不能归因于这条路。** detail#2 的 145.9 看着像掉了 22%，但同一条路
（slice）在上一轮 A/B 里的两采样就是 183.8 / 149.2——**采样波动比这 20% 还大**。
这一轮 slice 两采样 184.6 / 186.9，detail 两采样 178.3 / 145.9。

## 六、引用条数上去了，覆盖率一定上去吗？

不一定，而且这一轮**两个数都没上去**（条数 37→38、33→38；落点段数 23→23、22→24）。
两个数不同步的原因是算术：

```
覆盖率 ≈ Σ(不同区间) × 引文均长 / 全文
        = 35 × 52.9 / 14,120 ≈ 13%（实测 15.6–16.3%，因为区间长度不等）
```

条数翻倍但都挤在同一段时，并集不变、覆盖率不动——那买到的只是"更啰嗦的引用"。
所以判断这条路有没有真的覆盖更多地方，看的是**不同区间数 / 落点的段数 / 有引用的
章数**这三个数，不是条数。这一轮三者都平。

**下一步该动的不是"引文写长"，而是"谁有权写引用"。** 第三段手里现在已经有块并集
94–98% 的证据，而这些块本身就在原文坐标上（`block.start` / `block.end`）——如果让它
把这批块落成引用（与第二段那批按 `(source_id, start, end)` 去重合并），同样 61 个
节点、同样一次调用，覆盖率的上限从现在的 12% 直接抬到块并集那一侧（算术上 ≈ 94–98%）。
这一轮没有做，因为本轮的边界是"只改第三段的证据来源"，而"谁能写引用"是引用契约的
另一件事，它要连着 `verify_source_refs` 的证据集与界面高亮一起改。

## 七、边界（都钉着）

- **开关关掉逐字节不变**：不检索、`data.detail` 没有 `evidence` 键、`_detail_ask`
  的输出与加这条路之前一字不差（`tests/test_detail_retrieval.py` 前两条）；
- **没有章就没有这条路**：`chapters` / `source` 任一为空即退回（多份材料、
  `_fill_details_tool` 的续写路径都在这条线上）；
- **一条都没命中时退回原来的 `sections`**，并在 `data.detail.evidence.fallback`
  写 `"no_hits"`——"检索没成"不该把**已有**的证据一起丢掉；
- **一次检索抛错只让那一个节点没有证据**，整段说明照常写回；
- **块池跨节点去重、按分数封顶**（`DETAIL_RETRIEVAL_MAX_CHARS = 16_000`/半），
  封顶按分数而不是文档序——按文档序截断会系统性饿死最后几章；
- 第二段、骨架、图渲染、限额（`INITIAL_MAX_NODES = 80` / `INITIAL_MAX_DEPTH = 3`）
  一个都没动。
