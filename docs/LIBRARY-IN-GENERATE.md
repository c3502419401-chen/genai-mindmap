# 库参与生成（`MINDMAP_LIBRARY_IN_GENERATE`）

> 一句话结论：**块级检索本身是准的，"要不要用这批命中"没有便宜判据——唯一能分开
> 相关与不相关的是 reranker 的分，而它在今天挂过一次。所以这个开关默认关、重排不可用
> 时自动跳过，并且只在"用户没材料"时才补。**

相关代码：`backend/app/agent/tools.py`（`library_in_generate_enabled` /
`LIBRARY_SUPPLEMENT_CHARS` / `LIBRARY_RELEVANCE_GATE` / `_library_supplement` /
`_library_evidence_section`）。测量脚本：`backend/scripts/measure_library_relevance.py`
（相关性）、`backend/scripts/measure_library_in_generate_ab.py`（A/B）。用例：
`backend/tests/test_library_in_generate.py`。

## 0. 这件事要解决什么

知识库此前只有**一条**入口：模型自己想起来调 `rag_query`。而 `_generate` 的三步
（骨架 / 结构 / 说明）一次都不碰库——于是"库里躺着 51 份来源、1265 块切好的原文、
3938 个向量"这件事，对"用户只给一个主题"的生成完全没有影响。

改法：`_intake` 在生成之前由代码主动查一次库，过门的相关父块作为**一节独立证据**拼进
prompt。默认关（`MINDMAP_LIBRARY_IN_GENERATE=1` 才开）。

## 1. 先量：库里那 51 份，检索得准不准

### 库的构成（这是后面所有数字的解释边界）

```
library_sources  51 份 / 154,553 字 / 1,265 块
  markdown  4 份 / 66,536 字   ← docs/ 下的开发文档（AGENT_PLAN / PLAN / RAG-DECISIONS / ARCHITECTURE）
  web      25 份 / 80,549 字   ← 外部检索抓的网页（其中约 15 份是"机器学习"科普与课程页）
  paper    22 份 /  7,468 字   ← 外部检索抓的摘要（单份中位 223 字）
```

**没有一份是用户真的上传的。** 74% 的正文（66.5K / 154.5K）是四份开发文档——它们的
词频分布与"用户想问的主题"完全不对齐，这一点后面会以 BM25 的反向表现爆出来。

## 2. 唯一能分开相关与不相关的东西是 reranker（这一节比 A/B 重要）

### 2.1 三个字段各自能不能当判据

| 字段 | 「海绵城市建设」（8 条全真相关） | 「量子计算的基本原理」（8 条全无关） | 能不能当门 |
|---|---|---|---|
| `score` | 0.0164 → 0.0147 | 0.0164 → 0.0147 | **不能**：它是 RRF 名次分 `1/(60+rank)`，只由名次决定，第 1 名与第 8 名的差恒为 10%，与内容无关 |
| `score_bm25` | **1.31 – 1.89** | **6.11 – 9.94** | **不能，而且方向是反的** |
| `score_vector` | 0.727 – 0.781 | 0.442 – 0.571 | 不够：真相关最低 0.562（碳中和的两篇摘要），噪声最高 0.571，两个分布重叠 |
| `rerank_score` | 0.584 – 0.794 | 0.223 – 0.290 | **能**：真相关 0.584–0.890、无关 0.191–0.294 |

**BM25 为什么会反。** BM25 奖励"稀有词命中"。库里有 66.5K 字开发文档，里面塞满
"量子计算""向量检索""索引""注意力"这类技术术语，于是「量子计算的基本原理」的
`量子`/`基本`/`原理`/`计算` 在开发文档里全是低频词 → idf 高 → 6.11–9.94 的高分。
反过来「海绵城市建设」的 `海绵`/`城市`/`建设` 在正文里反复出现（同一份维基讲了几十次），
tf 高但 idf 低、块又长（693 字），长度归一化把它压到 1.3–1.9。

按 `bm25 ≥ 5` 过门的效果是：**挡掉 8 条真证据（海绵城市 0 条过门），放进 4 条噪声
（量子计算 4 条过门）**。这是决定性的反向证据——BM25 不能当这个门。

### 2.2 重排不可用时，库参与会引入什么

拿「量子计算的基本原理」算：`MINDMAP_RERANK=0`（或 reranker 调用失败）时，
`rerank_score` 全是 `None`，8 条命中里有 5 份来源、合计 4387 字**全部**是机器学习课程
大纲与注意力机制教程（`东北大学秦皇岛分校本科课程教学大纲`、`《机器学习》课程教学大纲`、
`人工智能学习基础`）。它们会被当成"知识库里的相关原文"拼进 prompt，而 system 同时
要求"每个节点都要有引用"——**模型于是给一张讲量子计算的图挂满机器学习课程的引用**。
逐字校验会全部通过（引文确实来自那些文件），只有人看内容才能发现不对。

这就是代码里那道 `LIBRARY_SKIP_NO_RERANK`（fail-closed）的由来，它不是一句注释：
`all(hit.rerank_score is None for hit in hits)` 成立时**不用库**，并报一条 warn 诊断说明
是重排没生效。`tests/test_library_in_generate.py::test_missing_rerank_scores_fail_closed`
钉着这条。

### 2.3 0.35–0.58 之间是什么

**是空的。** 8 个主题 × top8 = 64 条命中，`rerank_score` 的分布是**双峰**的：

```
0.187 – 0.231   纯噪声（「碳中和」主题下的机器学习块）                    6 条
0.223 – 0.294   纯噪声（红烧肉 / 量子计算 / 咖啡机 三个零相关主题）       24 条
0.300 – 0.354   同领域、不同子话题（「雨污分流」主题下的"海绵城市"5 条）   7 条
                + 一条无关技术文档（AGENT_PLAN 0.346）
0.354 – 0.584   —— 0 条 ——
0.584 – 0.890   真相关                                                    24 条
```

这个"空"要读成两件事：

1. **对当前这个 reranker，它把 query–文档对判成"要么像、要么不像"**，没有"有点相关"
   这一档。对一道门来说这是好消息：阈值取 0.45 还是 0.75，结果完全一样。
2. **不能读成"0.45 附近的材料一定无关"**。样本只有 8 个主题、一个 reranker 模型
   （qwen3-rerank）、一个 51 份的库。换模型、换库、换语言（库里 6 份是繁体中文），
   这个谷会被填上。所以阈值必须跟着**实测**走，不能跟着"谷底"走——谷底是这次观测的
   性质，不是这个模型的性质。

外面还有一个常被忽略的事实：`0.300–0.354` 那 7 条是**同领域不同子话题**（讲"海绵城市"
的段落出现在"城市雨污分流改造"这个主题下）。它们对人不算错，对"给这棵树挂引用"算错
——引用必须支撑**这个**主题。

### 2.4 阈值定在哪，定低了/定高了各错在哪边

**取 0.6**（`LIBRARY_RELEVANCE_GATE`）。

- **定低（0.5）**：多放进 0.512（「城市雨污分流改造」主题下的 `AGENT_PLAN.md`）、
  0.493（「碳中和」主题下的 `AGENT_PLAN.md` 碳中和段落——那一段恰好是"申报书 3.3.1
  要输入碳中和"，语义上沾边但不是碳中和知识）。错误形态：**假阳性**，一段无关文字
  进 prompt 并被引用，逐字校验查不出来。
- **定高（0.7）**：丢掉 0.584–0.699 的那一批，包括「海绵城市建设」的"争议"段
  （0.584）、「碳中和」的两条真相关摘要（0.664 / 0.634）。错误形态：**假阴性**，
  库明明有材料却说"没有相关的"，用户看到的是"库没帮上忙"。
- **两侧代价不对称**：假阳性会在图上留下一段读起来通顺、但出处错的引用，而假阴性
  只是这次少了几段可引用材料（本来也还有模型的常识）。所以门宁严勿松，0.6 而不是
  0.55——0.55 会把 0.354 那一类"同领域不同子话题"全部放进来，而 0.584 那一条真相关的
  损失只有 1 条。

**残余错误率（8 个主题 × top8 = 64 条命中）**：过门 26 条，全部相关；被挡掉的真相关
**1 条**（「海绵城市建设」的"争议"段，0.584）；被挡掉的噪声 37 条，放进来 0 条。
即 **假阳性 0 / 假阴性 1**。样本只有 8 个主题、库只有 51 份——这个 0 是"这次没观察到"，
不是"保证没有"。

## 3. 三源优先级与"补足"判据

```
① request.sources（用户这次传的）      最高优先
② 库检索（本地，0.18–0.25 秒 + rerank 0.9–1.4 秒）   补足
③ 外部检索（联网，中位 4.3 秒，97.2% 能拿到 ≥1 条）  最后
```

`_intake` 里"补足"的判据是**已有材料合计字数**（用户材料 + 外部检索补进来的）：

```
已有材料 < LIBRARY_SUPPLEMENT_CHARS(3000)  → 查库
已有材料 ≥ 3000                            → 不查（skip = enough_material）
```

为什么是 3000（而不是"有材料就完全不查"或"无条件都查"）：

- **3000 字 ≈ 6 个父块**（450–700 字/块），是一棵 20 节点树"每节点一条引用"的下限
  （20 条引文 × ~100 字 + 冗余）。低于这个数，用户那批材料撑不起这棵树——正是库该
  补的区间；高于这个数，库的边际贡献已被材料覆盖。
- 实测库能提供的量就在这个量级：过门后合计 **424 / 467 / 2566 / 4286 / 4700 字**
  （见第 1 节）。它不是一个"知识源"，是"几段补充"——把它当第二个知识源用会失望。
- **不用 `SHORT_MATERIAL_CHARS=300` 当这道闸**：那个数管的是"材料太短、切不出可检索
  单元"（低于它整份降级成 `hint_block`）。300–3000 字恰恰是最需要补的区间：用户给了
  一页纸，而一棵树要十页。
- **不无条件查（方案 c）**：库里有 74% 是开发文档，与用户材料主题几乎必然不同。两份
  不同主题的材料混进同一棵树，表现出来就是"有几支讲 A、有几支讲 B"，而用户只上传了 A。

## 4. 命中的块怎么进 `sources`

**两样东西分开，这是整条链最容易做错的一处**：

```
hits    = 过门的**父块**（450–700 字，start/end/quote 都是原文坐标）→ 进 prompt
sources = 命中 source_id 用 library.load() 取回的**整份原文**（持久 id）→ 给校验器
```

- 只给 `hits`：模型能看到片段，但收尾 `verify_source_refs` 用 `{source.id: source}` 查
  原文时查不到 → 引用被判 `SOURCE_TEXT_UNAVAILABLE` → 在 `remove_invalid` 那一步被
  静默删掉。表现是"检索成功、引用写对、界面上一条都没有"。
- 只给 `sources`：把 26K 字的 `AGENT_PLAN.md` 整份拼进 prompt，上下文直接撑爆。

**持久 id 由构造保证**：`hits[].source_id` 就是 `library_sources.id`（检索侧从库里读的
`Source` 带的 id），`_remember_library_hits` 用它 `library.load()` 取回整份并
`ctx.record_library_sources(...)`，`_verify_sources` 再把 `ctx.library_sources` 并进
校验来源集合。所以"能查到 → 就点得到"这条老规则没有破。
`test_persistent_ids_survive_reference_verification` 直接拿 `verify_source_refs` 跑一遍
断言引用存活。

**库来源不进 `_Intake.sources`**（这条是刻意的）：`sources` 是"按支检索的语料"，
把 26K 字的库来源并进去之后，20 支每一支都会在它上面切块 → 噪声以"按支检索"的形式
重新进来，而这个功能唯一要防的就是噪声。库证据走**单独一节**，不参与按支检索。

1. **引用覆盖率 0% → 62–99%。** 关臂是 0% 不是巧合：`sources` 为空时 system 拼的是

   功能唯一的、也是决定性的收益。
2. **开臂的树更小，或者更小但更密。** 城市雨污 59 → 32 节点（只有 467 字库证据，

   那份材料有 14120 字，够撑。所以"库参与"把规模从**模型想写多少**变成**材料能支撑
   多少**，方向对，幅度取决于库有多少。
3. **79 条引用只来自 1 份来源**（思维导图那行）。这是"证据多样性"的真实瓶颈，不是
   bug：`LIBRARY_PICK=5` 按字面覆盖率排序取前 5 份，第一名（`RAG-DECISIONS.md`，
   覆盖 0.67）切出的 8 个父块全部过门，top_k 被它一个包揽。树看起来满身引用，
   其实全部指向同一份文件。
4. **负样本那行是这个功能能不能上线的前提。** 「如何做红烧肉」开臂过门 0 条 → 走
   `LIBRARY_SUPPLEMENT_SKIPPED` → 与关臂同形（0 引用、节点 71 vs 59 的差是同一主题
   两次生成的正常方差）。**库里没东西时不引噪声**，这一点由门保证，不由运气保证。

**耗时**：开臂 32.2–46.7 秒、关臂 37.9–45.0 秒——库检索 + rerank 那 1–2 秒完全被生成
本身的方差（同一主题两次差 6–10 秒）盖住了。所以这个功能的成本不是时间，是"树变小"
与"库噪声的风险"。

## 6. 自评：现在值不值得做

**值，但只在"库里有这个主题的材料"时才值，而这件事今天只有 reranker 能判断。**

三条实话：

1. **库里没有一份是用户真上传的。** 51 份 = 4 份开发文档 + 47 份外部检索抓回来的
   网页/摘要。也就是说用户从没为"这个库"贡献过内容，它是开发过程的副产品。
2. **对一般主题，库更像噪声源而不是知识源。** 11 个主题里 3 个零相关（红烧肉 / 量子
   计算 / 咖啡机），2 个只有 2 条相关（碳中和 / 雨污分流，各 424 / 467 字）。真正
   "库能撑起一棵树"的只有 6 个——而那 6 个里有 4 个是**关于这个项目自己**的主题，
   剩下 2 个（注意力机制 / 海绵城市）是外部检索误打误撞抓对了。
3. **它买的不是"更多内容"，是"有出处的更少内容"。** 见第 5 节：库臂的节点数通常
   更少（"每节点必引用"的约束把没有依据的方面挡掉了），换来的是 0% → 62–99% 的引用
   覆盖率。而 99% 那种情形里 79 条引用可能只指向 1 份文件——覆盖率不等于证据多样性。
   这是产品取舍，必须让用户能看见、能关。

**什么条件才让它真的值**（按重要性排序）：

1. **库里有用户自己上传的材料**（哪怕 5–10 份）。这是唯一让"库"区别于"搜索引擎缓存"
   的东西：同一份合同改了三版、一个项目的全部制度文件、自己写的论文初稿。到那时
   "材料不足才补"就会频繁命中，而不是像今天这样只在开发文档上命中。
2. **库按主题分成可选的集合**（项目 / 领域），而不是一张 51 行的表。今天检索只能在
   "最近 100 份"里按字面粗筛取前 5 份（`LIBRARY_SCAN_LIMIT=100` / `LIBRARY_PICK=5`），
   库一大，粗筛就会成为瓶颈——现在 51 份还能全进窗口，200 份时就不一定了。
3. **reranker 稳定可用**，并且这条链把它当成硬依赖（今天它挂过一次）。挂掉时的行为
   已经定成"不用库"（fail-closed），不要把这条改成"降级到 BM25"——BM25 在库上方向
   是反的，那不是降级，是引噪声。
4. 如果只想要"库参与"而不要"库引噪声"，退一步的形态是：**只把库命中的标题/来源名
   列给骨架**（不影响引用、不承诺证据），让一级分支跟着库里有的东西走。这个形态不需要
   reranker 也能成立，代价是它买不到引用覆盖率——那是另一个开关，本轮没做。
