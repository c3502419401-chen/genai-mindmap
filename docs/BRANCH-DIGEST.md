# 一级分支的概括角标：这一支还有多少、讲的是什么

在每一条**一级分支**上挂一枚常驻角标：

```
还有 21 个 · 分数归一化与向量加权
```

两半来自完全不同的地方，这也是这一轮改动之所以分成"零成本"与"一次调用"两截的原因：

| 半个角标 | 从哪来 | 成本 |
| --- | --- | --- |
| `还有 21 个` | 渲染层自己数（`viewTree` 的 `unshown`） | **0**：一次树的遍历，纯函数 |
| `分数归一化与向量加权` | 生成时调一次模型，落库在 `content.branch_digests` | **1 次调用 / 6 支实测 2.4 秒** |

## 〇、它补的是哪个缺口

`docs/VIEW-COLLAPSE.md` §七 的自评把上一轮的边界划得很清楚：

```
做到    看得出"这里被截了" —— `+N` 常驻、19 处截断 = 19 枚，顶部「显示 40 / 136」
没做到  看得出"这一支讲没讲完" —— 一枚 `+3` 只证明"这里还有 3 个直接孩子"，
        证明不了一共还有 21 个、还有两层
```

并且给了正解：**不要给每个父节点再加字（会把画布糊满），而是在一级分支上挂一枚
"这一支还有 N 个节点"的按支统计角标**——一级分支只有 6 个、位置固定、语义干净，
与父节点上"这一处断了"的角标并存。

这一轮做的就是它，外加产品负责人要的那半句"**要概括调用**"：光有数字只回答了
"还有多少"，回答不了"值不值得展开"。

## 一、三件事的答案

### ① `Node.note` 不能占——它已经有主

`note` 是**用户自己写的批注**：`agent/ops.py` 的 add/update 之外，只有
`stores/mindmap.ts::commitNote`（界面上的编辑框）会动它。契约层的注释写得很明白：
任何"模型生成"的内容都**不许**写进 `note`，因为重新生成一次就会把用户敲的字整段
盖掉，而那种丢失在界面上看不出来（它长得就像"模型又写了一遍"）。

同理另两个文本槽也都有主：`label` 是标题，`detail` 是生成侧逐节点的说明
（一级分支自己那一段也在里面）。`style` / `role` / `icon` / `pos` 各有语义。

**结论：`Node` 上没有一个能借的空位。**

### ② 概括放 `MindMapContent.branch_digests`——一个**契约新字段**，不是 `data`

候选本来是"只在 `ToolResult.data` 里带出来给前端"（那条路零契约改动，仓库里
`data["verify"]` / `data["input"]` 就是这么走的）。否决它只有一条理由，但足够：

> `data` 是**一次运行的读数**，它不落库、也不进 `done` 帧的 `content`。
> 走那条路的话，用户刷新一次页面、或者从库里重新打开这张图，概括就没了——
> 而"这一支有多少节点、讲的是什么"是**这张图的属性**，不是这一次运行的属性。
> 让它每次重开都再调一次模型（实测 2.4 秒/6 支）是拿钱买一个本来就在手里的答案。

所以契约层加一个字段（`backend/app/contracts/mindmap.py`）：

```python
branch_digests: Annotated[
    dict[str, str], Field(default_factory=dict, exclude_if=lambda value: not value),
]
```

四条设计决定，每条都有一个"不这么写会怎样"：

- **`exclude_if` 而不是普通默认值**：空表**根本不进序列化结果**。于是"开关关着时与
  改动前逐字节相同"这句话是字面成立的——`model_dump()` 的键集与加这个字段之前
  逐个相同，不只是值相同（`tests/test_branch_digest.py` 第一条用例钉着它）。
- **`id → 文案` 而不是 `list[{id, label, summary}]`**：键就是节点 id，重复在结构上
  不存在；多一层对象只会让渲染层每次重画都多解一层。
- **不做键校验**：键指向一个已经不存在的节点（用户删了那一支、导入改了 id、模型
  给错了 id）时不报错。读者是渲染层，按 id 查不到就不画；而"删节点要顺手清理另一张
  表"要在编辑、撤销、`ops`、导入四条路上各写一遍，漏一条就是用户什么都没干却保存 422。
- **加在 `MindMapContent` 而不是 `ContentBase`**：鱼骨图中没有这个字段，流程图中也没有。
  两种图的一级结构分别是"固定六类"和"阶段序列"，概括不出新东西。

代价是必须重生成 `backend/openapi.json` 与 `frontend/src/api/schema.d.ts`
（各一条命令），并同步手写的 `frontend/src/api/types.ts`（`contract-check.ts` 的
`SameKeys` / `SameShape` 会在 `npm run type-check` 时强制它们一致）。这一处是
**只增一个可选键**，`openapi.json` 的 diff 是 +14 行、`schema.d.ts` 是 +8 行。

### ③ 视觉上与 `+N` 怎么分：位置 / 形状 / 配色**三处同时不同**

```
+3            右下角，白底细边圆形，只有数字            ← 这一处断了
还有 21 个 · 分数归一化与向量加权   左上角，深底白字长胶囊  ← 这一支还有多少、讲的什么
```

三处一起改是刻意的：只改一处（比如都放右下角），用户扫一眼只会看到"一列数字"，
然后开始猜哪个数字是哪个意思。现在它们连"读的动作"都不同——`+N` 是一个标记，
概括角标是一句话。

**一行，不是两行。** 角标是绝对定位的，不参与布局；两行会向上多吃 20px，而在
`both` / `down` 两种朝向里，节点上方正好是上一层节点的连线。压住一条线比截断一句
概括更糟（概括本来就限定 8–12 字，`max-w-[11.5rem]` 之外的部分 `truncate` 掉）。

## 二、后端：一次批量调用

```
时机   说明那一次之后（`_fill_details` 返回、`_stamp_expandable` 之后、`check()` 之前）
       ——一级分支已是最终形态（分组 / 裁剪 / 配色全部落定），下位节点标题也定稿
       ——往前挪到结构那一次之后也调得通，但那时分支标题还是骨架原话，写出来的
         概括会在二十秒后过期
批量   **一次**调用覆盖全部一级分支（不是每支一次）
输入   每条一级分支：id + label + 前 3 个子节点的 label
       **不塞 detail**：一段 80–150 字的说明 ×6 支会把这一节从两百字撑到一千字，
       而"只看目录"恰恰比"读完正文"更容易写出准确的概括
输出   {"<一级分支 id>": "8-12 字"}
失败   一律降级成"只用数字"：调用抛错 / 额度用完 / 一条都对不上号 → 概括是空表，
       角标不画（理由见 §四的显示判据），**绝不让一句概括把已经成型的树判成失败**
```

开关是 `MINDMAP_BRANCH_DIGEST`，**默认关**。关着时 `_generate` 那一段一行都不执行：
`content` 一个字节不动、`data` 的键集不变、模型调用次数不变。

读数进 `data["branch_digest"]`（只有开关开着才有这个键）：

```json
{"branches": 6, "written": 6, "missing": [], "unknown": [], "skipped": null,
 "failure": "", "seconds": 2.438, "prompt_tokens": 643, "completion_tokens": 106}
```

三档诊断：`BRANCH_DIGEST_SKIPPED`（没调成：额度 / 调用失败 / 一条都没写回来）、
`BRANCH_DIGEST_INCOMPLETE`（少写了几支）、以及"两条都够不上"时的沉默（全写回来了）。

上限是 `BRANCH_DIGEST_MAX_BRANCHES = 50`，与 `Node.children` 的契约上限
（`MAX_NODE_CHILDREN`）同一个数：超过它的一级分支根本存不进契约，所以 50 就是
"所有合法树都能一次覆盖"的那个界。最初写的是 20，实测库里那棵 50 支的探针树
有 30 支永远没有概括——而"为什么这 30 支没有角标"在界面上查不出来。

## 三、实测：两次提示词，一次对照

同一棵真树（库里 `c1d30b17`「注意力机制的核心思想」，136 节点 / 6 支），
`scripts/measure_branch_digest.py`，真 DeepSeek。

**初版提示词只说了"不要复述分支标题本身"**——实测 6 条里 **5 条是标题的改写**：

| 分支标题 | 初版概括 | 判 |
| --- | --- | --- |
| 从信息过载到选择性关注 | 关键输入筛选与干扰抑制 | 新（"抑制干扰"标题里没有） |
| 查询、键与值的三元结构 | 查询键值相似度检索机制 | 标题改写 |
| 相似度打分与权重分配 | **相似度打分与归一化权重** | 几乎逐字重复 |
| 加权求和生成上下文向量 | 值向量加权求和上下文 | 同一件事换语序 |
| 多头并行捕捉多类关系 | 多头子空间并行关系捕捉 | 同一件事换语序 |
| 自注意力与跨序列对齐 | 序列内部与跨序列对齐 | 同一件事 |

这正是自评担心的"第二套标题"，而且它是**真的**。所以提示词改成一条硬约束：
**标题里出现过的两字以上实词，一个都不许写进概括**；并且明确"从下位节点的词里取词"。

**改后（当前版本）**，同一棵树、同一份输入：

| 分支标题 | 改后的概括 | 字数 |
| --- | --- | --- |
| 从信息过载到选择性关注 | 关键输入筛选与干扰抑制 | 10 |
| 查询、键与值的三元结构 | **按需检索的权重计算框架** | 11 |
| 相似度打分与权重分配 | **分数归一化与向量加权** | 11 |
| 加权求和生成上下文向量 | **关注程度决定上下文表示** | 10 |
| 多头并行捕捉多类关系 | **独立子空间并行学习** | 11 |
| 自注意力与跨序列对齐 | 序列内部关联与跨序列匹配 | 10 |

6 条里 5 条给出了标题没有的信息，1 条仍然重合——而它恰好是唯一违反那条硬约束的
一条（"跨序列"三个字直接复用了标题）。**留存数据**是 `scripts/_branch_digest_sample.json`
（`_` 前缀，不进提交）。

### 成本

| 场景 | 墙钟 | 输入 token | 输出 token | 写回 |
| --- | --- | --- | --- | --- |
| 6 支 · 初版提示词 | **1.877 秒** | 538 | 106 | 6/6 |
| 6 支 · 改后提示词 | **2.438 秒** | 643 | 106 | 6/6 |
| 50 支（库里那棵 561 节点的探针树） | **3.244 秒** | 2,231 | 550 | 50/50 |

与 `docs/FOLD-RETIRED.md` §5 那条独立实测（5 组 1.87 秒）对得上。**逐组各调一次是
9 秒量级**（同一条注释），而批量只有一次往返……

### 失败时是什么样子

三种，每一种都有用例钉着（`backend/tests/test_branch_digest.py`，15 条）：

| 来路 | `content.branch_digests` | `data.branch_digest` | 诊断 |
| --- | --- | --- | --- |
| 调用抛错（上游 502） | `{}`（键都没有） | `skipped: "error"`, `failure: "上游 502"` | `BRANCH_DIGEST_SKIPPED`（warn） |
| 额度用完 | `{}` | `skipped: "budget"` | `BRANCH_DIGEST_SKIPPED`（warn） |
| 一条都对不上号 | `{}` | `skipped: "error"`, `unknown: [...]` | `BRANCH_DIGEST_SKIPPED`（warn） |
| 少写两支 | 只有写回来的那支 | `missing: ["b0","b2"]` | `BRANCH_DIGEST_INCOMPLETE`（info） |

三种情况下**树本身一个节点都不少**、`+N` 与顶部「显示 40 / 136」一个字都没变。

## 四、前端：一行、左上、深色

### 显示判据：四条与一条全部成立才画

```
① 它是一级分支（depth === 1）
② 这一支真的还有没画出来的节点（unshown > 0）
③ 还有的个数 ≥ MINDMAP_BRANCH_BADGE_MIN_HIDDEN（4）
④ content.branch_digests 里有这一支的概括
```

第 ③ 条的理由是**决策成本**不是审美：一支只差 1–3 个节点时用户会直接点开（一次
点击），而读一句概括再决定要不要点反而更贵；何况那 3 个数与它头上那枚 `+N` 说的是
同一件事。实测那棵 136 节点的真树六支分别是 12 / 15 / 21 / 6 / 18 / 24——**都过线，
一枚都没被这条判据拦掉**，所以它不制造"为什么这枚没了"的困惑。

第 ④ 条是"没有概括就不画"。这条容易引起误解，所以说清：**这枚角标的价值全在概括
上**。没有概括时它只剩一个数字，而"这一支还有 N 个"与 `+N`、顶部「显示 40 / 136」
说的是同一件事——一枚只会重复别人的角标不值得占位置。旧图（`branch_digests` 这个
键根本不存在的那些）因此一枚角标都没有，而收起这件事一个字都没变。

### 数字用的是 `unshown`，不是 `folded.closedSubtree`

`viewTree` 这一轮多了一个出口：

```ts
folded:  Map<id, FoldInfo>   // 这个父节点**自己有直接孩子**没画（`+N` 的判据）
unshown: Map<id, number>     // 这棵子树里**任何一处**有节点没画（角标的判据）
```

两者不是同一个量，而这个区别是角标能不能站住的关键：BFS 铺满 40 个节点时，
前三层几乎全在画布里——**一级分支的孩子通常都已经画出来了**，它们的孩子才被截。
用 `folded` 判，六支会有相当一部分拿不到角标；而用户看不出为什么这一支没有。
实测（`tests/branch-digest.spec.ts`）：六支全部在 `unshown` 里，而 `folded` 里
只有一部分。

### 点击：整支，不是一层

```
+N       写的是"这一处缺 3 个直接孩子"  → 点它只放一层
概括角标  写的是"这一支还有 21 个"       → 点它放出整支
```

**数字决定粒度**，这两枚角标共用同一条规则。做成"只放一层"的话，预算铺满时点下去
往往什么都没发生（孩子已经在画布上），那会得到一个比 `+N` 更没用的角标。

实现是 store 里的 `expandBranchInView(id)`：把这一支里**每一个有孩子的节点**都放进
`expanded`（"用户要求看它"那一档），同时清掉这一支内部的收起标记。视图层不新增概念。

代价是这一支里每个有孩子的节点都会挂一枚「−」（叶子不挂）——浏览器实测：点开一支
之后 19 枚「−」里有 **9 枚常驻**。回程有顶部「收起到上限」与逐枚「−」两条，而且
用户刚刚明确要求了"看这一支"。

## 六、自评：这枚角标会不会变成"第二套标题"？

**会——初版提示词下它真的会，而且数据是我自己量的**（§三：6 条里 5 条是标题的改写，
「相似度打分与权重分配」→「相似度打分与归一化权重」）。这不是"可能的风险"，是
**已经发生过的失败**，改提示词之后才降到 1/6。

所以这个问题该拆成两问：

**第一问：概括比标题更准时，它是不是在批评标题？**

**是，而且这个批评是对的。** 「相似度打分与权重分配」这个标题本身写的就是内容摘要
（"打分""分配"都是动作），它没有说"这一支的边界在哪"；而「分数归一化与向量加权」
说的是这一支里**具体在算什么东西**。标题在生成那一轮是骨架给的（它要短、要能和
兄弟支并排），概括是读完下位节点之后写的——**后者天然更准，因为它看到的东西更多**。
这不构成"要改标题"的理由：标题的任务是"在图上认得出"，概括的任务是"判断要不要展开"。

**第二问：那两个标签并排，用户该看哪个？**

看**数字**，两个文字都不是主角。这枚角标的第一个信息是「还有 21 个」——那是标题
给不了、`+N` 给不了（`+N` 只说一层）、而且免费的量。概括只回答"那 21 个大概是什么"。
把主次搞反（先读一句概括再看数字）才会觉得"两个标题打架"。

**值得显示的条件**（四条，与 §四 的判据一一对应，缺一条就该省掉）：

1. 这一支**真的被截断**（`unshown > 0`）——全展开时没有"还有"，一枚都不该在；
2. 截得**足够多**（≥ 4）——差 1–3 个时用户直接点开，读一句概括反而更贵；
3. **概括存在**——开关关着 / 模型没写回 / 旧图时，它只剩一个与 `+N` 重复的数字；
4. 它**是一级分支**——深层节点挂概括会把画布糊满（这正是上一轮否决"给每个父节点
   再加字"的理由），而且深层的"这一支讲什么"由它自己的 `detail` 与悬停卡片承担。

**多久之后该回头看它**：如果某一天生成侧的 `label` 也从下位节点收上来（而不是
骨架给一个短标题），这两个标签会真的开始重复——那时该做的不是删角标，而是**让
`label` 承担概括**、角标退回纯数字。这条边界现在还没到，但它是这条路上第一个会
到期的东西。

**回滚**：后端 `MINDMAP_BRANCH_DIGEST=0`（出厂即这样）就是"一句概括都不写"；
前端 `MINDMAP_BRANCH_BADGE_MIN_HIDDEN` 调到 `Infinity` 就是"一枚角标都不画"。
两条各自独立——关掉后端只是让角标不出现（概括为空 → 不画），关掉前端不影响已有
的 `branch_digests` 数据。

## 八、已知边界（不要当成 bug 修）

- **概括与标题仍可能重合**（实测 1/6）。字面判据抓不住它——用"公共子串 ≥ 4 字"去
  比那 6 条，一条都拦不住（重合是**语义**上的，「相似度打分」与「分数归一化」没有
  四个连续相同的字）。要做语义判据就得多一次模型调用，不值。
- **角标只覆盖树型**。鱼骨的一级是固定六类、流程的一级是阶段序列，都概括不出新东西，
  产物里也没有这个字段。
- **`+N` 与它并存**，一枚在右下、一枚在左上，一个说"这一处断了"、一个说"这一支多大"。
  两者都用得上：`+N` 标的是**截断点**（19 处，散在各层），角标标的是**整支的规模**
  （6 处，固定在一级）。
- **旧图永远没有概括**，除非重新生成一次（或将来加一条"给已有图补概括"的接口）。
  这是"概括随图走"的代价，也是它比 `data` 旁路值得的地方：**只需要付一次**。
- **50 支的树点一支会一次冒出 20+ 个节点**。这是"数字决定粒度"的必然结果；
  回程有「收起到上限」。
