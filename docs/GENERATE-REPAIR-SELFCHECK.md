# 生成收尾的两件便宜事：确定性修复 + 结构自检

2026-11-26。`docs/SUBAGENT-VS-SELFCHECK.md` 把"每支一个子代理"否掉之后，指了两件
"便宜得多、收益更实"的事。这一份是**接线之后**的记录：改了什么、判了什么、实测
多少、以及那个自评问题的答案（这两件能不能替代"每支一个子代理"）。

两件都不改架构：一件是零调用的确定性修复（`optimization.repair()` 早在代码里，
缺的只是"收尾只跑 `check()` 没跑 `repair()`"这一行），一件是 +1 次调用的自检回路
（输入是已经交付的那棵树，输出是一份清单）。

---

## 一、第 0 件：收尾接上确定性修复（零模型调用）

```
位置    app/agent/tools.py::_generate，"七条结构规则"那一带
顺序    先 repair（修）→ 再 check（报）→ 再 _cross_branch_duplicates（判）
开关    MINDMAP_AUTO_REPAIR，默认**开**
```

### 判断一：自动修哪几条，判据是"修法唯一"

| 码 | 修法唯一吗 | 收尾自动做吗 |
|---|---|---|
| `DUPLICATE_LABEL` | 唯一（并进该父下第一个同名的） | **做** |
| `SINGLE_CHILD` | 唯一（外层并进内层，保留内层 id） | **做** |
| `HEADING_ONLY_BRANCH` | 同上（它只是 `SINGLE_CHILD` 在第 2 层的替代表述） | **做** |
| `NEAR_DUPLICATE_LABEL` | 不唯一：字面像 ≠ 语义同（实测 40 对里 0 对真近义） | 不做，只报 |
| `SHALLOW_BRANCH` / `MISSING_DETAIL` | 不唯一：补什么内容要模型 | 不做，只报 |
| `DEPTH_LIMIT` | 没有可执行动作 | 不做，只报 |

"唯一"是可检验的意思：结果与"分段跑还是一趟跑"无关（`optimization/repair.py` 的
模块注释 + `test_order_of_repairs_does_not_change_the_result`）。

### 判断二：并进这一次生成，不留给用户点

三条理由，一条是产品、两条是代码：

1. **它没有需要用户做的决定**。输入是模型刚写的树，输出是同一棵树的去冗余版本；
   放到界面上让他点，等于让他为一段自己没看见过的中间态付账。
2. **撤销栈天然是一条**。修复在 `publish_tree` 之前完成，于是前端落地那次
   （`frontend/src/stores/mindmap.ts::commitGenerated`，压 `past` 一步并装入候选）
   拿到的**就是修好的那一棵树**，用户按一次 Ctrl+Z 回到"生成之前"，而不是"第 1 处
   修复之前"。这一条与前端一键修复的 `replaceContent`（同样只压一步）口径一致。
3. **可以关掉**。`MINDMAP_AUTO_REPAIR=0` 时 `data` 的键集与接线之前逐字相同——那份
   报告里所有数字都取自那条路，能回去重跑才算"可复现"。

一条副作用要交代：压链保留内层 id，所以一级分支可能换 id，而一级分支概括
（`branch_digests`）是按外层 id 写的。收尾会把这一类死键删掉（**不搬给内层**——
那句话说的是"外层那支讲什么"，挂到另一个标题底下是错的归属）。

第二条小账要对齐：`data["detail"]`（要补几个、写回几个）是**说明那一步**的读数，
它在修复之前量；修复之后节点会变少，所以 `detail.filled` 与 `node_count` 不必相等。
被并掉节点的说明不会丢——`repair()` 把两段正文拼起来（`_join_text`）并进保留者。

### "它会不会把模型写的东西悄悄改掉"

不会悄悄，但确实会改。两件事分别说：

**改了什么是可查的**。`data["auto_repair"]` 里除了计数，还有 `items`——每一步
`{code, node_id, message}`，message 是 `repair()` 自己那句人话（「把「甲」并进了
同级同名节点「乙」：子树取并集（2 + 1 个），引用取并集（0 条）」）；跳过的每一步也带
`reason`（超出契约上限 / 诊断过期）。上限 30 条，超出的报 `items_truncated` 而不静默
截断。加上一条 `STRUCTURE_AUTO_REPAIRED` 诊断，用户不需要信任"它说它只修了结构"。

**哪些可以自动，判据是"修法唯一"**（见上表）。补一条界面上真正的分界线：
`NEAR_DUPLICATE_LABEL` 那种"字面像、语义像"的合并**永远留给用户点**——自检回路那
10 条语义重复也一样，它们的精度是 88%，而合并没有反操作。

### 实测（`scripts/measure_generate_repair.py`，65 张去重后的 `runs.candidate`）

```
三条可修规则的命中（修复前）：
  SINGLE_CHILD        178 次，涉及 26/65 张图
  DUPLICATE_LABEL       0 次
  HEADING_ONLY_BRANCH   0 次（它在压链过程中才冒出来，见下）
只报不修的（对照）：
  NEAR_DUPLICATE_LABEL  2 次 / SHALLOW_BRANCH 8 次 / MISSING_DETAIL 2 次

修复：178 步，涉及 26/65 张图；跳过 0 处；幂等全部成立
节点：3551 → 3373（−178）
```

改动最大的 5 张里有 3 张是 16 节点的小图、步数 10（`SINGLE_CHILD 6 +
HEADING_ONLY_BRANCH 4`）——正是"一级分支只有一个叶子孩子"那种形状，也是这份图在
界面上看起来最空的原因。

用 `mindmaps`（用户保存过的图，含探针树）量的另一份口径：72 张里 28 张可修、
685 步、最大一张 504 步（那张 561 节点的探针树有 500+ 处同级重名）。两个分母不能
混，见 `scripts/measure_repair.py` 的文件头。

### 一个真的会漏掉的顺序问题（改之前测出来的）

`_cross_branch_duplicates` **只比逐字**，而压链会改 label（`外层 / 内层`）。如果先修
后判，"两条一级分支各只有一个孩子、两个孩子同名"这种形状会在修完之后变成
「甲 / X」与「乙 / X」，判据再也看不见它——而模型确实把同一件事写了两遍。

所以判据跑在修复**之前**（`duplicates = _cross_branch_duplicates(content.root)` 在
repair 块之上），诊断说的是"模型写了什么"。用例：
`test_cross_branch_duplicates_are_judged_before_the_repair`。

## 二、第 1 件：结构自检回路（+1 次调用，默认关）

```
位置    _generate：结构那一次之后、说明那一次之前
输入    只有【一级分支 + 缩进节点 + 节点 id】，不给 detail
输出    [{node_id, kind, problem, fix}]，kind ∈ 四类
消费    一条汇总诊断 + data["self_check"]；**一个节点都不改**
开关    MINDMAP_SELF_CHECK，默认关
失败    budget / error → 一条 SELF_CHECK_SKIPPED 告警，生成照常交付
```

### 判断：为什么在"说明之前"，而不是之后

三条都不是口味：

1. 那一刻**标签已经定稿**：说明段只填 `detail`，不改任何 `label`；清单要的正是标签
   与位置。等说明写完再看，输入一个字都不会多。
2. 往前不行：结构之前树上只有骨架，下位节点还不存在，审出来的一半是"这一支是空的"。
3. 它和说明段**串行**：说明段本身是两半并发，插在之前是"先等这一次、再并发写说明"，
   插在之后是"并发跑完再单独等一次"——总耗时一样，但前者清单出来得更早。

### 判断：产出是清单，不是动作

报告实测精度 22/25 = 88%，误报全在 `chain` 一类；而**合并没有反操作**（`repair()`
有 `RepairUndo`，这条回路没有）。自动落地会伤到那 12%，所以它只报。这也正是用户
要的东西：**可指认**——每一条都带 `node_id` 与位置路径，用户知道是哪一支错了。

### 判断：不进 `optimization.suggest()` 那一套

试过这个方向，没做，理由是 `Suggestion` 的形状与这份清单对不上：`SuggestionKind`
的九个值是**动作**名词（`dedupe` / `merge` / `expand` / `add_detail` / `drop` …），
而这里的问题是**判断**（"这两处是同一件事"）。硬映射会有两个后果：语义重复被记成
`dedupe`，用户在"建议"面板点它一下——而那个面板的语义是"这条动作可以执行"，这份
清单没有可执行的动作（要执行得先决定保留哪一份，那是人的事）。所以它只出
一条诊断 + `data["self_check"]`：诊断负责"让你知道"，`data` 负责"让你查证"。

### 两个新码在界面上暂时显示原码

`STRUCTURE_AUTO_REPAIRED`（info）与 `SELF_CHECK_ISSUES`（info）没登记进
`frontend/src/mindmap/diagnostics.ts::DIAGNOSTIC_LABELS`——本轮边界不许动前端。
那个文件的约定正好容许这件事："**只登记已知码**，表里没有的一律显示码本身，这是
这个功能能扛住后端演进的全部机制"。所以用户看到的是原码 + 后端那句中文 message；
补两行中文标题是下一次动前端时的顺手活，不是技术债。


### 实测（`scripts/measure_self_check_live.py`，跑的就是产品代码）

| | `410ba3d0`（分片产物） | `3d71b0ab`（一次写完产物） |
|---|---|---|
| 节点 / 一级分支 | 56 / 5 | 79 / 5 |
| 清单规模 | 56 行 / 3,167 字 | 79 行 / 2,079 字 |
| 输入 / 耗时 | 1,418 token / **4.1 s** | 1,196 token / **2.9 s** |
| 报出 | 7 条（语义重复 5、跨支重复 2） | 6 条（跑题 2、语义重复 4） |
| **逐字判据看不见的** | **5 条** | **5 条** |

"逐字判据看不见"的定义是可算的：把 `optimization.check()` 的七条与
`_cross_branch_duplicates` 已经指过的节点 id 取成集合，清单里剩下的就是这条回路
独有的产出（`scripts/measure_self_check_live.py::_literal_coverage`）。

两张图合计 **13 条，其中 10 条**是七条规则 + 逐字比都不报的那一类。人判这 13 条：

- **12 条成立**，其中 3 条"确实写了一件事两遍，但不宜按它的改法删"（应用分支里重复
  列举模型名，删掉会丢"这个模型在这里是什么角色"）；
- **1 条边界**（「实验教学与深度学习」被报跑题——它写的是"机器学习的课程怎么教"，
  严格说不是"机器学习在某个领域的应用"，但用户未必觉得它错）。

跑题那两条正是报告里记的「财务报销流程优化 / 营改增」，以及「实验教学与深度学习」。

## 三、自评：这两件加起来，能不能替代"每支一个子代理"

那份报告的结论是"该分的是检查，不是生成"。接线之后，数据是这样的：

### 调用数

| 方案 | 6 支场景的调用数 |
|---|---|
| 现状一次写完 | 3–5 |
| **+ 确定性修复** | **3–5**（+0） |
| **+ 自检回路（开）** | **4–6**（+1） |
| 每支一个子代理 | 13–19 |

### 跨支重复（真产物，65 张去重后的树）

| 阶段 | 有跨支重复的图 | 重复节点 |
|---|---|---|
| 修前 | 12/65 | 44 |
| 确定性修复之后（代码侧模拟） | 11/65 | **38** |
| 自检回路开着、但按设计不落地 | 11/65 | **38** |

**这就是要修正报告的地方。** 报告那张表里"一次写完 + 自检 + 确定性修 → 跨支重复
0%（实测两次都清零）"成立，但它成立的前提是**把清单里的合并用代码落地**——那是
`measure_selfcheck.py` 里的实验动作，不是产品行为。产品里这条回路**故意不落地**
（88% 精度 + 合并不可逆），所以：

- 交付物上的跨支重复**没有减少**：44 → 38。
- 那 6 处的减少来自压链的副作用（`SINGLE_CHILD` 顺带把重复的两个节点之一改了名），
  不是"判据命中了重复"。
- 真正的变化是**可见性**：从"14–15% 的图里有一条逐字诊断"变成"清单能指认到具体
  节点、含 10 条逐字判据看不见的语义重复"。

所以报告那句"跨支重复 0%"该改成：**检查能把跨支重复清零的前提，是清单会被落地**；
在"检查只出清单"的产品形态下，它剩下的是"指认"，不是"消除"。要真的清零，需要
第三步——按清单合并的入口（前端已有 `replaceContent` 那条整体替换通道，但清单里的
语义重复不在 `AUTO_REPAIRABLE_CODES` 内，得先决定"哪一份是模型判的、凭什么信任"）。

### 跑题

| 阶段 | 可见的跑题 |
|---|---|
| `check()` 的七条规则 | **0 类**（没有这个码） |
| 自检回路（两张真图） | **2 条**（1 成立、1 边界） |

跑题这一项是**从"完全不可见"到"每次 1 次调用即可见"**，不存在"还剩几条"——因为
以前一条都没报过。交付物上它也没被改：用户看到清单，自己决定。

### 结论

- **"该分的是检查不是生成"这条成立，而且更硬了**：检查分项 +1 次调用，生成分片
  +9～+33 次，而它对"跨支重复"这一项的贡献是**指认**而不是消除——用户要的"哪一支
  错了能定位"拿到了，"树自己变干净"没拿到。
- **"这两件能替代每支一个子代理"只在三个条件同时成立时**：① 用户愿意按清单处理
  （否则跨支重复仍剩 38 处）；② 不需要"每次展开只写一小块"来解决单次输出装不下
  （`INITIAL_MAX_NODES=80` 撞线）；③ 不需要按支的进度可见性。
- **剩下的重复仍然明显**（38 处 / 11 张图），所以那份报告里"0%"那一行**要修正**；
  但修正的方向不是"回去做子代理"，而是补上"清单 → 落地"这一步。

## 四、可复现

```
cd backend
python scripts/measure_generate_repair.py           # 零调用：真实产物上修几处（本文件第一节）
python scripts/measure_repair.py                    # 零调用：用户在界面上点一键修复会发生什么
python scripts/measure_self_check_live.py           # 1 次调用/张图：跑产品代码的自检清单
python scripts/measure_self_check_live.py --dry     # 0 调用：只看喂进去的清单
python scripts/audit_self_check.py 410ba3d0 分支名   # 0 调用：人判某几条时把该支打出来
```

三个脚本都只读库；`measure_self_check_live.py` 是唯一会花模型调用的，凭据从
`run-backend.bat` 取，**不走游客配额**（这台机器没配 `MINDMAP_FREE_TIER_API_KEY`，
`free_quota` 表实测 0 行）。
