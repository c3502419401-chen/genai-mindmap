# 按分数取数：`top_k` 从"条数"变成"下界"

> 用户原话：**"rag 的检索范围有哪些，现在 rag 检索是不是只选分数最高的那几条，会漏很多，
> 改成分数差不多的都可以拼给大模型"**

这份文档记四件事：现在的截断到底漏了什么（§1）、这个仓库里哪种分数是可得且可比的
（§2）、四个常量各改成什么且为什么是那个数（§3）、改完的代价与多路融合下的边界（§4/§5）。

复现全部数字的两个脚本（都不吃 LLM、不吃生成）：

```
cd backend
python scripts/measure_topk_threshold.py --bm25-only      # §1 的分数分布（纯 BM25）
python scripts/measure_topk_threshold.py                  # §1 的分数分布（hybrid，需 embedding key）
python scripts/measure_keep_effect.py                     # §4 的条数/字数/token 对照（重排默认关）
```

真生成的 A/B（吃 DeepSeek，两条臂唯一的差别是一个环境变量）：

```
python scripts/measure_generation_strategy.py --batch thick --keep on  --repeat 1
python scripts/measure_generation_strategy.py --batch thick --keep off --repeat 1
```

## 1 三个数：现在的截断漏了什么

口径：五组真实材料（英文 PDF 37,973 字 / 中文长文 42,526、26,265、20,017 字 /
碳中和薄批 4 份共 670 字）× 每份 5 个**真实小节标题**当 query（分支标题在生产里就是
这个形态），`top_k` 开到 60 拿全量，23 组有效观测。父块口径（`_search_parent_core`，
每条对应不同的父块）。

### ① 分布形态：不是"3 附近断崖"，是"首位离群 + 3 之后长尾"

```
材料/query                    method   父块   r3     r10    r20   3→4跌  断崖位
pdf/Attention Is All You Nee  lexical   48  0.297  0.258  0.212  0.060    1
pdf/5 Training                lexical   28  0.792  0.499  0.328  0.004   27
attention/6 Results           lexical   21  0.775  0.510  0.350  0.011    5
agent_plan/先修三件小事         lexical   15  0.087  0.048    -    0.269    2
agent_plan/op、ID 与整树保存     lexical   47  0.290  0.251  0.172  0.015    1
plan/4 四周里程碑               lexical   17  0.306  0.098    -    0.451    1
（rN = 第 N 条的分 / 第 1 条的分；hybrid 那 23 组的 r3 是 0.80–0.98、r20 是 0.38–0.69）
```

两种形状同时存在，**中间没有"断崖恰好在 3"这一类**：

- **首位离群**：第 1 名常常是第 3 名的 2–11 倍（BM25 15.25 vs 4.52、58.7 vs 5.1）。
  原因是整句标题几乎原样出现在某一处——那是"标题定位"，不是"相关性更高"。
- **3 之后长尾**：第 3 到第 12 条缓慢下降。`pdf/Attention` 是 15.25 / 7.48 / 4.52 /
  4.25 / 4.24 / 4.19 / 4.14 / 4.10 / 3.95 …，从第 3 条往后 8 条差 16%。

**结论一：断崖在 3 附近这件事没有发生。** 所以"固定 `top_k=3` 是对的"这个假设不成立。

### ② 第 3→4 条的差距

```
第 3→4 条的跌幅：中位 0.026（hybrid）/ 0.047（纯 BM25）
最小 0.001（hybrid）/ 0.004（纯 BM25）
最大 0.117（hybrid）/ 0.451（纯 BM25）
```

大半情况下第 4 条与第 3 条差不到 5%。**但也有 0.45 那一侧**（`plan/4 四周里程碑`）：
那种材料第 4 条只有第 3 条的 55%，"差不多"不成立——所以阈值必须能停下来，
不能无条件多取（§3 的 `rel` 就是干这个的）。

### ③ 被砍掉的那几条，是同一父块的另一截吗

子块口径（折叠之前），第 4–10 条共 140 条：

```
纯 BM25：  7 条是同父块另一截、133 条换了新父块（95% 是新信息）
hybrid：   9 条是同父块另一截、131 条换了新父块（94% 是新信息）
```

父块口径下这个比例是 100%——`_fold_to_parents` 已经保证每条对应不同父块。所以
**"多给几条"是真的多给信息**，不是同一段换个开头。

注：`thin`（碳中和 4 份，670 字）整份只有 1–3 个父块，比 `top_k=3` 还小。这一端
阈值不能把结果砍成 0 条（§3 的 `min_k` 与 `len(hits)` 取小就是为它）。

## 2 哪种分数是可得且可比的

`EvidenceHit` 上有四列分，**只有三列能用，其中一列主用**：

| 字段 | 是什么 | 可比吗 | 用不用 |
|---|---|---|---|
| `score` | hybrid 时 **RRF 分**（两路 `1/(60+名次)` 之和）；单路时 BM25 原始分 | **不可以** | ❌ |
| `score_vector` | 余弦（0–1） | 跨 query 同量纲，有绝对含义 | ✅ hybrid 时用它 |
| `score_bm25` | BM25 原始分 | 同一次检索内可比；**跨 query 不可比** | ✅ 纯 BM25 降级时用它 |
| `rerank_score` | cross-encoder 概率（0–1） | 绝对可分（噪声 0.19–0.29 / 真相关 0.58–0.89） | ✅ 有值就优先用它 |

**为什么不能用 `score`（RRF）**：它是名次的函数。实测 hybrid 下前 12 名全落在
0.024–0.033（差 27%），第 20 名还有第 1 名的 38%——"用 RRF 做阈值"等于"按名次取",
只是换了个说法。用户点出的正是这一层，所以这一列在阈值里**一次都没用**。

**为什么 BM25 只能配相对系数**：同一个词在不同 query 下 5.1 与 58.7 差 11 倍（query
长度与命中词数都进了分母），所以它的"绝对阈值"只能是 0（= 命中过查询词）。

**为什么余弦的绝对阈值只能取 0.45**：噪声的余弦能到 0.571、真相关能低到 0.562
（`tools.py` 里那轮外部检索实测，两个分布重叠）。余弦的绝对值**不可靠**，可靠的是
它内部的相对形状，所以绝对阈值只负责"整批都在 0.4 以下"这种明显无关的检索。

**`rerank_score` 是最好的标尺**（有值就优先），代价是它只在 `MINDMAP_RERANK=1` 且
凭证齐备时才存在——而 `tests/conftest.py` 把它默认关掉，所以不能只靠它。

标尺的选择整批统一（`_keep_scale`）：重排 > 余弦 > BM25 > 融合分。同一批里混量纲
比大小比出来的是两个世界。

## 3 四个常量各改成什么

形状按要求是 `取所有 score >= max(绝对阈值, 基准 × rel)` 再 clamp 到 `[min_k, max_k]`。
**但"基准"不是第 1 名**——这是数据逼出来的改动，理由在下面。

### 3.1 基准为什么不是"最优分"

用户给的形状写的是"最优分 × 相对系数"。实测第 1 名是离群点（§1 ①），拿它当基准：

```
基准 = 第 1 名，rel = 0.85  → 中位只剩 3.0 条（等于没改）
基准 = 第 3 名，rel = 0.85  → 中位 4.5 条（纯 BM25）/ 取满 max_k（hybrid）
```

所以基准取**列表里第 `min_k` 名**的分（不是"前 `min_k` 名的中位数"——后者在
`[58.7, 37.6, 5.1, …]` 这种形状下会取到 37.6，门槛跟着离群点跑，又回到第 1 名那个错上）。

### 3.2 四个数

`service.DEFAULT_KEEP = KeepPolicy(min_k=3, max_k=6, rel=0.85)`，绝对阈值按量纲分三个
（余弦 0.45 / BM25 0 / 重排 0.30，依据见 §2）。

| 位置 | 原来 | 现在 | `min_k` / `max_k` / `rel` | 依据 |
|---|---|---|---|---|
| ① 按支检索 | `DEEP_BRANCH_TOP_K=3` | `DEEP_BRANCH_KEEP` | 3 / **6** / 0.85 | 影响最大（一支只看 3 块）；`max_k=6` 是成本闸：20 支 × 6 = 120 条父块 ≈ 6 万字 |
| ② 章内检索 | `DETAIL_RETRIEVAL_TOP_K=3` | `DETAIL_RETRIEVAL_KEEP` | 3 / **5** / 0.85 | 一章只有 3–5 个父块，`max_k=5` 就是"把这一章看全"；`DETAIL_RETRIEVAL_MAX_CHARS=16,000` 仍是总闸 |
| ③ `rag_query` | `top_k=5, le=5` | `RAG_QUERY_KEEP` + `le=10` | 3 / **8** / 0.85 | 模型唯一能自己调的入口；`max_k=8` 与 `LIBRARY_GENERATE_TOP_K=8` 同量级 |
| ④ 库补足 | `LIBRARY_GENERATE_TOP_K=8` | **不改** | — | 它已经有 `LIBRARY_RELEVANCE_GATE=0.6` 那道 rerank 门，`rerank_score` 的两簇实测不重叠（0.29 vs 0.58），比阈值更可靠 |

`DEEP_BRANCH_TOP_K` / `DETAIL_RETRIEVAL_TOP_K` 这两个**名字保留**，值改为
`KEEP.min_k`：六个测试文件与两个 `measu*` 脚本拿它们当锚。

### 3.3 两个坏法怎么防的

```
都很低 → 按相对系数会取到一条     → min_k 托底（test_min_k_holds_when_every_score_is_low）
都很高 → 能取到 30 条 → 撑爆 prompt → max_k 封顶（test_max_k_caps_when_every_score_is_high）
材料本来就不够（薄批 1 个父块）    → 与 len(hits) 取小（test_never_more_than_that_hits）
```

**还有一个第三种坏法，是实测先漏掉的**：`top_k` 当"下界"用时，下界必须取
`max(min_k, top_k)`。少了这一半，`rag_query` 的 `top_k=5` 而 `min_k=3` 时会取 3 条
——**比改之前的 5 条更少**（第一次跑对照表时出现的 `0.60x`）。现在
`keep_by_score(..., at_least=top_k)` 显式带上调用方的条数。

### 3.4 回滚闸

`MINDMAP_KEEP_BY_SCORE`（默认开）。设为 `0` 时四个调用点都传 `keep=None`，
**逐字节回到"取排序后前 N 条"**。真生成的 A/B 就靠它跑（两臂只差这一个变量）。

## 4 改完的代价

同一批 (材料, query)，`search_parent` 改前 / 改后对照（`scripts/measure_keep_effect.py`）：

| 口径 | 条数倍数（中位/最小/最大） | 材料总字数 | prompt token |
|---|---|---|---|
| 纯 BM25 | 1.33x / 1.00x / 2.00x | 74,234 → 105,289（1.42x） | 49,505 → 70,209 |
| hybrid | 1.67x / 1.00x / 2.00x | 75,836 → 127,495（1.68x） | 50,572 → 85,015 |

- **最小 1.00x** 是关键：没有一处变少（`at_least` 那一半修的就是这个）。
- **薄批不动**（1.00x）：材料比 `max_k` 还小，阈值没有东西可加——这是对的。
- **按支检索的最大放大是 2.0x**（3 → 6）。20 支的上界因此从 60 条变 120 条父块，
  约 6 万字 ≈ 4 万 token。这是 `max_k=6` 而不是 10 的原因。
- 耗时没有明显变化（纯 BM25 全部 < 120ms；hybrid 的时间花在 embedding 上，与条数无关）。
- **带重排时会多**：`_rerank_depth` 跟着 `want` 放大，候选池从 `pool_size(3)=12` 变成
  `pool_size(6)=24`，一次 rerank 请求体翻倍（仍是一次往返）。真生成日志里能直接看到
  这两个数字：off 臂「候选 12」、on 臂「候选 24」。

### 4.1 真生成 A/B：`repeat=3`，覆盖率按**可引用节点**计

两臂唯一的差别是 `MINDMAP_KEEP_BY_SCORE`（`--keep on/off`），真 DeepSeek、
`mindmap_generate` 整树一次生成，同一批材料。

**分母换了**：第一轮用的是"全部节点"，而骨架/结构层结构上不写说明、因此不可能有引用，
它们进分母等于给一条与检索无关的常量打折。改成**可引用节点 = `detail` 非空**（`source_refs`
挂在节点上、`detail` 是它支撑的那段文字）。两个分母都报，便于对照。

| 批次 | 臂 | 轮 | 节点 | 可引用 | 可引用覆盖率 | 全部节点覆盖率 | 耗时 |
|---|---|---|---|---|---|---|---|
| 厚批（66,536 字，按支检索） | on | 1 | 122 | 118 | 97.5% | 94.3% | 603.1s |
| 厚批 | on | 2 | 106 | 101 | 98.0% | 93.4% | 590.5s |
| 厚批 | on | 3 | 111 | 106 | 77.4% | 73.9% | 610.3s |
| 厚批 | off | 1 | 113 | 108 | 79.6% | 76.1% | 619.5s |
| 厚批 | off | 2 | 97 | 92 | 97.8% | 92.8% | 606.6s |
| 厚批 | off | 3 | 97 | 92 | 98.9% | 93.8% | 584.3s |
| 薄批（673 字，**全塞不检索**） | on | 1–3 | 37/40/46 | 同左 | 81.1 / 77.5 / 69.6 | 同左 | ~35s |
| 薄批 | off | 1–3 | 52/104/40 | 同左 | 65.4 / 99.0 / 75.0 | 同左 | ~39s |

均值与极差：

| 批次 | 臂 | 可引用覆盖率 均值（n=3） | 极差 | 全部节点覆盖率 均值 | 节点数 均值（极差） |
|---|---|---|---|---|---|
| 厚批 | on | **91.0%** | 20.6% | 87.2% | 113（16） |
| 厚批 | off | **92.1%** | 19.3% | 87.6% | 102（16） |
| 薄批 | on | **76.1%** | 11.5% | 76.1% | 41（9） |
| 薄批 | off | **79.8%** | 33.6% | 79.8% | 65（64） |

**判据（提前定死的）：厚批那 +5.9pp 在 `repeat=3` 之后还在不在。**

**不在了，而且不是"变小"，是"消失"。**

```
厚批 on   97.5   98.0   77.4     均值 91.0%   极差 20.6pp
厚批 off  79.6   97.8   98.9     均值 92.1%   极差 19.3pp
                                差 1.1pp（方向还对 off 有利）
```

两条臂的**分布完全重叠**：on 有 77.4 那一轮，off 有 79.6 那一轮；两臂各自都有两轮
98% 上下。**off 不动任何代码也能到 98.9%**——第一轮那个 74.8% 是低端样本，把它当
"改前的基线"本来就不对。

薄批那条（差 3.7pp、自身极差 33.6pp、且根本不经过检索）给出的是同一件事的独立量级
参照：**这份仓库的真生成覆盖率在样本间的波动就是 20–30pp 量级**，任何小于它的臂间差
都读不出来。

#### 过程记录：on 臂第一轮的 2/3 失败

按 `--repeat 3` 第一次跑厚批 on 臂时，3 轮里 2 轮失败：
`模型返回内容不是符合约定的导图 JSON，请重试`（`max_repairs=1` 也没救回来）。
同一时段 off 臂 3 轮 0 失败、薄批两臂 6 轮 0 失败。补跑 on 臂 3 轮则全成功。

所以 on 臂厚批的失败是 **6 次尝试 2 次失败（33%）**，off 是 **3 次 0 失败**。样本小，
但这个方向与"keep 让 prompt 变长"一致（材料字数 1.42–1.68x，长输出更容易被截断/跑
格式），**比覆盖率那 1.1pp 更值得盯**：它意味着 `max_k=6` 在 20 支的上界下可能压到
输出的稳定性，而这一轮没有针对它做量测。

**结论：这个改动在"引用覆盖率"上没有可复现的收益。** 按预定的判据，它该被当作
"未被证实"，而不是"已验证"。`MINDMAP_KEEP_BY_SCORE=0` 是现成的回滚臂。

要真的判它，需要：更多轮（每臂 5–10 轮）+ 固定树木规模（现在 `node_count` 臂内极差
就有 16–64，覆盖率的分母自己会漂），或者换成**与树规模无关的指标**（引用覆盖的材料
字数、被引用父块的不同个数、每支引用的去重父块数）。这三个都比"节点覆盖率"更能回答
"多给的几条有没有被模型用上"。

## 5 自评：多路融合（`search_multi` 的 RRF）下"分数差不多"还成立吗

**部分成立，边界必须说清。**

`search_multi` 的 `score` 是各路 RRF 累加，它是**名次**的函数：

1. **"分数差不多"在 RRF 上恒真、因此没有意义**。前 12 名落在 0.024–0.033（27%），
   第 20 名还有 38%——任何 `rel >= 0.6` 的阈值都会取满 `max_k`。这一层我**没有**假装
   它成立：`_keep_scale` 在多路里也会落到 `score_vector` / `score_bm25` 上，
   RRF 那一列一次都没进阈值。
2. **跨路不可比这件事，我的方案是"绕开"而不是"解决"**。`score_bm25` 在多路里取
   "各路中的最高分"、`score_vector` 取"各路中的最高余弦"——这两个"最高"是不同 query
   下的最好成绩，把它们放在一起排序，严格说也是不干净的。我的处理是：
   - hybrid 时用余弦（同一次检索、同一批块，量纲一致，只是 query 不同）；
   - 纯 BM25 降级时用 BM25 原始分（只用来定门槛，不是用来排序）；
   - **排序永远交给 RRF**，阈值只决定"截到第几条"。
3. **因此这个方案只对"排序已经是好的、只是被截短了"这条前提成立**。它覆盖的是：
   单路（`search_parent` / `search_exact_blocks`）、多路（`search_multi`，标尺换成
   余弦/BM25）、库补足（`library=True` 的跨批融合——那里两批的 `score` 都被
   `_merge_batches` 归一成 RRF，所以阈值同样只能看原始分）。
4. **它不覆盖**：图游走（`origin="graph"`，没有可比分数——按"条数"带着走，
   见 `keep_by_score` 的 `extra`）；也不覆盖"排序本身错了"的情况（那是 rerank 与
   查询扩展要解决的问题，不是多给几条能修的）。

一句话：**"分数差不多就多给"在单路与多路都成立，但在多路里它是"事后按余弦数条数"
而不是"按 RRF 分判相似"。RRF 做不到这件事，谁拿它做阈值都只是按名次取。**

## 6 这个函数承诺什么、不承诺什么

`keep_by_score` **承诺**：用可比原始分**估算该取多少条**，同时**保持上游的融合顺序不变**。

它**不承诺**："返回的每一条都达到了门槛"。因为它是按"达标条数"截长度、不是逐条筛，
所以前缀里可能出现未达标的一条，而一条达标的会被截掉。融合序与原始分不同序时就会出现：

```
融合排序后的余弦：0.80  0.70  0.60  0.40  0.69  0.55
基准取第 3 条  → 门槛 0.60 × 0.85 = 0.51
达标的是 0.80 / 0.70 / 0.60 / 0.69 / 0.55，共 5 条 → 返回前 5 条
→ 前缀里有未达标的 0.40，而达标的 0.55 被截掉了
```

**这不是 bug，是两个目标之间的既定取舍**（"条数按相关性估"vs"顺序不许动"）：

- 要做到逐条筛，就得允许重排，而 `search_multi` 的**保底段**（前 `ceil(top_k/2)` 条，
  来自用户原话那一路）会被挖空——那个代价更大；
- 图证据三列原始分全是 None，逐条筛会把整条图路判死；
- **单路时两者没有冲突**：`_pick_ordered` / `_fold_to_parents` / `_rerank_top` 出来的
  顺序就是分数序，"前缀"与"逐条筛"是同一个集合。冲突只在多路融合与重排之后存在。

所以引用 RRF 那条外部经验时要看清它约束的是什么：OpenSearch 的 hybrid search 文档
建议避免拿固定的 `min_score` 去过滤 RRF 结果——因为 RRF 分是**名次**的函数、不是
校准过的相关度。本方案在 RRF 那条路上做的正是**不用 RRF 分**（§2），阈值走余弦/BM25
原始分；而"截长度不逐条筛"这条是另一个取舍，与 RRF 无关（单路也这么写）。

谁需要"逐条保留达标结果"，那是另一个函数——不要在这里加开关：同一批证据按两种口径
返回，调用方没法判断自己拿到的是哪一种。

---

## 7 边界与已知取舍

- **图证据不参与阈值**：没有可比分，靠"截长度 + extra 补回"跟着走。属于"顺带保留"，
  不是"按分数保留"。
- **保底席位让顺序不单调**（`search_multi` 的"代价"一节）：所以阈值**截长度、不逐条筛**，
  否则保底段会被挖空。
- **`keep` 不改变重排**：`_rerank_top` 仍在 `keep_by_score` 之前跑，重排的 `top_k` 参数
  被换成 `want`（= `max(max_k, top_k)`），所以被重排打分的候选池也变大了。
- **既有测试全部走旧口径**：`tests/conftest.py` 把 `MINDMAP_KEEP_BY_SCORE` 置 0。
  新口径由 `tests/test_keep_by_score.py` 显式传 policy 覆盖（那个文件不读开关）。
