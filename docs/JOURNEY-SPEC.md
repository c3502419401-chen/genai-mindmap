# journey.spec：第一道问「能不能用」的闸

一份面向「这版能不能发布」的验收规程：真浏览器、真后端、真模型，手动触发。

脚本在 `docs/acceptance-scripts/journey.spec.mjs`（基建在 `journey-lib.mjs`，材料取自
`backend/scripts/acc_samples.json` 的 S08，548 字）。

## 它为什么和其余十六道闸不是同一类东西

那十六道读 AST、读快照、读文本，全都对着代码写。它们能回答"改了这个函数有没有回归"，
答不了"用户手里那张图能不能用"——因为那张图不在任何一个语法树里。

`docs/ACCEPTANCE-WALKTHROUGH-2026-11-28.md` §6.5 把这件事写清楚了：十六道闸全绿的状态下，
三件挡住交付的事零覆盖（上传卡在「正在解析…」、出图落地视图偏移、主题空时按钮灰而无解释）。
本闸就是补这一块，并且**只补这一块**。

它答不了的，仍然答不了：回归、性能、多用户、移动端。别指望它替那十六道做事。

## 五条断言，各自断什么

### ① 落地后视口 —— 按档位分，不写「≥0.8」

`≥0.8` 这条写不得：它在「适应宽度」档达不到，而达不到是产品**故意的**可读性取舍
（`fit-all` 会把 64 个节点缩到 5 px 字，那正是上一轮修掉的"第一眼以为生成失败"）。
写成 0.8 的后果是第一次跑就红，然后有人加一个豁免——那就成了又一道没人敢改的闸。

判据分档：

| 落地档位 | 断什么 |
|---|---|
| 「全图」 | 视口内可见数 == 已渲染数（100%） |
| 「适应宽度」 | ① 根节点在视口内 ② 可见比例 ≥ 该图的物理上限 ③ 界面自述的离屏数与几何事实一致 |

三条都要，缺一条这条闸就只剩"看起来差不多"：

- **根节点在视口内**是"适配过了"的硬证据。上一轮那个 bug（落地停在上一次的平移位置）
  的现场形态就是根节点贴左上角 (200,192)，修复后回到视口中心 (417,474)。
- **可见比例 ≥ 物理上限**：上限 = `视口高 / 该图矩形并集的纵向跨度`，与"可见"用同一把尺子
  （节点矩形与视口矩形有没有交集，不是"中心点在不在里面"）。两把尺子量同一件事，红的时候
  说不清是产品坏了还是闸太严——第一版就是拿中心点算上限，实测把"适配对了"的图判成了红
  （0.633 对 0.731），换同一把尺子后是 0.733 对 0.706。
- **界面自述的离屏数一致**（±1）：产品可以决定停在看不全的档，但它在画布上写
  「还有 8 个节点在视野外」时，这 8 必须是几何上的 8。

容差 `0.05` 只吸收"节点分布不均匀"的量化误差，不给"没适配"留余地：上一轮实测没适配是
0.563 对 0.66，差得远不止 5%。

### ② 引文逐字

引用抽屉（`SourceContextDrawer`）里 `[data-test="ref-quote"]` 的那句引文，必须**逐字包含**
`[data-test="ref-context"] mark` 里被高亮的原文，且高亮不少于 8 个汉字（低于 8 的"包含"是
平凡真——"的"永远被包含）。

上一轮验收实测命中在第 30–57 字，这条本来就已经过了；闸把它钉住，免得哪天定位逻辑被改成
"高亮整段"或"高亮第一个字"。

### ③ 刷新重开一致 + 连跑两次

先双击一个**看得见**的节点改一句话（唯一串，`验收改动-<时刻>`），走 ☰ →「保存」（不是
`Ctrl+S`：上一轮实测两次一次静默无反应，不能拿来当判据），然后：

- 界面上的「N 个节点」== 后端 `GET /api/mindmaps` 里刚保存那张树的节点数（两个口径）；
- 刷新 → ☰ →「打开…」→ 打开那张图 → 界面上还是 N 个，**且那句改动还在**。

`--repeat=2`（默认）时同一份材料连跑两次，第二次不许出现"重试/失败"字样。这条是上一轮
特意要求加的："两次卡一次过"恰好是只跑一次永远看不出来的形状。

### ④ 最长静默上限：**40 秒**

数的是**生成落地之前**，界面上连续多少秒没有新东西可说。

关键在"新东西"的定义：`N 秒` 这类计时器先被抹平成 `<t> 秒` 再比。生成期前端有个每秒 +1
的秒表（`ChatDock.vue::elapsedSec`），不抹掉它，界面永远"每秒都有新字"，这条断言恒真。
上一轮那个坑的形态是"一直显示「正在解析…38 秒」，数字涨到 46，而用户一无所知"——秒表不是
信息，是那颗一直在转的圈。**只抹秒数**，别的数字（"40 / 136 个节点"、"20 条诊断"）一律
保留，它们变了就是真的有新东西。

40 这个数的依据三条，缺一条都站不住：

1. **后端自己承认的静默是 25 秒**：`backend/app/agent/service.py` 写着"线上实测（3 路并发，
   GLM-5.3-Flash）最长静默 25 秒"，心跳取 10 秒。心跳只驱动状态行那句"已等 N 秒"，不带业务
   信息，所以它不打断静默。上限必须 ≥ 25。
2. **整期生成实测 39.5–50.1 秒**：40 秒静默比"整轮生成最短耗时"还长。真出现这种形态，
   不可能是"生成得慢"，只能是"这一轮什么也没说"。
3. **不取 30**：25 是 3 路并发下的最大值，手上没有分布，30 = 最大值 + 5 秒边距，下次模型
   慢一点就红；**不取 45**：上传卡住那次实测是 46 秒仍无出口，45 等于"症状出现 45 秒后才
   判死"，那时用户早关页面了。

本机两次实测读数：最长静默 2.0 秒与 8.1 秒（分别 32.2 / 26.5 秒落地）。8 秒那一档是
单次模型调用，与后端那句"单轮首字延迟平时 5–10 秒"对得上。

**兜底判据**：若这个数误红，正确的动作是改产品（把真进度帧发出来，或把"已等 N 秒"换成带
信息量的阶段文案），**不是**把这个数抬高。抬高它等于把"界面 40 秒不说人话"合法化。

上传期也采样，但**只报读数不判红**：上传有自己的出口与时延上限（`uploadDocument` 带超时 +
失败态 + 重试），而 ④ 的判词限的是"落地前"那一段。

### ⑤ 手册按钮名可点到

两个方向都必须机械可核：

- **手册 → 清单**：`MANUAL_POINTS` 里 19 条，每条都必须在 `docs/USER-GUIDE.md` 里以
  `「name…」` 的形式逐字存在。手册改名而清单没跟 → 红。这条是防"清单被悄悄收窄到永远绿"。
- **清单 → 页面**：每条在对应时点的页面上**按名点到**（存在 + 此刻可见，不要求 enabled）。
  时点分五组：`idle`（首屏）/ `ready`（材料就绪）/ `running`（生成中）/ `landed`（落地后）/
  `drawer`·`side`·`ref`（三个抽屉）。

`MANUAL_SKIPPED` 里 10 条写明"为什么不收"，理由分三类：出现条件取决于数据形状（`上一处`、
`再读上文`、`修复`、`全部展开`）、取决于生成结果（`回到生成之前`）、手册里根本没写这个
名字（`新建`、`关闭`、`演示示例`、`另存为`）。**第三类是文档缺口，不是页面缺口**。

`inViewport` 只报读数不判红：手册承诺的是"点 ☰ →「导出…」"，用户能滚到。把"1440×900 首屏
放不下 26 条历史"判死，会立刻换来一张豁免——`ACCEPTANCE-WALKTHROUGH-2026-11-28.md` §6.4
已经把那条记为"列表变长的正常滚动，不做"。真读数里 `side` 那两条现在就是"需滚动"。

**它和 `frontend/tests/user-path-*.spec.ts`（jsdom 那份 50 条动作清单）什么关系？**

两份清单问的不是同一件事，都不该改成对方：

| | jsdom 那份 | 本闸 ⑤ |
|---|---|---|
| 判据 | 三个判据同时满足才算过 | 只有一条：按名点到 + 可见 |
| 数据源 | 手写的动作清单（用户视角的动作名） | `docs/USER-GUIDE.md` 的「…」逐字核对 |
| 环境 | jsdom，`v-show` 靠沿祖先查内联 `display` | 真浏览器，真实的 `getBoundingClientRect` |
| 跑位 | 每次 `npm test`，与其余 spec 一起 | 手动，不进 push 门 |
| 答的问题 | "这个动作还在不在、点了发什么请求" | "手册说的那句话，页面上还找得到吗" |

所以**不补强那份，也不合并**。理由三条：① jsdom 里没有布局，`toBeVisible` 只查
`display/visibility`，管不了"被别的浮层盖住"和"滚出视口"；② 让每天跑的 vitest 去读
`docs/USER-GUIDE.md` 的正文，等于把一份 46KB 的文档变成单元测试的输入，改一句话就能让
CI 红；③ 那份清单的价值在"50 个动作各有断言"，本闸的价值在"19 个名字逐字对上手册"，
两者互相替代都会掉一半。

## 跑位：手动触发，不进 push 门

**不进 CI，不是因为跑不起，是跑起来也不可信。**

同一份 649 字材料五次生成给出 50 / 52 / 59 / 71 / 82 个节点——任何"节点数 / 比例"的断言
都得带容差，而带容差的闸会在真回归上放行。三条路各自的代价：

- **nightly**：红了没人看。它跑在没人等的时刻，第一次红没人管，第二次就没人看。
- **替身后端（录一次 SSE 回放）**：把"模型这次给的树"冻成字典，于是恰好测不到"这次给的树
  长什么样"——而 ① 的那个 bug 正是"树的形状变了、视口没跟上"。
- **本闸的取舍**：真后端真模型、手动触发、一次只回答一个问题。代价是它拦不住回归，只拦得住
  发布；补偿是判据窄到"人手点一遍十分钟能复核"。

## 什么时候跑它

必跑：

- 发布前（`deploy/` 那套镜像要推之前）。
- 动过 `src/canvas/**`（视口、缩放、布局）、`src/stores/sources.ts`、`src/stores/mindmap.ts`
  的落地路径、`SourceContextDrawer.vue`、`HistoryDrawer.vue` 之后。
- 改过 `docs/USER-GUIDE.md` 里任何一个「…」（⑤ 的手册那一半会当场红）。
- 版上出现"图看不见 / 按钮点不动 / 一直转"这类用户报障，先用它复现，再动代码。

不必跑：

- 纯后端重构、纯类型改动、注释与文档（除了手册正文）。
- 每次 push。它不进 `.github/workflows/ci.yml`。

## 怎么跑

```bash
# 依赖：前端与后端都要在跑（脚本会先查 /api/health 与 5173，缺哪个就报缺哪个）
cd backend && python -m uvicorn app.main:app --port 8000
cd frontend && npm run dev

# 两轮（默认）—— 一次约 3 分钟，其中两轮生成各 25–50 秒
cd frontend && npm run test:journey

# 快跑一轮、换材料、留浏览器看最后那一屏
node docs/acceptance-scripts/journey.spec.mjs --repeat=1
node docs/acceptance-scripts/journey.spec.mjs --sample=S01 --keep
```

退出码三种，对应的下一步完全不同：

| 码 | 含义 | 下一步 |
|---|---|---|
| 0 | 全绿 | 可以发 |
| 1 | 断言红 | 看那一条的读数，**先判"是产品坏了还是判据错了"**（下面 §判据与产品的边界） |
| 2 | 环境不满足（服务没起 / 依赖没装 / 浏览器找不到） | 按它打印的那一条命令补，别当成产品红 |

截图与 `summary.json`（含每一条的读数、界面最后几帧、页面异常）落在系统临时目录
`%TEMP%/journey-shots-<时刻>/`，**不进仓库**：它是这一次的现场，不是留档。

## 依赖放哪儿：`playwright-core` 在 devDependencies，浏览器不在

这是本轮判的一个转折。前两轮它装在项目外的隔离目录、跑完删掉——因为那是**一次性验收**。
本闸要**长期存在**，依赖就不能再靠"人记得重建一个隔离目录、装当时的最新版"：

| | 隔离目录（前两轮） | devDependencies（现在） |
|---|---|---|
| 版本 | 跑的时候最新 | `package-lock.json` 钉住 |
| 谁来装 | 人记得 | `npm ci` |
| CI 成本 | 0 | 实测 `npm ci` 多 1 个包、约 13.3 MB 解压、**1.8 秒**，无 postinstall、无原生编译 |
| 会不会被 CI 跑到 | 不会 | 不会（`ci.yml` 一个步骤都没加，`npm test` 也不收它——vitest 的 root 是 `frontend/`，`docs/` 在它外面；本轮实测收集结果里没有这个文件） |

**浏览器不进 devDependencies**，这是选 `playwright-core` 而不是 `playwright` 的全部理由：
前者不带浏览器（13 MB），后者 `npm ci` 会去拉 ~130 MB 的 Chromium。浏览器由
`npx playwright install chromium` 装到用户目录（只装一次），或由系统 Chrome 提供；脚本按
`JOURNEY_CHROME` → `ms-playwright` 缓存 → 系统 Chrome 的顺序找，找不到就报命令并退出 2。

**"装了但没人跑"会不会腐烂？** 会，所以 `package.json` 里有 `test:journey`，脚本里有
`import`，本文写着它——三处任一处被删，下一个人会在 `npm ci` 之后第一次跑时立刻发现
（脚本自己报"找不到 playwright-core，执行 cd frontend && npm install"）。

（它没有进 `docs/OPTIONAL-DEPS.md`：那份表登记的是"`backend/scripts/` 下哪个探针缺什么
Python 包才跑不起来"，而这一条是**声明在仓库里**的 devDependency，不是可选依赖。）

## 判据与产品的边界：红的时候先判哪一边

这道闸的红分两种，处理方式相反：

- **判据错了**（比如口径不一致、时点不对）。本轮的实例有三个，都已修：视口上限拿中心点算
  （换成矩形同一把尺子）、「管理材料」在 0 份材料时根本不叫这个名字（移到 `ready` 组）、
  「看上下文」点完自己变成「收起上下文」（加 `also` 变体）。**判据错就改判据，别改产品**。
- **产品错了**。那就是闸抓到了东西——**报出来，别顺手改**。本轮没有抓到新的产品问题，
  两条读数值得记下来：
  1. `docs/USER-GUIDE.md` 全文 0 命中「新建」，而 ☰ 抽屉里那个按钮就叫「新建」。手册第 7.4
     节说"用 ☰ →「新建」再粘一次"这句话只写在 `ACCEPTANCE-WALKTHROUGH-2026-11-28.md`，
     没进手册。
  2. `docs/USER-GUIDE.md` 承诺的「管理材料」只在"材料 ≥ 1 份"时才是那个名字；0 份时它叫
     别的东西（`materialEntryLabel` 的另一支）。手册第 2 步描述的正是"加了材料之后"，所以
     不算错，但第一次用的人可能先看到另一个名字。

**红线一条**：不许为了让它绿而加 `if`。它红了就把两种可能都摆出来（读数在 `summary.json`
里），加一个例外等于给下一道闸立一个坏例子。
