## 结论（先看这段）

| 方案 | 调用数（6 支） | 墙钟 | 跨支重复 | 该不该做 |
|---|---|---|---|---|
| 现状：一次写完 | **3–5** | 中位 38.4 s | 14% 的图有（38 处 / 79 张） | 是（已是现状） |
| 用户方案：每支一个子代理 | **13–19** | 32–36 s（**更快**） | **31% 的图有**（分片时代实测） | 不采用 |
| 一次写完 + 自检 + 确定性修 | **4–6** | 38.4 s + 3–5 s | **0%**（实测两次都清零） | **该做，而且是唯一该加的一件** |

一条重要的读法（2026-11-26 晚补，接线之后复核）：**表里那个 0% 是"把清单用代码
落地之后"的数，不是产品行为**。产品里自检回路按设计只出清单、不落地（88% 精度 +
合并不可逆），所以交付物上的跨支重复停在 11/65 张图、38 处。理由与全部实测见
`docs/GENERATE-REPAIR-SELFCHECK.md` 第三节。

三条要点：

- **用户方案在墙钟上不慢，甚至更快**（分片 32.3 s vs 一次写 38.4 s 中位）。它的代价
  不在时间，在**计费调用数 3–4 倍**、**跨支重复率 2.8 倍**（31% vs 11%），以及每次
  展开只看得到自己那条标题链。
- **跨支重复是这条方案唯一不可修的结构性缺陷**，因为它的根因是"各支互相看不见"。
  `SECTION_SLICE` 能防是因为机制不同：**每支只给它那一章的原文**，兄弟支的材料
  根本不在它的 prompt 里——那不是"派子代理"，是"切材料"。
- **"检查 + 修"值得单独做，且不必改架构**：实测 +1 次调用（3.0–4.7 s、1.0–1.2 k token
  输入）就能把跨支重复从 6 处清到 0、从 4 处清到 0，逐字重复召回 100%。而更便宜的那
  一半（`repair()`）**一次调用都不花**，现在却没接在生成收尾上。

> **数据快照**：下面所有 `runs` 表数字取自 2026-11-26 的一次只读导出（`backend/scripts/probe_history_health.py`）：
> 88 条有产物的运行，可量树图 **79 张**（含材料 41 张）。库里同时在跑别的实测，
> 重跑会小幅漂移——变的是分母，不是方向。

## 一、调用数算术：三种架构 × 五种输入

### 现状（`_generate`，代码逐段读出）

| 步骤 | 调用 | 备注 |
|---|---|---|
| ① 骨架 `_plan_ask` | 1 | 两段式（图谱骨架）时 0 |
| ② 按支检索 | **0** | 本地 + 向量，不占模型额度 |
| ②b 分支 query 扩展 `plan_branches` | **1** | 只在"有材料且没走全塞"时；走 `chat_async`，**不计入 `RunContext` 预算账本** |
| ③ 结构 | 1 | 按章切时是 N（`SECTION_SLICE_CONCURRENCY=4`） |
| ④ 说明 `_fill_details` | 1–2 | 节点 ≥ `DETAIL_SPLIT_MIN`(12) 时切两半**并发** |
| ⑤ 默认关的三项 | 0 | 生成后核对 / 分支概括 / 输入提取各 1 |

| 场景 | 调用数 | 并发形状 |
|---|---|---|
| ① 纯主题 | **3–4** | 骨架 1 → 结构 1 → 说明 2 并发 |
| ② 带材料 ≤ 5 万字（`FULL_TEXT_MATERIAL_CHARS`，全塞） | **3–4** | 检索与扩展**整段跳过** |
| ③ 带材料 > 5 万字（按支检索） | **4–5** | 检索 N 支并行（第一支串行预热），扩展 1 次串行 |
| ④ 按章切 6 章（`MINDMAP_SECTION_SLICE=1`） | **9–10** | 结构 `gather` 6 个、信号量 4（≈2 批） |
| ④' 按章切 12 章（既有 A/B 实测） | **15** | 同上，实测 36.0 s |

### 用户方案

```
一级节点 1 次
每支一个子代理 N 次（并行，但仍是 N 次计费）
每支检查 N 次
修 ≤N 次
→ 1 + N + N + k·N
```

N 是一级分支数。**库里的实测分布：中位 4，全期中位 5，范围 1–12**（79 张树图）。

| N | 无错 | 修一次 | 历史同类实测（`_generate_deep`） |
|---|---|---|---|
| 4 | 1+4+4 = **9** | **13** | — |
| 6 | 1+6+6 = **13** | **19** | 12 章 → **15 次 / 36.0 s** |
| 12 | 1+12+12 = **25** | **37** | 15 次 / 36.2 s（12 章，含骨架与说明） |

### 一次写完 + 自检

| 组成 | 调用 |
|---|---|
| 现状（骨架 + 结构 + 说明） | 3–4 |
| 自检（模型读整棵树，报问题清单） | **+1** |
| 修（代码执行合并；或用户点确认） | **+0** |
| 修（若让模型重写不合格的那一支） | +1 / 支 |

**即 4–5 次，与现状同一量级；而用户方案是 13–19 次。**

### 三条必须一起看的补充

- **预算不是障碍**：`RunBudget.max_model_calls` 默认 100（33×3 上取整），13–19 次撞不到。
  用户方案被否的理由从来不是预算。
- **token 上的账是反的**：一次写完的结构与说明各带整份正文（10 万字 ≈ 6.7 万 token，
  3 次带正文的请求 ≈ 20 万 token 输入）；用户方案每支只有 top_k=3 父块（≈6–8 k token × N，
  6 支约 4.8 万）。**用户方案的输入 token 少一个数量级**——这是它唯一的成本优势，
  在"材料很长、支很多"的场景下真实存在。
- **墙钟**：`runs` 表实测（`created_at → updated_at`，done 95 次；其中 11-18 之前 16 次、
  之后 79 次）：一次写完中位 **38.4 s**，分片时代中位 **32.3 s**。12 章的 A/B 更悬殊：
  full 61.3 / 56.2 s vs slice 36.0 / 36.2 s。**分片更快**，因为每次输出量小。

## 二、三条旧理由逐条复核

### ①「真实用法 100% 是无材料」→ **半失效，而且失效的名字叫错了**

`runs` 表 79 张树图的实测（`scripts/probe_history_health.py`）：

| 日期 | 有材料 | 无材料 |
|---|---|---|
| 11-16 | 3 | 2 |
| 11-17 | 7 | 1 |
| 11-18 | 1 | **18** |
| 11-19 | 0 | 4 |
| 11-20 | 0 | **7** |
| 11-21 | 4 | 3 |
| 11-22 | **14** | 0 |
| 11-23 | 2 | 0 |
| 11-25 | 6 | 0 |
| 11-26 | 4 | 3 |

- 那句"16 次全是 0 份"是 **11-16/17 的早期状态**，当时确实如此。
- 全期：有材料 **41** 次 / 无材料 **38** 次。**11-22 起：有材料 26 / 无材料 3。**
- **但"有材料"要拆开看**：随请求上传的只有 **11 次**，其余 **30 次是外部检索自动补进来的**
  （openalex / wikipedia / deepseek / crossref）。也就是说**用户并没有开始上传材料，
  是系统自己搜来了材料**，模型看到的 prompt 变重了。

所以这条理由的正确说法是：**"用户不带材料"仍然成立（41 次里只有 11 次带），
"prompt 里没有材料"已经不成立。** 结论不变（那一轮要解决的问题没变），
但"带材料多了所以分片划算了"这句话，用数据说不通——真正变多的是**系统检索来的材料**。

### ②「分片的覆盖率优势需要材料才成立」→ **仍然成立，而且现在更成立**

当时的依据是"分片覆盖 30.5% vs 整树 5.1%"，前提是有材料。现在材料确实多了
（11-22 起 26/29 的近期运行有材料），所以**这一条现在是分片那一边的论据，不是反对它的**。

但这条路已经**换过实现**：`_generate` 现在也按支检索（`_retrieve_branches`），
带材料时两边证据同源，差别只剩"单次输出量"。`docs/SECTION-SLICE.md` 的 A/B 说了
真正的差别在哪：

| 指标 | full#1 | slice#1 | full#2 | slice#2 |
|---|---|---|---|---|
| 有引用的章数 | 6/12 | **12/12** | 7/12 | **12/12** |
| 被裁节点 | 105 | **0** | 50 | **0** |
| 跨支重复 | 0 | 0 | 0 | 0 |
| 模型调用 | 4 | 15 | 4 | 15 |
| 总耗时 | 61.3 s | **36.0 s** | 56.2 s | **36.2 s** |

那两轮 full 有 5–6 章整章 0 引用，根因是"一次给了 185 / 130 个节点撞上
`INITIAL_MAX_NODES=80`，`_clip_tree` 按前序砍掉尾巴"。**而现在不折也不裁了**
（`docs/FOLD-RETIRED.md`），这个失效形态已经消失——所以 slice 那份优势里，
"不被裁掉尾巴"这一条现在归零。**② 在今天的代码上，只剩"每章都被写到"这半条。**

### ③「跨支重复」→ **仍然成立，是最硬的一条，而且现在有更大样本的实测**

见下一节。一句话：**分片时代 31% 的图有跨支重复，一次写完时代 11%。**

## 三、跨支重复的实测

### 3.1 两代产物的天然对照（零成本）

提交史给出了干净的分界：`170aaaa`（2026-11-16）删掉整树生成、只留分片；
2026-11-18 把 `_generate` 加回来。于是 `runs` 表自带一组 A/B——同一台机器、同一个
模型、同一批主题，只是生成架构换了。判据与生成收尾用的是同一个函数
（`_cross_branch_duplicates`：label 归一化后逐字相同、且不在同一条祖先链上）。

| 指标 | 分片（每支一个子代理，13 张） | 一次写完（66 张） |
|---|---|---|
| **有跨支重复的图** | **4 张（31%）** | **7 张（11%）** |
| 重复节点总数 | 17 | 21 |
| 每张图的重复节点 | **1.31** | **0.32** |
| 节点数中位 | 57 | 48 |
| 一级分支中位 | 5 | 4 |
| detail 中位 | 65.7 字 | 114.4 字 |
| 引用中位 | 7 条 | 0 条 |
| `SINGLE_CHILD` 命中 | 2 | **114** |

四件事值得单独说：

1. **跨支重复率 2.8 倍**。这条样本不大（13 张），但方向与 `docs/ONE-CALL.md` 记的
   "库里三张分片图各有 6 个跨支重复节点"一致，也与 `_generate` docstring 里那句
   「无监督学习：无标注找结构」在两条分支下一字不差出现两次一致。
2. **`detail` 差 74%（65.7 → 114.4 字）**，这是"一次写完 + 只写说明那一段"带来的，
   与架构选择无关，但它是现状不可退的收益。
3. **引用中位 7 → 0 是混杂项，不能当结论**：分片那 13 张恰好都在"有材料"的批次里，
   而一次写完的 66 张里有 38 张是纯主题（纯主题按设计零引用）。
   只看带材料的 41 张：引用中位 **33 条**，零引用只有 **4 张**。
4. **`SINGLE_CHILD` 114 vs 2 是反向的**：一次写完的图里，37/79 张存在
   "一个节点只有一个孩子"的冗余层——那是模型一口气写完整棵树时的典型形状。
   分片因为每次只展开一层，没有这个形状。**这是用户方案唯一的真实优势，
   而这恰恰是零成本可修的**（见第五节）。

### 3.2 用户方案下到底有多少

不跑新实验也能回答，因为 `_generate_deep` 就是它的实现，历史产物就是它的输出：
**13 张里 4 张有重复、共 17 处**。加上库里那三张 56 节点的分片图（各 6 处）：
`Python库与框架`、`半监督与强化学习`、`无监督学习：无标注找结构`。

### 3.3 `SECTION_SLICE` 为什么能防，而"每支一个子代理"不能

这是机制差异，不是提示词差异：

```
SECTION_SLICE：每支的 prompt 里**只有它自己那一章的原文**。
              兄弟支的材料根本不在上下文里 → 机制上写不出重复。
              实测四轮（full#1/slice#1/full#2/slice#2）都是 0 处。
每支一个子代理：每支的 prompt 里是**自己的标题链 + 自己的检索命中**，
              而检索是全局的（top_k=3 从整份材料里捞）。
              兄弟支写过什么，它不知道 → 重复照旧发生。
              跨支重复的根因正是这个：`PLAN_PROMPT` 里"彼此覆盖的范围不重叠"
              模型并不听（实测）。
```

所以"派子代理"与"防重复"没有因果关系。**要防重复，要么让各支看见彼此
（一次写完），要么让各支的材料不相交（按章切）。** 用户方案两条都不满足。

除非加一条补丁：**各支共享"已生成的一级清单 + 关键词黑名单"**。但那样做仍然只在
"标签层面"过滤——同义不同词（「偏差-方差分解」vs「偏差-方差分解量化泛化误差」）照样漏，
而第四节的实测正好证明了这类漏检有多少。

## 四、自检回路的实测：+1 次调用买到什么

### 4.1 怎么测的

`scripts/measure_selfcheck.py`。取两张**真实历史产物**（零成本基线），各发**一次**审查
调用：只给"一级分支 + 缩进节点 + id"（**不给 detail**，所以输入很小），要求它按五类
报问题（跨支重复 / 同父重复 / 冗余空链 / 标题与内容不符 / 与分支无关），只回 JSON。
然后：

- 代码逐条复核它报的每一句（能证伪的判 strict/near，证不了的记 `unjudged` 而不是判错）；
- 把能确认的重复用代码合并落地（**不再花调用**）；
- 同时跑一遍 `optimization.repair()`（零调用）做对照。

### 4.2 结果

| | 分片产物 `410ba3d0` | 一次写完产物 `3d71b0ab` |
|---|---|---|
| 节点 / 一级分支 | 57 / 5 | 80 / 5 |
| 基线跨支重复 | **6 处（3 个说法）** | **4 处（2 个说法）** |
| `repair()` 零调用修掉 | 0 条 | **1 条**（`SINGLE_CHILD`） |
| 审查耗时 / 输入 | **4.7 s / 1,224 token** | **3.0 s / 1,042 token** |
| 报出条数 | 15 | 10 |
| 代码可确认（strict+near+跨子树） | **7** | **4** |
| 语义待人工（`unjudged`） | 5（核对 5/5 成立） | 3（核对 2/3，1 条为边界） |
| 需人判（`unverified`：标题/内容不符、与分支无关） | 1 | 2 |
| 误报 | 2（`chain` 说"只有一个孩子"，实际有 3 个） | 1（同左） |
| **逐字跨支重复召回** | **3/3 = 100%** | **2/2 = 100%** |
| **修后跨支重复** | **6 → 0 处** | **4 → 0 处** |
| 修后节点数 | 57 → 51 | 80 → 77 |

一次调用的钱买了四样东西：

1. **把逐字跨支重复清零**（6→0、4→0），而且召回 100%；
2. **抓到逐字判据看不见的语义重复**：8 条 `unjudged` 里人工核对 **7 条成立**
   （「监督学习：依赖标注信号」vs「监督学习：从标注数据学映射」、
   「线性模型与核方法」vs「线性与核方法家族」、
   「开源机器学习软件套件」vs「Python 库与框架」），1 条是边界
   （把「误差降低 15% 以上」这种量化结果与「融合型深度学习表现最优」判成重复）。
   —— 现在的 `_cross_branch_duplicates` 对这类**完全瞎**（它只比逐字相等），
   `NEAR_DUPLICATE_LABEL` 只比同级，而这类是**跨支的同义**，落在两条规则的缝里。
3. **抓到"内容与主题无关"**：一张电力负荷预测的图里发现
   「营改增下的纳税管理」（属财税政策）——`check()` 的七种码里没有对应的一种，
   这类现在完全不报。
4. **精度足够落到人手上**：25 条报告里 22 条站得住（88%），误报全部集中在 `chain`
   这一类（它把"父有多个孩子但被点的那条同义"说成了"只有一个孩子"）——
   而**误报的代价是零，因为这些动作都不自动删**。

### 4.3 一条重要的边界

上表"修后 0 处"里，合并的只有代码能确认的那 9 个节点（strict/near）。
**8 条 `unjudged` 一条都没有自动落地**——它们是"看起来是同一件事"，而合并是不可逆的
（`docs/FOLD-RETIRED.md` 的教训：替用户做决定，代价是内容消失）。
这不是实现上的偷懒，是这次验证里最该保留的一条设计约束：
**模型只负责"指出并说清"，落地要过人的眼。**

## 五、结论：三件事的排序

| 序 | 动作 | 调用增量 | 买到的 | 现状 |
|---|---|---|---|---|
| **第 0 件** | 生成收尾接上 `optimization.repair()` | **0** | 79 张图里 37 张的 `SINGLE_CHILD` 冗余层（命中 116 次）、同级同名 | **代码已有，生成链路没接**（收尾只跑 `check()`，只报不修） |
| **第 1 件** | 自检回路：1 次审查调用 + 清单给人/给代码 | **+1** | 跨支重复清零（召回 100%）、语义重复 8 条、内容跑题 2 条 | **没有**（`verify_after_generate` 是"逐节点判 supported/unverified/contradicted"，不找结构问题，且默认关） |
| 第 2 件 | 每支一个子代理（`_generate_deep` 挂回 `create`） | **+9～+33** | 单次输出量解耦（200+ 节点时才需要） | 代码在，`_ALLOWED_BY_INTENT` 里没有 |

**如果只能加一件，加第 1 件**（自检回路），理由：

- 它买到的是**现状唯一给自己定义的缺陷**（`CROSS_BRANCH_DUPLICATE` 诊断存在、
  14% 的图命中、且明确写着"只报不删"）；
- 代价是 **+1 次调用 / 3–5 秒 / 1.2 k token**，比现状的抖动还小；
- 它**不改架构**：输入是已经交付的那棵树，输出是一份清单，与生成路径正交——
  今天能上，明天换架构也不用重写。

**如果要两件，先加第 0 件再加第 1 件**：`repair()` 是零成本确定性修复，
`tests/test_optimization_repair.py` 已经钉住它的幂等与可撤销，唯一缺的是"
生成收尾没调用它"这一行接线。

**第 2 件不该做**，除非触发条件是"一次响应装不下"（`INITIAL_MAX_NODES=80` 撞线）。
实测中位 48–57 个节点、最大 114，还没撞到"装不下"。而它现在被否的三条理由里，
① 半失效、② 归零、③ 反而更硬——**一条都没能翻案**。

**2026-11-26 晚：第 0、1 件已接线**（`MINDMAP_AUTO_REPAIR` 默认开、
`MINDMAP_SELF_CHECK` 默认关）。上表"现状"那两列因此过期；接线之后的实测、判断与
**对本文件那个 0% 的修正**见 `docs/GENERATE-REPAIR-SELFCHECK.md`。同一晚还量了
另一个 agent 留下的第 2 件建议（改图该查时查不查），结论是**不加兜底**：
`docs/EDIT-NO-RETRIEVAL.md`。

## 六、自评：他要的到底是什么

> 你的判断是"质量与可控性"（能看到每一支什么时候完成、错了好定位），
> "并行"是副作用。给判断：这个读法对不对，如果是，结论该怎么写。

**一半对，一半是我想拦一下的。**

对的那一半：**"错了好定位"是真的**。实测支持它——一次写完这条路上，
一个跨支重复只表现为一条 `CROSS_BRANCH_DUPLICATE` 诊断（还有 86% 的图根本没有），
用户拿到的是一棵成品树，"哪个节点是谁写的、有没有依据、有没有重复"三件事在界面上
一个都看不见。他能做的只有"整棵树重生成"。**这个痛是真的，而且现在的架构确实没解。**

要拦的那一半：**"把 node_grow 上报做细，让他看到哪一支正在写"买不到可控性。**
这条路上模型是**先想完整棵树再吐**，73 帧 `node_grow` 是回放而不是进度——把帧做得再细，
他看到的是"一个正在长的树"，不是"第 3 支正在写、它写错了"。**要"看到哪一支正在写"，
前提就是"一次只写一支"，那就等于把用户方案整个搬回来了。** 所以这个读法我不采纳：
用它当"更便宜的替代"，会把一个架构问题伪装成上报粒度问题。

我给他的读法是这样的：

> 你要的不是"并行"，也不只是"进度可见"。你要的是**责任单位变小**：
> 现在一棵树是一个整体，出错只能整体重来；你想让"哪一支错了"成为一个可指认、
> 可单独处理的东西。
>
> 这个诉求对。但"每支一个子代理"是实现它的最贵方式（+9～+33 次调用、跨支重复率
> 2.8 倍、每次展开看不见兄弟支）。有一条便宜 10 倍的路能达到同样的可指认性：
> **一次写完，然后让模型回头过一遍，报一份"哪个节点、哪件事、和谁重复/跑题/无依据"
> 的清单**——1 次调用、3–5 秒，实测两张真实图把跨支重复清到 0，还顺手抓到 8 条
> 逐字判据看不见的语义重复和 2 条内容跑题。
>
> 差别在于"可指认"落在哪一层：子代理方案把可指认性放在**生成时**（每支一个执行单元），
> 自检方案把它放在**交付前**（每个节点一条结论）。后者不需要动架构，也不改变
> "各支互相看得见"这个已经是现状收益的性质。

一句话收口：**他直觉里的"分而治之"是对的，但分错了对象——该分的是"检查"，
不是"生成"。** 生成分片会失去全局视野（跨支重复 31%），检查分项不会（它本来就
是在全局视野下做的）。
