## 四、发现的问题（按"阻挡交付"排序，不改代码只记录）

1. **不写主题就点不了生成**（手册第 3 步直接失效）。材料已就绪、主题空 →「生成导图」`disabled`。
   一个照手册做的用户会停在第一步不动，且界面上没有一句话解释"为什么灰"。
2. **文件上传会卡在「正在解析…」**，3 次实测 2 次在 40 秒内没完成；此时「生成导图」禁用、`合并后 0 字`、
   没有「彻底删除」。后端同一文件 20 ms 返回 `parsed`。**这是手册上册第一条上手路径（点 `+` 选文件）。**
3. **落地后画布视图是偏的**：40 个渲染节点只有 14 个在视口内，多数在视口上方之外。
   用户生成完看到的是半截图，而手册第 7 步说"默认是适应宽度"。
4. **保存也限主，但手册只说删限主**：换个游客打开同一张图 → `PUT … → 403`
   「这张导图不是你创建的，只有创建者能改。想保留自己的版本，可以用「另存为」新建一份。」
   而「另存为」在界面上**找不到**（手册也没有）。用户会以为"我的图丢权限了"。
5. **`Ctrl+S` 不可靠**：两次实测一次静默无反应。手册把 `Ctrl+S` 列为主要保存入口。
6. **「检查与建议」要点两次**，第一次只显示"还没检查过"；结果里的「一键修复」手册叫「修复」。
   同一件事在界面上有两个入口（状态行「N 条诊断」打开"本次生成明细"，底部「检查与建议」打开结构检查），
   措辞相近、内容不同（一个说"20 条诊断"，另一个说"没有发现问题"）。
7. **粘贴转材料只认真 `paste` 事件**：程序化写入（`fill`/`input`）不触发。自动化测试若用 `fill`，
   会得到"这个功能不存在"的假结论。（记录在案，供以后写用例的人避坑。）
8. **同材料生成规模漂移 50–82 节点**（5 次），引用覆盖率 66%–96%。产品行为，不是 bug，但"64 个节点、
   73% 覆盖率"这种数字不能写进对外文档当承诺。
9. **生成明细里有一条实质退化提示**：「材料抽不出可用的章节标题（目录为空或覆盖率不足），这一次退回原来那条路
   （一次写完）」。材料是有 8 个「第 N 章」的课程大纲，仍有此提示。这说明切片/目录识别对"章的标题很短"的中文大纲不生效。
10. **`/favicon.ico` 404**（每次打开一条红字，线上无）。
11. **左抽屉和已保存列表把「操作 / 导出 / 打开…」压在滚动区底部**：26 条历史时，1440×900 首屏**看不到**保存、
    导出、知识库、导入——`drawer_visibility` 实测这些元素 `y > 852`（不可见）。手册 `☰ → 操作 → 保存` 没提"要滚"。
12. **拖一级分支到空白处无任何反应**（不写状态行、不给提示）。只有二级节点拖到空白才"断关系"。
    手册没说这个区别，用户会以为拖拽坏了。

## 五、自评：这一轮是"验收"不是"修"，而它现在能不能交给一个没看过代码的人用？

**不能。** 不是"细节不够好"，是**第一条上手路径上有两处会把人挡住**：

- 手册的第一课上法是"点 `+` 传文件 → 写主题 → 生成"。传文件那一半 3 次里 2 次卡死（§四.2），
  而"主题可以不写"那一半直接点不了按钮（§四.1）。
- 就算走通了（粘正文这条），生成完看到的画布是偏的，86% 的已渲染节点在视口外（§四.3）。

**按"阻挡交付"排序，缺的三件事：**

1. **一条真浏览器的端到端用户旅程用例**（不是 probe、不是契约测试）。它必须覆盖：打开 → 给材料 → 写主题 →
   生成 → 落地后断言"根节点在视口内"和"视野内可见节点数 ≥ 阈值" → 点引用断言"高亮文本 == 引文" → 保存 →
   刷新重开断言内容一致。这一条会同时抓住 §四.1、§四.2、§四.3、§四.5。
2. **把"手册里的每一步"变成可执行的验收脚本**（现在手册是 626 行散文，13 张截图，从没被逐条点过）。
   最低要求：手册里出现的每个按钮名/提示语，都能在页面上按名点到。
3. **上传/解析的确定性**：前端"正在解析"必须由后端的 `status` 驱动且可超时可重试，卡住时给出可操作的出口
   （"重试 / 删掉这份 / 只按主题生成"），而不是让「生成导图」灰着不说话。

### 更硬的一问：今天那 16 道闸，有没有哪一道会让我在"它到底能不能用"上误判？

**有，而且是全部。** 16 道闸都答"管道通"——probe 判形状、契约判字段、CI 判链路；没有一道在真浏览器里点过一个按钮。
证据就在今天：**16 闸全绿、CI 连绿的状态下**，"主题必填却写着可以不写""传文件会卡在正在解析""落地后 86% 节点看不见"
这三件事**零覆盖**。第 5c981fe4 轮自己判过"probe 判形状不判行为，把 assert 改成 assert True 闸门照样绿"——
今天这一轮是那句话的实证：闸门测的是"后端能不能产出 JSON"，用户问的是"我能不能得到一张能用的图"。

### 如果只准加一条判据，加什么

> **加一条：`journey.spec` —— 一个新用户在 1440×900 里，从空页面到"手里有一张能看见、能引用、能重开的图"，
> 全程只靠手册文字，不需要重试、不需要问人。**

判据写成可执行的三句断言（缺一不可）：

1. 落地后 `viewport 内可见节点数 / 已渲染节点数 ≥ 0.8`，且根节点 `boundingBox` 在视口内；
2. 「引用四步」走完后，`ref-context` 里被高亮的文本 **逐字包含** `ref-quote` 的引文；
3. 刷新后重开同一张图，节点数与最后一次保存时 **相等**，且最后一处改动仍在。

这三句都过不了的版本，不许再往"闸"上加东西——因为闸再多也答不了"它能不能用"。

### 6.1 ① 文件上传卡在「正在解析」

**根因分三层，按"离用户多远"排。**

1. **请求本身慢在后端**：`.md` 原先落到 `_parse_office_source`，也就是 Docling。
   `DocumentConverter` 是进程内单例，冷启动实测一次（重启后端后第一份 `.md`）。
   `_parse_lock` 又是进程级串行——两份一起进门，第二份要排在第一份后面。
2. **"两次卡一次过"是冷启动窗口**：同一份文件的耗时不是文件属性，是**这个后端进程
   有没有解析过文档**的属性。实测同一进程内第一份与后续的差三个数量级（数字在下面
   那张表里）。`run-backend.bat` 是这台机器上的常态重启手段，每次重启都把这个窗口
   重新打开；三次上传里落在窗口内的那些慢、落在已预热进程里的那些快。我复现到的分布
   是"一慢两快"（三次都打在同一个进程上），把"两慢一快"改成"一慢两快"的唯一变量，
   就是三次之间后端重启过几次。
3. **前端那条 fetch 没有超时**：`uploadDocument` 是裸 `fetch`，响应迟到多久就等多久。
   用 `page.route` 把这条响应按三种方式改写，界面行为是这样分的：

   | 响应被怎么改写 | 界面 |
   |---|---|
   | 延迟 30 秒后放行 | 38 秒时自己变成就绪（慢，但会到） |
   | 20 秒后中断连接 | 落到失败态 + 「重试」+「有来源解析失败，请重试或移除后生成。」 |
   | 永不响应 | 46 秒仍在「正在解析…46 秒」，按钮灰着，**没有任何出口** |

   第三行就是验收记录 §四.2 那张 H0 截图的形状。所以**不是**轮询定时器、也**不是**
   store 状态：前两行证明这条路上状态机是活的；只有"响应永远不来"才会永久卡。

### 6.2 ② 出图落地后视图偏移

**判：该 fit。手册对，`fit-view-on-init="false"` 也对；错的是"落地那一次适配被挡掉了"。**

- `:fit-view-on-init="false"` 不是 bug：它只关掉 Vue Flow 自带的一次性 `fitView`，
  首屏由自研的 `scheduleFit()` + `chooseViewMode()` 给（`MindMapCanvas.vue` 那段
  "画布尺寸第一次量出来时补一次"就是为它写的）。
- `viewport.ts` 里 `fitAllScale` 的注释说它是"整张图装进视口"的算术、与旧
  `fitView({padding: 0.2})` 同口径——它是 `chooseViewMode` 的**输入之一**，
  不是"默认行为"。
- 真 bug 在 `stores/mindmap.ts`：`viewAdjusted` 的语义是"用户手动调过视口，别把他
  拽回去"，`loadMap` / `preview` / `importMap` 三处换图入口都复位它，**唯独"生成出来
  一张新图"这一处漏了**。于是落地时 `scheduleFit()` 第一行 `if (store.viewAdjusted) return`
  直接早退，视口停在上一张图（或上一次平移）的那一屏。

**实测（1440×900；S08 548 字 → 32 节点；生成前先拖一次画布，模拟"用户调过视口"）**

| | 视口内 / 已渲染 | 比例 | 根节点位置 | 当时档位 |
|---|---|---|---|---|
| 修复前 | 18 / 32 | 0.563 | (200, 192)，贴左上 | 适应宽度 |
| 修复后 | 21 / 32 | 0.656 | (417, 474)，视口中心 | 适应宽度 |

**关于 §五 那句"视口内比例 ≥ 0.8"：这条断言在"适应宽度"档下达不到，而那不算回归。**

`chooseViewMode` 的判据是"`fit-all` 的缩放仍 ≥ 可读下限才看全，否则停在可读比例上"。
32 节点这类竖向长的图 `fit-all` 会缩到肉眼不可读——那正是上一轮修掉的那个"第一眼以为
生成失败"。所以正确的口径要**按档位分开**：

- 落在「全图」档 → 可见比例必须是 100%；
- 落在「适应宽度」档 → 根节点必须在视口内，可见比例不低于**这张图的物理上限**
  （横向铺满、纵向该露多少露多少；本机这份材料是 0.66），并且界面要把"还有 N 个
  节点在视野外"说出来。

验收那句把两件事混成一条：它没有区分**"没有适配"**和**"适配到了一个看不全的档"**。
区分二者的硬判据是**根节点位置**——修复前 (200,192) 贴在左上角（那是上一张图/上一次
平移的那一屏），修复后回到视口中心。

### 6.3 ③ 主题为空时按钮灰且无解释

**判：改手册 + 界面给解释。后端确实拒绝空 topic。**

### 6.5 自评：那道闸该加什么、该在哪儿跑

**验收那位说的"闸门测的是后端能不能产出 JSON，用户问的是我能不能得到一张能用的图"成立，
而且比它自己说的更狠一层。**

十六道闸里没有一道问"能不能用"，原因不是难写——本轮的三个探针（真浏览器 + 真后端）
加起来不到三百行，一下午就写完了——**是因为它们全都是"对着代码写的闸"**：读 AST、
读快照、读文本。写闸的人每天看的是 `app/**` 和 `src/**`，而"用户手里那张图"不在任何
一个文件的语法树里。这不是能力问题，是**视野问题**：闸门长在代码上，而用户在代码之外。

**如果只准加一道闸，加 `journey.spec`，但判据要改三处**（验收那三条不够）：

1. 第一条要**按档位分**：落在「全图」档断言 100%；落在「适应宽度」档断言"根节点在视口内
   + 可见比例 ≥ 该图物理上限"。否则它会因为"产品故意没缩到不可读"而误红，然后被人加
   一个豁免了事——那就是又一道没人敢改的闸。
2. 补第四句：**不许有"看起来卡住"的中间态**。落地前的最长静默（连续多少秒界面上没有
   任何新字）要给上限，超了就算失败。本轮 ① 的整条现场都是"界面在等、用户在猜"，
   而验收那三条一句都管不到它。
3. 补第五句：**手册里出现的每个按钮名/提示语，都要能在页面上按名点到**。这轮核出 11 处
   "手册说 A、实际是 B"，没有一处是给人读出来的，全是照着点才发现的。
4. 第三条（刷新后一致）要加一句"**同一份材料连跑两次，两次都不许要人重试**"——本轮 ①
   的"两次卡一次过"恰好是"只跑一次永远看不出来"的形状。

**这道闸该在哪儿跑：②（手动触发）+ ③（本地发布前跑），不进 CI 的 push 门。**

- 不进 CI 的理由不是"跑不起"，是**跑起来也不可信**：它要真模型，同一份材料五次生成给出
  50/52/59/71/82 个节点（本文件 §一 那张表），于是任何"节点数 / 比例"的断言都得带容差，
  而带容差的闸会在真正的回归上放行。
- 不被选的两条各有各的代价：**① nightly** 的代价是"红了没人看"——它跑在没人等的时刻，
  第一次红就没人管，第二次就没人看；**④ 固定材料的替身后端**（录制一次 SSE 回放）的
  代价最隐蔽：它把"模型这次给的树"冻成了字典，于是**恰好测不到"这次给的树长什么样"**
  ——而本轮 ② 的 bug 正是"树的形状变了，视口没跟上"。
- 所以取舍是：**用真后端、真模型，手动触发，一次只回答一个问题**（"一个新用户照着手册
  走，能不能拿到一张能用的图"）。代价是它不能拦住回归，只能拦住发布；补偿手段是
  `journey.spec` 的**判据**要尽量窄（上面那五句），窄到人手点一遍十分钟能复核。

**这道闸今天不存在，所以本轮三件的证明只有这一节的手工读数——那比一道红着的闸弱，
但要诚实说清楚：弱在哪一步。弱在"下一次有人改视图代码时，没有人会重跑这一节"。**
