# 断关系 / 删除 / 新增节点：三个动作各自的判据

第二轮。第一轮（`docs/NODE-DRAG.md`）定的是"拖动 = 改结构、坐标只来自布局"；
这一轮在同一套地理上补三件事：**把节点从树上摘下来、删掉、加一个**。

第一轮的两条铁律这一轮一个字节都没破：

1. `Node.pos` 仍然没有写入口径 —— 坐标唯一来源是 `layoutDiagram`；
2. 手势只表达**结构关系**（谁是谁的父 / 谁是第几位），不表达位置。

三条新路径都走同一句话：**手势的位置必须被翻译成"挂到谁下面、排第几"，而不能被
保存成坐标。** 三个动作的差别只在"翻译什么"。

| 动作 | 手势 | 翻译成 | 进撤销栈 |
| --- | --- | --- | --- |
| 断关系 | 拖到**空白处**松手 | "从原父下面摘下来，挂到根的最后" | 是（`move` 事件） |
| 删除 | 工具栏「删」/ Delete | "这一整支都不在了" | 是（`remove` + `subtreeSize`） |
| 新增 | Tab / Enter / **双击空白** | "在某个节点下插一个空节点" | 是（`add` + `parentId`） |

## §一、拖到空白处：选"断成孤儿挂在根下"，不选"拒绝"，更不选"游离节点"

三档候选，逐档说清代价：

| 候选 | 能不能做到"断关系" | 代价 |
| --- | --- | --- |
| **a. 拒绝**（第一轮就是这样） | 做不到 | 最安全，但"断关系"这个词在这个产品里就没有落点 |
| **b. 挂到根下**（选中） | 能 | 一级分支 +1，整条右侧子树因此多一格 |
| c. 单独悬在画布上 | 能 | 需要"无父节点"这个概念，而 `content` 是**一棵树** |

**为什么 c 不是"大改"而是"换数据结构"**：`MindNode.children` 是一棵树，
`shape.ts` 的 `rootsOf` / `iterNodesIn` / `findParentIn` / `replaceContainer` 全部
建立在"每个节点恰好有一个父，除了根"之上。引入游离节点意味着：

- 要么加一个 `content.loose: MindNode[]`（第四套遍历，三种形状各写一遍校验）；
- 要么把树换成 DAG —— 那 `planDrop` 的环检测、`layoutTidy` 的层号、`validateDraft`
  的 8 层上限全部作废。

**判断：`content` 是一棵树这件事这一轮不动。** 于是"不再属于原来那一支"在这套数据
结构里**唯一**的合法落点就是根的孩子列表。选 b。

### 为什么不是"拒绝"（第一轮的选择）

第一轮拒的理由是"这里没有目标"—— 那句话在**只有拖动**的那一轮是对的。而现在
用户明确要"可断关系"，拒绝就等于把这个需求落到"没有入口"上。一个手势能表达意图、
却故意不执行，比执行错了更糟：用户会认为这个功能没做。

### b 的连带影响（都查过了）

| 影响 | 结论 |
| --- | --- |
| 一级分支数 +1 | 只是数字变，**不触发任何校验**（见下） |
| 原父的孩子数 −1 | 可能让原父变成叶子 —— 合法，`validateDraft` 不看这个 |
| 根的孩子数上限 | `LIMITS.children = 50` 是契约硬上限，`planDetach` 在这里先拦一次（`branch-cap`） |
| **颜色** | `store.nodes` 的颜色是**沿父链取最近的有色祖先**（`inheritedColor`）。断开之后它会换色：原来跟着「甲」的红，现在自己是一级分支、父是根（无色）→ 回到默认。**这是故意的**："按分支分色"这条约定在断开之后确实变成了两支，换色是这条约定在说实话；想保住原色就显式点「色」。 |
| 排版 | 根多一个孩子 → 整棵树的竖直范围变高，右侧那一支整体错位。落点在**末尾**，所以新的一支出现在最下面。 |
| 视图收起 | 新位置是根的孩子，可能落在 `visibleNodeLimit` 之外 → `detachNode` 里必须 `revealInView` |
| 视图适配 | **必须重新适配**（与普通拖动相反）。普通拖动的落点紧挨着用户看得见的目标；断开的落点在根的最后，可能离原位一整屏。所以 `onNodeDragStop` 的 detach 分支**不设** `contentChangedByDrag`。 |

### `MIN_BRANCHES = 3` 管不到这里（判据）

`MIN_BRANCHES` 是**生成侧的质量门槛**，不是契约：

- `backend/app/generation/service.py::MIN_BRANCHES = 3`，只由
  `validate_generated_content(..., enforce_min_branches=True)` 使用，而这把开关
  只在**模型整图生成**那条路上打开；demo 占位结构与用户已保存的旧图显式传 `False`。
- 契约层 `MindMapContent.validate_tree()` **没有**这条门槛。`docs/AGENT_PLAN.md`
  的 0b 行原文：「`MindMapContent.validate_tree()` 不加此质量门槛，旧图与人工删支
  仍合法。」

所以：**断关系让一级分支变成 2 条、甚至 1 条，都不拦。** 用户有权把图整理成一条链
——那是他的作品。用例 `tests/node-structure.spec.ts` 里那条"断到只剩 1 条一级分支
也得存得下去"钉的就是这一条（`validateDraft` 返回 `null`）。

反过来说，"少于 3 条不成图"这句话只在**生成**时成立，而人工整理不生成。

### 空白处的预演（这一轮最容易被漏掉的一层）

`dragHint` 从"只有目标"扩成两档（`kind: 'move' | 'detach'`）。detach 时：

- **幽灵框照画**：`previewDetach` 用与落地同一个 `layoutTidy`、同一棵画布树算出
  根下末尾的真实位置。没有它，用户松手后会发现节点跑到画布另一头。
- **光圈画在原来的父节点上**，不是被拖的节点上。"要断的是它俩之间那条边"——空白处
  没有任何视觉锚点说明这一点，这一圈就是这个功能的可读性本身。
- **文字写两头**：「断开「甲二」与「甲」的关系 · 成为一级分支」。`dropPendingLabel`
  那一套只写目标，这里必须写两端。

### 两种拒绝，都**不是**"重排"

- `already-branch`：它已经挂在根下面。此时唯一可能的结果是"挪到根的孩子列表末尾"
  —— 那是一次**悄悄的重排**，而手势是"拖到空白处"。读不出"我要排到最后一位"。
- `root-moved`：中心主题没有父节点，无从断开。

`planDetach` 里**没有**"太深"这一档：断开只让树变浅（挂到根下一律是第 2 层），写一条
深度判据只会得到一个永远不触发的分支。

## §二、删除：整支一起删，代价由两步兜住

三档候选：一起删 / 子节点上提到父 / 只许删叶子。**选一起删。**

| 候选 | 为什么不要 |
| --- | --- |
| 子节点上提到父 | 用户点的是"删这一个"，结果 20 个节点同时换了父。他没点过那个，也看不出发生了什么。 |
| 只许删叶子 | 把删除变成"先自底向上扫一遍"的活，而这是一棵会长的树（最多 8 层、1000 节点）。 |
| **一起删**（选中） | 与画面上看到的一致：「甲」是**一个**盒子，它的子孙缩在里面。 |

### "会不会悄悄丢数据"的判据（三条，缺一条就算悄悄丢）

1. **状态栏明说**：`已删除该节点及其子节点，可撤销。` 不是"已删除"。
2. **账本记整支大小**：`diffEdits` 只为"被删子树的根"发一条 `remove`，
   `subtreeSize` 是这一支的节点数。删叶子（1）与删一整支（12）在统计里必须分得开
   —— 每个后代各发一条会让 `removed_depth` 在 2…5 层各留几条，读起来像"每层都在
   被删"，而真实动作只有一个。
3. **一步撤销原样还回**：用例断言 `JSON.stringify` 逐字节相等 + 节点 id 的**前序
   顺序**相等。只比数量的话，"删了又加回来但顺序乱了"会漏过去。

### 连带删边与关系（否则下一次保存 422）

`dropDanglingEdges(content, doomed)` 三张表一起清：

- 树的附加边：端点是节点 id；
- 流程的阶段内边：端点是**该阶段自己的**节点 id（这一层以前没有读者）；
- `relations`（跨节点关系线）：三种形状的顶层都有，端点永远是节点 id。
  契约 `_validate_relations` 硬拒指向不存在节点的关系，而界面不渲染 `relations`
  —— 用户既看不到那条残留，也没法删掉它，只能看着保存 422。

用例把这一条钉成"造两条悬空源 → 删 → `contentEdges` 里没有 → `validateDraft` 过"。

### 容器根删不得

中心主题 / 一根骨 / 一个阶段。判据走 `isContainerRoot(content, id)`，不看
`diagram_type`。工具栏的「删」按钮在那种情况下**灰着**（`store.isContainerRootId`）
—— 比点一次再看一句提示便宜。

## §三、手动新增节点：三条路，只有两条该做

用户要的三种场景确实不同：

| 路子 | 做不做 | 理由 |
| --- | --- | --- |
| ① **Tab / Enter**（键盘） | 第一轮就有，这一轮补实测 | 长节点的主力：纯键盘、不用瞄准，与 ProjectGraph 的"节点树"同一条交互 |
| ② **双击空白** | 这一轮新做 | 键盘那条只能沿"当前选中的那个节点"长；用户常常是先看见**这一片**还空着 |
| ③ 拖一个"新节点"出来 | 不做 | 拖动的语义是"改已有节点的关系"，长出一个新节点要另一套起点（从哪儿拖？），而收益只有"省掉双击" |

### 新节点的初始形状

| 字段 | 值 | 依据 |
| --- | --- | --- |
| `label` | `'新节点'`（**不是空串**） | 契约 `Node.label` 非空，`validateDraft` 也拦；空串会在保存时 422。而 `MindNode` 的编辑框打开时 `select()` **全选**，所以"按下去直接打字"就是覆盖这三个字，用户不需要先删。 |
| `detail` / `note` | 不写（`undefined`） | "还没写"与"写了空"是两件事，前者是缺省。 |
| `source_refs` | 不写（`undefined`，等价空数组） | 见 §四。 |
| `color` / `icon` | 不写 | 沿父链继承父节点的色，与"新节点属于这一支"一致。 |
| `pos` | **绝不写** | 铁律 1。 |

### 双击空白：位置参与推导的唯一合法方式

"在那儿"只能读作"挂到**离那儿最近**的那个节点下面"。几何全在
`canvas/layout/insert-zone.ts`（纯函数）：

1. 先按 `dropHitOf` 扫全部可见节点的命中区 —— 命中就按方位翻译，与**拖动共用同一张
   表**（`dropZoneOf`）。于是"在节点右边双击"与"往节点右边拖"长出同一个结果。
2. 一个都没命中（真正的空白）→ `nearestHitOf` 取最近的一个，固定算 `child`。
   这一档**不读方位**：空白可以落在某个节点的任何一侧很远处，按方位会读出"我要当
   它的父"这种没人期待的结果。

**"最近的"为什么不是欧氏距离**：盒子是 180×48，同一份"绝对像素"在水平与垂直上
含义差近四倍。欧氏距离几乎只听水平分量，于是右上角双击会挂到右边很远的节点下面，
而不是正上方那个。`nearestHitOf` 与命中区共用同一套归一化度量（除以半宽 + 外扩），
两轴在"几个盒子的尺度"上同权。用例里有一条把两种口径的**不同答案**钉住
（指针在「100,300」时归一化选右下、欧氏选正上）。

### 四档 zone 有两处必须降级

`planInsert` 原样接收四档（与拖动同构），但两处降级 —— 因为**新增一个节点不能顺带
重排已有结构**：

| 传入 | 实际 | 为什么 |
| --- | --- | --- |
| `parent`（"我要当它的父"） | `sibling-before` | 一个尚未存在的节点没法"收养"目标并把它降到下一层 —— 那是两次结构改动，而手势只是"在这里加一个"。 |
| `sibling-*` 且目标就是根 | `child` | 根没有兄弟。 |

降级必须在 `status` 里说出来（`plan.degraded` 那半句拼在最前面），否则用户会看到一句
与他点的方向无关的话。

### 视图：`zoomOnDoubleClick` 必须关掉

这一条是实测才发现的：Vue Flow 默认 `zoomOnDoubleClick: true`，而 d3-zoom 的
`dblclicked` 会 `noevent(event)`（= `preventDefault` + `stopImmediatePropagation`）
——双击**根本冒泡不到**画布外壳上绑的那个 handler。

所以 `<VueFlow :zoom-on-double-click="false">`。这不是"顺手关一个默认值"：双击在这个
画布上已经被"加节点"占用了，两个动作不能共用一个手势。代价是失去"双击放大"，而
滚轮缩放与「适应宽度 / 全图」两档都在。

## §四、键盘长节点实测（真机 5173，载入「树基线」7 节点）

| 步骤 | 结果 |
| --- | --- |
| 单击「叶子乙」→ **Tab** | 在它下面加一个子节点 `n_943adf76`，label「新节点」，输入框弹出且**全选**，状态栏「已加子节点，输入文字后按回车确认。」撤销可用 |
| 输入「第二轮测A」→ **Enter** | 提交成功，节点文字改为「第二轮测A」，状态栏「已修改，记得保存。」编辑框关闭 |
| **再按 Enter** | **什么都不发生** —— 见下面那条 |
| 单击「第二轮测A」→ **Enter** | 在**同一个父节点**下加一个兄弟 `n_4c72a270`，label「新节点」，状态栏「已加兄弟节点，…」 |
| 输入「兄弟B」→ **Tab** | 提交为「兄弟B」，并在**父节点**（叶子乙）下**又加一个**子节点，状态栏「已加子节点，…」 |
| **双击空白**（远离所有节点） | 在最近节点「叶子甲」下加一个子节点，状态栏「已在「叶子甲」下面加了一个子节点，输入文字后按回车确认（可撤销）。」 |

### 那条"再按 Enter 什么都不发生"是真的，而且值得单列

Enter 提交之后编辑框被移除，焦点落回 `document.body`。而结构键的判据是
`ownsStructureKeys`：**`document.activeElement` 必须在画布外壳里**。于是"提交完直接
连着按 Enter 长一串兄弟"这条链会断，用户必须再点一下节点。

这是第一轮留下的行为（不是这一轮引入的），代价是"连按 Enter 长兄弟"做不到；Tab 那
条**不受影响**，因为 `commitAndAddChild` 之后新节点的 `focusInput()` 会把焦点抓进新
输入框（`MindNode` 里那个 5 次 `nextTick` 的重试循环）。

修法很便宜（`finish(true)` 之后 `focusCanvas()`），但它改的是第一轮的焦点模型，而这一
轮的边界不含那个 —— 记在这里，下一轮或用户明确要求时再做。

## §五、自评：「手动加的节点没有引用」与「每个节点必须有原文」冲突吗

> **这一节的第三条理由已被推翻，判定见 `docs/NODE-ORIGIN.md`。**
>
> 三条事实与"手动节点无引用是合法的"这一段仍然成立（它们说的是验收判据）。被推翻的是
> 下面「将来要做『每个节点都能追溯』的验收」那三条理由里的**第三条**：
>
> - "唯一使用者是将来可能做的验收"——不准确。界面上那句引用覆盖率文案**现在**就在
>   使用这个信息（"生成时模型没在材料里找到对应句子，或者这个节点是你自己加的"），
>   只是用得**不诚实**：一边说"契约里没有标记"，一边替它给出答案。
> - "`origin` 要同时出现在三种形状的序列化 + 导入导出里"——成本被高估了。三种形状
>   共用同一个 `Node`（`MindMapContent.root` / `FishboneBone.root` / `FlowStage.root`），
>   导出走 `model_dump(mode="json")`，加一处就够。
> - "账本能读出『谁加的』"——只在**同一次会话**里成立：`listEditEvents` 在界面上零引用
>   （棘轮基线里 `status: "gap"`），`loadMap` 不回填账本，而导入进来的图**一条 add
>   事件都没有**。
>
> 结论改成：**补**，补成 `Literal["generated","manual","unknown"]`，缺省 `unknown`
> （与 `expandable` 同一条零迁移规矩）。设计与执行单在 `docs/NODE-ORIGIN.md`。
> 下面原文保留，作为"当初为什么这么判"的记录。

**不冲突 —— 它们作用在不同层、不同时刻，而且"哪一类节点"这件事本来就能读出来，
不需要给数据加字段。**

三条事实（都查过）：

1. `MUST_CITE_EVERY_NODE`（`backend/app/agent/tools.py`）是一段**提示词**。它对模型
   说话，不产生任何校验代码。
2. 真正的校验是 `verify_source_refs`，它的行为写在 `backend/app/optimization/source_refs.py`：
   没有引用的节点只产出一条 **`UNSOURCED_NODE` warn**，message 原文是
   「节点「X」没有可核验的原文引用；**不代表节点内容错误**」。**它不删节点**
   （`remove_invalid=True` 只跳过"引文对不上"的那些**引用**，节点留在树上）。
3. 契约 `validate_tree` 完全不看引用。用例把这一条钉住：
   `store.addNodeAt(...)` 之后 `validateDraft(content)` 返回 `null`。

所以**手动加的节点无引用是合法的，保存不会被拒，收尾校验也不会把它剔掉**。它会被
`UNSOURCED_NODE` 提示一次 —— 那是提示，不是判废。

### 将来要做"每个节点都能追溯"的验收，两类节点怎么分

**不要给节点加 `origin: 'manual'` 这类标记。** 判据：

- **"谁加的"已经能从账本读出来，而且比节点字段更准。**
  `mindmap/edit-log.ts::diffEdits` 为每个新节点发一条 `kind='add'` 事件，带
  `actor: 'user' | 'agent'`、`nodeId`、`parentId`、`depth`。手动加的走
  `applyContent(next, true, 'user')`，模型加的走 agent 那条路。账本是**按时间**记账的，
  而节点字段只能说"现在是什么"，说不出"什么时候、被谁"。用例
  `账本记的是 add，并把父节点 id 带上` 已经钉住 `actor === 'user'`。
- **"可追溯"该定义在生成产出上，而不是全部节点上。** 生成侧的节点的判据是
  `Node.source_refs` 非空；空的有两种（生成但材料不足 / 手动），而这两者用账本
  的 `actor` 就能分开，不需要新字段。
- **加字段的成本是不对称的**：`origin` 要同时出现在契约（`backend/app/contracts/mindmap.py`
  的 `Node`）、三个形状的序列化、导入导出、以及所有 `UpdateOp` 的"缺省 = 不动"语义里
  —— 而它唯一的使用者是"将来可能要做的验收"。**等有需求再加**，那时账本已经给了
  你按 `actor` 分组的能力。

一句话结论：**现在不该在数据里区分。** 该做的是把"哪些节点是生成产出"这件事继续由
账本回答（它已经在回答），而把 `source_refs` 这条判据留给"这条结论有没有出处"——
那是另一件事，手动节点本来就该回答"没有"。

> ↑ 上面这一句已被本节的顶注取代（`docs/NODE-ORIGIN.md`）。留下来是为了让下一轮
> 读得到"当时是怎么被说服不加的"——那份理由里的第三条（成本与使用者）经不起核对。
