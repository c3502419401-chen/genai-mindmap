# 薄材料上骨架只给两条：现在怎么处置、复跑到了什么

2026-11-28。这条改动本身早就在（`docs/OFF-TOPIC-AND-FEW-BRANCHES.md` 记的是病灶，
`tests/test_few_branches.py` 记的是判据），缺的是**一份把"跑过了"写成数的话**。
这一篇补的是那句，顺便把"这次到底复跑到哪一层"划清。

---

## 一、病灶一句话

骨架那一次只看到"主题 + 文件?"，材料只有三四百字、又只有两块标题时，模型就照着
那两块写两条一级分支。而 `MIN_BRANCHES = 3` 是一条**结构下限**（两条不成图），于是
整次生成判废，用户拿到的是一张错误卡片。验收里那三条立项材料的 `too_few_branches`
→ 重试 → `too_many_failures` 就是这么来的。

## 二、补丁在哪（三处，缺一处都不成立）

| 处 | 做什么 | 位置 |
|---|---|---|
| 上游：目录要认得真实材料 | `一、标题` 紧贴正文也算章节；正文列表项不算 | `tools._outline_entries` |
| 中游：目录比下限窄时取消"优先照它写" | `OUTLINE_FEW_BLOCKS_NOTE` 拼在目录行之后 | `tools._render_outline` / `tools.py::OUTLINE_FEW_BLOCKS_NOTE` |
| 下游：少于下限的三种结局 | 纯主题判死；有材料先**带证据**重问一次；重问仍少则**交树 + `BRANCHES_BELOW_MIN`** | `tools._generate`（"一级分支太少"那一段）+ `validate_generated_content(enforce_min_branches=...)` |

第三处是"补丁"这个词最容易被误读的地方：它不是把门槛拆掉，而是**把失败拆成两档**。
纯主题仍然判死（`too_few_branches`），只有"有材料"这一档才降级交付，并且每次都以一条
warn 诊断记账。`enforce_min_branches=not branches_degraded` 是为了让降级路径走得到出口
——否则出口用同一条下限再判一次死，中间那段代码等于不存在。

## 三、复跑到了什么（`scripts/_probe_thin_material_branches.py`）

跑法：

```
cd backend
python scripts/_probe_thin_material_branches.py
```

它做两件不依赖模型的事。

### 1. 目录侧：20 条真实验收材料，骨架那一次看得见几块

```
S08–S14（会议纪要）  4–6 块，覆盖率 0.82–0.89
S15–S20（立项材料）  6–7 块，覆盖率 0.96
S01–S07（课程大纲）  0 块，覆盖率 0.00（版式不吃 `一、` 这套编号，走"按主题归纳"那条）
合计 20 条，目录少于 3 块（会补 `OUTLINE_FEW_BLOCKS_NOTE`）的有 0 条
```

**这就是"修好了"的直接证据**：当初判死的那批立项材料，现在骨架能看见 6–7 块、
覆盖率 0.96，`OUTLINE_FEW_BLOCKS_NOTE` 一次都不触发——它不再是靠"补那句提醒"救回来的，
而是上游的目录本身就能看见结构。那句话现在只服务真正的两块材料（比如那两条制度要点）。

课程大纲那 7 条 0 块不是缺陷，是版式：它们不用 `一、` 编号，`_outline_entries` 的
判据本来就不认；那 7 条的树反而是全批最稳的（4–5 支），因为"按主题归纳"这条路够用。

### 2. 骨架侧：三种结局用同一套代码路径跑一遍

```
① 纯主题 + 2 条                 ok=False  code=too_few_branches  骨架调用=1  一级分支=0  BRANCHES_BELOW_MIN=无
② 薄材料 + 先 2 条、重问 6 条    ok=True   code=-                骨架调用=2  一级分支=6  BRANCHES_BELOW_MIN=无
③ 薄材料 + 两次都 2 条           ok=True   code=-                骨架调用=2  一级分支=2  BRANCHES_BELOW_MIN=有
```

三行与用例一一对应（`test_two_branches_without_material_still_fails` /
`test_two_branches_with_material_is_retried_with_evidence` /
`test_two_branches_twice_is_delivered_with_a_diagnostic`）。① 的"骨架调用=1"也是判据：
纯主题不重问——没有材料证据可以换，同一段 user 再发一次是同一个答案。

脚本里有一处必须做的准备：**把本机的开关全部压回"什么都没开"**（`_clean_env`）。
第一次跑的时候 `MINDMAP_EXTERNAL_KNOWLEDGE` 是开的，外部检索真的发了外网请求并补进来
7 份材料，于是"①纯主题"那一格跑成了 `ok=True` —— 一个**把结论反过来的假阳性**。
用例那边由 `conftest.clean_env` 统一负责，脚本没有那层。

## 四、真模型侧：今天新跑了十四格，两种处置都抓到了

上一版这一节叫"这一轮**没有**复跑到的一层"，理由写的是"本机 `.env` 里只有
`DASHSCOPE_API_KEY`，没有 `MINDMAP_LLM_API_KEY`"。**那个理由不成立**：`.env` 里确实没有，
但 `run-backend.bat` 第 3–7 行把 `MINDMAP_LLM_MODE` / `BASE_URL` / `API_KEY` / `MODEL`
全 `set` 了，而 8000 那条后端就是拿这个 bat 起的。缺的从来不是 key，是有人去读一眼 bat。

### 4.1 跑法

```
cd backend
python scripts/measure_acceptance.py structure --only S17,S19,S20   # 8000（bat 那条，开关全开）
MINDMAP_ACC_BASE=http://127.0.0.1:8010 python scripts/measure_acceptance.py structure --only S17,S19,S20
```

第二条要另起一条干净后端（全开关压 0、独立空库、8010）。两条都要，理由在 4.4。

### 4.2 二十条验收材料：一级分支 4–7，没有一条走到下限

`backend/data/acc_structure.jsonl` 里那批真跑是 **2026-11-27 02:00** 落盘的，而
`OUTLINE_FEW_BLOCKS_NOTE` 的提交 `a4d3692` 是 **01:34** —— 也就是说**那批读数本来就在补丁
之后**，只是从来没人把它读成"真模型侧复跑"。逐条读：

```
S01–S07（课程大纲）   4–5 条
S08–S14（会议纪要）   4–6 条
S15–S20（项目立项）   6–7 条（含本文关心的那批薄材料）
20 条全部 ok=True；planned_branches 与最终一级分支**逐条相等**（模型照骨架写，没有加也没有减）
BRANCHES_BELOW_MIN / too_few_branches 出现次数：0
```

### 4.3 今天新跑的八格（薄材料，生产配置 + 干净环境）

| 跑 | 材料 | 一级分支 | 骨架 planned | 骨架调用 | `BRANCHES_BELOW_MIN` | ok |
|---|---|---|---|---|---|---|
| S17 ×3（生产） | 654 字，六块 | 6 / 6 / 6 | 6 | 1 次 | 无 | True |
| S19（生产） | 611 字，六块 | 6 | 6 | 1 次 | 无 | True |
| S20（生产） | 624 字，六块 | 6 | 6 | 1 次 | 无 | True |
| S17 / S19 / S20（干净） | 同上 | 6 / 6 / 6 | 6 | 1 次 | 无 | True |

一级分支完全不动（恒 6），动的是节点数（S17 三次 59 / 53 / 53）与 `must_rate`
（0.5–0.875）。**有方差的量与这条判据无关**：这条判的是"会不会掉到 3 条以下"。

### 4.4 最该触发的那一档：两块标题 + 369 字

把 `_probe_thin_material_branches.py` 里那条 `thin`（`一、背景` / `二、结论` 两块标题 +
足长正文）原样发一次真生成，两条后端各跑三次：

| 后端 | 一级分支 | 骨架 planned | 一级标签 | 诊断 | ok |
|---|---|---|---|---|---|
| 8000（bat，开关全开） | 2 / 2 / 2 | 2 | `背景` / `结论`（三次逐字相同） | `BRANCHES_BELOW_MIN` **有** | **True** |
| 8010（全关 + 空库） | 4 / 4 / 4 | 4 | 材料背景与缘起 / 核心结论与判断 / 待办与后续动作 / 风险与不确定因素（三次逐字相同） | 无降级 | True |

复现这两行：`scripts/measure_acceptance.py` 只认 `acc_samples.json` 里那 20 条，所以这条材料它
跑不到。做法是复用它的两个函数——`post_json(opener, TEXT_SOURCE, {"text": THIN})` 拿 source，
再 `stream_run(opener, {"goal": …, "sources": [source]})`，读 `tools[0]["summary"]` 里的
`planned_branches` 与 `diagnostics`。干净后端要自己起一条：`MINDMAP_LLM_*` 从 `run-backend.bat`
抄、其余开关压 0、`MINDMAP_DB_PATH` 指一个空库、端口换一个，然后用 `MINDMAP_ACC_BASE` 指过去。

三件事同时成立：

1. **"只给 2 条"这个形态没有消失。** 生产配置上三次采样全部落在 2 条，标签都是
   `背景` / `结论`——就是病灶原文里那个形状。
2. **但它不再判死。** 三次都 `ok=True`：交树 + 一条 `BRANCHES_BELOW_MIN` warn。第三处补丁
   要的正是这个（把失败拆两档），今天在真模型侧**实际走到了这一档**，不是只用桩跑出来的。
3. **8000 → 8010 的差异稳定且未定位。** 同一份材料、同一份代码，两条后端稳定给出 2 条与
   4 条。已知差异只有"生产配置 + 主库"与"全关 + 空库"：主库有 `style_profile`
   （`branches` 建议值 5.0 / 区间 4–6）、13 条记忆、4 条偏好，干净库这三张表都是空的；
   开关侧还差着 `MINDMAP_SECTION_SLICE` / `MINDMAP_GRAPH_*` / `MINDMAP_DETAIL_SCALE` 等。
   **哪一项造成的，本轮没有定位**——二分要一条条开关重启，成本几十次生成。写在这里是
   为了不让下一个人以为"4 条是唯一的真读数"。

### 4.5 结案标准：判"形态"，不判"修复确认"

"跑过一次 ≠ 确认修好"这句话在这条上要换个读法：

- **判死（`too_few_branches`）的触发条件是骨架 < `MIN_BRANCHES`。** 这个条件今天在真模型
  侧仍然会发生（4.4 那张表，3/3）。要它"确认不再发生"，得能构造出一个必然 < 3 条的输入
  ——那就等于测桩，不是测模型。
- 所以这条能判的最硬的一句话是：**"真模型侧也观察到同一处置"** —— 掉到下限时交树 + 诊断，
  而不是整次判废。这一点**已经观察到，且 3/3 稳定**（同一材料同一后端，三次逐字相同的标签）。
- 采样几次够：**判"形态在不在"1 次就够，判"它稳定"3 次就够**。这里不能用"68/54/111 那种
  波动"当理由要求更多次——那三个数波动的是**耗时与节点数**（今天也有：S17 三次 59 / 53 / 53 个
  节点、耗时 29.5 / 28.2 / 27.4 s），而一级分支数在今天的 14 次采样里**同一环境内一次都没动过**
  （生产薄材料 5 次全 6、干净三份全 6、两块标题生产 3/3 是 2、干净 3/3 是 4）。
- 仍然空的：**纯主题（无材料）那一档**。真模型侧没测它，也没必要测——它不重问、直接判死，
  判据在 `test_two_branches_without_material_still_fails` 里，与"薄材料"不是同一件事。

**别把这一节读成"缺陷已修、且已验到底"。** 已验的是：三种结局的代码路径（§三那三行）、
"掉到下限时降级交付"在真模型侧的实际发生（§4.4）。未验的是：2 条与 4 条之间那个稳定差异
由什么决定（§4.4 第 3 条）。

> 这一条在 `docs/BACKLOG.md` 第 6 条，2026-11-28 由"半做"转"已做"——转的理由不是
> "真模型侧跑过了"，而是"真模型侧也观察到了同一处置"。本文件不维护状态。

## 五、顺带确认的一件旧事

`OUTLINE_MIN_COVERAGE = 0.6`、`MIN_BRANCHES = 3` 两个数没有动过。这一轮复跑它们仍然
在同样的位置生效：覆盖率不足的目录整段不进 prompt（S01–S07 那 7 条），条数不足的
按三档处置。门槛没有被这次改动悄悄降低。
