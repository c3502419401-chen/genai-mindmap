# 本期承诺边界：已交付 / 本期不交付 / 长期不做

> 这个仓库对应一份 2026 年申报书，原文一字未改地存在 [PROPOSAL.md](PROPOSAL.md)。
> 申报书里写的技术栈、部署形态与指标是立项时的说法，**不等于现在的实现**。
>
> 本文件只干一件事：把「没做什么」和「做了什么」放进同一张表、用同一套证据标准写清。
> 一条口径贯穿全文：**每条「不做」都必须能回答「要做到它得先有什么」。答不出的不是范围界定，是漏项。**
>
> 三个入口的分工：**本文**回答「本期承诺到哪为止」；[PLAN-VS-IMPLEMENTATION.md](PLAN-VS-IMPLEMENTATION.md)
> 给 22 项申报条目的逐条证据；[PLAN-REWORDING.md](PLAN-REWORDING.md) 给可直接抄进申报书的替换句
> （一页速查版见 [PROPOSAL-REPLACEMENTS.md](PROPOSAL-REPLACEMENTS.md)）；每项功能做到哪一步由
> [FEATURES_AND_OWNERS.md](FEATURES_AND_OWNERS.md) 的 F 编号追踪。本文与代码冲突时以代码为准。

## 一、三分类的判据

| 分类 | 判据（三条同时成立） | 有多少条 |
|---|---|---|
| **已交付** | ① 代码里有这条能力；② 有自动化用例或仓库内实测数字钉着它；③ 能指出它到哪为止 | 9 项 |
| **本期不交付** | ① 代码里没有，或只在文档/规划里；② 本期不动手；③ 写清了前置条件与证伪路径 | 5 项 |
| **长期不做** | ① 不是排不上期，是做了不划算或与本项目定位冲突；② 给了拒绝理由；③ 给了「什么条件下改变主意」 | 5 项 |

**跨类的移动规则**（写下来是为了让这张表能被别人改，而不是只有作者能改）：

- 「本期不交付 → 已交付」：代码 + 用例 + 本文 + 申报书四处同时改。只改代码不改本文，本文就成了谎；只改本文不改申报书，申报书里的旧承诺就还在。
- 「长期不做 → 本期不交付」：必须出现触发条件（见第四节第三列），而不是「有人想做」。
- 「已交付 → 本期不交付」：不应该发生。真发生了要先在 [FEATURES_AND_OWNERS.md](FEATURES_AND_OWNERS.md) 把状态改红，再回来改这里。

## 三、本期不交付（减承诺）

每条四段：**它是什么（申报书原文）→ 为什么不做 → 前置条件 → 做到之后先要能测什么**。第四段是这一节的承重墙：没有它，「不做」就只是一个姿态。

### 3.1 多人实时同期编辑与协作场景的 AI 辅助

**它是什么**：申报书 3.4.1 原文「在团队协作场景下，AI扮演"协作者"角色：自动整合多用户输入、解决冲突提议、记录讨论轨迹。」

**为什么不做**（四条，都在数据层与架构层，不在排期）：

1. **记不住是谁改的。** `edit_events.actor` 只有 `'user' | 'agent'`（`docs/EDIT-LOG.md:45`）。多人协作最基础的那句话「谁改了什么」在数据层就不成立。
2. **第二个人能看，不能改。** `mindmaps.owner` 的产品口径是「任何有身份的人都能看，只有创建者能改」（`backend/app/mindmaps/repository.py:167-176`）。协作的最小定义恰恰是「两个人能改同一张图」。
3. **乐观锁只能拒绝覆盖，不能合并。** `version` 不是合并语义；SQLite 单文件单写者，连接等写锁的上限是 10 秒（`repository.py:152`）。`docs/ARCHITECTURE.md:56` 自己写着「不应将当前版本号机制当作实时合并方案」。
4. **AI 那半边没有输入。** 自动整合多人输入 / 冲突提议 / 讨论轨迹，需要协作事件流；F18 依赖 F17，F17 未起步，所以 F18 是「没有对象可喂」，不是「算法没写」。

**为什么不能拿「账号体系 + 编辑账本」拼成协作雏形**：上一轮判过，三条硬理由即上面 1–3。拼出来的东西交不出任何能证伪它的实验——你没法设计一个实验去测「这是不是协作的雏形」。**一个不能被证伪的能力描述，就是粉饰的定义。**

**前置条件**（一条链，缺一环都做不成，顺序不能换）：

1. **身份到人**：`edit_events.actor` 从 `user|agent` 改成 `user:<id>|agent`，并给历史行补「未知」而不是补一个猜出来的 id；
2. **授权到图**：`mindmaps` 增加成员表（读 / 写 / 管理三档），把「读共享写限主」换成「按成员判」；
3. **合并语义**：CRDT 全套——共享数据类型、WebSocket 通道、鉴权、持久化、断线恢复、与现有 `MindMapContent` 的数据格式映射（`docs/ARCHITECTURE.md:65` 的候选方案）。
4. **坐标归属**：现在 `pos` 是视图属性，「自动布局保存时不得携带坐标」（`docs/ARCHITECTURE.md:51,54`）。协作要求坐标成为共享状态的一部分，否则两人拖同一个节点必然互相覆盖。**这一条最容易被漏**，因为它不在「加一个协作库」的预算里。
5. **常驻进程**：单机 2C2G 上多一个常驻 WebSocket 服务，需要先有并发与内存的压测口径（现在只有 1/2/3 路并发的生成压测，没有长连接压测）；
6. 走完 1–5，F18 才有输入。

**做到之后先要能测什么**（证伪路径）：两名客户端同时改同一节点 → 合并后两处改动都在、版本单调、无静默丢失；冲突提议的准确率需要一个 20 组并发编辑的对照集，并有「不提议」的基线圈。**现在连这个实验怎么搭都缺前置。**

### 3.2 多语言实时翻译

**它是什么**：申报书 3.4.1 原文「支持多语言实时翻译，消除跨语言协作障碍。」

**为什么不做**：代码里零实现——`translate` 的全部命中是 CSS `translate(-50%,-50%)`，`i18n` 只有三处 `toLocaleString('zh-CN')`，无翻译服务调用、无语言检测。更关键的是它的**语义位置**：翻译是协作消息的附加层。没有协作消息，「实时翻译」没有作用对象——翻译一段谁都不会同时看到的文字，不构成「消除跨语言协作障碍」。

**前置条件**：3.1 全部满足；再加三件：语言检测（导图节点是 ≤200 字的短标题，机翻质量与长文不是一回事）、术语表（同一概念在同一张图里必须译成同一个词，否则分支名会分裂）、双语存储（保留原文 + 译文，改一次翻一次会产生不可追溯的译文漂移）。

**做到之后先要能测什么**：节点级双语对照 + 挂在协作消息上的端到端延迟（原文发出 → 对方看到译文）。现在这条指标没有测量对象，这也是 `PLAN-VS-IMPLEMENTATION.md` 把它列进「5.3 目前无法测」的原因。

### 3.3 模型微调 LLMs

**它是什么**：申报书 6.2-3 原文「模型调优：通过用户反馈数据微调 LLMs，提升生成准确性。」

**为什么不做**：全仓 `fine-tune | 微调` 只出现在文档与注释里，没有训练代码、没有数据集、没有基线。而缺的是**分母不是样本**：一张典型导图只有 37 条改动事件（`docs/EDIT-LOG.md:326,368`——那 37 条还都来自**同一张图**），离「几百条偏好对」差一到两个数量级；没有基线评估，微调结果无法判断是变好还是噪声。

**前置条件**：① 评价数据采集口径（「改了什么」算「更好的写法」——这条比采集难）；② 提示词/模型基线评估（同一批样本、两次运行可比）；③ 偏好对量级到位；④ 一次训练与评估的成本核算（本期无 GPU）。

**本期替代物（已交付）**：`edit_events` + 风格画像。用户对生成结果的实际修改（改了哪个字段、哪个层级、人改还是模型改）作为偏好信号，参与后续生成的排序与提示词偏好，**不改动已确认内容**。

**做到之后先要能测什么**：同一批 20 条样本、微调前后各跑一次双人盲评，报通过率差与置信区间；区间跨 0 就不算提升。这条口径现在就能写下来，所以它不是「不知道怎么做」，是「没有可训练的料」。

### 3.4 知识图谱嵌入与「逻辑优化算法」

**它是什么**：6.2-2 原文「基于知识图谱嵌入优化节点层级关系」；6.4 创新点原文「基于知识图谱的逻辑优化算法」。

**为什么不做**（这条与上面三条性质不同：**做了一半，量过，零收益**）：

- 落地的是实体/关系抽取 + 两跳邻域游走 + RRF 融合，**没有任何向量化的图表示**（无 TransE / Node2Vec，也无嵌入训练代码，`FEATURES_AND_OWNERS.md:30`）。
- 实测：四份材料全量入库（130 块 / 1406 实体 / 993 边 / 267 条别名边），只切 `MINDMAP_GRAPH_SEARCH` 跑两套对照——crossdoc 14 条与 manual 28 条的 recall@1/3/5/10 与 mrr@3 **逐位相同**，coverage@10 掉 0.5pp，逐条延迟 +85ms。58 条图命中里落在标注目标区间的是 **0 条**。
- 原因是分布不是融合：14 条跨文档问法只有 8 条命中图里的实体，命中的是「浏览器」「候选」「agent」这类泛称。

**前置条件**：① 先让 query→实体从「泛称子序列」变成「专名/术语匹配」；② 补一份「不用图谱」的正式基线报告；③ 才是嵌入与优化算法的对比实验。**三步都不保证有收益**——这也是把它写进边界而不是写进排期的原因。

**做到之后先要能测什么**：同一批 42 条标注问法（crossdoc 14 + manual 28），recall@k 与 coverage@10 分开报，并给出「落区间命中数」这个分母。上一轮的教训正是：融合指标好看，落区间为 0。

### 3.5 多模态混合生成

**它是什么**：6.4 创新点原文「多模态混合生成的思维导图范式」。

**为什么不做**：输入侧四路都通（见第二节），但「混合**生成**」要求跨模态产出——按文本描述嵌图、按音频生成节点关系。实际所有模态最后都收敛成 `Source.text`，出口只有结构化树/流程/鱼骨。**图片只是被「看」的输入，不产出图片、不做图片编辑。**

**★ 这条必须与「多模态输入」分开写。** 「上传草图 → 出文字导图」是真成立的；减掉的是「混合生成」，不是「多模态输入」。混在一起写，读者会把已经做到的也当成没做——那是另一种失真。

**前置条件**：① 契约里有「图节点」这一类型（现在只有 `label` / `note` / `detail` + `source_refs`）；② 导出格式能承载位图（四种导出里没有一种带二进制载荷）；③ 跨模态对齐的评估口径（怎么判「这个节点确实对应草图那一块」）。

**做到之后先要能测什么**：给一张草图 → 生成的导图里有一个节点是「依据草图局部重绘的图片」，且能判断它与草图的对应关系。现在这条实验无对象。

### 3.6 本期不主张的两条量化结论（性质不同：可补，不该撤）

| 指标 | 现状 | 为什么它不属于「减承诺」 |
|---|---|---|
| 结构合理性 > 85% | **待评估**，零数据 | 能力在（三图型生成真能跑），口径已定死（20 条中文样本 × 双人独立盲评 × 4 维度），数据源在库里（`runs` / `library_sources` / `edit_events`）——缺的只是人工评分这一步 |
| 多模态支持率 ≥ 90% | **待评估**，零数据 | 三模态输入都在（P2–P5）；口径是「解析出非空 `Source` **且** 生成合法 `MindMapContent`」，比「解析成功」严，已写定 |

**把这两条当功能一样撤掉是自伤。** 它们是唯一能让「能力真的有用」变成数字的东西，而它们缺的是 2–3 天人工评分，不是能力。

**一条分界，写在前面免得被滥用**：

- **能力不在** → 减承诺（3.1–3.5）；
- **能力在、证据未采** → 补证据（本节，以及容器化真机验证）；
- **能力是真的、速度也是真的** → 只能说准（三段延迟口径，见 [PROPOSAL-REPLACEMENTS.md](PROPOSAL-REPLACEMENTS.md)）。

把「可补的证据」当成「要撤的承诺」是自伤；把「零实现」当成「待补」是留雷。这两句是这个文件存在的理由。

| 4 | 跨节点语义关系的界面渲染与「建议添加连接线」 | 3.3.2 括号里的例子 | `relations` 四类关系的契约有、界面不渲染（`frontend/src/mindmap/edits.ts` 原话：用户看不到那条残留关系，也没法删）。**做了用户也看不见结果** | 先把 `relations` 画出来——那是独立的一轮设计（连线语义、增删手势、与布局的关系），不是补一个检测函数 |
| 5 | 企业私有文档接入与组织级权限 | 3.3.1「企业文档或用户个人知识库」 | 个人知识库已落地（入库保留 90 天、最多 200 份）；企业侧要组织 / 角色 / 审计三件，与单机部署形态冲突 | 多租户需求成立，且部署形态先换掉单机 SQLite |

**这一节与第三节的差别不是程度，是性质**：第三节是「现在没有、需要一串前置」，第四节是「有了也不划算、或不可能」。写在一起会让人误以为第四节也可以排期。

## 五、这张表怎么维护（防它自己烂掉）

- **三个入口不许合并**：本文（边界）、`PLAN-VS-IMPLEMENTATION.md`（22 项证据）、`PLAN-REWORDING.md` / `PROPOSAL-REPLACEMENTS.md`（可直接抄的替换句）。合并成一份会同时失去「可查证」「可抄」「可判边界」三件事。
- **机器闸门管什么**：`check_doc_claims.py` 管「文档说的事与代码现在做的事是否一致」（双向，代码翻了禁句跟着翻）；`eval_cases_manual.py` 的 `MANUAL_SOURCE_HASHES` 管「人读过的那一章还读得懂没有」。**本文不在那四份指纹里**，但改本文之后仍要跑全量——闸门扫的是 `git ls-files '*.md'`。
- **改本文的四个时刻**：① 有功能上线（从第三节搬到第二节）；② 有前置条件完成（更新那条链，别只改一句话）；③ 申报书改稿（同步 `PROPOSAL-REPLACEMENTS.md`）；④ 有人问「这个到底做不做」——那说明本节哪一句没写清，回来改。
- **本文不是 `FEATURES_AND_OWNERS.md` 的替代**：那张表按状态机记录每一项（待实现 / 部分实现 / 已实现 / 待评估），本文只回答「本期承诺到哪为止」。两张表冲突时以 FF 表的状态为准，本文的范围判断以本文为准——因为范围是决策，状态是事实。

## 六、「减承诺」算不算缩水：一个判断和它的依据

**判断：不算——但只在一种情况下不算。**

先给缩水的可操作定义，否则这个词只是情绪：

> **缩水 = 承诺的东西没做，且没有交代。**
> **范围界定 = 承诺的东西没做，写了为什么、写清了「要做到它得先有什么」、而且同期的资源投到了别的可验证物上。**

按这个定义过一遍，三条依据：

1. **减掉的五项是一条链的末端，不是五次独立的失约。** 3.1 与 3.2 是同一串前置（身份到人 → 授权到图 → CRDT → 坐标归属 → 常驻进程），3.2 的「实时」还额外依赖 3.1 的存在。3.3（微调）缺的是分母，3.4（图嵌入）是量过之后零收益，3.5（混合生成）缺的是契约里的图节点。**没有一项是「本来能顺手做，我们没做」。**
2. **同期资源去向是可复验的，不是形容词。** 节点级引用（来源 ID / 页码 / 字符区间 / 引文 + 三层校验）、结构可编辑（三种图型各自几何 + 四种导出 + 逐字节回归）、单作者改动留痕（`edit_events` + 两条恒等式自校验）——这三样都有文件与用例，任何人在仓库里能查到。
3. **每一条都自己交出了证伪路径。** 见第三节每条的第四段。**一个不肯说「怎么证明我做错了」的边界声明，和粉饰没有区别。**

**★ 一句话必须补在前面**：如果评审的口径是「立项书里的功能清单就是交付清单」，那这个项目确实少了五项功能，那就是失约——只是失约的性质是「范围超前于前置能力」，不是「能力退化」。补法只有两种：给时间补齐那条链，或按本文改稿。**不认这一条，上面三条依据就都只是在给自己找台阶。**

### 要不要写「把资源集中在引用可追溯与结构可编辑上，这两项在同类工具里没有对手」

**不要写这句。** 三个理由，都与本文件自己的标准有关：

1. **它是不可证伪的比较断言。** 我在第三节判微调不可写、判「协作雏形」不成立，用的正是「交不出能证伪它的实验」这条标准。「同类工具里没有对手」同样交不出。**同一份文件里用两套标准，比不做承诺更伤可信度。**
2. **它没有依据。** `docs/research/readmes/` 下有 19 个同类项目的 README 摘录，但仓库里没有一份横向能力对表。要写这句话，得先做那张表——那是一件独立的活，不是一句状语。
3. **它把可验证的东西换成了形容词。** 这句想表达的其实是「这三项值得投入」，而这件事有更好的写法：**写成任何人都能当场做的三个动作。**

**可以写、也建议写进答辩材料的替代句**（三句都有依据，且不依赖任何比较）：

> 本期把资源集中在三处可被第三方当场自查的地方：① 打开任意一张导图，点任一节点，能否回到它所引原文的位置（`source_refs` 的页码与字符区间）；② 改一次结构再导出，字节是否只在该改的地方变（`tests/test_export.py::ByteIdenticalTest`）；③ 保存一次，改动账本的两条恒等式是否成立（`Σ by_actor = 总数`、`Σ by_field = update + style`）。这三处都是「看一眼就能判真假」的，而协作与微调即使做了，判断它有没有做好也仍然需要压测与基线——**这是投入方向的实证差异，不是修辞。**
