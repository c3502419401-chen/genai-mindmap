# 拖动第三轮：就地输入意图、两类图的拖动语义、以及"旋转"到底是什么

这一轮的三件事，用户原话是：

> 生成思维导图后**改节点改成点击节点出输入框，输入意图，大模型会执行修改**，节点改成可拖动，
> 可断关系，可删除，新增新建节点……**流程图和鱼骨图也需要单独适配**，还有**拖动父节点后面的
> 子节点也需要跟着移动**，**还有节点可旋转之类的**。

前两句在 `docs/NODE-DRAG.md`（第一轮：拖动改结构 + 子节点跟随）与 `docs/NODE-EDIT.md`
（第二轮：断关系 / 删除 / 手动新增）里做完了。这一轮做剩下的三件，并且**给每一件一个
明确的支持范围**——包括"不支持"。

| | 结论 | 一句话理由 |
| --- | --- | --- |
| 点节点就地出输入框 | **做**（候选 a：节点旁浮出小输入框） | 眼睛不用离开节点；两步里省掉的不是"点击"而是"跑到屏幕底部 + 叫回一个淡出的对话框" |
| 流程图 / 鱼骨图拖动 | **部分支持**：容器内重排放开，跨容器拒绝 | 跨容器改的是"这一步属于哪个阶段 / 这条原因属于哪根骨"，而且流程图的阶段内边会悬空 |
| 节点 / 子树旋转 | **A（整棵树的朝向）——而且它早就在了**；B 不可行，C 不做 | B 要换掉 `layoutTidy` 的空间模型，且在数学上必然重叠；C 不改变结构，只让图更难读 |

## §一、"就地"是哪里：选候选 a，以及它为什么不跟双击抢手势

三个候选摆出来时，真正的判据只有一条：**用户此刻的眼睛在哪**。

| 候选 | 眼睛 | 成本 | 判断 |
| --- | --- | --- | --- |
| a 节点旁浮出小输入框 | 不动 | 一个浮层 + 一套摆位（`overlay-layout` 已有第三块的位置） | **选它** |
| b 底部对话框聚焦并预填（上一版的现状） | 从节点跳到屏幕底部 | 零 | 少一步不等于省事：对话框在生成完是**淡出**的，得先被叫回来 |
| c 节点内联编辑 | 不动 | 零 | **不是同一件事**：那是改 `label`，双击已经在做 |

### 打出来的东西

- `frontend/src/canvas/NodeIntentBox.vue`：`Teleport` 到 `body` 的固定层（不跟画布
  `transform: scale()` 走——否则「全图」档下 13px 的框只剩 4.7px，而它要接键盘），
  位置由 `overlay-layout.ts::planOverlays` 的**第三块**算（`intent` 槽）。
- 提交走 `store.runEditOn(nodeId, goal)` → 那一个 `runGeneration(text, 'edit', …, { selection: [nodeId] })`。
  **不是第二条发送管线**：撤销栈、`clientRevision`、改动账本、失败分类、生成冲突裁决
  全部共用第一条。`ChatDock` 与它的差别只是入口（那边带材料面板、图型、深度思考这些
  "整张图"级别的开关）。

### 三个手势怎么分得开

| 手势 | 做什么 | 落在哪 |
| --- | --- | --- |
| 单击节点 | 选中 + 开合折叠 + **就地出框** | `MindMapCanvas.onNodeClick` |
| 双击节点 | 改这一行的**文字**（`label`，本地提交） | `MindNode` 的内联输入框 |
| 拖节点 | 改**结构**（父子 / 位次） | `MindMapCanvas` 的拖动链 |
| F2 | 改文字（键盘等价） | `MindMapCanvas.onKeydown` |

三条硬约束撑住这个分工：

1. **单击到出框之间有 120ms**（`canvas/intent-gesture.ts`）。浏览器的一次双击会先发
   两次 `click` 再发 `dblclick`；不等待的话，双击改标题会"先弹出一个意图框、再被编辑框
   顶掉"——一次看得见的闪，而那半秒里"回车提交给谁"是含糊的。
2. **框永远不自动抢焦点**。点节点会先 `focusCanvas()`（Tab / Enter / Delete 那套结构键
   依赖焦点在画布外壳里）。框要是自己抢了焦点，用户点完节点想按 Tab 加子节点就会变成
   在框里插入制表符。所以它出来时不聚焦，**点它一下**才进输入态。
3. **两个框互斥**：`openIntentFor()` 清 `editingId`，`beginEdit()` 清 `intentTargetId`，
   `setPrimary()` 把框关掉（换选中之后框还对着上一个节点说话就是纯粹的错位）。

### 这一步的诚实代价

用户说的是"点节点出输入框"，而**"点节点"这个手势本来就有主人**（选中 + 开合折叠）。
本轮选的是"点 = 看，额外给你一个就在手边的输入框"，所以严格算起来仍是
"点一下 → 框出现 → 再点框 → 打字"。

真要做成一步，只有一条路：把"点节点"整个改成"改这个节点"。那会吞掉"点一下读这一支"
——画布上最高频的动作。本轮不付这个代价（§四 会回到这条线上）。

### 已知的两个观感代价（浏览器实测，都不打算在这一轮解）

1. **框会压住下一个兄弟节点。** 实测一张 7 节点的树：节点高 48、兄弟间距 20，
   而框高 72 —— 兄弟之间那条缝根本放不下任何浮层，所以"紧贴节点下方"必然盖住下一层
   兄弟的左半边。这一条与工具条、悬停卡片是同一个宿命（它们也宽 150 / 288）。接受它
   的理由：框是**用户刚点出来的**，Esc 一下就走；而被盖住的兄弟此刻不是他的目标。
   真要解，得让浮层知道**所有**节点的矩形（`planOverlays` 现在只知道 anchor），那是
   一次重新设计，收益不抵成本。
2. **右侧放不下时它才翻到下方。** 向右布局的节点右侧通常正是下一层子节点，所以
   `right` 这个候选在密排的图上几乎总是"放不下"。候选顺序 `below → right → left → above`
   是对这个事实的让步（详见 `overlay-layout.ts::INTENT_ORDER`）。

## §二、流程图 / 鱼骨图的拖动：为什么是"部分支持"

### 结论

| 图型 | 容器内重排 | 跨容器 | 阶段/骨的次序 |
| --- | --- | --- | --- |
| 树 | 全部放开（第一轮就是这样） | 不存在（只有一块区域） | 位次可换 |
| 流程图 | **放开**：同一阶段里换位次、换父步骤 | **拒绝** | **拒绝** |
| 鱼骨图 | **放开**：同一根骨上换位次、换父原因 | **拒绝** | **拒绝** |

判据在 `frontend/src/mindmap/move-scope.ts::moveScopeProblem`（纯函数）：被拖节点与目标
节点是否在**同一个容器**里（`containerOfNode`）。树恒为放行，所以树的行为一个字节都没变。

### 跨容器为什么不做——三条，按硬度排

1. **流程图的阶段内部边会悬空。** `FlowStage.edges` 的端点是**节点 id**（与
   `FlowContent.edges` 的阶段 id 是两个命名空间），契约层硬拒 dangling。把一个步骤拖进
   另一个阶段，它身上那几条「是 / 否」出边就留在了原阶段里——端点已不在那个阶段，下一次
   保存 422。而用户只是拖了一个框。
   （同一条理由的镜像在第二轮的 `dropDanglingEdges`：删节点时**连带**清边，就是为了不
   留这种边。拖动没有"删"这一步，所以只能从源头挡。）
2. **阶段次序是流程语义，不是排版。** `layoutFlow` 的阶段先后来自前序位次（`order`），
   而那个顺序是生成时按材料定的执行顺序。拖动改它，等于改**流程本身**。
3. **手势里读不出意图。** 把一条原因拖到另一根骨旁边，可能想说"换个归类"，也可能只是
   "这根骨太挤"。树里两种解释都通向同一个结构改动，这里不是——猜错的代价是一次静默的
   语义修改。

### `edges` 与 `problem` 的连带影响：查清了

| 问 | 答 |
| --- | --- |
| 拖动会让流程图的 edge 指空吗？ | **容器内的拖动不会**（端点仍在同一个 `stage.edges` 里）；**跨容器会**，所以跨容器被拒——这正是第 1 条理由的来源。 |
| 鱼骨有没有同样的悬空问题？ | **没有 `edges`**（鱼骨顶层只有 `relations`，且 `relations` 的端点是节点 id、不随容器变）。但鱼骨有**更硬**的一条：`FishboneBone.category` 是类别，换归类就是改这张图的骨架。 |
| 拖完 `problem`（鱼头那句论点）会变吗？ | **不会**。`problem` 是鱼头文字，与骨的内容无关；拖动只改骨内子树。 |
| 拖完之后布局跟着改吗？ | **跟着改**。`previewMove` / `moveNodeTo` 从 `layoutTidy` 换成 `layoutDiagram` 分派——上一轮硬编码树布局，用 tidy 去排一张鱼骨会让幽灵框落在主骨上方几十像素的空气里。 |

### 顺手修掉的两处（不修就是错的）

1. **拖动的方位换算改用"布局自己报的朝向"。** `MindMapCanvas` 原来读 `store.direction`
   （= `theme.direction`），但流程图恒为上下（`layoutFlow` 报 `down`）、鱼骨恒为主骨横贯
   （`layoutFishbone` 报 `right`）。用用户的朝向去翻译，会把整张表翻反：在鱼骨上把原因
   拖到左边（画面上那是**更深**的方向，子永远在父左侧）会被判成"我当它的父"。
   现在读 `store.layout?.direction`——树型下两者恒等，所以树一个字节都没变。
2. **容器根不拖。** `draggable` 的 gate 原来是 `depth > 0`。合成根让鱼骨与流程的容器根落在
   `depth === 1` 上，那条判据对它们是**放行**的，而拖走一根骨的根 = 换掉一个类别。现在
   按 `rootsOf` 显式排除（树的中心主题已经由 `depth === 0` 挡住，这里是双保险）。

## §三、旋转：A 已经在，B 不可行，C 不做

### ① 先查：`direction` 现在从哪来

```
content.layout === 'vertical'        → 'down'
content.theme.direction              → 'left' | 'both' | 缺省 'right'
     （换算全在一处：mindmap/direction.ts::directionOf / withDirection）
```

**它已经能被用户改**：`App.vue:1114` 的左上角四个按钮直接调 `store.setDirection()`，
而 `setDirection` 走 `applyContent` —— 一次可撤销、可保存的内容改动。所以**理解 A 不是
"要做的功能"，而是"已经有了的能力"**。

唯一的边界是这张表的两端：

- `layout: 'vertical'` → 画布上的"向下"；
- `theme.direction` 只有 `right / left / both` 三个值，**没有 `down`**——所以 `withDirection`
  在 `down` 时把 `theme.direction` 归到 `right`，靠 `layout` 表达"向下"。这不是冗余，
  是"`theme.direction` 只描述横向布局朝哪边"这条契约（`types.ts:402`）。

### ② A / B / C 的成本，与我的选择

| | 是什么 | 成本 | 判断 |
| --- | --- | --- | --- |
| **A** | 整棵树的朝向可切（right / left / down / both） | **0** | **已经是现状**。本轮只补一处诚实性（见下） |
| **B** | 每个子树独立朝向（ProjectGraph 那句"多层次不同方向"） | 换掉 `layoutTidy` 的**空间模型** | **不可行**（三条硬理由见 ③④） |
| **C** | 节点自身旋转（文字角度、矩形倾斜） | 低，但要为旋转后的包围盒与连线重算一套几何 | **不做**：它不改变结构，只让图更难读。`NODE_SIZE` 是布局与渲染共读的一份尺寸，倾斜之后 `bounds` / `fitView` / 可读性选档 / 悬停卡片 / 内联输入框全部要反向旋转——`layout/flow.ts::DECISION_SHAPE_NOTE` 第 2 条记的就是这条路被否掉的原因 |

**所以本轮"旋转"的代码交付只有一处**：`store.setDirection()` 对非树型直接拒绝并给一句
话。这是真 bug 的修复——原来对着流程图点「向左」，`withDirection` 会把 `theme.direction`
真的改成 `left`、`applyContent` 记一步撤销并置脏，而**画布一个像素都不动**。一次"点了
没反应、但内容被改了"的静默写入，比按钮灰着更糟。

### ③ 如果选 B，`layoutTidy` 要改哪几处（以及为什么改完还是不行）

四处，从内到外：

| 位置 | 现在 | B 需要 |
| --- | --- | --- |
| `subtreeExtent()` | 只返回**一个标量**：这棵子树在兄弟方向占多宽 | 返回 **2D 包围盒**（宽 × 高），因为朝下的子树在另一个轴上占位 |
| `place()` | `depth + Math.sign(depth) \|\| 1` —— 层级只沿**一条**轴单调走 | 每个节点自带一组方向基（`b̂, d̂`），子树的层级沿它自己的 `d̂` 走 |
| `both` 的 `placeGroup()` | `sign = ±1` 只沿 depth 轴**镜像** | depth 轴本身要能换成"向下"这一条轴，而不只是翻符号 |
| 最后一步 `point.d * (depthSize + depthGap)` | 抽象坐标 → 屏幕坐标是**一次单轴映射** | 每节点一次基变换 |

四处的共同点：这套算法从头到尾只有**一个**兄弟方向轴的概念（`breadth`），深度只是一个
标量乘出来的。B 要的是"每棵子树有自己的两维坐标系"，那不是改四处，是**换一个算法**。

### ④"每层不同方向"会不会重叠：会，而且是必然的

不用试坐标，两行就能证完：

设根有两个子 `A`、`B`。让 `A` 朝右长、`B` 朝下长。

- `A` 的子树占据 `x ∈ [0, W_A]`、`y ∈ [−h, h]`（`h` 是 A 自己的兄弟方向占位，只要 A 有
  一个兄弟就 `h > 0`）；
- `B` 的子树占据 `x ∈ [−w, w]`（`w > 0` 同理）、`y ∈ [0, H_B]`；
- 两者的交集包含 `[0, min(w, W_A)] × [0, min(h, H_B)]`，**非空**。

`A` 的"兄弟轴"正好是 `B` 的"层级轴"，反之亦然——两个矩形必然在拐角处相撞。要消掉它，
得按 2D 打包（带旋转的矩形装箱）重排，而那不是 `layoutTidy` 的变体，是另一类算法，
并且会让**几十条钉着逐像素坐标的用例**（`tidy.spec.ts` / `fit-all-baseline.spec.ts` /
`layout-dispatch.spec.ts` …）同时失效。

**唯一在数学上安全的"不同方向"是同一轴上的镜像**：一支朝右、一支朝左。因为那时所有
子树的 `d̂` 相同、`b̂` 只差一个符号，`subtreeExtent` 的单轴假设仍然成立。而这正是
`both` **已经做的**（`placeGroup(rightKids, +1)` / `placeGroup(leftKids, -1)`）。

所以 ProjectGraph 那句"多层次不同方向结构的树"在本项目的自动布局下，能兑现的上限就是
`both`：**根居中、各支分列两侧，且支内仍统一朝外**。

### ⑤ 还有一个契约层面的事实

B 需要一个"每个子树朝哪"的字段——**契约里没有，而且写不进去**：

- `backend/app/contracts/mindmap.py:478-479`：`Node` 是 `extra="forbid"`，往节点上加一个
  `spin` / `dir` 会直接 422；
- `Theme`（`:423-428`）只有 `preset / accent / font / direction`，`direction` 是
  `Literal["right", "left", "both"]`——它描述的是**整张图**。

要落地 B，必须先扩契约（后端 + schema 生成 + 迁移 + 导入导出 + 三条统计口径），而
`backend/*` 这一轮不在我的改动范围里。**这是 B 的第二条独立否决理由**：即便几何能改，
数据也无处安放。

## §四、自评：「节点可旋转」用户真正想要的是什么

判断：**他要的不是"节点转 45 度"，是"这张图能摆成我想要的样子"。**

三条证据，都在他自己的话里：

1. 他说的动词是**"旋转"**，而他参考的 ProjectGraph 原文说的是
   **"多层次不同方向结构的树"**——那是**布局**的语言，不是**图形变换**的语言。
2. 同一轮里他还要了"拖动节点决定父子关系"。这两件事的诉求是同一个：**按我的理解重排
   这张图**。旋转只是他能想到的、表达"重排"的那个词。
3. 他真的会看结果：上一轮那些"幽灵框与落点逐像素相等"的验收标准说明他要的是**摆对的
   图**，不是特效。

那么 A 或 B 够不够？

- **A（整棵树的朝向）够用一半。** 四种摆法（右 / 左 / 下 / 双向）覆盖了"换一种读法"这个
  需求，而且它**已经在了**——所以我这轮的结论不是"做了旋转"，而是"旋转里能做的那一档
  本来就有，我做的是把它说清、并把点了没反应的静默写入修掉"。
- **B（子树朝向）不够用的那一半，缺的那块不是"每支一个方向"，是"自由摆坐标"。**
  证据：`both` 已经允许"一支在左、一支在右"，而用户仍然觉得不够——他要的是"这一支再往
  下一点""这两支分开些"。那不是朝向问题，是**位置**问题。

### 缺的那一块，与"坐标唯一来源"这条铁律冲突到什么程度

**冲突到底，但它已经在契约里留好了位置。**

- `MindMapContent.layout` 的枚举里有 `'manual'`（`types.ts:400`，
  注释原文："用户拖拽后进入，pos 生效"）；
- `Node.pos` 是契约 v2 的透传字段（`types.ts:77`），至今**没有渲染层的读者**——这是
  第一轮刻意维持的性质（`docs/NODE-DRAG.md` §一 三条理由）。

所以"自由拖坐标"不是做不到，而是**一旦做，就要付这四笔账**（第一轮列过，这里换成从
`manual` 这一侧看）：

1. **`bounds` / `fitView` / `clipped` / `offscreen` 全要分叉出"手动"这一支**——它们现在
   都假设坐标可以从 `content` 算出来；
2. **可读性选档（`clarity.chooseViewMode`）与收起计数（`view-collapse`）失效**——那两个
   算法的输入是布局算出来的整齐网格，手动摆放的图没有"层宽"这个概念；
3. **拖动的手势语义要重新定义**：现在的四个方位 = 四种关系（父/子/前兄弟/后兄弟），而
   自由布局下同一个手势要说"放这儿"——两个语义不能共用一次拖动，所以要么加修饰键，
   要么把它做成两种模式；
4. **`layout: 'manual'` 一旦写进 content，就对所有读者生效**：导出（三种格式里的坐标）、
   导入校验、后端 `validate`、以及"换朝向"那条路径（手动布局下换朝向该做什么？）。

**我的建议**：那块单独一轮，且必须是"显式模式切换"（`layout: manual` 开关 + 一键回到
自动布局），而不是让拖动悄悄把图变成手动。理由和这一轮拒掉"跨容器拖动"是同一条：
**一次手势承担两种语义时，猜错的代价是静默的结构/内容变化。**
