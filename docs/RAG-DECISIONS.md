# RAG 与召回：一轮评估记录与取舍

> 记录 2026-11-10 至 11-11 这一轮针对「检索增强」的调研、实现与放弃。
> 数字分两类：**实测**（本仓库真机跑的，带样本与命令口径）与**引用**（开源项目或论文的公开实验，附出处）。
> 目的是让"为什么不做某件事"有据可查，避免半年后重新调研一遍。

## 一句话结论

**切块与混合检索已经落地；agentic 召回（改写 / 多轮 / 充分性判断 / HyDE）实测在我们的语料条件下发散，不做。**
下一步是**结构引导的召回**：多源进 `Source`，按导图一级分支分别检索，每支带自己的证据生成、引用按支回填。

---

## 1 已经落地的两件事

### 1.1 递归切块（`knowledge/service.py`）

原来是「按码点定长 300、无重叠、无边界感知」。同一个文档两次解析可能得到不同块边界，检索回来的片段读起来是半句话。

现在是五级降级：

| 优先级 | 分隔符 | 存在的理由 |
|---|---|---|
| 1 | 结构标题行首（`#`、`第N章`、`一、`、`（一）`、`1.1`） | 作者划的章节边界，比任何算法猜的准 |
| 2 | 空行 `\n\s*\n` | 真段落边界 |
| 3 | 句末标点（`。！？；…`，含闭引号；英文 `.!?` 需后跟空白且前非数字） | 句子边界 |
| 4 | 单换行 `\n` | 列表项、表格行；PDF 提取文本里它是**版面折行**，所以排在句末之后 |
| 5 | 次级标点 `：，、` | 长句退让 |

三条安全规则：成对引号/括号/书名号内部不切、URL/数字串/ASCII 单词内部不切（差分数组一次标完，O(n)）、切点落点不安全时向两侧回退。

参数：`TARGET=450 / MAX=700 / MIN=150 / OVERLAP=100`。重叠起点吸附到**句首**而非定长回退；吸附不到就不重叠，绝不从半句中间起步。

> `TARGET` 真正生效靠的是"先在 `[TARGET,MAX]` 取最靠前、再退 `[MIN,TARGET)` 取最靠后"——只写"取最靠后"会让每块都贴着 `MAX`，`TARGET` 变成一句空话（第一版就是这么错的）。

### 1.2 混合检索（`knowledge/embedding.py`、`vector_cache.py`、`service.py`）

- **BM25**：中文 bigram / 英文按词切，`k1=1.2`、`b=0.75`，IDF 与长度归一化都算。替换了原来的「交集/查询词数」——那个指标既无 IDF 也不做长度归一化，长块白吃亏。
- **向量**：`text-embedding-v3`（1024 维），走阿里云 MaaS 的工作空间级 OpenAI 兼容端点。双协议客户端：`openai`（默认）/ `dashscope` 原生。
- **融合**：RRF，`k=60`，两路各取 `top_k*3` 候选再融合。不做分数归一化，因为两路的分数不可比。
- **缓存**：按 `sha256(quote)` 存 SQLite，跨请求复用（`Source.id` 每次是新的 uuid4，按 id 缓存等于不缓存）。float32 小端，20 万行上限。
- **降级**：判据是「向量路是否真的贡献了候选」，不是「有没有 key」。无 key / 无 base / 超时 / 5xx / 向量全零，全部自动落到纯 BM25，`method` 逐条标注 `lexical` / `hybrid`。

`EvidenceHit` 新增三个带默认值的字段：`score_bm25`、`score_vector`、`method`。`search_sources` 签名不变。

## 2 实测数据

### 2.1 切块：四份真实材料的对照

| 材料 | 字符 | 块数 | avg | 真硬切 | 块尾句末率 | 主要切点来源 |
|---|---|---|---|---|---|---|
| arXiv 1706.03762（英文 PDF） | 39511 | 84 | 532.5 | 0 | 78.6% | 句末标点 60.2% |
| 中文 docx①（思维导图申报书） | 8374 | 17 | 537.6 | 0 | 47.1% | 空行 |
| 中文 docx②（含 C++ 代码） | 12227 | 30 | 486.4 | 0 | 16.7% | 空行 27/29 |
| 中文 docx③（项目申报书） | 5667 | 13 | 489.0 | 0 | 76.9% | 空行 |
| 扫描件 PDF | 0 | — | — | — | — | `NotSupportedSource` 在提取层拦截 |

三件事值得记：

**改分隔符顺序的效果**：把句末标点提到单换行之前，英文 PDF 的块尾句末率从 **20% → 79.5%**，块尾样本从 `'the Transformer,\n'` 变成 `'for over 2 BLEU. '`。原因是 PDF 提取文本几乎每行一个 `\n`，那是版面折行不是句子边界。

**中文 L4 占比低不是缺陷**：Docling 每段之间输出 `\n\n`，而空行（L2）优先于句末标点（L3）是正确的——段落边界比句子边界更强。中文切点 75%–93% 来自结构层，这是设计意图。

**硬切的真实数量是 0**。四份材料的 `_hard_cut` 触发次数全为 0，窗口命中率 100%。所谓"无标点长段只能硬切"在这批材料上没有发生。

### 2.2 混合检索：两个查询的对照

同一批块、同一份材料，只切换 `MINDMAP_HYBRID_SEARCH`：

| 查询 | 纯 BM25 | hybrid | 向量余弦 |
|---|---|---|---|
| 「预算审批流程」 | 5 条 | 5 条 | 0.798 |
| 「谁能批钱」 | **0 条** | **5 条** | 0.533 |
| 「出差花销怎么报」 | **0 条** | **5 条** | 0.620 |

「谁能批钱」与原文的「审批权限」「财务经理核准」一个字都不重合，BM25 是零召回——这是词面检索的结构性盲区，不是调参能补的。

延迟：embedding 单次往返 1.3 秒（冷），检索本身（BM25 + 1024 维余弦）毫秒级。缓存命中后第二次查询 0 次 HTTP。

### 2.3 多轮判断：发散（负结果，重要）

用真实 LLM 做判断器（qwen-plus）与改写器，跑「检索 → 判断是否充分 → 改写 → 再检索」的循环。3 组材料 × 3 个变体：

| 材料 | 无上限（20 轮封顶） | 上限 3 轮 | 上限 + 无进展检测 |
|---|---|---|---|
| 有答案 | 第 1 轮收敛 | 同左 | 同左 |
| **完全无关** | **跑满 20 轮**，5483 tok，48.9s | 3 轮，605 tok | 第 2 轮触发（重合 1.0），284 tok |
| **部分相关** | **跑满 20 轮**，3775 tok，37.9s | 3 轮，495 tok | 第 2 轮触发，241 tok |

合计 127 次 LLM 调用、75 次检索，其中 17 个轮次是纯浪费。

三条机制叠加导致发散：

1. **判断器不是噪声源，是系统性失效**。同一 query 跑 3 次（temperature=0）、再跑 3 次（默认温度），6 次全部 `INSUFFICIENT`，输出只有一种。投票救不回来——它不是在犹豫，是确定地在说"这些片段不足以回答"，而这正是循环继续的唯一燃料。
2. **改写器完全不看材料**。材料是预算审批，它把 query 改成引入 `T₁/T₂*`、DOI/arXiv、超导/离子阱；另一组引入《中央企业合规管理办法》。与材料的 2-gram 覆盖率**恒为 0.0**。
3. **混合检索让"召回为空"这个止损信号失效**。hybrid 下召回恒非空（余弦总有正值）→ 纯规则版判断器会跑满 20 轮，比 LLM 判断器更糟；而纯 BM25 下虽然第 1 轮就停，但「谁能批钱」在 BM25 上 `score_bm25=0.0`，会把有答案的材料判成"没找到"。

最直观的两个证据：

- 关掉判断器只跑改写循环，5 轮内问题从「谁能批钱」漂到「中国个人住房贷款审批流程…银保监会/国家金融监督管理总局」，与材料的覆盖率从 0.0769 降到 0.0286。
- 另一组跑到第 11–20 轮，改写结果退化成**两句逐字交替、长度锁死 65 字符**，检索结果一个字节没变。

如果将来真要开多轮，最小硬约束是：`MAX_ROUNDS=2`（20→2 轮省 95% token、97% 耗时，答案质量无差）、无进展判据用「新增区间数 = 0」而非重合率阈值、改写器必须喂材料上下文、`rewrite()` 挪到 `MAX` 判定之后（实测 1/3 的改写调用从未被检索使用）、单次 3000 prompt token 硬顶。

## 3 评估后决定不做的

| 方案 | 结论 | 依据 |
|---|---|---|
| agentic 召回（改写 / 多轮 / 充分性判断） | **不做** | 本仓库实测发散（见 2.3）；RAGFlow 注释：「Sufficiency asks whether the passage alone settles the question, which no answer-blind judge can decide」 |
| 逐段相关性过滤（relevance grader） | **不做** | RAGFlow 实测：全量 gate 比关闭过滤 **token +48.7%**（被丢的段落会被重新读回来），且"仍然丢了大部分金标准证据"；其本地蒸馏 head precision 0.62 / recall 0.36 |
| HyDE | **不做** | +800ms（四方案里延迟最高），收益 +2~8 点；而向量检索本身已在桥接语义鸿沟，边际收益被抵消大半 |
| 语义切块 | **不做** | 词面检索下收益≈0（bigram 不看话题自洽性），且需要每句一次 embedding、阈值随语料漂移 |
| 父子切块 | **已实现、默认关、未接入**（`search_parent` + `MINDMAP_PARENT_RETRIEVAL=0`） | 当前的顾虑是父子切块会让引用链失真：`score` 来自 200 字的子块，`quote` 却是 450–700 字的父块，模型从父块里挑一句与查询无关的话也照样通过逐字校验，`verify_source_refs` 就从「证据核验」退化成「格式检查」。所以默认关；等库落地、且引用校验支持子块区间（`EvidenceSpan.leaf_start/leaf_end` 已就位，调用点待接）后再评估 |
| 子问题分解引擎 | **不做** | 每个子问题跑完整流水线（含各自合成调用）；我们的 agent 循环本就能多轮调 `rag_query`，缺的只是"一次带多 query" |
| 全局 top-k 塞 prompt | **不做** | 大材料下会被"反复出现关键词的模板段落"占满，且证据归属不清 |

### 一条容易误用的证据

「全塞入 vs 切片检索」那组一手实测（64 份文档全塞进上下文 **93 分**，切成 1583 段做检索 top5 只有 **59 分**）**只适用于定位型检索**——材料里已有答案、检索帮模型找到它。它是我们"材料整份进 prompt"这个形态的支持证据，不能拿去反对"扩展型"检索（材料里没有、靠搜索补）。

## 4 三种检索形态，别混着谈

这一轮讨论里最容易出错的地方是把三件事当成一件：

| 形态 | 检索的角色 | 我们的结论 |
|---|---|---|
| **定位型** | 材料里已有答案，检索帮模型找到那一段、给出引用偏移 | 收益低，模型自己也能扫全文；全塞入反而更好 |
| **扩展型** | 材料里没有的东西，靠搜索/知识库补进来 | **这才是该做的**，对应申报书 3.3.1 与"知识准确性" |
| **循环型** | 由模型判断"够不够"，不够就改写重查 | 实测发散，不做 |

我们已有的 `rag_query` 是定位型；申报书 3.3.1（"输入碳中和，自动关联政策、技术路径、企业案例"）要的是扩展型；2.3 那个实验证伪的是循环型。

## 5 下一步：结构引导的召回

**思路**：不检索 top-k 塞给模型，而是**按导图的一级分支分别检索**，每支的证据跟着那支的生成走。

```
输入（材料 / 主题）
  → 有材料转 Source；没材料先搜索，网页也转 Source（kind=web，带 url 与 retrieved_at）
  → 递归切块 + 向量缓存
  → 骨架生成：N 个一级分支（已有能力）
  → 每支一次检索：query = 主题 + 分支标题 → 混合检索 → top-3 证据
  → 每支并行展开：证据 + 分支 → 子节点 + source_refs（逐字校验）
  → 确定性验收 → 候选 → 用户确认
```

**为什么是它**：检索次数由结构决定（8 个分支就是 8 次），不由模型临场判断——没有"该不该停"这个问题需要回答，因为它天然有界。而且它复用了 90% 的已有代码：切块、混合检索、骨架、层内并发、引用校验全都在。

**要改的三处**：

1. 放开 `build_registry` 的 `discard("mindmap_generate_deep")`（现在有来源时禁用 deep，因为它不读来源）
2. `expand_branch` 前插一次检索：拼 query → `search_sources` → top-3 进那次展开调用的 prompt；检索不到就如实留空并记诊断
3. 引用按支回填：某支的节点只能引用该支检索给它的证据

**唯一的不确定点**：骨架给的分支标题较短（"监督学习"），直接当 query 可能召回泛。解法是让骨架调用顺带为每支输出一组检索关键词（同一个响应里多一个字段，零额外调用），但先用分支标题实测，看够不够。

**多源（扩展型）的四个设计点**：`SourceKind` 加 `web` 与 `url` / `title` / `retrieved_at`；提示词分区（用户材料必须忠实整理，检索资料只作补充且以材料为准）；引用标注来源类型（界面显示"网页标题 + 链接"）；可信度启发式分级（官方/学术 vs 博客/论坛，低可信只作线索）。

三条风险：搜索内容要独立设量（最多 30% 预算，否则挤掉用户材料）、`retrieved_at` 必记（否则三个月后用户以为是现行）、**冲突时不能替用户选**（材料说 A、网上说 B，两个都呈现并标注冲突）。

## 7 未验证与已知限制

- MaaS 网关的批量上限（25 条是按 DashScope 文档取的，实测只验过 3 条）
- `429` 未纳入重试（只重试 5xx + 超时），真机撞限流会直接降级
- 20 万行向量表时 `COUNT(*)` 的耗时与磁盘占用
- 并发进程同写一个 SQLite 的锁争用
- **混合检索是否比纯 BM25 更准，尚无真机对照**——已证明的是"零召回时能捞回"，排序质量还没有数据

## 8 图存储选型：Neo4j 还是 SQLite

原先的判断是「2C2G 装不下 Neo4j——JVM 堆起步就 1G+」。**实测推翻了这个说法**，但结论（用 SQLite）不变，理由是换掉的。

### 实测（Neo4j Community 5.26.14，Windows，Job Object 限 commit 模拟 cgroup）

| 配置 | 硬限 | 启动 | 常驻 | 两跳中位 |
|---|---|---|---|---|
| heap 1g / pagecache 512m | 无 | ✅ 11.3s | 1272 MB | 54 ms |
| heap 512m / pagecache 512m | 无 | ✅ 15.3s | 750 MB | 38 ms |
| **heap 256m / pagecache 256m** | 无 | ✅ 13.3s | **488 MB** | 42 ms |
| heap 256m | **1G** | ✅ 13.7s | 245 MB | 64 ms |
| heap 1g | **1G** | ❌ 启动即死 | — | — |

最后一行是唯一的失败：`-Xms1g` 配上默认的 `AlwaysPreTouch`，启动瞬间提交整堆，1G 限额必死（`页面文件太小 errno 1455`，正好 1 GiB）。

**所以 2C2G 跑得起来。** 256m 堆常驻约 490MB，2G 总账：OS 200~300 + Neo4j 490~530 + Python 后端 600~1000 + nginx 20 = 1.31~1.85 GB，余量 400~600 MB。共存实测也过了（Neo4j 234MB + Python 900MB 在 2G 内，查询仍正常）。

但 512m 堆（约 750MB）就顶到边缘，1g 堆（约 1280MB）没戏。

### 为什么仍然用 SQLite

不是装不下，是**不划算**：

| 同数据同语义（1000 实体 / 3000 边，两跳） | 两跳中位 | 进程内存 |
|---|---|---|
| SQLite 双向邻接 + `MULTI-INDEX OR` | **0.05 ms** | 19.6 MB |
| Neo4j 5.26（纯执行，已扣协议基线 3.8~7.0ms） | 8.5 ms | 488 MB |

差 100~340 倍与 25 倍。原因是这个负载的形状：**两跳邻域浅路径正好落在关系库索引 join 的最优区，同时落在图库路径语义的最差区**。Neo4j 为多跳与变长路径优化，而我们的查询是"从某个实体出发走两步看有哪些邻居"——SQL 的索引查找本来就够。

外加两条代价：10 万边灌入后 store 只有 1MB、**事务日志 136MB**（10G 磁盘的下限主要喂它）；`AlwaysPreTouch` 让小内存机器上"堆配了却拿不到"（1.5G 限额配 1g 堆，Private 只有 400MB）。

### 两边都撞到的同一个陷阱

用 `UNION ALL` 邻接视图再 join 的写法很自然，但会让 SQLite 丢掉索引下推——`EXPLAIN QUERY PLAN` 变成两次 `SCAN graph_edges`。实测 100k/300k 规模下天真写法 **9317ms**，换 `MULTI-INDEX OR`（`src_id = ? OR dst_id = ?`）后 **0.08ms**。

**别拿天真写法的耗时当作"SQL 不适合图"的证据**——那测的是写法，不是引擎。本仓库这两位实现者独立踩到并各自绕开，结论一致。

### 如果真要上 Neo4j

最小可行配置：heap 256m / pagecache 128~256m / tx 128m，冷启动 13~16 秒，常驻约 490MB。代价是吃掉一半内存却换不来查询性能，且事务日志持续增长。

### 测量局限

Windows 没有 cgroup，Job Object 限的是 commit 不是物理页；JVM 的默认 auto 读宿主 15.7GB 而非 2GB，所以「MaxRAM=2g」那一组才是 2G 机器的真实代表。Linux 上 RSS 会更接近 Private 列。CPU 侧（2 vCPU）未测。

## 9 图数据库落地时踩到的三件事

第 8 节是选型时的实测对比（当时的结论是 SQLite 更划算）。这一节是**换掉之后**才知道的事——上游后来决定用 Neo4j，`knowledge/graph_store.py` 从 SQLite 重写为 Cypher。三个坑各花了一次排查，共同点是**症状离根因很远**：报错的地方不是写错的地方。

### 9.1 `CREATE CONSTRAINT` 不能与数据写同事务

**症状**：建图的第一句就炸，`ForbiddenDueToTransactionType`，消息是 `Tried to execute Write query after executing Schema modification`。看着像权限问题，但账号有全部权限。

**根因**：Neo4j 把语句分成四类（read / write / schema modification / administration），**同一事务里不允许混**。`CREATE CONSTRAINT ... IF NOT EXISTS` 是 schema modification，哪怕它什么都没改；跟在后面的 `MERGE` 是 write，两条一撞就报错。SQLite 那边 `CREATE TABLE IF NOT EXISTS` 与 `INSERT` 同连接同事务是合法的，所以这个直觉是从上一版移植过来的——正是它错的地方。

**处理**：约束走独立事务（`driver.execute_query`），不挂在任何写事务里；失败只记 warning 不抛。约束是"并发下的加固"，不是"能不能用"的前提——单线程的 `MERGE` 没有约束也幂等，而"一次建不上就整层不可用"是更差的交换。

### 9.2 driver 6.x 的 `ServiceUnavailable` 不在 `Neo4jError` 树下

**症状**："连不上 7687"，但降级分支没接住，异常一路抛到接口层——而同一段代码在 driver 5 上是好的。

**根因**：6.0 把异常树重排成 `GqlError` → (`DriverError` | `Neo4jError`)，而 `ServiceUnavailable`（连接失败、认证失败、连接池耗尽）挂在 `DriverError` 那一支。5.x 里 `DriverError` 是 `Neo4jError` 的子类，所以 `except Neo4jError` 兜得住；6.x 里两者是兄弟，只捕获 `Neo4jError` 会漏掉最常发生的那一类。

**处理**：捕获 `(Neo4jError, DriverError, OSError)`。两个名字一起写还有个好处：driver 5.x 里这套写法同样成立，`requirements.txt` 的 `neo4j>=5.14,<7` 才有意义。测试里有一条指向 1 号端口（连接被拒，立即失败）的用例专门钉这条路径：读接口返回空、写接口抛 `GraphStoreError`。

### 9.3 `id()` 弃用与 `elementId()` 的类型冲突

**症状**：日志被 WARNING 刷爆——每写一个实体一条 `id is deprecated and will be removed without a replacement`，一次入库上千个实体就是上千条，把真正要看的东西埋掉。

**根因**：Neo4j 5.26 起 `id()` 被弃用，推荐 `elementId()`，但后者返回**字符串**（`4:66399144-...:4100`），而 `upsert_entity` 的返回类型是 `int`（对着 SQLite 版的自增主键）。换掉就是改接口，而接口在这轮里是硬约束：调用方拿它做"两次 upsert 是不是同一个节点"的比较。

**处理**：保留 `id()`，在 driver 上**只关这一类通知**（`notifications_disabled_classifications=["DEPRECATION"]`），不整体关——别的通知（性能警告之类）还有价值。这条写进了 `_driver()` 的注释，因为下一个看见 `id()` 的人第一反应会是"为什么不用 elementId"。

> 顺带一个必须知道的差异：**Neo4j 的内部 id 会被复用**（节点删掉之后新节点可能拿到同一个 id），SQLite 的 `AUTOINCREMENT` 不会。所以这个返回值只能当"这次是不是同一个节点"的比较键，不能持久化、不能跨重建假设不变。

### 9.4 附带：`failed` 的语义没变，代价变了

这一条不是 bug，是图库与嵌入式库在失败路径上的本质差别，但它决定了编排层要不要加熔断。

换引擎时为了让 `graph_ingest` 原有的 `except (sqlite3.Error, OSError, ValueError)` 原样接住，`GraphStoreError` 被做成 **`OSError` 的子类**。这不是"异常类该继承谁"的风格问题：`failed` 的语义（"这一块没写进去"）与块级原子性都保持不变，一块坏掉只丢那一块。

（那一层后来收敛成了 `except (GraphStoreError, ValueError)`，`sqlite3.Error` 那条死分支删掉了。`OSError` 的继承留着：它本来就准确，而且按 `except OSError` 兜底的调用方不会因为换引擎而失守。）

变的是**失败一次要付多少钱**。SQLite 库不可写是毫秒级失败——它就是一次函数返回；Neo4j 连不上要付连接超时 + 重试（默认各 3 秒），20 块就是两分钟，而调用方（上传接口）在那里等着。

所以后来给 `graph_ingest` 加了熔断，并按失败类型分开：

| 失败类型 | 处理 | 理由 |
|---|---|---|
| `GraphStoreNotConfigured`（没配密码） | **第 1 块就停** | 配置错误不是偶发抖动，等 3 块只是多花两次 LLM 调用 |
| 其余 `GraphStoreError` | 连续 3 块停 | 偶发一次不该让整份材料作废，连续三次说明引擎确实不在了 |
| `ValueError`（区间倒置、空名） | 只算这一块 | 一块数据坏不代表引擎坏了；熔断它等于让一条坏数据终止整份材料 |

统计里加 `aborted` 而不是把 `failed` 数字改大：调用方要能分清"跑完了但有 3 块失败"与"停在第 3 块、后面 17 块没试过"。成本闸（`max_chunks`）造成的截断**不**置 `aborted`——那是配置好的行为，不是故障。


## 10 分支查询扩展：实测零收益

分片生成时把每个分支标题扩成 2–3 个同义问法再检索（`plan_branches`，一次 LLM 调用处理所有分支），每支用 `search_multi` 多路融合。同一材料（12,392 字 / 52 段 / 8 支 / 纯 BM25 / scripted provider）：

| 组 | 每支 query | 覆盖率 | 并集段落 | 检索 调用/查询 |
|---|---|---|---|---|
| A 今天（`search_parent` 单路） | 1 | **28.8%** | 13/52 | 8 / 8 |
| B0 只有标题走 `search_multi`（基准） | 1 | 23.1% | 12/52 | 8 / 8 |
| B 标题 + 2 同义问法 | 3 | **23.1%** | **12/52** | 8 / 24 |
| C 标题 + 2 真实小节名（上界） | 3 | 25.0% | 13/52 | 8 / 24 |

两个必须分开看的效应：

**A→B0 是粒度效应，-5.7 点。** 多路走单级块（450–700 字匹配），单路走子块匹配 + 父块返回。把扩展接进分片检索，这一项要先付。

**B0→B 是扩展效应，净 0。** 新增 2 块同时挤出 2 块，段落并集一动不动。

原因是机制性的：同义问法与标题共享同一批 bigram（"结论是什么" vs "一句话结论"），多路只在**同一批块**上重复投票——累加分只抬高票数、不改变排序；而 `search_multi` 在 `top_k=3` 时保底席位 `reserve=2`，扩展路最多抢 1 席。

C 组（问法直接取材料自己的小节名）也只多 1 段，堵住了"是不是扩展得不够准"这个辩解：**瓶颈在融合结构与 `top_k=3`，不在改写质量**。

所以开关保持默认 `0`。这个能力要真正值钱，前提有两个：给 `search_multi` 一条父块返回路径（补回那 -5.7 点），以及接上向量路——同义问法的价值本来在语义桥接，而本组是纯 BM25，**结论不能外推到 hybrid**。

## 11 Graph RAG 的接入方案（已设计，未实施）

### 两个前置条件，都还没做

**来源身份跨请求**：图的每条边存的是入库时的 `source_id`，而 `Source.id` 每次请求现生成 `uuid4`，检索时对不上。需要 `content_hash`（目前是空占位，没有写入方）或持久 id。

**版本一致性**：重复入库不会更新已有边的 `chunk_end`。材料重新解析后文本可能变（换解析器、改清洗规则），旧边指向的偏移就失效了——那时图会指向一段错的原文位置，逐字校验能通过（区间里确实有字），但那段与边代表的语义关系已经无关。

### 方案：按块交付，路径只作召回依据

1. 新增 `search_graph` 与 `fuse_hits`，在 `search_parent` / `search_multi` 之后、空结果判断之前融合。存储层不改，`_fuse` 仍只处理词法/向量评分。
2. 展开 `GraphPath.evidence`，按 `(source_id, start, end)` 去重；只接受本次过滤后的来源与合法区间；`quote` 严格取原文码点切片。**每块一条 `EvidenceHit`，禁止拼接引文、禁止取区间包络**。
3. 图路按最短跳数稳定排名，同块只投一票；扩大候选池后用名次 RRF 融合，**文本路前几名保底占半数席位**——否则图证据会把文本证据挤掉。
4. 路径与方向留内部旁表，不塞进 `quote`。图独有命中的 `score_bm25` / `score_vector` 为 `None`，`method` 沿用 `lexical`。

### 代价

模型失去显式链路与方向；截断可能拆散一条路径；`method` 表达不了"这条来自图"；逐字校验只证明块级对齐，不证明多跳推理。
