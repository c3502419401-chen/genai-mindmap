# 生成之后的核对：一次搜索能核对到什么程度

> 2026-11-22，本机（Windows / Python 3.13 / DeepSeek `deepseek-chat` + DeepSeek Search）。
> 复现：
> `cd backend ; python scripts/measure_verify_states.py --strict`（第 1、2、5 节）；
> `python scripts/measure_fulltext_retrieval.py`（第 3 节）。
> 结论先行：**"整树一次搜索"这个便宜版本判出来的 supported **精度**够（94.3% 真被
> 支持），**召回**远远不够（17.5%），而且分布极不均匀——10 张图里 6 张一个 supported
> 都没有。所以它只能当"标注 + 挂引用"，不能当"删掉没依据的节点"的依据。**

---

## 0 一句话结论

| 问题 | 答案 |
|---|---|
| 这一步补的是哪一环 | **"整棵树写完之后没有任何一步回头看它是不是真的"**。材料那条路有逐字校验，但它管的是"引文出处在不在原文里"，不是"这个节点对不对"；纯主题那条路两者都没有 |
| 整树一次搜索够用吗 | **精度够、召回不够**。判 supported 的 227 条里，第二次严格复核 214 条（94.3%）"这段引文本身就在说这件事"；但 1299 个节点里只有 227 个（17.5%）被判 supported，而且 6/10 张图是 0 |
| 那它能做什么 | 给节点打三态、给 supported 的挂逐字引用、把 contradicted 标出来给用户看 |
| 它不能做什么 | **不能用来删节点**。82.5% 的 unverified 里混着"小众但正确"与"模型编的"，这两件事在"搜不到"这个结果上长得一模一样 |
| 下一步该上逐节点搜索吗 | 本节的数字**不支持**这个结论，也**不否定**它（见第 6 节：一次搜索的失败面主要是"文章本身不对题"，逐节点搜同一批文章救不了召回） |

## 1 先量：真图上的三态分布（10 张 / 1299 个节点）

三条读数，每条都改变结论的用法：

1. **contradicted 恒为 0，而且这不是"树上没有错"的证据。** 判据是"文章说的与节点相反"，
   而 4 篇正文里出现"与某个节点正面相反"的概率本来就低。这个 0 只说明**这一档在
   整树一次搜索里几乎不会被触发**，不能用来向用户承诺"这棵树没有矛盾"。
2. **分布极不均匀：3 张图承载 98% 的 supported**（138 + 75 + 10 = 223 / 227）。0 的
   那 6 张图不是"树更假"——「检索与召回的取舍」「多智能体思维导图系统的架构与取舍」
   是用户自己的项目，网上本来就没有；「刑法」这次回的四篇是高校教务与法学院的
   **课程大纲页**，也不是"这个词条是什么"。**这就是整树一次搜索的主要失败面：
   检索回来的 4 篇不对题，与树上写得好不好无关。**
3. **引文逐字率 95.2%，剩下 11 条里 9 条的"开头 12 字"在正文里**——那不是凭空编的，
   是改写/拼接（实测例：标签「点积结果越大说明查询与键越匹配」，引文写成
   「分数越大，表明第 i 个位置与第 j 个位置的语义相关性越强」——意思对，字不对）。
   只有 2 条完全找不到出处。所以"逐字校验"这道闸必须留着：11 条里 9 条会被它拦下来，
   而这 9 条如果挂上去，就是 9 条**点开对不上的引用**。

## 2 一次搜索拼的 query 长什么样

规则（`optimization/verify.py::build_query`）：**标题在前**、一级分支名去重（跳过
"已经在串里"的）、满了就停在词边界（`external.QUERY_MAX_CHARS = 50`）。真实五条：

```
机器学习的主要方向 定义与领域关系（改） 理论基础（改） 分类体系（改） 模型与方法（改）
注意力机制的核心思想 从信息过载到选择性关注 查询、键与值的三元结构 相似度打分与权重分配
检索与召回的取舍 目标与边界 技术选型与依据 已落地与实测 图存储与踩坑 后续方向与限制
刑法 犯罪构成与排除事由 共同犯罪与罪数形态 刑罚种类与量刑制度 分则罪名与法益保护
多智能体思维导图系统的架构与取舍（两段式·图谱） 后端可调用 agent 循环
```

第 4 条是 50 字截断后的样子（原文还有「分则罪名与法益保护」之后的几条被切掉）；
第 5 条是**只有一条分支进来**的那种——标题自己就吃掉 40 字。这两条都指向同一个
已知缺陷：**50 字里标题与分支抢预算，标题越长，分支提供的信息越少**。没有更好的
替代（把分支放前面实测搜回来的是"怎么写方案"而不是"这个主题是什么"），所以这里
保持现状并把它写下来。

## 3 "全塞不检索"：成立，但只成立在第二步

用户那句话是「全塞的话不用检索了直接大模型依据全文总结就行」。`scripts/measure_fulltext_retrieval.py`
用计数替身包住三条检索路径（按支检索 / 按节点章内检索 / 兜底整树检索），跑三格。
同一份正文，925 字（无标题）与 973 字（加了 4 个 `##` 标题行，段落逐字相同）：

| 格 | 闸门 | 材料 | 章节 | 按支检索 | `search_parent` | 章内检索 | 合计 | `retrieval.mode` |
|---|---|---|---|---|---|---|---|---|
| A | 全塞 | 925 字 | 无 | **0** | 0 | 0 | **0 次** | `full` |
| B | 全塞 | 973 字 | 有 | **0** | 0 | **71** | **72 次** | `full` |
| C | 按支 | 973 字 | 有 | 1 | 4 | 71 | 77 次 | `branch` |

两条结论，第二条是对原始假设的一处纠正：

1. **A 格 0 次**——全塞时按支检索整段跳过，一次 `search_parent` 都不发。代码上它就是
   那道 `if sources and not full_text:`（`tools.py` 第二步），而这条不是"条件没满足"，
   是**刻意跳过**：正文已经整份在 prompt 里，检索的召回上限（由分支标题命中原文决定）
   不再是瓶颈。这条已经写进那段注释（★ 那一行）。
2. **B 格 72 次：全塞 ≠ 全程零检索**。第三段那条"每个节点在它自己那一章里检索"
   （`MINDMAP_DETAIL_RETRIEVAL`）的前置条件是 `chapters`，而**一份带标题的小 markdown
   会让"全塞"与"按章切"同时成立**——原始假设里"全塞路径不满足 `chapters`"只在
   多份材料（按章切要求恰好一份）或材料抽不出目录时成立。所以准确的说法是：
   **全塞跳过的是"按支检索"这一条；第三段查不查，取决于材料有没有章节、以及那个
   开关。** B 与 C 的差（0+71 vs 1+4+71）才是"全塞省下的那部分"。
3. **成本替换值得点明**：按支检索那部分省下来的钱（每支一次检索 + 向量往返）正好
   付给新加的核对搜索（一次搜索 + 一次判定，实测检索 1.15 秒、判定 6.7 秒/80 节点）。
   这是这一步在成本上唯一站得住的理由——**同一笔钱从"召回材料"换成"核对这棵树"**。

## 4 落了什么代码

```
backend/app/optimization/verify.py     判据与执行（query / 判定 / 定位 / 挂引用）
backend/app/agent/tools.py             _generate 收尾那一步（开关默认关）
backend/scripts/measure_verify_states.py        第 1、2、5 节那张表
backend/scripts/measure_fulltext_retrieval.py   第 3 节那张表
backend/tests/test_verify_states.py    29 条（判据 / 定位 / 挂引用 / 键集不变）
```

**开关**：`MINDMAP_VERIFY_AFTER_GENERATE`，默认关。关着时 `data` 的键集与加这一段之前
逐字节相同（`test_switch_off_keeps_the_data_keyset` 钉着）——它要额外一次外网往返与
一次模型调用，默认值不该替用户决定这两笔。

**三态只进 `data`，不进 `Node`**：`Node` 是 `extra="forbid"`，加字段要重导
`openapi.json` 与 `schema.d.ts`；而"哪个节点是 supported"本来就是一次运行的读数，
不是这棵树的一部分。形状：

```python
data["verify"] = {
    "query": "机器学习的主要方向 定义与历史 …",
    "states": {"supported": 15, "unverified": 65, "contradicted": 0},
    "judged": 80, "articles": 4, "invalid": 0, "skipped": "",
    "attached_refs": 5, "dropped_refs": 0, "calls": 2,
    "search_seconds": 1.147, "seconds": 6.695,
    "nodes": {"<node_id>": {"state": "supported", "quote": "…", "article": 1}, …},
}
```

**三种状态的处置**（`attach_refs` + `_drop_unverifiable_refs`）：

| 状态 | 处置 |
|---|---|
| `supported` | 留下并挂引用。`quote` 是**原文切片**（`locate_quote` 定位后取 `text[start:end]`），不是模型抄的那版——后者换行被替换过，`verify_source_refs` 会判它不是原文 |
| `unverified` | **保留**，标 unverified，不删 |
| `contradicted` | 保留，标 conflict，让用户看 |

挂上去之后还要过一遍 `verify_source_refs`（`_drop_unverifiable_refs`），不合格的摘掉并
记进 `dropped_refs`：判据用现成的那一份实现，不另写。**只校验这一步亲手挂的引用**
（`report.attached_nodes`）——把树上原有的引用一起塞进去，会用一个新步骤去改一棵已经
被校验过的树，实测这么写一跑真图就 `ValidationError`（探针里 58 条引用超过
`Node.children` 上限，顺手也修成按 50 条一批）。

**抽检（真模型，`机器学习的主要方向`，80 节点）**：

| 节点 | 判定 | 引文（截断） |
|---|---|---|
| 机器学习的主要方向 | supported | 機器學習是一門多領域交叉學科，涉及概率論、統計學、逼近論、凸分析… |
| 人工智能分支视角 | supported | (1)机器学习是一门人工智能的科学,该领域的主要研究对象是人工智能… |
| 机器学习的多种定义 | supported | 机器学习有下面几种定义：……（这一条是**段落引子**，勉强算"在说这件事"） |
| 经验自动改进视角 | supported | (2)机器学习是对能通过经验自动改进的计算机算法的研究。 |
| 定义与历史（分组节点） | unverified | —（分组是分类名，本来就不该有依据） |

## 5 自评：判 supported 的那些，是**真被支持**还是**只是主题相关**？

这两件事差别很大，所以单独测了一次：把每条（节点, 引文）**单独**再问一次模型——
不给文章、不给上下文，只问"这段引文本身是否在陈述这个节点的内容"，三选一
（`entails` / `same_topic` / `unrelated`）。

| 读数 | 数值 | 它回答什么 |
|---|---|---|
| 严格复核：`entails` | **214 / 227 = 94.3%** | 判 supported 的那批，绝大多数是"引文本身就在说这件事" |
| 严格复核：`same_topic` | 13（5.7%） | 引文在聊同一个话题、但没陈述这个节点。**这就是"只是主题相关"的那一类**，占 5.7% |
| 严格复核：`unrelated` | 0 | — |
| 对照：引文覆盖节点标签二元组 ≥50% | 33 / 227 = 14.5% | 零成本词面旁证：只有 14.5% 的引文把标签里的词带全了 |
| 对照：覆盖 <20% | 65 条 | 词面几乎不重合 |

两组数字**不一致**，而这正是自评要说清的地方：词面覆盖只有 14.5%，严格复核却有
94.3% ——因为节点的 label 是压缩过的短标签（「三要素：T、P、E」「以Mitchell三要素界定
学习」），引文是原文里的一整句（「如果计算机程序在完成某类任务T时，通过经验E在某一
表现度量P下的表现有所提高，则称该程序…」）。**词面不重合 ≠ 不支持**，这也是为什么
判据不能做成词面匹配。

必须一起读的三个限制，否则 94.3% 会被高估：

1. **复核用的还是同一个模型**（同一个 `deepseek-chat`），它倾向于为它自己刚做的判定
   背书。这一栏能排除"明显只是同话题"，排除不了"两边一起错"。
2. **只复核了 supported，没有复核 unverified**。所以这份数据**不能**说明"unverified
   里有多少其实是有依据的"——那是另一个方向，而它决定的是"这个功能漏掉了多少"。
3. `same_topic` 那 13 条全部集中在两张图上（「机器学习的主要方向」的派生节点）。
   样本量太小，不足以说"5.7% 是这类判定的固有噪声"。

## 6 这张表支持什么决定、不支持什么决定

**支持**：

- 这一步可以上线（默认关），产出是"三态 + supported 的逐字引用"，而不是"删掉没依据的"。
  召回 17.5% 意味着它天然漏掉大部分节点——把漏掉的删了，删的是 82.5%。
- 引文逐字率 95.2%、严格复核 94.3%：挂上去的引用可以点回原文，用户核对时不会扑空。
- 顺序上先做贵的逐节点搜索**没有依据**：这次 6/10 张图 0 个 supported，失败面是
  "搜回来的文章不对题"（刑法那 4 篇是高校教务页）。逐节点搜 40 次救不了这件事，
  它换掉的是"query 太粗"，不是"文章不对题"。

**不支持**：

- 不支持"用 supported 比例判断一棵树的好坏"。同一批生成里「检索与召回的取舍」是用户
  自己的项目，0% 是**正确**结果；把它当成"这棵树全是编的"会误导用户。
- 不支持"整树一次搜索已经够了，不必再做逐节点"。这次只证明了**精度**够；**召回**
  （哪些该被找到却没找到）没有测，而它才是"要不要逐节点"的唯一判据。
- 不支持把 contradicted 当作"没有矛盾"：10 张图 1299 个节点里 0 条，这个 0 是判据
  触发条件太窄的结果，不是"树上没有矛盾"。

**下一步如果要提高召回**，按成本从低到高，判据分别该看什么：

1. 多搜一轮换 query（`标题 + 一级分支`之外再发一次"主题问句"）——看 unverified 里
   有多少变成 supported；
2. 抬头部节点逐节点搜（只搜前 N 个高层节点）——看 supported 的增量与花费的比值；
3. 换检索源（维基条目正文 + OpenAlex 摘要混进来）——看"文章不对题"这一档能不能降。
