# 说明那一轮的句子数下限：放开它会不会变差

`DETAIL_ONLY_PROMPT` 里有一句「每一段说明写 80–150 字、**至少 3 句完整的话**（不是
3 个短语），少于 3 句就是没写完」。这份文档只回答一件事：**把"至少 3 句"放开，说明
会变差吗？**

结论先行：

- **可以放开，代价是"句子变长"，不是"变短"**：B 臂（去句数）均长 −4.7%、ρ 完全不变、
  κ 不变、耗时不变；薄批 86 段里 0 段退化成"1 句 90 字"。
- **80 字下限一个字都不能动**：C 臂（连下限一起去掉、改成"按材料分量"）在薄批上
  86/86 段塌成 1 句、均长 53.3（−45%）、最短 26 字。它同时制造了"说不够"和"一句硬撑"
  两种坏形态（厚批 33% 的段是"1 句 ≥80 字"）。
- **"至少 3 句"确实在制造凑句子，但凑出来的句子还有 25 字左右**，是轻度冗余而不是
  垃圾句。它真正的代价在别处：它把长度往上顶（厚批均 188.9），而 150 字上限在厚批上
  早就 22/24 段越界——**句数比字数更容易被执行，于是模型保句数、弃上限**。

## 1. 这条要求是从哪来的

它是在救一个已经消失的失效：把「结构 + 每支说明」压在同一次输出里时，detail 五采样
只有 45.3 / 28.0 / 28.5 / 26.2 / 27.4 字（红线 40）；在 system 里加"不少于 60 字"
反而更短（28.5 → 26.2）。所以真正的解药是**单独一段只写说明**（第三段），句子数只是
在那之后的第二道加固，第一道是 `DETAIL_MIN_CHARS = 80`。

`docs/DETAIL-SCALE.md` 里留过一句判断：「模型对下限的执行力来自**句子数**，不是字数」。
这句话现在可以拿数据核对——它是对的，但方向和当时想的不一样：句数确实比字数更好执行，
代价是**它会连上限一起推开**（见下面 §3 的厚批读数）。

## 2. 三臂（加到四臂）× 两批 × 每批 2 次

    A  现状        80–150 字、至少 3 句完整的话
    B  去句数      80–150 字，不设句子数            ← 产品开关 MINDMAP_DETAIL_SENTENCES=1
    C  去句数+去下限  不设句数、不设下限，按材料分量，150 只作建议上限
    D  去句数+限句长  80–150 字，单句不超过 45 字     ← 对冲 B 暴露出来的"长句化"

D 是跑完 A/B/C 之后加的：B 臂的读数显示代价不是"变短"而是"一句变长"（均句长
34.9 → 45.7），所以再跑一臂，看"限句长"能不能替代"限句数"。答案见 §4。

两批材料：

    薄批  库内 filename 含「碳中和」的 4 份 / 670 字（材料探针 669，strip 后）
    厚批  docs 四份：AGENT_PLAN / PLAN / ARCHITECTURE / RAG-DECISIONS / 66,536 字

**四臂跑的是同一份清单、同一份证据**：先走一次完整生成把结构树与第三段的真实输入
（`sections` / `full_text` / `material_chars` / `skip_ids`）整份截下来，之后每次重放都
只换 system。不钉清单的话，臂间的差里会混进"树的形状不同"——κ 的分母固定、分子一变，
均长与句子数分布就同时漂，句子数分布也不再可比。

清单规模：薄批 44 个节点（43 段说明 + 中心主题），厚批 22 个节点（12 段 + 中心主题，
其余是分组节点，`skip_ids` 跳过）。表格里只统计**这一次真的写回来的**段（重放前后逐
id diff）。这份报告采集于折叠还在的时候，所以厚批里那些「其他 N 项」聚合节点也算在
`skip_ids` 里（它们的 `detail` 是"含：A；B；C"那行清单，不是第三段的产物）；折叠已
退休（`docs/FOLD-RETIRED.md`），同样的采集现在会得到更多段说明。

固定住的开关：`SECTION_SLICE=0` / `EXTERNAL_KNOWLEDGE=0` / `RERANK=0` /
`DETAIL_SCALE=0` / `NODE_SCALE=0`。真模型 `deepseek-chat`，`branches=6`。
同一轮里先跑完所有格再下一轮（把 ±5pt 的采样噪声摊平）。

检索状态：**完整**（`embedding` 探测 ok，1024 维）。今天 embedding 挂过一次
（40 批 chunk 向量全失败 → 降级纯 BM25），所以这一项每次都实测并写进报告。

## 3. 读数

### 3.1 六类指标（每格 2 轮均值；最短/最长取该格极值）

| 薄 | A | 43 | 4,162 | 96.8 | 95.0 | 74 | 149 | 0.17 | 100% | 34.9 | 14.93s |
| 薄 | B | 43 | 3,968 | 92.2 | 94.5 | 71 | 116 | 0.17 | 100% | 45.7 | 15.77s |
| 薄 | C | 43 | 2,292 | 53.3 | 52.5 | 26 | 116 | 0.29 | 100% | 53.3 | 7.89s |
| 薄 | D | 43 | 3,652 | 84.9 | 89.0 | 55 | 119 | 0.18 | 100% | 38.7 | 10.66s |
| 厚 | A | 12 | 2,268 | 188.9 | 179.0 | 150 | 232 | 29.41 | 17.9% | 64.4 | 6.43s |
| 厚 | B | 12 | 2,202 | 183.5 | 174.2 | 146 | 253 | 30.21 | 18.0% | 74.7 | 7.41s |
| 厚 | C | 12 | 1,584 | 132.0 | 124.5 | 65 | 217 | 42.00 | 16.9% | 84.6 | 4.47s |
| 厚 | D | 12 | 1,966 | 163.8 | 159.0 | 122 | 228 | 33.84 | 17.9% | 54.4 | 5.64s |

κ = 材料字数 / Σdetail（>2 是膨胀）。薄批 κ 0.17 说明"670 字的材料写出了 4,000 字的
说明"——薄批本来就是膨胀最厉害的一格（历史 `DETAIL-SCALE.md` 里 0.08–0.13），这一轮
四个臂在这一格上没有分歧。厚批 κ 29–42 是"22 个节点覆盖 6.6 万字材料"的必然，同样
不区分臂间差异。

**ρ 在两批上都没有分辨力**：薄批材料 4 份短摘要，8-gram 句覆盖全部命中（100%，四臂
一样）；厚批 17–18%，四臂差 ≤1.1pt。所以"有没有因为变短而漏材料"这件事，这两批只能
给出"没有变差"，给不出"变好了"。

|---|---|---|---|---|---|---|---|---|---|---|
| 薄 | A | 0 | 7.0 | 36.0 | 0 | 0 | 0 | 5 | 4 | 0 |
| 薄 | B | 0 | 42.0 | 1.0 | 0 | 0 | **0** | **39** | 12 | 0 |
| 薄 | C | 43.0 | 0 | 0 | 0 | 0 | 1.5 | 22 | **83** | 0 |
| 薄 | D | 0 | 33.5 | 9.5 | 0 | 1 | 0 | 7 | 33 | 0 |
| 厚 | A | 0 | 1.0 | 10.0 | 1.0 | 0 | 0 | 22 | 0 | **22** |
| 厚 | B | 0.5 | 3.5 | 7.0 | 1.0 | 0 | 0.5 | 21 | 0 | 19 |
| 厚 | C | 4.5 | 6.5 | 1.0 | 0 | 0 | **4.0（33%）** | 21 | 1 | 7 |
| 厚 | D | 0 | 2.0 | 5.5 | 4.5 | 0 | 0 | 15 | 0 | 15 |

三个方向逐个回答：

1. **"1 句 90 字"没有出现**：B 臂 1 句段是 0/86（薄）与 1/24（厚）。任务书里"如果
   B 臂出现大量 1 句 90 字的段 → 只放开到至少 2 句"那个预案**不需要触发**。
2. **"3 个短句"也没有出现**：末句 <12 字的段在所有臂、所有批上都是 0。现状 A 臂
   86 段里也没有一段是"第 3 句只有 8 个字"。
3. **真正变的是句子长度**：薄批均句长 34.9（A）→ 45.7（B），含 ≥60 字长句的段从
   5/86 涨到 39/86。B 臂的典型形态是"2 句 × 46 字"，而 A 是"3 句 × 32 字"。
   一段 92 字读两句话是顺的，但其中一句 60–80 字需要回头读——这是 B 的真实代价，
   也是 D 臂存在的理由。

### 3.3 C 臂：下限是唯一有效的护栏

薄批 86/86 段塌成 1 句、均长 53.3（A 的 55%）、83/86 段低于 80 字、最短 26 字。
厚批 37% 的段只有 1 句，其中 4 段 ≥80 字——**"说不够"与"一句硬撑"同时出现**。

这一格的意义不是"另一个候选措辞"，而是**反证**：`DETAIL_MIN_CHARS = 80` 不是配额，
它是"越写越短"唯一的刹车。放开句子数时必须把它留在原地。

### 3.4 A 臂自己就没在执行"3 句"

薄批第 1 轮：43 段里 **14 段只有 2 句**（33% 未达 3 句）；第 2 轮：43 段全部 3 句。
同一提示词、同一清单，两轮之间从 67% 执行率跳到 100%。

这说明"至少 3 句"这条约束的实际形态是：**它把本来会写 2 句的段撑成 3 句**，而它自己
的执行率本来就在 67%–100% 之间摆。放开它，模型的行为变化很小（3 句 → 2 句），这也是
B 臂均长只掉 4.7% 的原因。

### 3.5 那条约束到底在制造什么：一个固定的收尾句，不是垃圾串

"3 句但第 3 句只有 8 个字"这个假设，**按数据不成立**：末句 <12 字的段在所有臂、所有
批上都是 0，末句 <15 字的段 A 臂只有 1/86。

成立的是另一件事——**末句被写成了"全段最短的那一句"**：

| 批 | 臂 | 末句均长 | 末句<25 字 | 末句是**全段最短句**的段 |
|---|---|---|---|---|
| 薄 | A | 31.2 | 35/86（41%） | **57/86（66%）** |
| 薄 | B | 56.6 | 1/86 | 14/86 |
| 薄 | D | 39.0 | 5/86 | 39/86 |
| 厚 | A | 42.0 | 1/24 | 14/24（58%） |
| 厚 | B | 52.1 | 5/24 | 15/24 |

薄批 A 臂 72 个 3 句段里，末句落在 15–24 字的有 34 段、<15 字只有 1 段。也就是说：
模型确实在按"3 句"凑，但它凑出来的是一个**十来字到二十几字的小结句**，语法完整、常常
还有信息（"这一点在长材料上更明显"），只是不如前两句承载内容。

判断：这条约束在制造**结构性冗余**（每段末尾固定挂一句最短的收尾），不是噪声串。所以
放开它的收益是"读起来不再有那个尾巴"，不是"省字数"或"少废话"；放开它的风险也很小
（长度不掉、ρ 不掉、1 句段不出现）。这也是为什么建议"可以先不翻默认值"——收益是真的，
但小。

## 4. D 臂（限句长）为什么没有成为最终措辞

单句 ≤45 字确实消掉了长句（薄批含 ≥60 字长句的段 39 → 7），但代价是**吃掉下限的
余量**：薄批均长 84.9（−12% vs A）、最短 55 字、33/86 段低于 80 字。模型把"80 字"当成
了配额目标——第 2 轮 43 段全部 2 句、均 80.5，正好踩在下限上。

厚批更明显：4+ 句的段占 37.5%（9/24），均 163.8。它把"3 句"换成了"4–5 句短句"，
不是在放开句数，是在**换一种句数下限**。

所以 D 不进产品。它留在脚本里作为备选：如果将来真实用户反馈"说明里有一句读不下去"，
把 B 的措辞换成 D 的（单句上限 45 字）并重跑这一格。

## 5. 最终措辞（B）

system 的最后一段（`tools._detail_only_prompt_open` 的全部内容就是这份 system，
与 A 只差这一段；前四段是同一个常量 `_DETAIL_ONLY_SHAPE_RULES`）：

```
每一段说明写 80–150 字，少于 80 字就是没写完。分几句按意思走，几句都行，但不要把一句话硬拉长到 80 字——那样的说明读不下去。如果这个节点的标题是一串并列的东西（几个算法、几种变体、几类方法、几个阶段），要逐个说清它们各自做什么、差别在哪，不要只把名字列一遍就收。超过 150 字就挑最关键的两三点，长文留给节点下面的子节点。
```

user 末尾的自查句同步换成（`tools._detail_self_check`）：

```
写完后自查一遍：上面 N 个 id 是不是都写了？每一段是不是都在 80–150 字？不够的补写，然后再返回。
```

**它为什么能防住"越写越短"**，三条，各对应一个读数：

1. **80 字下限原地不动**——C 臂证明它就是刹车（卸掉之后均长 −45%）。这一条不是"还
   留着"，是"唯一还在的"。
2. **"几句都行"只放开句数，不放开"写多少"**——B 臂均长 92.2 / 183.5，与 A 的
   96.8 / 188.9 齐平；ρ 与 κ 不变。
3. **补一句"不要把一句话硬拉长到 80 字"**——这是对 B 臂代价的对冲（45% 的段出现
   ≥60 字长句）。它只禁"硬撑"，不给句数配额，所以不会变相恢复"至少 3 句"。

**为什么不加"如果一句话就能说清，那也够"**：它与 80 字下限直接矛盾，模型会拿它当
逃生口——C 臂那一格就是这句话的实测版本（均长 53.3、最短 26）。两句话方向相反，
只能留一句，留的是下限那一句。

**为什么 C 臂保留 150 作建议上限**：上限管的是可读性与输出量（第三段墙钟 = 输出字数
÷ 吞吐），下限管的是"写多少才够"。去掉上限等于同时放开 κ 与耗时，而且契约硬截是
`MAX_NODE_DETAIL_CHARS = 2000`，去掉 150 之后一无约束。实测 A/B 两臂在厚批上本来就有
19–22/24 段越界（150 是软上限），但它仍是唯一的方向提示。

## 6. 成本

| 批 | A | B | 差 | C | D |
|---|---|---|---|---|---|
| 薄 | 14.93s | 15.77s | +5.6% | 7.89s | 10.66s |
| 厚 | 6.43s | 7.41s | +15% | 4.47s | 5.64s |

B 与 A 的墙钟差在噪声里：B 的输出总量比 A **少** 4.7%，却慢 5.6%/15%，两轮之间也互相
颠倒（厚批第 1 轮 B 8.61s vs A 6.41s，第 2 轮 B 6.22s vs A 6.45s）。所以"放开句数"不
改变成本。

第三段墙钟的实测斜率（按两半里更慢的那一半折算）是 **126–186 字/秒**，中位约 140。
按这条斜率外推"均长从 107 涨到 180"的场景（56 个节点）：最大半从 2,996 字涨到 5,040 字，
墙钟从 ~21s 涨到 ~36s（+15s）。**但这不会发生**——四臂里没有任何一臂把均长推高，
C 与 D 反而是往下走的。

反方向的那笔账才是真的：均长每涨 10 字，56 个节点的最大半多 280 字 ≈ 2 秒。所以
"长度"这件事在产品里值得继续盯，只是这次的改动不在那个方向上。

## 7. 开关

    MINDMAP_DETAIL_SENTENCES=1     # 开：说明那一轮不再要求句数下限
    （不设 / 0）                    # 关（默认）：system 与加这个开关之前逐字节相同

关着时 `_detail_prompt` 直接返回 `_detail_only_prompt` 的输出，`DETAIL_ONLY_PROMPT`
的整份文本（467 字符、sha256 `5064c027…dddd04b`）由 `tests/test_detail_sentences.py`
钉着；同时那一条 `_detail_self_check` 也逐字不变。开着时多两处可观测：

    data["detail"]["sentences_open"] = true
    diagnostics 里多一条 code = "DETAIL_SENTENCES_OPEN"

`_fill_details` 的 `data["detail"]` 只在开关真接管时多这个键——默认路径的键集与改动
之前相同（`test_detail_round` 的断言比的就是那个键集）。

要不要翻默认值：**建议先不翻**。B 的收益是"不再硬凑第三句"，代价是"句子变长、
12/86 段贴近下限"，两边都不大；而这台机器上真实用户的反馈还没有指向"说明像凑出来的"。
开关留着，等有那类反馈再翻，翻之前用本文件的读数当对照。

## 8. 复现

    cd backend
    python scripts/measure_detail_sentences.py --capture          # 两批各一次完整生成
    python scripts/measure_detail_sentences.py --replay --repeat 2 --arms A,B,C
    python scripts/measure_detail_sentences.py --replay --repeat 2 --arms D
    python scripts/measure_detail_sentences.py --report data/detail-sentences-ab.json

`--capture` 那条路会在 `_fill_details` 处截住（不花第三段的两次调用），生成的快照在
`data/detail-sentences-capture.json`；`--replay` 只认快照，不再重新生成树。报告写到
`data/detail-sentences-ab.json`（`data/` 不入库，所以本文件里的表格就是留存的那一份）。
