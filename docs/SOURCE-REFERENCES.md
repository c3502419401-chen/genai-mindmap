# 节点来源引用

本次只扩展后端 v1 契约的 `Node.source_refs`，不启用完整 v2 契约。
旧请求和数据库记录可省略此字段，读取时默认为 `[]`；现有 SQLite JSON
存储会自动保存新增字段，无需表结构或数据迁移。

## 引用格式

```json
{
  "id": "n1",
  "label": "发布安排",
  "children": [],
  "source_refs": [
    {"source_id": "meeting", "quote": "下周发布", "start": 4, "end": 8}
  ]
}
```

这里 `Source.text` 为 `会议决定下周发布。`。字符区间使用原始 `Source.text`
上的 Python Unicode 字符索引，从零开始，左闭右开；不是 UTF-8 字节偏移，
也不是 JavaScript UTF-16 代码单元偏移。原文开头的空白、换行都计入索引。

每个节点最多 20 条引用。`source_id` 必填、非空白、最长 100 字；可选
`quote` 最长 300 字，空白引文归为 `null`；可选 `page` 为从 1 开始的整数。
`start` / `end` 要么都省略，要么同时提供非负整数，且 `end > start`。

## 三层校验

| 层次 | 执行位置 | 规则与行为 |
| --- | --- | --- |
| 1：字段 | `SourceRef` / `Node` | 类型、长度、页码、字符区间和数量限制；拒绝未知字段。请求不合法返回 422，模型结构不合法返回 502。 |
| 2：关联 | `MindMapContent` | 每条引用的 ID 必须存在于 `source_usage`；摘要 ID 不得重复。所有接收导图的接口共用此约束。 |
| 3：原文 | `verify_source_refs` | 引文必须逐字出现在指定来源中；带区间时检查边界和非空白内容。区间与引文对不上时由服务端**按引文重新定位**：唯一定位就补正偏移，多处出现就标待核，定位不到才剔除。 |

第三层不做模糊匹配或跨来源拼接，也不证明节点文字被引文语义支持。
既没有引文也没有字符区间、或只有区间而引文为空的引用标记为
`UNVERIFIED_SOURCE_REF` 并剔除——坐标本身说明不了引的是哪一段。
没有可核验引用的节点标记为 `UNSOURCED_NODE`，不自动删除节点或建议删除。

### 生成时的第三层判定表

内容与出处是两件事：节点内容可以凭模型自己的知识展开，**但引用必须标出处**。
判定只作用于引用，不影响节点是否保留。

| 情况 | 处置 | 诊断 |
| --- | --- | --- |
| 引文与区间逐字一致 | 保留 | — |
| 只给引文、没给偏移 | 保留并补上精确区间 | —（补齐元数据不算问题） |
| 偏移写错、引文在可见范围内唯一定位 | 保留并补正偏移 | `SOURCE_QUOTE_OFFSET_FIXED`（info） |
| 引文在可见范围内多处出现 | 保留，标"待核" | `SOURCE_QUOTE_AMBIGUOUS`（warn） |
| 引文在原文里定位不到 | **剔除** | `SOURCE_QUOTE_MISMATCH`（warn） |
| 引用落在本次可见的父块内、但不在命中的子块内 | 保留 | `SOURCE_REF_OUTSIDE_EVIDENCE`（warn） |
| 引用只有区间、没有引文 | **剔除** | `UNVERIFIED_SOURCE_REF`（warn） |
| 引用既无区间也无引文 | **剔除** | `UNVERIFIED_SOURCE_REF`（warn） |
| 来源不存在 / 未解析成功 / 正文为空 | **剔除** | `SOURCE_TEXT_UNAVAILABLE`（warn） |
| 页码超过总页数或指向解析失败的页 | **剔除** | `INVALID_SOURCE_PAGE`（warn） |

"可见范围"按形态区分：`rag` 形态下是本次检索命中的父块（450–700 字）加全文兜底；
`full` 形态下整份正文都在 prompt 里，因此**不做父块约束**，引用任何段落都是合法的
（`full` 这个形态 2026-11-16 已删除，现在只剩 `rag` 那一档，见 `docs/ONE-PATH.md`）。
`rag` 形态一次证据都没检索到时允许零引用，由 `GENERATION_WITHOUT_EVIDENCE`（warn）
说明这次没有依据——诊断从不参与成功判定。

反过来，"证据已拼进 prompt、最终却一条引用都没有"是另一件事：模型没写，或写了但
过不了第三层被剔光。`EVIDENCE_UNUSED`（warn）报出"给了几条证据、最后剩几条引用"，
并在 `content` 里点明这不等于"材料里没有相关内容"。分母口径按**剩下的两条路**各算
各的：`mindmap_generate_deep` 用按支证据去重后的条数（`whole` 兜底时各支拿到同一批，
逐支相加会虚报），`node_expand` 用本次为这个节点检索的命中数。没有证据时它不报——
那种情况归 `BRANCH_NO_EVIDENCE`。整树生成的主题预检索（`_retrieve_topic` / `_TopicEvidence`）
已随 `full` 形态一起删除（`docs/ONE-PATH.md`）；2026-11-18 回来的整树生成（`bc3494e`，见
`docs/ONE-CALL.md`）**没有"一次主题检索"这一步**——它与分片共用按支检索（`_retrieve_branches`，
每支各一次），所以"按一次主题检索的命中数"那个口径不再存在，两路的分母都以按支证据为准。

子块约束保留下来是为了**可观测**：谁引了父块里与查询无关的部分，诊断里看得见；
要求模型精确落在命中的那 200 字里过于苛刻，实测会成批剔掉合法引用。

## 可选的第四层：NLI 语义打分

前三层都是机械判据，它们管不住一种情况：引文逐字对得上，但节点论断与原文
**语义相反**（原文「只在小数据集上验证」，节点写成「已在大规模数据上验证」）。

`app/optimization/nli.py` 用一个小型 ONNX cross-encoder 对「节点论断 ↔ 引文」
判一次语义蕴含，**只产出诊断，不改变任何引用**：

| 判定 | 诊断 |
| --- | --- |
| contradiction | `SOURCE_REF_CONTRADICTED`（warn），引用保留 |
| entailment / neutral | `SOURCE_REF_NLI`（info），附置信度 |

hypothesis 是 **`label` + `detail`**（`source_refs._claim_of`），不是 `label`：

```
预算审批流程。五万元以内由财务经理核准，超过五十万元报总经理审批。
```

拿"预算审批流程"这种名词短语当 hypothesis，模型能回答的只有"这段引文提到这个
短语了吗"——一段话几乎不可能**否定**一个名词短语的存在，它顶多不提它。真模型
实测（Erlangshen int8，20 条真实引文）：只给 `label` 时模式相反的论断一条都抓
不到，全被盖成 entailment；换成 `label + detail` 之后才出现三档分布。

设计约束：概率模型不得推翻确定性判据。冲突时引用留着、同时给出警告，
由人判断。没有 `quote` 也没有字符区间的引用直接跳过——拿整篇原文去比一句
论断，NLI 只会给 neutral。

**默认关闭**（`MINDMAP_NLI_ENABLED` 未设即关）。关闭时连 `onnxruntime`
都不会 import，`annotate_nli` 立刻返回空列表。启用需要
`MINDMAP_NLI_MODEL_DIR` 指向含 `model.onnx` / `tokenizer.json` / `config.json`
的目录。加载前有内存闸门（默认 700 MB，Linux 可检测）。

**生成路径的第二道闸**（`MINDMAP_NLI_ON_GENERATE`，默认**开**）：模型启用之后，
`_generate_deep` 的收尾就默认跑一次语义复核——这条路径是这一层唯一的消费方，
默认关会让"接了"与"没接"在部署上无法区分。成本实测（
`scripts/measure_generation_diagnostics.py`，脚本化分片生成 + 等价延迟）：

| 骨架 | 树 / 引用 | 15 ms/条 | 44 ms/条 |
|---|---|---|---|
| 8 支（默认量级） | 33 节点 / 24 条 | 0.37 s | 1.07 s |
| 20 支（工具上限） | 61 节点 / 40 条 | 0.62 s | 1.78 s |

撞满 `MAX_NLI_CHECKS=100` 才是 1.5–4.4 s，那种图设 `MINDMAP_NLI_ON_GENERATE=0`。
**必须在线程池里跑**：同步调一次 374 ms 的 NLI，事件循环心跳 0 次（整段被独占）；
`to_thread` 之后同一段心跳 25 次、最大停顿 16 ms。

分片路留存的引用**必带 `quote`**（实测 24/24、40/40，且同时带字符区间）：
`_check_reference` 把"只有区间没引文"和"两者都无"都判 `UNVERIFIED_SOURCE_REF`
并剔除，而收尾那一步是 `remove_invalid=True`。所以"没有 quote 就跳过"这条规则
在生成路上不触发。

### 实测：这一层到底抓不抓得到「语义相反」

模型是真模型（Erlangshen-Roberta-110M-NLI int8 98.3 MB / mDeBERTa-v3-base-xnli
int8 302.6 MB，onnxruntime CPU），材料是本仓库 `docs/RAG-DECISIONS.md`，引文逐字
来自原文。三组：**A** 忠实论断 20 条（论断与引文同向）、**B** 反向论断 10 条
（论断与引文相反，即这一层唯一声称能抓的故障）、**C** 真分片生成出来的 24 条
引用（`detail` 为空，走回退）。

| 组 | claim | entailment | neutral | contradiction |
|---|---|---|---|---|
| A 忠实 20 | 旧：`label` | 20 (100%) | 0 | 0 |
| A 忠实 20 | 新：`label + detail` | 19 (95%) | 1 (5%) | 0 |
| B 反向 10 | 旧：`label` | **10 (100%)** | 0 | **0** |
| B 反向 10 | 新：`label + detail` | 6 (60%) | 3 (30%) | **1 (10%)** |
| C 真实 24 | 旧 = 新（`detail` 空） | 20 (83%) | 0 | 4 (17%) |

同一批数据换 mDeBERTa：A 组 旧 50%/50%/0 → 新 80%/20%/0；B 组 旧 10%/90%/0 →
新 10%/90%/0（**一条也没抓到**）；C 组 38%/62%/0。

三条结论都有数字支撑：

1. **旧 claim 不是"灌一堆 neutral"，是把错的方向盖成"有原文支持"**。B 组 10 条
   写反的论断，Erlangshen 给 100% entailment（置信 0.49–0.91），mDeBERTa 给 90%
   neutral。前者比中性更糟——它让错误看起来被引文支持。
2. **新 claim 能把反例的 contradiction 概率从 5–7% 抬到 16–39%，但 top-1 只抓到
   1/10**。信号真的进来了，可还不够压过 entailment。两个模型、同一批样本，召回
   上限都是 10%。
3. **旧 claim 在真实数据上产出的 warn 是噪声**。C 组那 4 条 contradiction 里 3 条
   claim 是 markdown 表格行（`| 扫描件 PDF | 0 |`、`| 4 | 单换行 \n |`），被判
   "与原文相反"——`annotate_nli` 会把它们逐条报成 `SOURCE_REF_CONTRADICTED`。

合起来：这一层在真反向样本上召回 10%，在真引用上精确率 25%（1 真 / 3 假），
成本 36–55 ms/条（238 字引文，int8，本机 i5-13500H）。`DEFAULT_ON_GENERATE=True`
的依据是"低于每次生成多等三秒"，而按真实引文长度算 24 条是 0.9–1.3 s、100 条是
3.6–5.5 s——量级仍成立，但 0.37–1.07 s 那组数字是等价延迟注入的，不是真模型。

实测参考：

| 模型 | 文件 | 内存增量 | 加载 | 单次推理 | 中文准确率 |
|---|---|---|---|---|---|
| `typeform/mobilebert-uncased-mnli` int8 | 25.7 MB | +83.5 MB | 9.9 s | 11–23 ms | 0/4 |
| `IDEA-CCNL/Erlangshen-Roberta-110M-NLI` int8 | 98.3 MB | +140.3 MB | 1.4 s | 15–44 ms | 6/6 |

"单次推理"那一列是在**短样本**上量的。同一台机器、同一个 int8 模型，耗时随 premise
长度变化很大：引文 50 字 11.8 ms、238 字 36.4 ms、300 字 54.7 ms、400 字 721 ms、
1200 字 1159 ms（Erlangshen，本机 i5-13500H）。300→400 字之间有一个台阶，同样的
台阶在 fp32 权重上也有、只是位置不同（150→200 字），所以它更像本机 CPU 线程调度的
产物而不是模型固有的；但父块级引文（450–700 字）一旦进了 `judge()`，成本就得按
台阶之上算。

**英文模型对中文完全失效**，不是「偏弱」：它对「完全不能识别图像」vs「本系统可以识别图像」给 `entailment 0.52`，对「数据库采用主从架构」这种无关内容给 `entailment 0.65`——四条中文用例全判成蕴含，说明它只在数词汇重叠，没有识别否定结构。中文场景必须用中文模型。

`id2label` 顺序各模型不同（mobilebert 是 `0=ENTAILMENT / 2=CONTRADICTION`，Erlangshen 是 `0=CONTRADICTION / 2=ENTAILMENT`），代码从 `config.json` 读，写死会整体错位。

## 各接口的行为

`SourceSpan.page` 是文档总页数，没有逐页文本映射。超出总页数或指向解析失败
页面的引用标记为 `INVALID_SOURCE_PAGE`；其余页码仍标记为
`SOURCE_PAGE_UNVERIFIED`，即使引文已在全文匹配。模型提示词要求只返回来源 ID
与逐字引文，不猜测页码或字符偏移。

## 生成、诊断与保存

- `POST /api/agent/runs/stream` 的请求带 `sources: [...]` 时，`mindmap_generate_deep`
  把**结构线索**（材料自带的章节标题行）交给骨架、把**按支检索的命中**交给每条分支
  ——正文段本身一个字都不进 prompt（`MINDMAP_SOURCE_MODE=full` 那条"整份原文放进
  prompt"的路已删除，见 `docs/ONE-PATH.md`）。`source_usage` 由工具自己按真实来源
  拼出，不信任模型提供的摘要；未知来源与确实对不上原文的引用会被剔除
  （判定表见上节：父块越界与多处出现只告警、不剔除），原因通过 `diagnostics` 返回，
  并带上 `node_id`。节点本身保留，合法引用保留。
- 不带来源的生成（`intent=create` 且没有 `sources`）没有可追溯的来源记录：
  没有可检索材料时系统提示词里会加一句"不要写 source_refs"，而落在树上的引用在
  合并前就被清空（`_refs_from` 没有本支证据时一条都不收）——`source_usage` 为空时
  带引用的树过不了契约。`node_grow` 预览帧也不携带未经核验的引用——它只有 `label`
  与 `expandable`。demo 不编造引用。
- `POST /api/optimization/check` 和 `/api/optimization/suggest` 可额外传
  `sources` 执行第三层；省略时只做原有结构诊断，传 `[]` 会明确报告缺失原文。
  两个接口都不改写导图或数据库，重复来源 ID 返回 422。
- `POST/PUT /api/mindmaps` 校验前两层并持久化引用，版本冲突仍返回 409。
  保存接口没有原文，不能执行第三层；重新核验时须把原文传给诊断接口。
  本功能不增加原文存储，引用匹配针对本次请求提供的原文，不代表外部事实核验。

诊断请求示例：

```json
{
  "content": {
    "title": "会议摘要",
    "root": {
      "id": "n1", "label": "发布安排", "children": [],
      "source_refs": [{"source_id": "meeting", "quote": "下周发布"}]
    },
    "source_usage": [{"source_id": "meeting", "kind": "text", "char_count": 9}]
  },
  "sources": [{
    "id": "meeting", "kind": "text", "status": "parsed", "text": "会议决定下周发布。"
  }]
}
```

针对引用的测试：在 `backend` 目录执行
`python -m pytest -p no:cacheprovider tests/test_source_refs.py tests/test_generation.py tests/test_stream.py`。

## 界面：点引用回到原文那一段

数据层一直在，界面这一环是本轮补上的。四个动作对应四层，缺任何一层都会让
"引用可追溯"停在半路：

| 动作 | 入口 | 界面上发生了什么 |
| --- | --- | --- |
| ① 看这个节点有哪些引用 | 节点右上角的引用角标 / 详情面板 | 角标可点（`openRefs` → 选中 + 打开右抽屉）；抽屉里逐条列出**材料名 + 位置 + 引文** |
| ② 看某一条引用的原文 | 点列表里那一条 | `SourceContextDrawer` 打开，顶部是**逐字引文**（后端校验过的 `quote`） |
| ③ 看它在原文里的位置 | 抽屉里的「看上下文」 | 正文定位到 `[start, end)`，命中段用 `<mark>` 包住，**前后各 600 字**上下文 |
| ④ 读不够就往外扩 | 「再读上文 / 再读下文」 | `pad` 每次 +1800 字，贴到全文两端时按钮消失 |

### 正文从哪来

`source_refs` 只存 `source_id / start / end / quote / page`，**不存正文**。所以正文有两条路，
按"有没有"依次退让：

1. **本会话解析过的来源**：`sources.readySources` 里有全文，直接用，不发请求；
2. **打开已保存的导图 / 重新解析**：内存里没有正文，按 `source_id` 走
   `GET /api/knowledge/library/{id}?limit=` 取。该接口默认只回 4000 字（列表预览口径），
   而 `start/end` 是**全文码点偏移**——37973 字的材料里第 20000 字处的引用用预览永远
   看不见，所以抽屉传 `limit=200000`（`shelf.MAX_READ_CHARS`）一次取整份。

`limit` 的上界由 schema 的 `le` 挡成 422，不在服务层静默夹断：一个越界的 `limit`
是调用方的错，悄悄纠正会让它以为自己拿到的是全文。

### 为什么不把全文摊进抽屉

抽屉 520px 宽，37973 字是几百屏——摊开等于没定位，用户还得自己找。所以只渲染**窗口**
（命中 ± 600 字），其余按需扩展。这也把 DOM 里的大字符串从"整份正文"降到"一两千字"。

### 三种降级，各说各的话

混成一句"原文不可用"，用户就分不清是功能坏了还是这份材料本来就没依据：

| 情况 | 界面措辞 | 有没有高亮 |
| --- | --- | --- |
| 来源不在知识库里（一次性粘贴的文本、已被清理的材料） | 「这份来源没有可回查的原文……下面只是生成时记下的摘录」 | 无，摘录照常显示 |
| 正文超过单次上限、引用落在没载入的部分 | 「界面一次只载入前 N 字，这条引用在第 M 字处」 | 无，且不给「看上下文」按钮 |
| 引文在正文里逐字定位不到 | 「这段引文在正文里定位不到（逐字比对不上）」 | 无 |

### 定位判据（前端 `mindmap/refs.ts`）

- **坐标优先，但不盲信**。`start/end` 合法时先核对 `text[start:end]` 与 `quote`：
  逐字相同 → 用坐标（`via='range'`）；只差首尾空白 → 仍用坐标。**对不上才退回按引文搜**
  （`via='quote'`）。盲信坐标的代价很低调：手改过/旧版本的引用会把一段不相干的原文
  框成"这句的出处"，而界面没有任何提示说它错了。
- **首尾空白不算不一致**。实测踩出来的：英文论文的引用片段常以空格或换行开头，
  而比较时用的是 `trim()` 过的引用。只比 `excerpt === quote` 会把坐标正确的引用判成
  "对不上"，退回全文搜索 → 高亮**少一个字**、位置说明偏 1、并多出一句"这条引用没有
  坐标"。回归用例在 `frontend/tests/refs.spec.ts`。
- **只有 `quote`、没有坐标**（后端的 `SOURCE_QUOTE_AMBIGUOUS` 就是这一类）：前端自己搜，
  并给出**全部出现位置**。「上一处 / 下一处」逐个核对，而不是笃定地指向第一处。
  后端 `source_refs._locate_quote` 的定位结果不落库（只在生成时补 `start/end`），
  所以前端必须能独立处理"没有坐标"这一态。
- **码点，不是 UTF-16 下标**。全部切片走 `Array.from`；`String.slice` 会在 emoji 与
  CJK 扩展区字符上错位。后端的 `total_chars` 与前端 `Array.from(text).length` 同一坐标系。

### 实测（2026-11-26，本机库）

库里有 24 份导图、731 条引用。逐条拿 `library_sources.text` 核对坐标：

- 有坐标的 **729 条全部满足 `text[start:end] === quote`（100.0%）**，0 条坐标错位；
- 另 2 条引用的来源不在库里（一次性粘贴的 `text` 材料），界面走"没有可回查的原文"那一档；
- 37973 字的 `1706.03762v1.pdf`：`?limit=37973` 取回 37973 码点、`truncated=false`；
  第 20001 码点起的 61 字片段在全文唯一出现；
- 浏览器端到端（真实导图 + 库原文）：`<mark>` 文本与库原文同一区间的 **SHA-256 完全相同**
  （`3120907e…e973`），长度 61 字，位置说明 `第 20001–20061 字 · 共 37,973 字`。

### 覆盖率与"这个节点没有引用"

一次生成总有节点拿不到引文（薄批 78–80%、厚批 86%）。详情面板原本只写一句"这个节点
没有来源引用"，用户看到的是一枚**洞**：引用功能坏了？这条点不开？

界面这一侧能做的是**把口径摆出来**：`refCoverage` 与前端的 `refIndex` 同一次遍历，
算出"这张图 N 个节点里有 M 个带原文引用（X%）"，跟在"这个节点没有原文引用"后面。
这样"没依据"读起来是一张图的属性，而不是一个坏掉的功能。

不能做的是**断言原因**：`MindNode` 契约里没有"这个节点是手动的还是生成的"（只有
`label` / `detail` / `source_refs`），所以文案只能并列说"生成时模型没找到对应句子，
或者这个节点是你自己加的"，不假装能分。
