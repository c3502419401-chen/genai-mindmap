# 知识库：落库与「只靠库检索」实测

> 2026-11-13，`backend/scripts/measure_library.py` 的一次真实运行（本机 = 开发机，
> Windows / Python 3.12 / 单进程）。
> 复现：`cd backend ; python scripts/measure_library.py --hundred`。
> 库落临时目录，不碰 `backend/data/mindmaps.db`。

## 1 三份真实材料

| 材料 | 字符 | 切块行 | 入库 | 正文 KB |
|---|---|---|---|---|
| `docs/AGENT_PLAN.md` | 25,845 | 195 | 12.1 ms | 43 |
| `docs/RAG-DECISIONS.md` | 14,119 | 107 | 7.6 ms | 26 |
| 桌面 `螺线管磁场测量实验报告_填写内容.docx` | 3,552 | 28 | 16.9 ms | 8 |
| **合计** | **43,516** | **330** | **36.6 ms** | **127** |

库文件：建表后 40,960 B → 入库后 188,416 B（**+147,456 B**，3.39 B/字符）。
入库耗时中位 12.1 ms/份，约 1,189 千字符/秒（只算切块 + 写库，**不含解析**；
那份 docx 的 Docling 冷启动另算 16.8 s，不进这张表）。

## 2 只靠库检索（请求内 `sources = []`）

这是库唯一不可替代的证据：同样输入下 `library=False` 必须是 0 条。

| query | `library=False` | `library=True` | 耗时 | 命中来源 |
|---|---|---|---|---|
| 工具调用的轮数上限是多少 | 0 条 | 3 条 | 91 ms | RAG-DECISIONS ×1、AGENT_PLAN ×2 |
| 两路名次怎么融合 | 0 条 | 3 条 | 83 ms | RAG-DECISIONS ×3 |
| 霍尔元件的输出电压怎么算 | 0 条 | 3 条 | 78 ms | docx ×3 |

第三条问法与材料用词几乎不重合（材料写「霍耳传感器」「U\_0 称为剩磁电势」），
仍然召回对了——三个 query 都是纯 BM25（本机没有 embedding 凭证）。

**第 1 条 query 的第 1 名是噪声**：命中的是 `RAG-DECISIONS.md` 里讲
`GraphStoreError` 继承的那段，不是 `AGENT_PLAN.md` 的 `RunBudget`。纯 BM25 的排序
质量本来就没有真机对照（`RAG-DECISIONS.md` 第 7 节自己列着这条限制），而库把候选
集从 1 份扩到 3 份之后，这类"共享常用 bigram 的长块"更容易挤进头部。接上向量路
是它该有的解法，本轮不做。

## 3 100 份的成本实测

库清空后用副本轮换生成 100 份（正文几乎相同，只多一行唯一注释），**只测成本**：

| | 数值 |
|---|---|
| 正文合计 | 1,463 千字符 / 11,052 切块行 |
| 库文件 | 188,416 B → 4,653,056 B（**+4.26 MB**，3.05 B/字符） |
| 入库 | 100 份 **2.9 秒**（34.8 份/秒） |
| `search_sources(library=True)` | 中位 **133–138 ms** ／ 每次读最近 100 份 ≈ 1,463 千字符 |
| `list_sources(50)` | 15.5 ms |
| `prune(keep_days=90, keep_count=200)` | 13.0 ms |

按单份均值外推（14,505 字符 / 49,152 B / 110 行 / 12.2 ms）：

- **100 份**：4.69 MB、11,000 切块行、入库 1.3 秒
- **200 份**（`prune` 默认 `keep_count`）：9.38 MB、22,000 行

## 4 2C2G 上的判断

**装得下，而且不是瓶颈。** 9.38 MB 的库文件对 2G 内存与 10G 磁盘都是零头；100 份
时一次检索 133 ms，其中大头是 5 份来源的两级切块（73 千字符），粗筛本身是
100 × 14.6 千字符的 `str.__contains__`。

**真正的代价是读放大，不是体积**：每次 `library=True` 检索都要把最近 100 份的
**正文整份**读进内存（1.46 千字符 ≈ 4.3 MB 的 UTF-8），SQLite 的默认页缓存
（2 MB）装不下。100 份实测 133 ms 里有一部分就是它。两个旋钮在
`service.LIBRARY_SCAN_LIMIT`（100）与 `LIBRARY_PICK`（5）——前者决定读多少，后者
决定切多少。要压延迟就调小前者，代价是召回面变窄。

**没解决的**：`prune` 只有入口、没有触发器（本轮不做自动调用）。`library_sources`
没有等价于 `vector_cache.MAX_ROWS` 的硬上限，所以"库无限增长"这件事只解决到
"有办法清"，没解决到"不会涨"。要真上线，得在启动时或定时任务里调一次。
