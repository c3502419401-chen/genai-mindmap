# 输入先读成「意图 + 主题」：那一段话不该直接进 `主题：` 那一行

用户输入的是**一段话**，而生成提示词要的是**一个中心词**。这一轮在 `mindmap_generate`
的入口加了一步「读输入」：把这次输入读成 `topic` + `intent` + `questions` + `constraints`，
再往下走原来的流水线。开关 `MINDMAP_INPUT_EXTRACT`，默认**关**，关着时与改动之前逐字节相同。

两个关键点先摆在最前面，它们都是被测量推翻过一次的结果：

- **提取读的是用户原话**（`ctx.request.goal`），不是工具参数 `args.topic`——后者是外层
  agent 压过一遍的字符串，压缩丢掉的东西提取再聪明也捞不回来（§0.5）；
- **自检是纯规则、零额外调用**，它在输入源修好之后几乎无事可做，真正的产出是让
  `constraints` 稳定（§1.5）。

下面还有三处，是**先前的说法被数据推翻**：现象的位置（§0）、漏捞的归因（§0.5）、单次
采样能不能用来下结论（§3）。它们比新功能本身更重要——一个错的归因会让下一轮修错地方。

## 0. "把用户输入原样当主题"在真实链路上不成立

用户描述的现象是"`topic` 就是用户那一整段话"。实测（五条真实输入、走完整 agent 链路、
记的是**模型填出来的** `args.topic`）不是这样：外层 agent 模型自己就会压缩。

| # | 原话 | 字 | `args.topic`（模型填的） | 字 | 根节点 label | 字 | 一级分支 | 节点 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| ① 带背景的诉求 | 我想了解怎么在制造业团队里推行AI工具，公司300人，担心员工抵触 | 33 | 制造业300人团队推行AI工具：路径与抵触化解 | 23 | 制造业300人团队AI工具推行 | 13 | 10 | 104 |
| ② 多问题混合 | 帮我梳理一下RAG的召回问题，另外我们的向量库选型也没定，还有成本怎么控 | 36 | RAG 召回问题、向量库选型与成本控制 | 19 | RAG 召回与成本控制 | 10 | 9 | 104 |
| ③ 带约束的任务 | 下周要给老板讲清楚为什么我们的检索效果差，要有数据支撑，别太技术 | 32 | 为什么我们的检索效果差：给老板的汇报 | 18 | 检索效果差汇报 | 7 | 8 | 83 |
| ④ 几乎不成句 | AI学习 怎么学 路线 | 11 | AI 学习路线：怎么学 | 11 | AI 学习路线 | 7 | 6 | 79 |
| ⑤ 纯主题（对照） | 机器学习的主要方向 | 9 | 机器学习的主要方向 | 9 | 机器学习主要方向 | 8 | 8 | 50 |

（`scripts/measure_input_extract.py --arm off`；真 DeepSeek `deepseek-chat`、无材料、
外部检索关、单次采样。）

**"根节点 label 是不是整句话"这一列的答案是：不是。** 三层压缩叠在一起——33 字 → 23 字
（外层 agent）→ 13 字（模型写 root 时再压一遍），而且 `label` 有 16 字硬上限
（`GENERATED_LABEL_MAX_CHARS`，`tools.clip_label`）。一个 33 字的 topic 走到画布上必然
是被腰斩的前 16 字（`tests/test_input_extract.py::TestBaseline` 钉着这条）。

现象的真实位置在**另一个地方**，而且比"整段话"更隐蔽：**`主题：` 那一行是一句话**。
冒号前是中心词、冒号后是用途（`"…：路径与抵触化解"` / `"…：给老板的汇报"`），它带着
从句进提示词，于是整棵树的切法围着那句话转：

- ① 的三支「抵触情绪来源识别 / 沟通透明与参与感营造 / 激励与安全感机制设计」——原话
  里"担心员工抵触"这**一句话**被展开成了三条一级分支，10 支 104 个节点（可读性参考值
  是 80）；
- ③ 的分支是「现状 / 问题定位与归因 / 数据与索引质量 / 查询理解与召回 / 排序与相关性 /
  评测体系缺失 / 改进方案与优先级 / 资源需求与预期收益」——一个通用的分析框架。
  用户要的是"**给老板讲清楚**"，而"下周""别太技术""要有数据支撑"在树上**一处都没有**。

所以这一步要修的不是长度，是**压缩过程中被丢掉的三样东西**。

## 0.5 一次归因错误：不是模型判错，是输入里本来就没有

第一版把"③ 的 `constraints` 里没有'别太技术'"归因为**模型判定它不是硬条件**。一验就翻：

| 提取看的是什么 | ③ 的 `constraints` |
| --- | --- |
| 用户原话（`ctx.request.goal`，32 字） | `["下周汇报", "面向老板", "别太技术"]` |
| 外层 agent 压缩后的 `args.topic`（18 字） | `["面向老板汇报"]` |

**"别太技术"从来没进过提取的输入。** 工具层的 `args.topic` 是压缩产物，压缩发生在工具被
调用之前——那一步丢掉的东西，提取层再聪明也捞不回来。

所以这一轮的主修是**输入源**（`_extract_source`：原话与 `topic` 取更长的那个），自检只是
第二道。这个顺序很重要：先修输入，再看"自检补了什么"——否则测出来的全是压缩的损失，而
不是自检的价值（下面的读数就是修完输入源之后的）。

## 1. 判据：什么时候值得多花一次调用

长度阈值 `INPUT_EXTRACT_MIN_CHARS = 20`，依据是上表：两个真主题 9 / 11 字，三条"一段话"
18 / 19 / 23 字，20 落在两簇中间。

**判据只看 `topic`（压缩后的那个），提取看的是原话**——两件事分开：判据要回答"这段输入
值不值得多花一次调用"，而 `topic` 是"外层 agent 把它压成了什么"，最省事的信号；真要看
的是原话，那是输入源（`_extract_source`，更长者胜，见 §0.5）。

但**长度不是唯一判据**，两处实测缺口：

- ④（11 字）：`"AI 学习路线：怎么学"`——短，但一个冒号加一个"怎么"已经说明它不是名词
  短语。判据是**形状**：子句标点（`，；：、？！` 与括号）、诉求/疑问词（帮我 / 我想 /
  怎么 / 如何 / 为什么 / 汇报 / 讲解 …），任一条成立就提取。
- ③ 的**阈值不稳**：同一句原话两次运行，被外层 agent 压成 18 字与 21 字，落在 20 两侧。
  18 字那次是 `"检索效果差的原因分析（面向老板汇报）"`——纯长度判据会放行，而"面向老板
  汇报"恰恰是最该被捞出来的那件事。**括号是形状信号**：括号里的东西天然是用途/口径的
  注释，不是主题的一部分。补上这条之后 ③ 才稳定触发（`test_parenthesised_purpose_is_extracted`
  钉着它）。

判据落在 `_too_short_to_extract` 一个函数里，返回值是"为什么没提取"（`short` / `empty`
/ `off` / `budget` / `failed` / `unshaped` / `no_topic`），全部进 `data["input"]["skip"]`。

## 1.5 自检：四类线索，纯规则，零额外调用

提取返回之后，拿**原话**再对一遍四类线索（`_SELFCHECK_CUES`）：

| 类 | 抓什么 | 为什么是它 |
| --- | --- | --- |
| `amount` | 数字 + 量词（300 人 / 两周 / 十万） | **必须带量词**：光数字在主题里多是型号（RAG 2.0），补进去只添噪声 |
| `audience` | 给老板 / 向客户 / 新员工 / 内部 | 决定口径与深浅，是提取最该捞的一类 |
| `tone` | 别太技术 / 要有数据支撑 / 尽量简单 / 量化 | 原话里几乎全是祈使句，而模型最容易把它们算成"不是硬条件" |
| `deadline` | 下周 / 明天 / 这个月 | 时间压力会改变"要写到多细" |

判"漏"用的是**字面包含**：线索的匹配文本（`audience` 会先剥引导词，`"给老板讲"` 的核心是
`"老板"`）只要在 topic / intent / questions / constraints 任一处出现过就算接住。漏的按
**原文匹配片段**追加进 `constraints`（≤12 字、最多 3 条、不改写、不重排）。

### 检出率（五条输入，看原话的提取）

| # | 线索 | 接住 | 补 | 漏 |
| --- | --- | --- | --- | --- |
| ① | 2 | 2 | 0 | — |
| ② | 0 | 0 | 0 | — |
| ③ | 4 | 2 | **2**（`要有数据支撑`、`别太技术`） | `tone:要有数据支撑`、`deadline:下周` |
| ④ | 0 | 0 | 0 | — |
| ⑤ | — | — | — | 未提取（`skip="short"`） |
| 合计 | 6 | 4 | 2 | 2 |

**这张表本身就说明：输入源修好之后，自检几乎无事可做。** 模型看原话时自己就捞到了
"别太技术"、"面向老板"、"下周"；自检补的两条属于"这一次模型漏了"。②④ 一条线索都没有
（原话里确实没有硬条件）——自检不会凭正则**造**约束，这是它的硬边界。


## 2. 产出形状，以及"意图"影响了什么

```
{
  "topic":       "10-20 字的名词短语（唯一进 `主题：` 那一行的东西）",
  "intent":      "想了解 / 想对比 / 想规划 / 想排查原因 / 想讲解给别人听 / 想做决策 / 想动手做",
  "questions":   ["他真正想问的那几件事", "一件一条"],
  "constraints": ["制造业", "300人团队"]        ← 会影响内容的硬条件
}
```

消费点只有两处，都不改契约、不碰前端：

1. **`topic` 替换** `主题：` 那一行 **与** `_intake` 的两条 query（`_external_query` /
   `_library_supplement`）——同一份文本，两处都该是它。改动前 `_generate` 里有 9 处
   `args.topic`，现在一个不留（`data["input"]` 之外）。
2. **`intent` / `questions` / `constraints` 进 user 的一小段**（`_intent_block`），骨架与
   结构**两次**调用都带。

`data["input"]` 是这一步的读数（只在开关开着时才有这个键）：`topic` / `intent` /
`questions` / `constraints` 四个产出、`from`（这次读的是原话还是 topic）、`selfcheck`
（线索几处、接住几处、补了哪几条）、`seconds` / `prompt_tokens`。**`from` 是必需的**：
"提取不全"与"提取不准"在产物上长得一样，只有它能分开——而这两种的修法完全相反。

### A / B / C 三个候选里选了什么

- **A（只影响 topic）**：做了。理由最硬——它是唯一能直接回答"根节点为什么是一句话"的
  那一处。
- **C（`questions` 的条数 → 建议 `branches`）**：**没做**，两处依据：
  - `args.branches` 在整树这条路上**已经不进提示词**（`NO_BRANCH_CAP_RULE`，
    `docs/BRANCH-CAP.md`）。要让它生效就得先把"一级分支不设上限"这个上一轮的决定翻回来，
    那是另一件事；
  - 更重要的是**方向是反的**：实测分支数的下界从来不是瓶颈（②三件事 → 9 支，①一件事 →
    10 支），瓶颈在上界那一头（①10 支 104 节点）。给一个下界解决不了"为整齐/为凑数把
    不同的事合成一支或拆成三支"的问题。
- **B（意图决定骨架怎么切）**：这一轮没做。但做了它的**极小切片**：`intent` 与
  `questions`、`constraints` 作为**内容约束**进 user，不改切法、不改算法。③ 的 A/B 差别
  就来自这一片（见下）。

## 3. A/B：③ 那条三臂 × 三采样（"汇报支"是判据）

单次采样不可比（同一臂两次实测就能给出 4 支 / 7 支），所以这条**只测一条输入、每条臂跑三次**，
判据是"一级分支里有没有出现汇报/受众类的那一支"（标题含 汇报 / 老板 / 通俗 / 讲法 / 沟通 /
表达 / 呈现 / 受众 / 结论 之一）：

| 臂 | 提取 | 自检 | 汇报/受众支（3 次） | `constraints` |
| --- | --- | --- | --- | --- |
| off | 关 | — | **0 / 0 / 0** | — |
| a1 | 开（看原话） | 关 | 2 / 1 / 2 | 3 条，条目不固定 |
| b | 开（看原话） | 开 | 1 / 2 / 1 | **4 条，3/3 一致** |

（off 第 1 次是上一轮的读数：8 支、无汇报支——`docs` 这一节的表里没留 JSON，其余六次见
`scripts/measure_input_extract.py` 重跑。）

三条结论：

1. **输入源修复可归因**：off 三次一条汇报/受众支都没有；开了提取的六次**次次都有**
   （`面向老板的通俗讲法` / `面向汇报的结论与改进` / `改进方向与汇报要点` / `结果呈现与交互`）。
   这是"限定进 prompt 之后真的影响产出"的证据，也是这一轮唯一站得住的归因。
2. **自检的增量在噪声内**：a1（2/1/2）与 b（1/2/1）分不开。原因是 §1.5 那张检出率表——
   看原话时模型基本已捞全，自检补的那一两条改不了结构。
3. **自检的真实产出不是树，是 `constraints` 的稳定性**：b 三次都是 4 条且相同，a1 是 3 条
   且条目不固定（有时 `面向老板汇报`、有时 `下周汇报`）。这是一个**可观测、非噪声**的差别
   ——它在 `data["input"]` 里，不在画布上。

还有一条 ① 的读数（a1 臂）：8 支，「抵触情绪疏导」只占一支（关臂里"担心员工抵触"那句占
三支），`constraints = ["制造业团队", "公司300人"]`，自检 2/2 全接住、零补。

## 4. 代价

| 项 | 值 | 口径 |
| --- | --- | --- |
| 额外调用 | **1 次**（仅在判据触发时） | 短主题零调用（`skip="short"`）；自检**零调用** |
| 这一步的耗时 | 0.95 – 7.3 秒（十次，中位约 2.5） | `data["input"]["seconds"]`，含一次网络往返 |
| 这一步的输入 | 306 – 323 token | `estimate_input_tokens`，`data["input"]["prompt_tokens"]` |
| 这一步的输出上限 | 800 token | `INPUT_EXTRACT_MAX_TOKENS`（原 400，见下） |
| 输出上限 | 400 token | `INPUT_EXTRACT_MAX_TOKENS` |

也就是说：一次提取约 0.4k token 输入，换掉的是一棵按"一句话"切出来的树。

## 5. 自评：提取会不会丢信息？限定该进哪里？

**会丢**，而且已经测到过一次。三个判断：

1. **限定不能进 `topic`**。`topic` 直接决定根节点 label，而 label 有 16 字硬上限
   （`GENERATED_LABEL_MAX_CHARS`）——把"制造业 / 300 人 / 别太技术"塞进去，画布中央那一格
   就是一句被腰斩的话，正好回到要修的那个毛病。基线用例
   （`test_raw_text_reaches_the_topic_line_unchanged`）就是这条的实证：33 字的 topic 走到
   根节点只剩前 16 字。
2. **限定也不能进 system**。这四样是**这一次**的输入，不是树规则；本仓库已经三次记过
   同一条教训（`role=decision`、`_detail_ask` 的自查句、全塞模式的引用规则）——写在 system
   里的具体指令会被那段长而稳定的规则稀释。所以它们进 user，位置紧跟在 `主题：` 那一行
   之后（`_intent_block`）。
3. **"主题那一行会不会又变长"——不会。** 两块是分开的：主题行只有一个名词短语（≤24 字，
   实测开臂 16–20 字），限定各占一行、不参与根节点。代价是 user 多约 80 字（≈50 token），
   而一次结构调用的输入是 3000+ token。

**已经兜住的那一半**（第一版在这里写的是"还没兜住"，后来发现归因错了，见 §0.5）：输入源
改成原话之后，③ 的 `constraints` 稳定拿到 `别太技术` / `面向老板` / `下周`；自检再补上模型
偶发漏掉的那一两条（§1.5）。**注意次序**：先修输入源，自检才有意义——测"自检的价值"必须
在输入修好之后，否则量到的是压缩的损失。

**仍然没兜住的**（诚实记下两条）：

1. **语义重复靠规则拦不干净**。`_overlaps` + `_cue_core` 只挡得住"同一段原文被两刀切"和
   "受众被剥成同一个核心词"（实测拦掉了 `["面向老板", "给老板讲"]`）。`"别太技术"` 与
   `"通俗易懂"` 是同一件事，规则判不出来——那需要语义，而语义那一步已经花过一次调用。
   代价可接受：`constraints` 上限 5 条，多一条同义表述只是提示词多一行。
2. **线索表覆盖不到的口吻**。四条正则收的是实测出现过的写法（别太 / 要有 / 尽量 / 务必 /
   最好 / 通俗 / 量化 …）。`"按我们老板的习惯来"` 这种没有落到词表上的，仍然漏。
   这一条的正确解法**不是**继续加正则（越加越像在给一个样本量 5 的数据集过拟合），而是
   在 D 那 5 条之外**攒真实输入**——`data["input"]["selfcheck"]["missed"]` 就是攒它的入口：
   什么时候 `missed` 里出现了新形态，什么时候再扩表。

## 6. 开关与回滚

```
MINDMAP_INPUT_EXTRACT=1     # 默认关；正列举真值（1/on/true/yes），与其它四个开关同写法
MINDMAP_INPUT_SELFCHECK=0   # 自检默认开（零成本），A/B 时用它切那一臂
```

关着时：`_read_input` 只做一次 `os.getenv`，`topic` 与 `args.topic` 逐字节相同，
`_intent_block` 恒为空串（两处 `+=` 等于没写），`data` 里**没有** `input` 这个键。
四种退化都**不失败**：额度不够（`budget`）、调用失败（`failed`）、返回不合法
（`unshaped` / `no_topic`）时退回原话，并在诊断里留一条 `INPUT_EXTRACT_UNAVAILABLE`
——一个会改变提示词形状、会花一次调用的步骤，必须留下它的决定。

**输出上限从 400 提到 800**：400 实测贴边——③ 跑出过一次 `GenerationError`（返回内容不是
合规 JSON），四个字段稍写长一点就撞上限，被截断的 JSON 在 `parse_model_json` 那里就是
"不合规"。上限只影响"最多能写多少"，不动平时那 200 字的成本。

不覆盖的地方（刻意）：`mindmap_generate_deep`（`create` 意图不注册它）、
`node_expand` / 编辑那八条路、以及按章切（`MINDMAP_SECTION_SLICE`）时每章的那次调用
（它的 user 是 `_slice_ask`，只带主题，不带那三样）。

## 7. 复现

```
python scripts/measure_input_extract.py --arm off                  # 基线：五条输入，现状
python scripts/measure_input_extract.py --arm on                   # 开臂：同一批
python scripts/measure_input_extract.py --arm on --selfcheck off   # A1 臂（关自检）
python scripts/measure_input_extract.py --arm on --extract-only    # 只量检出率（不生成树）
python -m pytest -o addopts="" -q tests/test_input_extract.py
```

脚本走的是完整 `service.run`（不是直接调工具），所以第一列 `args.topic` 是**模型真的填出来
的**参数——这一列是这一轮所有结论的前提。`--extract-only` 走 `_read_input` 本身，一条一次
小调用，量的是"提取 + 自检能捞到什么"。
