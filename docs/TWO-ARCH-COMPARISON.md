# 同条件对比：整树一次生成 vs 逐支分片

**这份文档回答一件具体的事**：`docs/SUBAGENT-VS-SELFCHECK.md` 里"分片产物 31% 有跨支重复、
一次写完 11%，每张图 1.31 对 0.32"那个对比，能不能用来否掉"每支一个子代理"那条架构。
结论是**不能**——那个对比的取得方式、判据、统计与分母都有问题（第三方复查指出四条，
我逐条复核过，四条都成立，见第 6 节）。所以这里重做了一遍同条件实测。

**一句话结论**：旧裁定的**依据**必须撤回；重做的对比给出的方向仍然偏向整树（每百节点
多余重复 2.46 对 5.51 = 2.2 倍，旧口径那两个是 2.8 倍与 4.1 倍），但区间贴边、样本
12 张/臂，**不足以支撑"因跨支重复否掉逐支"这个裁定**；而且在延迟、token、引用覆盖
三项上逐支反而更好。

## 1. 两条路让"逐支方案"跑起来——我选了哪条

**我选的是"从代码里把真实现找回来"，不是手动模拟。**

原以为分片实现已经被删干净（`bc3494e` 把主路径换成整树一次生成，提交信息里写着
"为什么回到一次生成"）。查下来它**没被删**：

```
bc3494e  feat: 主路径改成一次调用生成整棵树（detail 偏短，已知缺陷）
   tools.py 里删掉的是"注册"，不是实现：
   _generate_deep / _generate_deep_spec 仍在（HEAD 的 tools.py:11835 / 16360），
   _ALLOWED_BY_INTENT 里留着一条 create_deep → ("mindmap_generate_deep",)（16261），
   注释写着"等真有大图需求时把 mindmap_generate_deep 加进 create 那一行即可，
   实现一行都不用改"。
```

所以 B 臂用的是**产品里那份真实现**：`registry = build_registry("create_deep", ...)` +
`RunContext(request.intent="create")`（工具内部那句 `intent != "create"` 的守卫要过），
工具名 `mindmap_generate_deep`，一条产品代码都没改。

### 1.1 这个"逐支"与用户描述的那个方案，差在哪

用户提的是：**先定一级节点 → 每支一个子代理生成 → 每支再各做一次检查 → 错就修**。

真实现是：**骨架一次调用 → 每支并发展开 → 确定性验收（`_audit_branches`，零模型调用，
只数"这一支的子节点够不够 `points_per_branch` 个"）→ 只补不合格的那一支**。

| 用户方案 | 我测的 B 臂 | 差在哪 |
|---|---|---|
| 每支一个子代理生成 | 每支一次展开调用（`run_branch` 流水线） | 等价：都是一支一次独立上下文 |
| **每支各做一次检查** | **确定性验收，不发模型调用** | **不等于**：`_audit_branches` 只数子节点个数，不看内容 |
| 错就修 | 只对"点数不足"的那一支重发一次 | **更弱**：内容错、语义重复都不触发重试 |

**这是 B 臂相对用户方案系统性偏弱的一处**，不是偏强：用户方案里"每支一次模型检查"正是
抓语义重复的那一步，而实现里根本没有那一步（`MINDMAP_SELF_CHECK` 只接在
`_generate` 里，`tools.py:11076`；分片那条路一个开关都不读）。

为什么不在测量脚本里替它补上：补上了，测出来的就不是产品、也不是用户方案，而是第三种
东西；而且我没有那套"检查 → 修"的逐支提示词，自己拼一份等于把结论建在我的措辞上。
**所以本报告关于"逐支"的一切结论，都只对"产品里那份分片"成立，不能直接推到用户方案；
用户方案多了一道模型检查，重复率很可能更低、调用数更高。**

| 模型 | 同一个 `deepseek-chat`、温度 0.2、同一份凭据，同一进程连跑 |

### 2.1 判据：人工判，不机械判

**计数单位 = "多余出现"**，规则先定死再开跑：

1. 取每棵树全部非根节点（标签 + 完整路径）。
2. 把"说的是同一件事"的标签聚成一簇：允许换词、简称/全称、中英混写、括号补充、
   "X 的过程"与"X"、同一概念被拆成两层说。
3. **不**算同簇：上位与下位（"机器学习"对"监督学习"）、同层并列子项（"编码器"对"解码器"）、
   互为因果或前后步骤、泛化与实例、"优势"与"局限"（两个侧面）。
4. 一簇内保留第一次出现为正当，其余每一次记 1 处多余重复。
5. **只数跨一级分支的**；同一支内部、父子/祖孙包含关系、一级分支自己又出现在自己子节点里
   ——都不数（那是结构问题，另有判据在管。旧判据把它们算进去了，这是复查②指的"判据宽"）。

## 4. 结论

### 4.1 哪个方案在哪个指标上更好

| 指标 | 谁更好 | 强度 |
|---|---|---|
| **每百节点人工判多余重复** | **整树**（2.46 对 5.51，5/6 组同向） | 中等偏弱：CI 贴边 [−6.18, −0.15]，n=12/臂 |
| 机械跨支重复（旧口径） | 打平（0.68 对 0.75） | 这个判据本身抓不到 81% 的问题，不该再当主指标 |
| 墙钟 | **逐支**（30.0s 对 63.6s，快 2.1 倍） | 强：两臂各 12 张、差距远超组内极差 |
| token/图 | 逐支略低（44.2k 对 47.7k） | 弱：同一量级 |
| token/节点 | **整树**（486 对 665） | 中：逐支每次调用都要重发一次路径与证据 |
| 调用数 | **整树**（6.7 对 21.2；合计 80 对 255） | 强：3.2 倍，这是架构决定的 |
| 可引用覆盖率 | **逐支**（有材料那 8 张：91.2% 对 79.5%） | 中：逐支每支只看自己那份证据，写引用更"贴" |
| 材料份数覆盖 | 打平（有材料 8 张两臂都是 100%） | — |
| detail 长度 | **整树**（115 字对 75 字） | 中：与 `bc3494e` 那条"整树 detail 偏短"的历史结论相反，那批开关下不成立 |
| 交付完整性 | **整树**（0 对 2 张 `partial`） | 逐支会因额度分配交半棵树，这是实打实的代价 |
| 结构整洁度（离线再修） | **逐支**（0 步对整树生成期 114 步） | 整树自己在造结构问题，修复层是它的补偿而非中立工具 |

**旧说法里"分片付了 25 次调用、30 秒"的那个代价描述，只剩一半是真的**：调用数确实 3 倍，
但**它是更快的那一个**（30s 对 64s），token 也更省（`bc3494e` 那句"30 秒"其实早被
`SUBAGENT-VS-SELFCHECK.md` 自己修正过——那里写的是"分片 32.3s vs 一次写 38.4s，分片更快"，
只是那条修正没被带进后来的裁定）。原因是整树的一次输出更长（输出 token 190k 对 107k），
单次生成把延迟全压在最长的那一次调用上。

### 4.2 我今天那个否定裁定，该不该撤回

**该撤回的是"依据"，不是一个字都不剩。**

- **撤回**：`docs/SUBAGENT-VS-SELFCHECK.md` 里"31% 对 11%、每张图 1.31 对 0.32"这个
  对比不成立（四条理由我全部复核，见第 6 节）。它**不能**用来否掉逐支，也**不能**
  反推逐支更好——它是不可比的。
- **不撤回**：方向。同条件重做之后整树仍然更低（2.46 对 5.51），我不打算因为"旧数字错了"
  就把结论翻过来；那会是我今天犯的同一个错的镜像。
- **降级**：强度。从"4 倍差距、直接判死"降到"2.2 倍、区间贴边、12 张/臂、判据是我定的"。
  按这个强度，"跨支重复"只能当**一条次要理由**，而且必须同时承认逐支在延迟、token、
  引用覆盖上更好。

所以裁定应当重写成：

> 采纳整树一次生成，理由是**可审计与可终止**：一次成型、一个提示词、一处失败点、
> 调用数 6.7 对 21.2、不会交半棵树（0 对 2 张 `partial`），而修复层能确定性收掉结构问题
> （12 张共 114 步）。**不再**以"跨支重复"为主要依据；那一项在可控条件下只差 2.2 倍，
> 且样本不足以定论。逐支在延迟（快 2.1 倍）、token、引用覆盖上更优，若将来图的规模
> 超过一次输出能写的量（`bc3494e` 留的那条 `create_deep` 入口），它仍是正确的备选。

### 6.2 消不掉的，按"会不会改变结论"排序

1. **我测的"逐支"不等于用户方案。** 产品里那份分片没有"每支一次模型检查"（`_audit_branches`
   零模型调用，只数子节点个数），也没有内容层的"错就修"。用户方案多一道模型检查 →
   重复率很可能更低、调用数更高。**这一条消不掉**（要消掉就得改产品代码，那正是本次不做的事）。
   影响方向：**对逐支不利**，即真实用户方案可能比这里的 5.51 更好。
2. **两臂看到的材料形态不同，这是架构差异本身。** 整树在材料 ≤50,000 字时把正文全塞进
   prompt；分片永远按支检索（`tools.py:11950` 明说它不采用全塞）。所以 S/M/L 三组两臂
   的输入并不相同——**只有 X（>50k，两臂都走按支检索、语料同一）与 P1/P2（零材料，
   输入只有主题）是同一形态**。
   而恰恰在 X 组，逐支是 **0.00**、整树是 **1.01**（逐支更好）；无材料的 P1/P2 又是逐支更差。
   **这一条消不掉**，而且它让"整树重复更少"这个结论**不能**归因于"一次写完"这个形态本身
   ——很可能是"看到全量材料时，模型会用一个中心把话题分配开"这个副作用。
3. **盲评是 LLM 评审，不是人。** 四份结果用同一条 rubric，但我只把 L-B-2 的几条证据
   （"路径长度为常数"对"一步直连"）与 M-A-1 / M-B-1 的标签清单对回了原始树，其余 20 张
   没有逐条复核。评审者对"换词算不算同一件事"的宽严若在两臂间系统性不同，我这边看不出来。
   缓解：随机命名、四个互不知情的评审者、口径写死、不数拿不准的。**残留消不掉。**
4. **节点规模的分布不同。** 逐支被 `INITIAL_MAX_NODES=80` 卡住（实测 53–80），整树能到 214。
   每百节点只解决量纲，不解决混杂。自检发现：**整树臂内**"每百重复率"与节点数正相关
   （r=+0.64），也就是树越大重复越多——这个梯度对整树**不利**，所以"整树更低"不是大树
   带来的假象；但**逐支在 100 节点以上会怎样，这批数据一个字都没有**。
5. **组数与主题覆盖。** 6 组、4 个主题、每臂 12 张。按组配对 5/6 同向，bootstrap 区间贴边
   （上界 −0.15）。**这个样本量够说"方向一致"，不够说"整树更好"。**
6. **材料本身的结构会造重复。** M 组用的是维基条目，整树那条路会跟着材料的目录/参见结构
   生成一个"目录索引"支，把别的支的标题再写一遍——M-A-2 那 15 处里有 6 处牵扯"参见条目"支。
   这既是整树的真实缺陷（它把材料的目录结构当成了内容），也让 M 组的"整树 5.14"偏高。
   两臂都会受影响，但受影响的方式不同。

### 6.3 所以结论该写成什么

- **"旧对比不成立"**：证据充分（四条我逐条复核，含 Fisher p=0.0764 自己算了一遍）。
- **"整树在跨支重复上明确更好"**：**证据不足**（区间贴边、n=12、判据我定、最可比的 X 组反向）。
- **"逐支更快、更省、引用覆盖更高"**：证据较充分（延迟差 2.1 倍、远超组内极差）。
- **"逐支会交半棵树"**：证据充分但是低频（2/12），不能当主要理由。

**如果只允许写一句**：跨支重复这条依据要撤回，架构决定改立在"调用数 3.2 倍 + 交付完整性
+ 可审计"上；"整树重复更少"这条只留作**次要**、且标注证据不足。
