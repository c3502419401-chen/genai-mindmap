> 2026-11-27，本机（Windows / 16 逻辑核 i5-13500H / Node 24 / vitest 5.0.5 / jsdom 30）实测。
> 触发：同一天第三次在**负载**上翻车，而前两次的处置都是"给这一条加宽"。
> 前置：`docs/TEST-COST-136-NODE.md`（136 节点那两条）、`docs/TEST-COST-3-CASES.md`（三条裸奔在 5 秒线上）。
> 数据：`docs/TEST-LOAD-SENSITIVITY-TABLE.md`（脚本生成的完整表，勿手改）。
>
> **结论先行**
>
> 1. **"满载（后端 pytest 全量同机）"对前端全量的影响很小：墙钟 +10.7%，逐条中位 1.27×、p90 2.0×。**
> 2. **真正把用例推过线的是"全量并行"那一层：慢用例的单跑 → 满载放大的中位是 9.88×、最大 13.64×。**
> 3. 按本机满载算，风险区（余量 < 30%）只有 **1 条**（`defects.spec.ts` 那条，余量 13.7%）——所以

>    落成了一个落库基线 + 静态闸门（`npm run test:cost:gate`，已进 CI），不再靠"以后注意"。

## 1 怎么测的（脚本，不是估算）

三个脚本，都在 `frontend/scripts/`，只读测试文本、不改业务代码：

| 脚本 | 干什么 |
|---|---|
| `measure-test-cost.mjs` | 跑一次 vitest，连同**当时的 CPU 占用**一起落成 JSON 快照（`--label idle/loaded/solo`） |
| `report-test-cost.mjs` | 把快照拼成表：空闲 / 满载 / 倍数 / **现有上限（静态解析）** / 满载余量；可 `--baseline` 落基线 |
| `check-test-cost.mjs` | 闸门：上限是否还够（`--gate` 失败即退出码 1），已进 CI |

三档负载，同一天同一份代码：

```bash
# ① 空闲：机器上没有别的重活（后端 pytest 已退出，静默 20s）
cd frontend && npm run test:cost                    # 落 _test-cost-idle.json

# ② 满载：真跑后端全量（不是伪造的 CPU 占用）
cd backend && python -m pytest -o addopts="" -q &   # 约 9 分钟
cd frontend && node scripts/measure-test-cost.mjs --label loaded \
  --note "backend pytest 全量在跑（PID 18264，21:21:23 起）" --out _test-cost-loaded.json

# ③ 单文件串行：开发者本地验证一条用例的形状
node scripts/measure-test-cost.mjs --label solo --solo \
  --files tests/defects.spec.ts,tests/view-collapse-canvas.spec.ts,... --out _test-cost-solo.json

# 拼表 + 落基线
npm run test:cost:report
```

### 1.1 每一轮的实际负载状态（脚本采的，不是回忆）

| 轮次 | 时间 | 外部负载 | 开跑前 CPU | 全程 CPU 均值 / 峰值 | 墙钟 | 结果 |
|---|---|---|---|---|---|---|
| idle | 21:34:18 | 后端 pytest 已退出，静默 20s | 37.7% | **81.8%** / 100% | 45.9s | 1462/1462，0 失败 |
| loaded | 21:23:56 | **后端 pytest 全量在跑** | 44.3% | **82.1%** / 100% | 50.8s | 1462/1462，0 失败 |
| solo | 21:36:53 | 无（单文件串行，`--no-file-parallelism`） | 19.8% | **23.4%** / 48.1% | 41.1s | 201/201，0 失败 |

**读法**：idle 与 loaded 两轮的全程 CPU 均值几乎相同（81.8% / 82.1%）——因为 vitest 自己的
并行（15 个 worker / 16 线程）已经把机器吃满。后端 pytest 一个进程加进来，只能抢到剩下的那点
边角。这就是 §2 里"外部负载只有 1.27×"的成因，也是这条结论**不能**被推广成"满载无害"的原因：
它的前提是"vitest 已经先占满了机器"。

### 2.1 倍数分布（满载 ÷ 空闲；两轮都是全量）

| 区间 | 条数 | 占比 |
|---|---|---|
| < 1.5× | 1174 | 80.3% |
| 1.5–3× | 238 | 16.3% |
| 3–10× | 48 | 3.3% |
| 10–30× | **2** | 0.1% |
| ≥ 30× | 0 | 0% |

中位 **1×**、p75 1.35×、p90 1.99×、p99 5.88×、最大 11.5×。

**那两条 >10× 的是什么**：`node-drag` 的一条（0.2ms → 2.3ms，11.5×）、`sources` 的一条
（1ms → 10.7ms，10.7×）。**都是毫秒级、余量 99.8% 以上、永远不会红。**

> 所以第一个结论：**倍数不是风险判据。** 10× 以上的用例一条都不危险，而唯一危险的
> （`defects` 4313ms）倍数只有 1.18×。倍数只说明"这条被 CPU 争用影响多大"，不说明"它够不够用"。
> 风险判据只能是 **满载耗时 ÷ 现有上限**。

### 2.3 放大来自哪一层

这 10 条（表里取 top20 算的同一口径）：

- **单跑 → 全量满载**：中位 **9.88×**，最大 **13.64×**
- **空闲 → 满载（外部负载那一层）**：中位 **1.27×**

也就是说：**把慢用例推过线的 90% 是"全量并行"，不是"机器上还跑着 pytest"。**
而开发者本地验证用的是前者（`npx vitest run tests/x.spec.ts`），CI 跑的是后者 —— 中间那
9.88× 从来没有人看见过。

## 3 那几条慢的共同点，与两个可算的判据

### 3.1 共同点不是"挂得多"，也不是"算得重"

`defects.spec.ts` 那条**一行 `mount` 都没有**，却是本仓库第四慢的用例（4313ms）；
而 `canvas-edges` 只挂 5–7 个节点，也比很多挂 40 个节点的用例慢。所以"看起来重"这个直觉不可用。

真正的共同点是**"一条用例里重复付的真实工作量 × CPU 时间片"**：

| 成本项 | 标定值（满载 / 全量并行） | 来源 |
|---|---|---|
| jsdom 里挂一个 `MindNode` | **≈ 40ms** | 136 节点那条 5437ms ÷ 136；`docs/TEST-COST-136-NODE.md` 的 33ms/节点是同一量级（旧读数） |
| 一次真画布挂载（`@vue-flow/core`） | **≈ 350–450ms** | `canvas-edges` 1956ms ÷ 4 条 mount、`relation-lines` 1857ms ÷ 3 条 |
| 一次真几何（`previewMove` / 落点计算） | **≈ 6.3ms** | `defects` 4313ms ÷ 684 组合（单跑口径 0.93ms/次） |

三者都随机器负载线性走，没有一条是"卡在计时器上"。这就是它们的放大系数接近同一个值的原因
（9–14×），也是"给这一条加宽"永远只能救一条的原因。

### 3.2 判据一：写用例时就能算（误差 ±2 倍，够用）

```
满载估计 ≈ 40ms × 挂载的 MindNode 数
          + 400ms × 真画布挂载次数
          + 6.3ms × 真几何/真布局调用次数
```

校核：136 节点那条 → 40×136 = 5440ms（实测 5437ms）；`defects` → 6.3×684 = 4310ms（实测 4313ms）；
`canvas-edges` → 400×4 = 1600ms + 节点（实测 1956ms）。三条都落在 ±20% 内。

**用它的方式**：算出 > 2500ms 就别裸奔。2500ms 是默认 5000ms 的 2× 安全线——
CI runner 通常比本机慢 1.3–2×，2× 是"下一次不翻车"的最低要求。

### 3.3 判据二（更硬、无需估算）：**单文件串行 ≥ 500ms ⇒ 必须有显式上限**

500ms × 6（实测并行放大下界 6.79×，保守取 6）= 3.0s > 2500ms 安全线。所以"单跑超过半秒"
就是"默认上限迟早不够"的**最早可观测信号**，不必等全量翻车。

这条已经做成闸门的第二条规则（`check-test-cost.mjs`）：基线里 `soloMs ≥ 500` 却仍是默认
上限的用例，`--gate` 直接红。

### 3.4 写用例时要避的三种形状（本轮实测支持的）

1. **一个 `it` 里挂 ≥ 40 个 `MindNode`** → 满载 ≥ 1.6s，必须显式上限（这是"规模型"，别想着减）。
2. **一个 `it` 里真几何/真布局调用 > 200 次**（`for` 穷举 × `previewMove`）→ 满载 ≥ 1.3s；
   超过 400 次就过 2500ms 线。
3. **一个 `it` 里 `mount(MindMapCanvas)` 且文件里有 ≥ 3 条这样的用例** → 每条 350–450ms，
   全量并行下每条 1.5–2s。

反过来，**不该做**的是：为了"快"把 136 节点的树降到 20 个节点（抽掉断言前提）、或者把真几何
mock 掉（`previewMove` 的价值就是"坐标真的算出来了"）。这两条在 `docs/TEST-COST-136-NODE.md` §4
与 `docs/TEST-COST-3-CASES.md` §3 已经各写过一次，这里只补一句：**减负载只能减"与断言无关的负载"**
（例如 `canvas-preview` 从 `mount(App)` 改成 `mount(MindMapCanvas)`，省掉 223 个 DOM 里与断言无关的 174 个）。

## 5 自评：这是"少数意外"还是"普遍现象"？

**都不是，但更接近后者——而且后者的落点不是"CI 满载"，是"本地单跑"。**

分开看两个量：

- **"满载下会红"的用例：少数。** 1462 条里 1 条（0.07%）在 30% 余量以下；把 CI 折算（×2）算进来
  是 3 条（0.2%）。所以"整个套件在满载下普遍会红"不成立，不必因此去做全局超时翻倍。
- **"用单跑结论判绿"这件事：普遍失效。** 全量并行把慢用例放大 9.88×（中位）——只要一条用例
  单跑 ≥ 500ms，它的本地绿灯就与 CI 的结论没有关系。本轮只对 top 慢用例所在的 12 个文件采了
  单跑读数（45 条），其中 **8 条单跑 ≥ 500ms**（占采样 18%），全部落在"单跑的绿灯不可信"的区间里。
  这 8 条现在都有显式上限，所以不会有"下一条翻车"的那一条——但那 9.88× 的放大对**未来**任何
  一条新写的、单跑 ≥ 500ms 的用例都同样成立，这就是判据二存在的理由。

所以：**问题不在个别用例，也不完全在"CI 是满载的"，在于"验证口径"与"验收口径"不是同一个。**
CI 的口径是 `npm test`（全量、15 worker 并行）；本地验证的口径长期是
`npx vitest run tests/某一条.spec.ts`（串行、单 worker）。两者之间那 9.88× 没人量过，
于是每次都是"本地绿 → 合并 → CI 红 → 给这一条加宽"。

### 5.1 该改什么（三条，都带执行点）

1. **判绿的唯一口径是全量。** 单文件跑只用来"快速看某条有没有明显坏掉"，不能作为"这条没问题"的
   结论。写进 `frontend/tests/README.md`（就在写用例的人眼皮底下），并在 `docs/TEST-LOAD-SENSITIVITY.md`
   （本文）保留完整理由与数据。
2. **贵用例的上限定在全量读数上，不在单跑上。** 操作规程：新写/改动一条用例 → 若单跑 ≥ 500ms →
   跑一次 `npm run test:cost` → 用满载值 × 2 定上限，并在注释里记**三项读数**（单跑 / 空闲全量 / 满载全量
   + CI 折算）。这是 `docs/TEST-COST-136-NODE.md` §4 已经立过的规矩，本轮把它扩到"所有 ≥500ms 的用例"。
3. **不靠自觉：闸门 + 基线进 CI。** `frontend/scripts/test-cost-baseline.json` 落了 199 条
   （满载 ≥ 300ms 或写了显式上限的用例），`npm run test:cost:gate` 在 CI 的 `npm test` 之后跑：
   - 上限 < 1.5 × 满载 → **红**（就是今天 `defects` 那条的位置）
   - 上限 < 2.0 × 满载 → 黄（CI 慢 1.3–2× 就会过线）
   - 单跑 ≥ 500ms 却仍是默认 5000 → **红**（判据二，不必等全量翻车）

   它是**静态**的（只读 `tests/**/*.spec.ts` 的文本 + 基线 JSON），确定性、秒级、与机器无关，
   与后端那条 `find_unwired.py --gate` 同一套棘轮语义：基线之外不阻断，基线之内不许退化。
   改测试成本的人必须重跑 `npm run test:cost` 更新基线——**这一步有产物（基线 diff），review 时看得见。**

为什么这三条比"以后跑全量"更可能被执行：第 1 条是纪律（只能写在文档里），第 2 条给了可算的门槛
（500ms / 2500ms / ×2），第 3 条把它变成 CI 的退出码。一回事说三遍不如把它变成一次失败。

## 6 复现

```bash
cd frontend

# 1) 空闲档
npm run test:cost

# 2) 满载档（另开一个终端先起后端全量，约 9 分钟）
#    cd ../backend && python -m pytest -o addopts="" -q
node scripts/measure-test-cost.mjs --label loaded \
  --note "backend pytest 全量在跑" --out _test-cost-loaded.json

# 3) 单跑档（把 top 慢用例所在文件列进去）
node scripts/measure-test-cost.mjs --label solo --solo \
  --files tests/defects.spec.ts,tests/view-collapse-canvas.spec.ts,tests/branch-digest.spec.ts \
  --out _test-cost-solo.json

# 4) 表 + 基线
npm run test:cost:report
npm run test:cost:gate
```

产物：`docs/TEST-LOAD-SENSITIVITY-TABLE.md`（表，脚本生成）、`frontend/scripts/test-cost-baseline.json`
（基线，入库）。快照 JSON（`frontend/scripts/_test-cost-*.json`）是中间产物，用完即删。

**本机的噪声下界**：同一档两次独立运行的墙钟差可达 10%（45.9s / 50.8s），逐条读数差可达 ±30%
（对照 `docs/TEST-COST-3-CASES.md` §0 记的"同一分钟里 365ms / 6606ms"）。所以：
**上限按"见过的最坏值 × 2"定，不按单次读数定**——这条已经被这个仓库的两次独立实测各自印证过一次。
