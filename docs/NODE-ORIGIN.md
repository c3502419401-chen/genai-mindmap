# `origin`：补不补、补成什么

> 这一份只做**判定与设计**，不改契约。`backend/app/contracts/**` 一个字节都没动。
> 执行单在最后一节，下一位接手的人照它做就行。

## 〇、这件事是怎么被提出来的

三处互相矛盾的证据，凑到一起才成为证据：

1. **`docs/NODE-EDIT.md` §五** 论证"现在不该加 `origin`"，最后一句是"**等有需求再加**"。
2. **界面上已经有一句话在替这个字段说话**（`App.vue` 的引用覆盖率）：

   > 这张图 24 个节点里有 12 个带原文引用（50%）。没有引用的节点不代表内容有错：
   > 生成时模型没在材料里找到对应句子，**或者这个节点是你自己加的**。

   它把"两种情况之一"当成了用户能自己分辨的事实——而数据里没有这个信息。
3. **写用户路径测试的 agent 撞到**：手动节点无标记 → 抓不到，且**本来就没有红灯形态**；
   契约里没有 `origin`，断言不了一个不存在的信息。

三件事指向同一个判据：**一句话在界面上承诺了数据没有的信息时，要么补数据，要么改那句话。**
不存在"两个都不动"的选项——现在的状态是第三种：那句话已经被写出来了，所以 §五 的
"等有需求"已经不是中立等待，而是"需求到了而文档还在说没到"。

## 一、§五 那三条理由，逐条判

### 理由 1：「谁加的」已经能从账本读出来，而且比节点字段更准

**半成立。** 它在一个时刻成立，在另一个时刻不成立，而那两个时刻恰好可以分开。

成立的部分：`mindmap/edit-log.ts::diffEdits` 为每个新节点发一条 `kind='add'` 事件，
带 `actor: 'user' | 'agent'`、`nodeId`、`parentId`、`depth`，随保存请求一起落进
`edit_events`。同一次会话里，"这个节点是谁加的"确实查得到，而且带时间——字段说不出时间。

不成立的部分，三条都是**现在就能验证的**：

- **账本读得回来，但读的不是"这个节点"。** `GET /api/mindmaps/{id}/edits` 有测试
  （`tests/test_edit_events.py`）、有前端封装（`client.ts::listEditEvents`），第 3 件
  之后还有界面入口（`components/EditLedger.vue` 的「改动记录」）。但它是**一张图的
  列表**：要知道"这一个节点是谁加的"，得先在列表里找到它（或勾「只看选中节点」），
  而那要求那条 `add` 事件存在——见下面两条。
- **打开旧图时账本是空的。** `stores/mindmap.ts::loadMap(content, record)` 只接
  `content / id / version / updated_at`，`pendingEdits` 不随打开动作回填。三天前保存的
  图里，"这 12 个没引用的节点"里哪些是手动加的——界面此刻没有任何依据。
- **导入的图根本没有账本。** `POST /api/import` 进来的一张图，一条 `add` 事件都不存在，
  而那张图**全部节点都是手动的**。这是"手动节点"最大、最集中的来源，恰好是账本
  覆盖不到的那一块。

顺带一个更根本的差别：账本是**事件流**，字段是**节点属性**。要拿账本回答"这个节点
现在是谁加的"，得重放 `add` / `remove` / `move`，还要处理分批截断
（`EDIT_EVENT_LIMIT` 满了留到下次保存）和账本本身可能被清掉的情形。字段是一次读取。

**判定：成立范围只有"同会话"，而界面那句话最常被读到的场合（打开一张旧图）恰好不在
那个范围里。**

### 理由 2：「可追溯」该定义在生成产出上，而不是全部节点上

**成立，但它不能拿来给那句文案背书。** 这两件事主语不同：

- 验收说的是"**生成产出**里有多少能追回原文"——这条判据到现在仍然正确，
  `verify_source_refs` 只产出 `UNSOURCED_NODE` warn，不删节点，也不判废。
- 那句文案说的是"**这个节点**为什么没引用"——这是对单个节点的归因，而验收从不需要它。

所以理由 2 只能证明"不补 origin，验收不会失效"。它证明不了"界面可以不区分"。
把两者混在一起谈，会让"验收不需要"听起来像"用户不需要"。

**判定：成立，但与本题无关。** 它说的是验收的判据，不是界面可以说实话的范围。

### 理由 3：加字段的成本是不对称的，而且唯一使用者是"将来可能做的验收"

**成本被高估了，使用者被低估了。** 两条都用仓库自己的代码核对过：

成本那半：「`origin` 要同时出现在契约、**三个形状的序列化**、导入导出、以及所有
`UpdateOp` 的『缺省 = 不动』语义里」。实际上：

- 三种形状**共用同一个 `Node`**：`MindMapContent.root`（`contracts/mindmap.py:745`）、
  `FishboneBone.root`（`:860`）、`FlowStage.root`（`:965`）都是 `root: Node`。
  字段加一处，三种形状同时有。
- 导出 JSON 走 `content.model_dump(mode="json")`（`export/service.py:874`），
  注释里那句是现成的："契约加字段时这里自动跟上，不会漏"。导出侧**零改动**。
- `UpdateOp` 的"缺省 = 不动"只约束**可编辑字段**。`origin` 描述写入来源，它不该被
  `UpdateOp` 写——加节点时由执行方设，不从 op 里读。于是那条语义**不用改**。
- 旧数据零迁移：`Node` 上已经有先例——`expandable: Literal["yes","no","unknown"] = "unknown"`
  （`:507`）与 `role: ... | None = None`（`:560`），两条注释写的是同一条规矩
  "**新字段一律有默认值**，库里所有旧图不需要迁移脚本就能读进来"。

于是真实成本是：`Node` 加一行 + 一个 `Literal` 常量 + 两条写路径各设一次 +
`openapi.json` / `schema.d.ts` 重导 + 前端在两三个地方读它。**不是"四种形状"那一摊。**

使用者那半：「唯一使用者是将来可能做的验收」在写下时就已不准确——`App.vue` 的覆盖率
那句、以及 `MindMap` 面板里"契约里没有手动/生成标记"那段说明，**现在**就在用这个信息，
只是用得**不诚实**：一边说"没有标记"，一边替它给出答案。

**判定：成本成立但比文档写的小一个数量级；使用者不是将来，是现在那句文案。**

## 二、结论：补

三条理由都不足以支撑"不补"。但只说"补"不够——**补它必须是为了让那句话能说实话，
而不是为了将来某次验收**。判据写在这里，免得下一轮又变成"要不要做"：

> 补 `origin` 的收益只有一个：**把一个数字拆成两类，而这两类的下一步动作不同。**
>
>   · 生成链路写的、但材料里没找到对应句子 → 可以补材料 / 换个更具体的主题再生成一次；
>   · 不来自生成链路的节点 → 它本来就没有原文可引，**不需要处理**。
>
> 现在界面上这两类被一个"或者"糊在一句里，用户读完不知道该做什么，只知道界面在解释
> 自己。这是那句话真正的毛病：**它不是不准确，而是不给出下一步。**

如果哪天这个二分被推翻了（比如用户根本不关心 12 个没引用节点里哪些是手动的），
那 `origin` 就该跟着不补——而不是"反正加都加了"。

## 三、设计（契约那一轮的执行单）

### 3.1 字段

```python
class Node(BaseModel):
    # 这个节点是**怎么写进来的**。它服务一句话："没有引用是不是问题。"
    #
    #   - `generated`：生成链路写出来的（整树 / 分片 / 展开），可能有 `source_refs`；
    #   - `manual`   ：不经过生成链路写入——用户加的、剪贴导入的、agent 在**编辑轮**
    #                  里 `add_node` 加的。语义是"没有走过生成链路"，**不是**"人手打的"；
    #   - `unknown`  ：不知道（旧图、第三方格式导入的图）。
    #
    # 三态而不是布尔，理由与 `expandable` 逐字相同：布尔没有"不知道"，它会把旧图默认成
    # `false` = 生成产出——老图里几乎全是手动节点，报成生成产出比不报更糟。
    #
    # `manual` 的措辞是刻意的：若把它定义成"用户加的"，agent 的 `add_node` 就没有位置
    # （它既不是生成产出也不是人加的），而界面只能跟着撒谎。定义成"不来自生成链路"，
    # 那句文案就永远成立，无论那个按钮是谁按的。
    origin: Literal["generated", "manual", "unknown"] = "unknown"
```

### 3.2 三条写入路径

| 路径 | 谁写 | 值 |
| --- | --- | --- |
| 生成落地（`mindmap_generate` / `_deep` / `expand_node` / `fill_details` 之后） | **后端**统一刷，不让模型写 | `generated` |
| `add_node` / `add_child` 等细粒度工具（编辑轮） | 后端 `agent/ops.py` | `manual` |
| 用户手动加（双击空白、Tab 加子节点、Enter 加兄弟、拖动插入） | 前端 `stores/mindmap.ts` 的 `addChildAt` / `addNodeAt` | `manual` |
| `POST /api/import` | 导入侧 | 源是我们自己导出的 JSON → 读原值；第三方格式（FreeMind / OPML / XMind） → `unknown` |
| 其它（旧图、未标注） | — | `unknown`（缺省，不用写） |

**不让模型写这个字段**：它是自证（"我是谁加的"），而模型没有任何办法知道。生成侧的
归一化函数统一刷，与 `normalize_color` 同一条口径——契约里能收，但产出侧要管。

### 3.3 明确不做的事

- **不加进 `UpdateOp`**。它描述来源，不是内容；能被 op 改就等于能被伪造溯源。
- **不写迁移脚本**。缺省 `unknown`，旧数据天然合法（`expandable` 的先例）。
- **不用重跑实体消解那类"事后推断"来补值**。推断出来的 `manual` 与真的 `manual`
  在界面上长得一样，而那正是这份文档要消灭的那种谎。

### 3.4 前端接线（契约落地那一轮的顺序）

1. `schema.d.ts` 重导 → `types.ts` 里 `Node` 加 `origin`（可选，读的时候按 `?? 'unknown'`）。
2. `App.vue` 覆盖率那句拆成两类（见 3.5）——**先拆文案，再拆数据**会让中间态撒谎，
   所以顺序反过来：字段先到，文案后改。
3. `MindNode` / 引用抽屉里"没有引用"的说明同样按三类分开：`generated` 说"模型没在
   材料里找到对应句子"（可补材料），`manual` 说"这个节点不来自生成链路，本来就没有
   原文可引"，`unknown` 什么都不说。
4. `frontend/src/mindmap/shape.ts` 里如果有按字段摘取节点的地方，顺带确认 `origin`
   跟着走（它不改形状，只该透传）。

### 3.5 那句"或者"在字段落地之前怎么改

**不要等字段。** 那句话现在就在撒谎，而字段要等到下一轮。改成不归因、但给出下一步的
版本：

> 这张图 24 个节点里有 12 个带原文引用（50%）。**这个数是"有多少条结论能核对到原文"，
> 不是质量分数**：没有引用的节点也可能是对的，只是没有出处可核。要出处就把材料加进来
> 再生成一次，或者点开节点看它有没有正文。

判据：**每一句都以"用户能做什么"结尾**。"或者这个节点是你自己加的"之所以该删，不是
因为它错，而是因为它把一个**免责**写成了**归因**——用户读完只知道自己被解释了，
不知道下一步。字段到了之后可以把"12 个"拆成"9 个 + 3 个"，但**结论句仍然是上面这句**
（要出处就补材料），拆出来的分类只是让这个数字更可读，不是替代下一步。

## 四、执行单（契约那一轮照着做）

1. `backend/app/contracts/mindmap.py::Node` 加 `origin` 字段 + 上面那段 docstring。
2. `backend/scripts/export_openapi.py` → 提交 `backend/openapi.json`。
3. `frontend`：`npm run gen:api` → 提交 `schema.d.ts`（CI 有 `git diff --exit-code` 钉着）。
4. 写入路径：`agent/tools.py` 的生成收尾刷 `generated`；`agent/ops.py` 的 `add` 设 `manual`；
   `stores/mindmap.ts` 三个手动入口设 `manual`。
5. 导入侧：`importing/json_import.py::_raw_node` 读 `origin`（缺省 `unknown`）。
6. 用例（每条都要能红）：
   - 后端：生成产出的每个节点 `origin == "generated"`；`add_node` 工具写的节点是
     `manual`；旧 JSON（无 `origin`）读进来是 `unknown` 且能保存回去；
     导出再导入一次，`origin` 逐节点不变。
   - 前端：覆盖率那句话在三种 `origin` 下各说各的，且 `unknown` 时不替用户下结论。
7. 上一节 3.5 的文案改动**在字段落地那一轮一起做**（先字段后文案，避免中间态撒谎）。

## 五、这一轮做了什么、没做什么

- **做了**：三条理由的逐条判定（用仓库里的行号核过）、成本的重估、字段设计与执行单。
- **没做**：`backend/app/contracts/**` 一个字节都没改；没有新增 `origin`；没有重导
  `openapi.json` / `schema.d.ts`。
- **留给下一轮的一句话**：这件事已经不是"要不要补"，而是"补的时候别只补字段——
  那句话的下一步动作才是它存在的理由"。
