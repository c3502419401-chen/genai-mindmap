# 拖动改结构：坐标仍然只有布局一个来源，拖动只表达"关系"

用户原话（这一轮的全部需求）：

> 生成思维导图后改节点改成点击节点出输入框，输入意图，大模型会执行修改，**节点改成可拖动**，
> 可断关系，可删除，新增新建节点，假如要成为一个节点的父或子，或者兄弟的话就是**拖动节点放在
> 一个节点的放上面或下面是兄弟，左边是父，右边是子**，流程图和鱼骨图也需要单独适配，
> 还有**拖动父节点后面的子节点也需要跟着移动**

拆成三轮，这一轮只做第一件：

| | 这一轮 | 下一轮 | 第三轮 |
| --- | --- | --- | --- |
| 范围 | 拖动 + 拖动决定父子关系 + 子节点跟随（**只 tree**） | 断关系 / 删除 / 新增节点 | 点节点就地出输入框 / 流程图 / 鱼骨图适配 |

理由：drop 判定、与 `layoutDiagram` 的冲突消解、`content` 的写回路径是地基，定错后面两轮全返工。

## §一、最大的那个冲突：松手之后落在"手指的位置"还是"布局的位置"

**落在布局的位置。** `Node.pos` 至今没有渲染层的读者，这一轮也**不给它开**。

布局是自动算的（`layoutDiagram` 从 `content` 推出所有坐标），拖动是手动的，两者只能有一个赢。
三条理由，从硬到软：

1. **坐标的唯一来源不能有两个。** 引入"手动坐标"意味着 `bounds`、`fitView`、可读性选档
   （`canvas/clarity.ts::chooseViewMode`）、收起计数（`canvas/view-collapse.ts`）全都要分叉出
   "手动"这一支。而 `Node.pos` 现在的身份很明确——它是契约 v2 的**透传字段**
   （`api/types.ts:77` 的注释："界面都还不渲染，但必须声明成可选字段并原样透传保存"）。
   给它开一个写入口径，等于让这张图从此不再是"完全自动布局"的图。
2. **用户的原话本身就是结构语义。** "假如要成为一个节点的父或子"说的是**关系**；位置只是
   手势的载体。他要的不是"把这块画布按我的手摆放"。
3. **在 `tidy` 这套几何下，"拖的方向"与"布局给的落点方向"同构。** 拖到右边 = 子（子本来
   就排在右边一层）、拖到左边 = 父（父本来就在左边一层）、拖到上下 = 兄弟（兄弟本来就沿
   兄弟轴上下排）。于是松手之后节点是**朝手势的方向吸附过去**的，不是弹回原点。
   **这一条是这个决定成立的前提**：没有它，剩下的就只有"拖了个寂寞"。

第 3 条同时解释了为什么"落在布局位置"不等于"弹回"：重排之后落点就在手势指向的那一侧。
唯一仍会错位的情况是"拖到目标左边当它的父"——那时落点会**顶替目标原来的那一格**
（见 §二），仍然是朝左的方向，视觉上依旧连续。

### 那"松手前不知道会变成什么"怎么解

不靠记住约定，靠**在松手之前就把结果画出来**。`store.previewMove()` 用**与真正落地同一个**
`layoutTidy`、在**同一棵假设树**上算出落点，画布把它画成虚线幽灵框：

- 它画在哪里，松手之后节点就落在哪里（实测逐像素相等，见 §五）；
- 于是"弹回"读作"吸附"，用户不需要理解"左父右子"这条规则；
- 非法落点不画幽灵框，改画一句原因——**禁止发生在松手之前**，而不是松手之后弹"操作失败"。

这是这一轮设计里唯一"必须做"的视觉层，理由与 `docs/VIEW-COLLAPSE.md` 里那行「显示 40 / 136」
同构：界面不能既改变结果又不说明结果。

## §二、四个方向怎么判

### 2.1 命中区：先决定"指针算不算在这个节点上"

两个轴**各自**外扩，两个数不一样（`canvas/layout/drop-zone.ts`）：

| 常量 | 值 | 依据 |
| --- | --- | --- |
| `DROP_PAD_X` | 20 | 沿层级方向。相邻层的空隙是 `depthGap = 56`，20 够不到下一层 |
| `DROP_PAD_Y` | 24 | 沿兄弟方向。相邻兄弟中心距 68（48 高 + 20 间距） |

命中区判定在**归一化之后**做：`dx = Δx / (半宽 + PAD_X)`、`dy = Δy / (半高 + PAD_Y)`，
`|dx| > 1 或 |dy| > 1` 就是没命中。所以命中区是个椭圆，不是"矩形各边外扩"。

上下外扩 24 会让相邻兄弟的命中区在中间**重叠 28px**——允许，因为重叠区两侧给出的答案恰好
等价："上面那个的后面"与"下面那个的前面"是同一个下标。真正的仲裁是 `nearness`
（`0` = 正中心、`1` = 命中区边界），取最小者。

### 2.2 四个区域：按归一化的最大分量，不按"离哪条边最近"

节点盒子是 180×48。两种判据在这里**会给出不同答案**：

| 判据 | 落在节点左上角（水平 20px、上方 6px）判什么 | 一类手势的成败 |
| --- | --- | --- |
| 离最近边 | `top`（更贴上面那条边） | 上下内圈各只有 24px，"放到上面"几乎做不出来 |
| 归一化最大分量 | `left`（0.64 > 0.375） | 四种手势四块区域，与看到的图对得上 |

取归一化。代价是**角落上的手势有歧义**（少见的落点，而且幽灵框会当场纠正）；换来的是
"放到上面"这类手势**系统性地可用**。

平局（正好在 45° 线上、或正好在中心）判**水平轴**：这套布局里"父 / 子"是比"兄弟"更重的
操作（前者改变层级），误触的代价是"多挂了一层"（Ctrl+Z 一步回来）；反过来把"想改层级"
判成"只挪个位次"，用户会以为拖动没生效。所以节点正中心恒为 `right`（= 子）——与"把节点
盖在目标身上 = 挂进去"这条直觉一致。

### 2.3 屏幕方位 → 结构关系：随朝向翻转

这一层是**表**，不是规则（`dropZoneOf`）。用户那句"左父右子"只在 `direction: right` 下成立：

| direction | left | right | top | bottom |
| --- | --- | --- | --- | --- |
| `right`（根在左、层级向右） | 父 | 子 | 前兄弟 | 后兄弟 |
| `left`（根在右、层级向左） | **子** | **父** | 前兄弟 | 后兄弟 |
| `down`（层级向下） | 前兄弟 | 后兄弟 | **父** | **子** |
| `both`（双向） | 见下 | 见下 | 前兄弟 | 后兄弟 |

`both` 的左右是"层"不是"方向"：靠近中心主题的一侧是父、远离的是子，所以要先算目标在根的
哪一侧（`outwardOf`）。目标**就是根**时（`outward === 0`）左右两侧都长着子节点，两个方向
都是"子"——根没有父，把节点拖到根的左边挂成一级分支是这张图里最常见的整理动作。

## §三、非法情形挡在哪一层

三层，各自有各自的责任，**不重复**：

| 层 | 位置 | 拦什么 | 用户看到什么 |
| --- | --- | --- | --- |
| UI 不给拖 | `stores/mindmap.ts::nodes` 的 `draggable` | 根、预览树、非树型 | 压根拖不动（根上拖动 = 平移画布） |
| 松手前提示 | `store.previewMove` → `dragOverlay` | 全部六种 | 红色目标框 + 一句原因，**没有幽灵框** |
| 写回前校验 | `mindmap/drop-plan.ts::planDrop` | 全部六种（纯函数，独立可测） | `status` 一句话，`content` 一个字不动 |

`planDrop` 的判据顺序按"用户最想知道的答案"排：

1. `self` —— 拖到自己身上；
2. `descendant` —— 目标在**自己这一支里**。这是**唯一**会把树变成图的判据，必须在构造任何
   新树之前挡住；
3. 根的两条特例：
   - `root-moved`：根不能被拖走（`draggable: false`，这里是兜底）；
   - `root-as-child` / `root-as-sibling`：根不能被塞进别人下面，也没有兄弟。
     **不做什么**：让二级节点"拖成根"（换整棵图的根）——手势里读不出"旧根该去哪"，
     猜错的代价是整棵树重组。这一轮拒绝，理由写在 `planDrop` 里。
4. `no-change` —— 手势合法但结果与现状相同。**不记一步撤销**；
5. `too-deep` —— 超过契约的 8 层。判据是**构造完新树再量**，不按公式推：公式要分别处理
   四档（`parent` 那档的子树高度会因为多了一层 target 而变化），四份推导 = 四处可以写错的
   地方。

### "拖到自己的父上"不是非法

结构上它并不特殊，三档各有各的正确结果，统一拒掉会让最自然的几个整理动作被无故拒绝：

| zone | 结果 |
| --- | --- |
| `child` | 已经在末尾 → `no-change`；不在末尾 → 挪到 children 末尾（真实的位次变化） |
| `sibling-*` | 合法的**提升一级**（变成父的兄弟） |
| `parent` | 合法的**把父顶下去**：目标成为自己的子，自己顶替它在它父节点下的位次 |

### 环检测只有一条判据

`findNode(dragged, targetId) !== null`。其余全部情况（摘走之后再挂回去）都不会成环：
被移动的那一支摘下之后，剩下的树仍然是一棵树，任何"目标 → 自己"的挂法都会被这一条先挡住。
`moveNode` / `reparentAbove` 里那两句 `throw` 是最后一道网（摘完之后还找不到父节点 =
父节点就在被摘走的那一支里），不是主判据。

### 位次：`parent` 那档不落到末尾

拖到目标的左边时，落位取**目标原来的那一格**，不是 children 末尾。用户改的是一处父子关系，
不该顺带重排它旁边那些不相干的节点；而画面上期望的也正是"我在它刚才的位置，它被我挤到右边
一层"。

## §四、与既有机制对齐

| 机制 | 结论 | 落点 |
| --- | --- | --- |
| 撤销栈 | **进**。拖动是内容改动，`applyContent(patched, true)` 压一步 | `pushHistory(actor='user')` |
| dirty / clientRevision | **置脏 + 递增**，与改标题同一套 | `applyContent` |
| 视图收起 | 可见集合会变（结构变了），所以 `revealInView(draggedId)` 必须补一枪 | `moveNodeTo` |
| `edit_events` | **进得了账本**，不用扩 `EditField` | 见下 |
| 视图适配 | **不重新适配**（`contentChangedByDrag`） | `MindMapCanvas` |

### `edit_events`：查清了，`kind='move'` 早就在

原本担心"`EditField` 只有 label/title/detail/note/color/icon，关系变化进不了账本"。查清结果：

- `mindmap/edit-log.ts::diffEdits` **已经有** `kind: 'move'` 这条分支（`old.parentId !== entry.parentId`
  时发一条，`before`/`after` 是两端父节点的名字；同父换位次也发一条，`before/after` 是位次）；
- 后端 `backend/app/contracts/edits.py:61` 的 `EditKind` 字面量里 `"move"` 也在，统计走
  `by_kind`（`contracts/edits.py:197` 的分子把 `move` 算进"用户改了多少"）。

所以拖动**自动**进账本，一条父变化 + 可能一条位次变化，**不需要**扩 `EditField`
（`move` 属于 `by_kind`，`by_field` 里本来就不该有它）。实测见
`tests/node-drag.spec.ts`「进的是账本的 move 事件」。

### 视图适配：拖完不重新适配

`content` 一变就会触发 `watch(() => store.content)` → 按可读性重新选档 + 重新适配。
拖动引起的这一次要跳过：用户刚松手、眼睛还停在原地，视角被重新算一遍等于把他刚拖完的那一屏
扔掉。落点紧挨着他拖到的那个目标（那是他看得见的东西），所以不重新适配也不会跑到视野外。
标志 `contentChangedByDrag` 在 `moveNodeTo` 前设、失败时回滚。

## §五、子节点跟随

**不需要额外实现**：坐标的唯一来源是 `layoutDiagram`，被拖节点的整支跟着重排是它的默认行为。
需要的是钉住它——判据照抄上一轮（`f5c956f9`）验证布局的那一条：**逐节点比对坐标**，而不是
"位移 + 旧位置"。

`tests/node-drag.spec.ts`「子节点跟随」：

1. 拖之前记下被拖那一支 4 个节点的坐标；
2. 拖动（`zone: 'child'`）；
3. 对每一个后代：`store.nodes[id].position === layoutTidy(新树).positions[id] - 半个节点`；
4. 再断言**确实动了**：4 个节点没有一个是原坐标（"位移 + 旧位置"那种实现会让父子相对关系
   仍然是旧的，差别只有这一句能钉出来）；
5. 另有一条：`nodeCount` 不变（重排不丢节点）。

`view-collapse.spec.ts` 里那条旧断言（"拖不动节点，所以坐标只有布局一个来源"）换成新口径：
节点可拖、拖动只改 `content`、**内容里一个 `pos` 都没有**（`Node.pos` 仍然没有读者）。

浏览器实测（1280×800、zoom 1.2 / 0.84 各一次）：

| 手势 | 落点 | 结果 |
| --- | --- | --- |
| 支持向量机 → 分类的**左边** | 顶替分类的位次 | 监督学习 → 支持向量机 → 分类 → 逻辑回归 ✓ |
| 降维 → 线性回归的**右边** | 线性回归的下一层 | 幽灵框与松手后的真实位置逐像素相等 ✓ |
| 策略梯度 → 无监督学习的**上方** | 无监督学习前一位 | 标签「插到「无监督学习」前面（兄弟）」 ✓ |
| 支持向量机 → 聚类（同父）的**下方** | 聚类后一位 | 标签「插到「聚类」后面（兄弟）」 ✓ |
| 监督学习 → 逻辑回归（自己的后代） | — | 红框 +「在它自己这一支里，挂上去会绕成一个环」 ✓ |
| 任何节点 → 空白 | — | 没有任何指示；松手后归位 ✓ |
| Ctrl+Z | — | 一步退回原结构（含整支坐标） ✓ |

### 三个"画在哪儿就落在哪儿"的坑

幽灵框是这个功能的承诺，而它成立需要三件事同时成立。三件都踩过一次，每一条的表现
都是"差几十像素"——看起来像"差一点没对准"，用户会反复微调。

**一、预演必须走同一条画布树。** `renderSource.root` 不是 `content.root`：它带着视图层
收起（`canvasTreeOfContent`）。预演如果直接拿 `content.root` 排，两者在"用户点开过某
一支"之后**就不再相等**——实测幽灵框比真实落点高 40px。所以那一段被抽成
`canvasTreeOfContent` 一个函数，画布与预演共用；`tests/node-drag.spec.ts`「视图收起
生效时也一样」用预算 20 + 136 节点的真图钉住它（去掉这次抽取，那条用例偏 2176px）。

**二、读响应式的 `viewport`，不要 `getViewport()`。** 后者是一次性取值，不会让 computed
与视口建立依赖；而拖动时 `autoPanOnNodeDrag` 会推着视口走（拖到画布边缘就发生），
视口一变、`dragHint` 却没变 → computed 不重算 → 幽灵框停在**旧视口**算出来的位置。

**三、`dragOverlay` 先判 `hint` 再读 DOM。** `getBoundingClientRect()` 会强制一次
layout，而这个 computed 挂在模板的 `v-if` 上、每次重渲染都求值。顺序颠倒的那一版让
"136 个节点 + 点几次折叠"这条画布用例多出上百次强制重排，实测从 3 秒推过了 5 秒超时
（`tests/view-collapse-canvas.spec.ts`）。不拖动时它必须零开销。

### 还有一个坐标换算的坑：别用 `flowToScreenCoordinate`

Vue Flow 1.48 的实现是 `(point + 容器偏移) * zoom + translate`——它把容器偏移也乘了一次
zoom。容器 y = 48（顶栏）、zoom = 1.2 时，它给出的位置比真实位置少 9.7px，而这个偏差**随
zoom 变化**（缩放一次，幽灵框就和落点错开一点）。

视口变换的定义就是 `translate → scale`，所以正确的换算是 `flow * zoom + viewport`。
改成自己算之后，幽灵框与目标节点的 `getBoundingClientRect()` 逐像素相等（zoom 0.84 和 1.2
两档都验过）。反方向的 `screenToFlowCoordinate` 没有这个问题（两处偏移互相抵消），命中判定
继续用它。

## §六、自评：「左 = 父」是最容易误用的那一个

判断：**四个方向里，`左边 → 成为目标的父`最容易误用。**

三条理由，都是这套布局自己长出来的：

1. **它是唯一一个"结果与手势方向相反"的**。其余三个都是"拖过去，东西朝那边长"：拖到右边
   节点出现在右边、拖到上面兄弟排到上面。只有"拖到左边"的结果是**目标往右跳一层**——手往
   左，能动的东西往右。用户看着画面很容易把它读成"我想排在它前面"（而"前面"在这里是**上**）。
2. **它要求一次反向推理**。"我把 X 拖到 A 的左边"要翻译成"X 成为 A 的父"，中间那一步
   （A 会变成 X 的子）在画面上不写出来。用户在心里做的是"谁当谁的父亲"，而手势给的是方位。
3. **它与"上 = 兄弟"共享左上的竞争区**。归一化之后左上角判 `left`（§2.2 那个取舍的代价），
   而用户在那一片最可能想说的是"放上面"。

### 靠什么让人在松手之前就知道

不是"加视觉反馈"这种话，是四条各有分工的东西：

1. **幽灵框（根本手段）**。画的是 `layoutTidy(假设的新树)` 算出的**真实落点**，不是箭头、
   不是高亮。用户看到的是"它会去那儿"，于是"左=父"这条约定**根本不需要被理解**——
   这恰好把第 2 条理由（反向推理）整个绕过去。这是唯一一条能把"猜约定"降级成"看结果"的。
2. **关系措辞的跟随标签**。写「成为「甲」的父节点」，不写「放到左边」。方向是手势，关系是
   结果；把翻译放在标签里，用户不必自己翻。
3. **目标节点的光圈**。画布上同时有上百个节点，"这次要动的是这一条关系"必须被单独标出来，
   否则幽灵框会被读成"附近某个位置"。
4. **非法时红框 + 原因（在松手之前）**。环和超层是最容易在"左父右子"上踩到的两类——
   把 X 拖到它自己的子孙左边，会立刻得到一个环。这一条必须在拖动中就红着说清，
   松手之后再说已经晚了一步。

**刻意不做的**：松手后的 toast。它出现在决定之后，对"拖错"没有预防作用；而状态栏那一句
（`dropMessage`，四档措辞互不相同 + "可撤销"）已经承担了"事后确认"。

**还剩下的风险**（这一轮不解决）：幽灵框落到视口外时看不见（落点常常在目标右侧一层，靠边的
目标会把幽灵框推出去）。这一轮不做"落点在视口外"的提示，因为落点紧挨着用户看得见的目标，
而目标本身已经在视野内。下一轮如果出现"拖完必须平移才看得见"的反馈，再补。

## §七、这一轮没做的（明确划出去）

| 事项 | 为什么不在这一轮 |
| --- | --- |
| 流程图 / 鱼骨图的拖动 | 它们的画布树是**合成**的（虚拟根 + 每个容器一个子），拖一个节点要改的是"它属于哪个阶段 / 哪根骨"，语义与树完全不同。这一轮只做 tree，其余留单独适配 |
| 断关系 / 删除 / 新增节点 | 第二轮 |
| 点节点就地出输入框 | 第三轮（`components/ChatDock`、`AgentPanel` 那一侧） |
| 让二级节点"拖成根" | 手势里读不出"旧根该去哪"；换根是整张图重组，不该由一次 drop 猜出来 |
| `Node.pos` 的读写 | 这一轮的结论恰恰是：不需要它。手动坐标一旦落地，布局就不再是纯函数 |
| 键盘可达的等价操作 | 现有 Tab/Enter/Delete 已经能改结构；拖动只服务"换个父/换个位次"这一类重排，而键盘版需要另一套焦点模型（"选一个目标 + 选一个方向"），单独一轮 |
