# 按章切：每支只给它自己那一章的原文

`MINDMAP_SECTION_SLICE=1` 走这条路，不设就是现状。**默认关**，因为它是 A/B 的一臂，
而且把结构那一次调用换成了 N 次。

## 它替换的是哪一段

```
① 骨架（_plan_ask，不变）          ① 同左
② 结构：一次调用，整份正文进 prompt  ② 每章一次调用，只给它这一章的原文 → 组装成整棵树
③ 说明：_fill_details 两半并发      ③ 同左，一个字都没改
```

> ③ 那一栏有第二条路了：`MINDMAP_DETAIL_RETRIEVAL=1` 让第三段按节点在**它自己那一章内**
> 检索证据，见 `docs/DETAIL-RETRIEVAL.md`。它只在这一条路（按章切）成立时才有意义，
> 且默认关——**本节的全部数字都是它关着时量的**。

第三段、裁剪、套色、跨支重复检测、`check()` 全部复用同一条出口：组装的 `raw` 与
"一次写完"那条路形状相同（`{"title","root"}`）。所以两组之间**只可能**有第二段的差别。

## 一、`_outline_lines` 收哪一级（这决定切法）

**只收一个级别**——`app/knowledge/service.py::_outline_lines` 的两条规则是同一条意思：
markdown 取"井号最少、且至少 `OUTLINE_MIN_ITEMS`（2）条"的那一级；没有 markdown 结构时
取编号行里**出现次数最多**的那一级。不存在"一级二级都收"。

`docs/RAG-DECISIONS.md` 的实测（`scripts/probe_outline_levels.py`）：

```
各层 markdown 标题： # ×1   ## ×12   ### ×18
_outline_lines 收到：12 条（取 ##）
Σ coverage / 全文：13,959 / 14,120 = 98.9%
```

所以 `text[start : start + coverage]` 切出来的 12 章**互不相交**，每章含着它自己的
3–5 个 `###` 子节——"同一段原文被两支拿到"这个隐患不存在。

缺的 161 字是文件导语（第一个标题之前）。`_chapter_slices` 把它并进第 1 章，
于是分母是全文而不是"被目录管住的那部分"（实测 Σ 章字数 = 14,120 = 全文）。

**边界**：多份材料时不切。`OutlineEntry.start` 是**那一段文本内部**的偏移，两份材料共用
一个坐标系会把 B 的偏移套到 A 上。这时记一条 `SECTION_SLICE_UNAVAILABLE` 并退回现状
——不说的话，用户以为自己在看 B 组，而跑的是一次完全一样的现状。

## 二、三个待定点的决定

### 每支给多少原文：整章，上限 8,000 字

`SECTION_SLICE_MAX_CHARS = 8_000`。这份材料的章长是 144–2,894 字（12 章），
所以**真实材料上这个上限基本不触发**；它防的是"一章一万多字"那种形状
（`docs/PLAN.md` 最长一章 11,697 字）。8,000 字按 `estimate_input_tokens` 的
1.5 字/token 折算是约 5.3k token，加 system 约 7k——离 `CONTEXT_TOKEN_LIMIT`（20 万）
很远，所以这个数守的不是"装不下"，而是"一章给 5k token 的原文已经够写它的所有要点，
再多买到的是注意力分散"。

### 节点预算：平分，不是"自由写然后裁"

`SECTION_SLICE_MIN_PER_BRANCH = 3`，实际取 `max(3, (80 - 1 - N) // N)`：

```
12 章 → (80 - 1 - 12) // 12 = 5 个后代/支，每支预算 6
合计 12 × 6 + 1 = 73 ≤ INITIAL_MAX_NODES(80)
```

不平分的代价在别处已经付过一次：`_clip_tree` 是**前序裁尾巴**，自由写时（实测现状那一臂
模型给了 185 个节点）被整支砍掉的恰好是最后几章，"每章覆盖率"在尾部直接归零——那正是
这条路要消掉的失效形态。平分让每章先拿到确定的份额，总量也恒在上限内。

### 深度：分支下 2 层

`SECTION_SLICE_DEPTH = 2`。`INITIAL_MAX_DEPTH = 3` 是 root 之下的层数：
root → 分支（第 1 层）→ 两层后代，正好用完。新路**不请求两级骨架**——分组会再吃一层
（root → 组 → 章 → 章内），章内只剩一层，而这一章里明明有 `###` 子节可写。

### 引用：`source_id` 与 `start/end` 由服务端在**本章范围内**算

模型只抄 `quote`（与全塞同一条契约：全文进 prompt 之后它的坐标感不可靠）。服务端在
`[章首, 章末)` 里定位：唯一命中就写绝对偏移，多处命中只留引文，**找不到就丢掉这条引用**
（节点保留）。丢掉的条数在 `data.section_slice.refs.dropped` 里。

这条是"每章覆盖率"可测的前提：引用只可能落在它自己那一章里。

## 四、数据回答了什么

**"每支只看自己那章"确实能消掉跨支重复——但重复本来就不是现状的问题。**

两臂都是 0。分片那版（已删）是 6 处（3 个说法各写 2 遍），它的根因是"每支检索是全局
top_k，兄弟支的内容会被捞进输入"。这条路把那句话反过来说了一遍：兄弟支的原文**不在
它的 prompt 里**，写不出重复。这是机制，不是提示词——`SECTION_SLICE_PROMPT` 里那句
"只写这一章原文里确有依据的内容"只是补一句，删掉它，重复也不会回来。

所以"消掉 6 处重复"是这条路**相对分片**成立的，不是相对现状。现状（全塞一次写）本来
就能看住全局，重复恒为 0。

**真正的差别在别处：现状会整章缺席，这条路不会。**

full 两轮分别只有 6/12 与 7/12 章被引用到，**第 8–12 章在两轮里都是 0**。原因不是模型
不想写：它一次给了 185 / 130 个节点，撞上 `INITIAL_MAX_NODES = 80`，`_clip_tree` 按前序
砍掉尾巴 105 / 50 个——被砍的正是后面那几章。`partial=True` 就是这件事的记录。

slice 两轮都是 12/12 章、`cut_nodes=0`、`partial=False`。每章一次调用天然知道"自己只有
6 个节点的额度"，不需要靠事后裁剪把尾巴砍掉。

一句话：**这条路把"每章都被写到"从概率事件变成了机制**。

### 近似重复也测了（逐字判据会漏掉"改了一个字"）

`_cross_branch_duplicates` 只做逐字判据（只折空白），对改写完全瞎——那是刻意的
（只报不删，宁可漏不误报）。用更宽的判据再看一眼（`analyze_section_slice.py` 的
`_near_duplicates`：相似度 ≥0.8、且不在同一条祖先链上）：

| | full#1 | slice#1 | full#2 | slice#2 |
|---|---|---|---|---|
| 近似重复对数 | 1 | 1 | 1 | 2 |

两轮里都有的那一对是「agentic 召回实测发散不做」↔「agentic 召回不做」（0.85）——
**材料自己在两个地方说了同一件事**（第 3 章与第 10 章都在讲 agentic 召回），与切不
切章无关。slice#2 多出来的一对是「下一步结构引导的召回」↔「5 下一步：结构引导的召回」
（0.95）：**新路特有的**——一级分支就是章标题，而模型在这一章里又写了一个同名的要点。
它不是跨支重复（两处在同一条分支的上下层），但确实是这条路要多看一眼的形状。

## 五、每章覆盖率为什么不接近 100%（算术，不是模型不努力）

`scripts/analyze_section_slice.py` 从 A/B 的产物里算三个数：

```
slice#1  引用 38 条｜引文均长 52.9 字（最短 8 / 最长 170）｜每节点 0.63 条
         实测覆盖 13.2%   天花板（38×52.9 / 14,120）= 14%
slice#2  引用 38 条｜引文均长 46.8 字｜实测 12.2%   天花板 13%
full#2   引用 80 条｜引文均长 59.5 字｜实测 31.8%   天花板 34%
```

**实测值贴在天花板上**。覆盖率 = Σ(引文字数) / 全文，于是它被两个数夹住：

1. **引文长度**：提示词写的是"不超过 300 字"（`SourceRef.quote` 的硬上限），模型平均写
   47–53 字。若每个节点按 150–300 字摘整段，同样 38 条引用能覆盖 5.7k–11.4k 字
   （**40%–81%**），节点数一个都不用加；
2. **预算分配**：slice 的"章字数 ↔ 覆盖率"相关系数是 **−0.68 / −0.78**（章越长覆盖率越低），
   因为 73 个节点的预算按章**平分**。2,894 字那章与 214 字那章都拿 4 条引用，
   前者 5–10%、后者 38%。按字数比例分预算能让这条曲线变平，但**不会抬高绝对值**
   ——算术上限仍在"引用总字数"那一侧。

所以"每章接近 100%"不是这条路成不成立的问题，而是引用长度与预算分配的问题。
这条路的贡献是把**每一章都放进分母**（12/12），而不是把分子做大。

## 六、代价

| | full | slice |
|---|---|---|
| 模型调用 | 4 | **15**（1 骨架 + 12 章 + 2 说明） |
| 输入 token | 23.2k | 26.8k（**+15%**） |
| 输出 token | 14.7k | 11.6k（**−21%**） |
| 墙钟 | 58.8s | 36.1s（**−39%**） |
| 图宽 | 6–7 | 12 |

输入几乎不涨，因为**总量守恒**：全塞是"1 次 × 14k 字"，按章是"12 次 × 14k/12 字"，
多出来的只是 12 份 system 与 12 次请求的固定开销。

墙钟反而更短，但这个数**不要直接外推**：full 那一臂输出了 185 / 130 个节点
（被裁 105 / 50），输出量本来就比"预算 73"的 slice 大一截。材料章数少、撞不到 80
上限时 full 会更快——那时这条路的账只剩"调用次数 ×N"。

值不值取决于要什么：要**每章都有内容**（不整章缺席），它买到了，代价是 4 → 15 次调用
与 +15% 输入；要**每章 100% 覆盖**，它买不到——那要靠引文写长与预算按字数分配，
是另外两件事，与切不切章无关。

## 七、边界（都钉着）

- **开关关掉逐字节不变**：没有 `data.section_slice` 键、没有新诊断、骨架的 ask 与结构
  那次调用与原来完全一样。`tests/test_edges.py::TestTreeIsByteIdentical` 比的是
  整份 `model_dump()`，`tests/test_section_slice.py::test_switch_off_keeps_the_old_shape`
  是更快的那一道；
- **第三段一行没改**：`tests/test_section_slice.py::test_switch_on_keeps_the_third_stage_system_byte_identical`
  比的是两臂所有 `DETAIL_ONLY_PROMPT` 开头的 system，集合相等。`MINDMAP_DETAIL_RETRIEVAL`
  打开时第三段的证据会换（见 `docs/DETAIL-RETRIEVAL.md`），但那是**另一个开关**，默认关；
- **图渲染没动**：这条路产出的仍是一棵 `MindMapContent`，出口照旧 `_shape_output`；
- **限额没动**：`INITIAL_MAX_NODES = 80` / `INITIAL_MAX_DEPTH = 3` 仍是全树的上限，
  平分只是把 80 分给 N 支；
- **节点生长预览接在这条路上**：`_slice_structure` 在并发之前先报根与 N 条一级分支，
  每章的 `_slice_one` 各自带 `on_delta` 边收增量边报孩子。预览的两把尺子与
  `_slice_nodes` **同一套**（`quota = budget - 1`、`max_level = SECTION_SLICE_DEPTH`），
  所以帧里的节点数与落树之后的 `node_count` 相等——实测 37,973 字的 PDF：73 帧、
  落树 73 个节点；首帧 1.09s、最大空档 2.77s、末帧 10.91s（改之前这条路上
  **一帧都没有**，整棵树在 10.9s 之后一次性落画布）。用例见
  `tests/test_section_slice.py` 第 5 节（`test_growth_frames_*`）。

## 八、这条路曾经没有流式输出

`_generate` 把 `on_delta` 接在"结构那一次调用"上，而按章切与它是 `if slice_chapters:
… else: …` 的**互斥**关系——切了章，那次调用根本不会执行。于是整棵树要等 N 次调用
全部 `gather` 完、在 `_slice_structure` 末尾组装好，才一次性落画布。

复现那次的形态：37,973 字的 PDF（`MINDMAP_SECTION_SLICE=1`）→ `0` 个 `node_grow`
帧，几十秒空白之后 73 个节点同时出现，而 73 = `_slice_budget(6)` 的
`6 × 12 + 1`。节点数本身就是"走的哪条路"的指纹。

修法不是"把流接回结构那一次"（那条路上没有它），而是接在这条路自己的两个入口：
根与分支在 `_slice_structure`、孩子在各章的 `_slice_one`。响应形状也不同——这里是
`{"children":[…]}`（无 id），所以用 `stream_items.closed_items` 与 `_GrowStream`，
而不是整树那条的 `parse_partial` + `collect_new_nodes`。
