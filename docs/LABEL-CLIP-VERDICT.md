# label 的 16 字硬切：三处判定摆在一起之后

第 6 件账的判定记录。结论先说：

> **`tools.py:2624` 的"宁可丢掉那半句"是对的**，验收报告 §6.4① 那句"44 个节点被截成
> 半句"的**计数与前提都不对**（实测 21 个被切、16 个是自然 16 字、7 个是 `repair`
> 拼接；而 44 个的 `detail` 全部非空且已含全称，所以"信息丢了"不成立）。真正该修的是
> **切点**，不是"残尾去哪"——改了 `clip_label`：切点落在半个 token 上时往前退。

---

## 一、三处原文

### ① 契约侧（`backend/app/contracts/mindmap.py:91`，现 :101）

```
# AI 生成时的标题上限 = 16 码点。这是**生成侧**的约束（`generation.service` 与
# `agent.tools` 的归一化都读它），不是契约校验：把 `Field(max_length=200)` 直接
# 改成 16，等于让所有旧图在下一次保存时 422——用户什么都没改，图却存不回去。
#
# 16 这个数的依据是画布：`180px` 宽的圆角框里放 14px 字，一行约 12 个字、两行
# 24 个字，16 字是"缩到能看见全貌"之后仍读得出的长度。超过它的内容属于详情
# （`detail`），不属于标题。
GENERATED_LABEL_MAX_CHARS = 16
```

### ② 生成侧（`backend/app/agent/tools.py:2624`，`_slot_from` 的 docstring）

```
`label` 截到 `GENERATED_LABEL_MAX_CHARS`（16）；超出的**不**升级成 `detail`：
那不是模型写的说明，是标题的后半截，拼进去会得到一句从中间断开的话。宁可
丢掉那半句，也不要制造一段读不通的正文——真正的长内容应该由 `detail` 承载。
```

同一件事在 `tools.py:1690`（骨架分支）有一句配套的：

```
截断长度是 `GENERATED_LABEL_MAX_CHARS`（16）：骨架标题就是画布上的一级分支，
它与其余节点受同一条限制。**不做二次校验**——模型偶尔写长一点不该判整次失败，
截断后仍是一棵合法的树。
```

### ③ 验收报告侧（`docs/ACCEPTANCE-REPORT.md` §6.4①，连带 §6.2）

```
1. **label 的 16 字硬切**（影响 44 个节点、44/1130 = 3.9% 的节点，但它在视觉上最显眼）
   ——改语义切 + 后半截进 detail。
```

§6.2 把修法写成两条："① 把 16 字硬切改成语义切（不在拉丁词、括号、书名号中间切），
并把被切下的后半截写进 `detail` 首行（`原上级：…` 已有先例）；② 或提高生成侧上限"。

## 二、判：不是 a，不是 c，是 b 的一个精确化

先排除两个读法。

**a（16 只管一级分支标题，2624 管深层节点）不成立。** 16 是"全节点一个数"，证据是
`clip_label()` 的调用点：骨架 `branches`（`tools.py:1706`/`1715`）、分组骨架
（`1821`/`1829`/`1838`）、分支展开的子节点（`2637`/`2646`）、章节导入（`9700`/`9978`）、
根节点（`12241`），再加上 `generation/service.py:1576` 在落库前对**每个** node 再兜一次。
没有任何一处按层级换数。

**c（真矛盾、一处该改）也不成立**，因为它们说的是两个动作："残尾去哪儿"与"正文怎么写"。
但这一层要再说细一点，因为报告确实提了"后半截进 detail 首行"，而 2624 明确反对
——**表面上这两句在同一个动作上给了相反结论**。判它不矛盾，靠的是实测：

> 20 棵验收树里 44 个 16 字 label，**44 个的 `detail` 全部非空，且全部已经含全称**：
> `Kruskal`、`VLAN`、`BGP`、`Machine Learning`、`PNG`、`Word`、`21ms`、`#218`、
> `created_at`、`Element Plus`、`PostgreSQL`、`归一化`、`执行计划`、`凭直觉`、
> `全文索引`、`分半`。

也就是说报告设想的那个损失（"后半截没了"）**在数据里不存在**——后半截的**信息**在
`detail` 里，丢掉的是标题**自己**的可读性。既然没有信息要救，2624 那条"不要拿残尾
制造一段读不通的正文"就是唯一正确的选择；报告那条处方是给一个不存在的病灶开的药。

**真相是 b 的精确化，而且还要再拆一层：**

- 16 确实是**全局硬切**（a 错），这一点没有争议；
- 2624 的理由在**这件事的数据上**成立（残尾不必搬，`detail` 已有全称）；
- 但 2624 的措辞"宁可丢掉那半句"里藏着一个它没管的情况：**有些半句不是"半句"，
  是另一个东西**。`错位问题已提 issue #21`（原文 `#218`）不是短了两个字符的标题，
  它指着另一个 issue；`平均查询 180ms 降到 21`（原文 `21ms`）差三个数量级。
  这两条是 `#21` 与 `#218` 都被**当成标题落库**之后才看得见的——它不是"读不通"，
  是"说错事"。

所以判定落成三条：

| # | 判定 | 依据 |
|---|---|---|
| 1 | 报告 §6.4① 的"44 个被截成半句"**不成立** | 实测 21 被切 / 16 自然 / 7 拼接，见 §三 |
| 2 | 报告的"信息丢了"**不成立** | 44/44 的 `detail` 非空且含全称，见 §二 |
| 3 | `tools.py:2624` 的判定**成立**，但范围要补一条 | 残尾不搬（对）；切在 token 中间那次**不是**可读性问题，是内容错误 |

## 三、量：44 个里几个是被切的

复算入口：`python scripts/measure_label_clip.py`（明细落 `scripts/_label_clip.json`）。

**第一步先纠正提问方式。** "44 个里几个切在词中间"问不出来：`clip_label` 是
`text[:16]`，原文后半截在落库那一刻就没了，`len(label) == 16` 也不等于被切过——
模型自己写一个 16 字完整句，落在同一个桶里。所以换三个能证的角度：形状、来源、断层。

### 3.1 长度直方图：16 处有尖峰，但**没有断层**

acc_trees（20 棵 / 1130 节点）：

```
15  23   16  44  ←上限   17   9   18   7   19   7   20   8   21   9   22   4   23  10   24   5
```

16 处 44 个相对 15 处的 23 个是**弱尖峰**，但 17 字以上还有 59 个——如果生成侧硬切是
全覆盖，17 以上应该一个都没有。

### 3.2 那 59 个全是 `repair` 拼接的（59/59）

`59 个 >16 字的 label，含 " / " 的 59 个。` 全库 1130 节点里含 `" / "` 的正好 75 个
（报告 §6.1 那张表的数）。这说明两件事：**生成侧 clip 是全覆盖的**（模型写长的都被压到
16，一个没漏），而**长出来的是 `repair._absorb` 事后拼接**的——拼接在 clip 之后跑，
拼成多少字不再受 16 约束（`docs/OFF-TOPIC-AND-FEW-BRANCHES.md:140` 写过这一点）。

**推论**：16 处那 44 个，要么是"被压到 16"，要么是"本来就在 16 以内"。这就要靠形状。

### 3.3 44 个的四档（`measure_label_clip.py` 的判据）

| 档 | 判据 | 个数 |
|---|---|---|
| `joined` | 含 `" / "`：`repair` 拼接产物，与 16 无关 | 8 |
| `clipped_symbol` | 存在未闭合的成对符号（`《》（）()[]`） | 5 |
| `clipped_token` | 末尾拉丁/数字 token 在**自身 `detail`** 里以更长 token 出现 | 10 |
| `unverified` | 其余（**不是"自然"，是"这份数据判不了"**） | 21 |

`clipped_symbol` 这 5 个：`第 5 章 树与二叉树（8 学时`、`Silberschatz《操作系`、
`第 3 章 数据链路层（6 学时`、`《Hands-On Machin`、`(user_id, create`。

`clipped_token` 这 10 个（证据串全部来自该节点自己的 `detail`）：

```

CSMA/CD 与交换机 VLA       VLA → VLAN
路由协议 RIP OSPF BG        BG  → BGP
平均查询 180ms 降到 21      21  → 21ms
错位问题已提 issue #21      21  → 218        ← 说错事的第一条
```

### 3.4 人工补那 21 个 `unverified`

机械判据判不了的，逐条看（判据与结论都在这张表里，反驳可以直接对着改）：

| 归类 | 个数 | 例子 |
|---|---|---|
| **被切（中文词内切）** | 5 | `训练技巧：dropout 与归一`←归一化、`构建时间 11 分钟压到 6 分`←6 分半、`Code Review 未查执行`←执行计划、`Canvas 与 SVG 取舍凭`←凭直觉、`检索用 PostgreSQL 全`←全文索引 |

### 3.5 结论数字

```
44 = 21 被切（15 有结构证据 + 5 中文词内切 + 1 既拼接又被切）
   + 16 自然 16 字

```

**所以"44 个被截成半句"这个数，实测是 21/44 = 48%。** 报告把它写成 44（100%），
量级差一倍；而"信息丢了"这一条是 0/44。

### 3.6 另一批样本（主库 `mindmaps.db`，24 棵 / 1085 节点）

同一脚本跑出来的形状不一样，值得单列，因为它是**真实开发过程攒下的图**：

- 剩下 70 个里，**有一大批是完整的 16 字中文短句**（`机器学习是人工智能的一个分支领域`、
  `研究如何让计算机从数据中学习规律`……整整一张图都是），**也有一批肉眼可见被切的**

## 四、改了什么：选 b，并把它收窄成"不切 token"

`clip_label` 加了一层切点回退（`_clip_index`，`contracts/mindmap.py:303`）：

> 切点两侧都落在"标识符字符集"（字母、数字，以及 `._+#%<>=-`）里时，往前退到 token
> 之前，再抹掉末尾悬着的空白 / `/+|` / 悬空运算符（`率≥` 的那个 `≥`）。

`16` 这个上界**一点没动**。

### 4.1 为什么不是"不切在词中间"，而是"不切在 token 中间"

父任务倾向的写法是"遇到切点落在词中就往前退到边界"。**"词"这个判据在中文里不存在**，
能落地的只有"token"——它有客观边界符（空格、标点、汉字）。所以收窄，并把收窄的理由
留在代码里（`_clip_index` 的 docstring）。

这条收窄不是妥协，是**判据的诚实**：能证的才改，证不了的写进 §六的账。

### 4.2 效果（21 条被切里的 13 条）

原文由 `detail` 里的全称复原——**不是模型的原始响应**（`runs` 表不存 raw，`candidate`
列也没有；原文的后半截在落库时就没了）。所以这 13 条是推演，不是重跑：

```
最小生成树 Prim 与 Kru      → 最小生成树 Prim 与
CSMA/CD 与交换机 VLA       → CSMA/CD 与交换机
路由协议 RIP OSPF BG        → 路由协议 RIP OSPF
平均查询 180ms 降到 21       → 平均查询 180ms 降到
错位问题已提 issue #21       → 错位问题已提 issue          ← 事实错误被消灭
导入 docx 生成导图导出 P     → 导入 docx 生成导图导出
导出 PNG / PDF / W          → 导出 PNG / PDF
后端 FastAPI 加 Pos         → 后端 FastAPI 加
后端 Node.js + Pos          → 后端 Node.js
PostgreSQL 加 Pos           → PostgreSQL 加
前端 Vue 3 + Eleme          → 前端 Vue 3
《Hands-On Machin           → 《Hands-On                 （16 → 9，最短的一条）
(user_id, create            → (user_id,
```

**代价写在明处**：`《Hands-On Machine Learning》` 从 16 字落到 9 字，丢了 `Machine
Learning`——它的全称在 `detail` 里（这正是 §二那条判定的前提）。其余 12 条长度只掉
1–3 字。`人工编辑不跑 MIN_BRANCHES` 这种前面有长中文的会退得更多（主库里那条会落到
`人工编辑不跑`，6 字）——这是"整条 token 退无可退"的必然后果，不是 bug。

### 4.3 一个要知道的副作用

`label` 变短会让 `repair._absorb` 的第二档（"拼起来 ≤24 字就拼"）**更容易触发**：
`READABLE_LABEL_CHARS = 24` 量的是拼接结果，输入变短，结果更容易落在 24 以内。
量级很小（只对被切的那 1–2% 节点），但第 7 件动拼接准入时要把它算进去。

## 五、为什么不选另外三条

**a · 放宽 16 → 24（与画布两行对齐）：不做。**
24 是"排得进"的上界，不是舒适值；而**可读是验收里唯一下降的维度**（3.30 → 3.15，
`ACCEPTANCE-REPORT` §6.1，两条独立读法同向）。在这条维度上把上限抬高，方向是反的。
另一个常被忽略的点：`label` 同时是**分片检索的 query**（`_search_branch` →
`_branch_query`），`scripts/measure_title_length.py` 就是为这个平衡点测的（24→16 掉
零点几 pp，24→12 才踩到陡坡）——动了 16 就动了那个已测过的平衡点。

**c · 被切的部分进 `detail` 首行：不做。**
理由见 §二：44/44 的 `detail` 已含全称，搬进去是制造重复正文，2624 的反对成立。
唯一的例外是**节点没有 `detail`** 的情形——但那在实测里一次都没出现（44/44 非空），
为一个没出现过的情形加一条会污染正文的规则，不划算。

**d · 不改（判 2624 那条对）：只对了一半。**
2624 对"残尾去哪"是对的，但它把这件事整体归给"可读性"，于是 `#21` 这类**内容错误**
被一并归进了"读不通"里，没有单独的账。`measure_label_clip.py` 的四档里专门有
`clipped_token` 一档，就是为了让这一类能单独数出来。

## 七、自评：16 是谁定的，以及"一个数两个身份"的清单

### 7.1 16 的来历

- **引入**：`3918366 feat: 节点概括化，初次限额，预算自洽`（`git log -S
  'GENERATED_LABEL_MAX_CHARS = 16'` 的唯一一次命中）。也就是说它跟着"提出 `detail`
  这个概念"一起进来的——**16 不是从画布量出来的，是"必须给 detail 留位置"这个决定的
  副产品**，画布那段注释是事后补的理由。
- **依据（代码里写的）**：180px 宽、14px 字、一行约 12 字、两行 24 字；16 是"缩到能看见
  全貌之后仍读得出"。
- **为什么不是 24**：注释只说了"24 是两行的量"，没说为什么选保守值。能查到的唯一硬证据
  是 §五那条——可读维度在两个独立读法下都是负的，且 24 这个数在前端已经另有身份
  （`TRUNCATE_CHARS`）。

**一句自评**：16 是一个**没有量过就定下来、事后补了理由**的数。它的方向（比 24 保守）
是对的，但"16 而不是 14 或 18"没有任何一条实测支持——这一轮也没有补上这个测量，因为
补它要重跑 20 次生成（模型调用），超出这一件的范围。**账留着。**

### 7.2 扫全部长度/数量上限常量：同值不同职责的清单

`grep` 全 `app/**` 的 `*_CHARS / *_MAX / *_LIMIT / *_BYTES / *_NODES / *_DEPTH`，
按值分组后只有三类值得说。

**A · 同源却写了两遍（真隐患：改一处另一处不跟，且都不报错）**

| 常量 | 位置 | 契约侧的对应物 |
|---|---|---|
| `MAX_DEPTH = 8` | `optimization/service.py:97` | `contracts/mindmap.py:29 MAX_TREE_DEPTH = 8`，**没 import**，注释自己写着"与契约保持一致" |
| `MAX_LABEL_CHARS = 200` | `agent/stream_items.py:25` | `contracts/mindmap.py:82 MAX_NODE_LABEL_CHARS = 200`，**没 import**，注释写着"与契约里 `Node.label` 同口径" |
| `LEAF_MAX_CHARS = 300` | `knowledge/service.py:651` | `contracts/source.py:332` 的 `max_length=300` 是**内联字面量**，连常量都没有；而 `service.py` 的注释说"不得超过 `SourceRef.quote` 的 300" |
| `GENERATED_LABEL_HINT = 16` | `frontend/src/mindmap/edits.ts:390` | `contracts/mindmap.py:101 GENERATED_LABEL_MAX_CHARS = 16`，**跨语言手写**，没有构建期同步 |

判：**这四个都该统一**。前两个是"字面量复制 + 注释承诺同步"，第三个更糟——被引用的那一侧
根本不是常量，第四个是跨语言复制（而这个仓库已经有"值域单一源、构建期生成"的先例，
见 `93acee6 fix(图型): 值域与中文名也改成单一源（构建期生成）`）。**这是一类静默失败**：把
契约深度从 8 改成 9，优化层的诊断会继续在第 8 层说"到顶了"；把生成上限改成 18，前端提示
还在 16——没有任何东西会红（`tests/` 里也各测各的）。

顺带一条：`GENERATED_LABEL_HINT` 只作**提示**（"标题有点长，画布上会折行"），不做校验，
所以这一件把实际 label 改短之后它更少触发，不受影响；`schema.d.ts` 里 `label` 也只是
`string | null`，没有 `maxLength: 16`。**前端不依赖 16 这个数做校验**——这一点是查过的，
不是推的。

**B · 同值不同职责（都各自成立，但读代码的人会以为是同一个东西）**

| 值 | 承担者的第一种身份 | 承担者的第二种身份 |
|---|---|---|
| 24 | `repair.py:156 READABLE_LABEL_CHARS`：**拼接预算**（超了就取内层，不切） | `frontend/src/stores/mindmap.ts:92 TRUNCATE_CHARS`：**显示兜底**（`len > 24` 加省略号）。第三个 24：`tools.py:7395 INPUT_EXTRACT_MAX_TOPIC_CHARS`（主题抽取上限） |
| 16 | `GENERATED_LABEL_MAX_CHARS`：生成侧标题长度 | `MAX_NODE_ICON_CHARS`（emoji 码点）；另有 `SALT_BYTES`、`GUEST_SIG_CHARS`（`auth/store.py`，密码学，与长度无关） |
| 40 | `MAX_EDGE_LABEL_CHARS`（边标签） | `MAX_FISHBONE_CATEGORY_CHARS`（鱼骨类别）、`OUTLINE_MAX_TITLE_CHARS`（大纲标题） |
| 200 | `MAX_NODE_LABEL_CHARS`（契约硬拒） | `MAX_FISHBONE_PROBLEM_CHARS`、`PROMPT_DETAIL_MAX_CHARS`、`MATERIAL_HEAD_CHARS`、`DEDUPE_TEXT_CHARS`、`MAX_URL_CHARS`、`PASSWORD_MAX_CHARS`、`MAX_LIMIT` |

判：**这些保持分离，但三个 24 该互相点名。** 理由：它们的值一样是巧合，职责不一样
（一个是"不切只归内层"，一个是"切了加省略号"，一个是"抽出来的主题该多长"）；把三个
合并成一个常量会把三种策略绑死。**但 `ACCEPTANCE-REPORT` §6.4④ 已经因为这两个 24 被
绕过一次弯**（有人以为显示层的 24 是 44 处截断的原因），所以至少要在三处注释里互相
指名道姓——第三个 24（`INPUT_EXTRACT_MAX_TOPIC_CHARS`）现在**一处都没被提过**。

**C · 一个数在契约里当硬约束、在别处当可读性建议（父任务问的那个形状）**

| 硬的那一侧 | 软的那一侧 | 现状 |
|---|---|---|
| `MAX_NODE_LABEL_CHARS = 200`（`Field` 硬拒，旧图必须能读） | `GENERATED_LABEL_MAX_CHARS = 16`（生成侧硬切） | **已经写清了**（"这是生成侧的约束，不是契约校验"），是本仓库处理得最好的一对 |
| `MAX_TREE_DEPTH = 8`（第 9 层加不出来） | `optimization/service.py` 的 `MAX_DEPTH`（只报 warn 诊断） | 值对了，同步机制没有（见 A） |
| `SourceRef.quote max_length=300`（硬拒） | `LEAF_MAX_CHARS = 300`（分块目标长度，注释说"不得超过"） | 靠注释维持，没有常量（见 A） |

判：**这一族里只有第一对是健康的**——因为它把两个数**放在同一个文件、相邻的位置、
并且在注释里互相解释**。A 里那三个的失败不是"值错了"，是"没有把'它们是一回事'写进
能被执行的东西里"。这一轮不动它们（不在第 6 件的地盘），但它该是下一件：把 `MAX_DEPTH`
与 `MAX_LABEL_CHARS` 改成 `from app.contracts.mindmap import ...`，再给 `quote` 的 300
一个常量名。**三条 import 的改动，加上两个用例就能钉住，成本比这一件低。**
