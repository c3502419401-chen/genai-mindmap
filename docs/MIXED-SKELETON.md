# 混合材料的骨架：有章节的走章节、没章节的走图谱

**一句话**：一批材料里只要**有一部分**抽得出章节，另一部分的去处就没有人问过。骨架
（一级分支的来源）现在是"整批二选一"，所以那几份不是"分得不好"，是**不在骨架里**。
这份文档记三件事：缺陷的实测形状、合并规则与它的三条依据、以及修完之后 A/B 量到了
什么（**包括没量到的**）。

代码：`backend/app/agent/tools.py`（`_outline_split` / `_merge_chapter_entries` /
`_graph_supplement_attempt` / `_pick_supplement` / `_mixed_outline`）、
`backend/app/knowledge/service.py`（`heading_outline_by_source`）。
用例：`backend/tests/test_mixed_skeleton.py`（19 条，前两条钉"现状"：旧口径没被改掉）。
实测脚本：`backend/scripts/measure_mixed_skeleton.py`（`--probe` 不花钱）。

---

## 1. 缺陷：判据是"标题总共管住了多少字"，不是"哪些材料有结构"

`heading_outline` 逐份出目录，然后**整批裁剪**（`_trim_outline` 按 coverage 挑前 30 条）；
`_outline_entries` 在裁剪后的目录上判一次覆盖率（≥60% 才拼进骨架）。两步的粒度都是
"整批"，于是输出只有两个值：**这批材料有目录**，或者**这批材料没目录**。

库里 29 份真实材料上的五个读数（`scripts/measure_mixed_skeleton.py --probe`）：

| 材料 | 份数 / 字数 | 章节条数 | 覆盖 |
| --- | --- | --- | --- |
| 只有 markdown（有标题） | 4 / 66,536 | 30 | 0.91 |
| 只有 paper（无标题） | 20 / 6,658 | 0 | 0.00 |
| **markdown + paper 混** | **24 / 73,194** | **30** | **0.83** |
| markdown 少量 + paper 大量 | 21 / 32,923 | 11 | 0.78 |
| web + paper 混（都短） | 22 / 16,968 | 16 | 0.56 → 过不了闸 |

第三行是缺陷的形状：**覆盖 0.83 看上去还行，因为分母是字数**——paper 那 20 份只占 9%
的字，一条标题都不贡献，在骨架里完全没有位置。第五行更狠：16 条标题确实存在，整批
覆盖率 0.56 < 0.60，于是**连那 16 条也一起不拼**（旧路径一条都不给）。

同一条缺陷更早的一次观测：维基 1 份（9 条标题）+ 论文摘要 2 份（0 条）→ 9 条全来自
维基，论文那 2,393 字（占 24%）只在按支检索时被零星捞上来。

### 根因（两处，同一个形状）

```python
# knowledge/service.py::heading_outline
for source in sources:
    entries.extend(_outline_entries(text))   # 分材料，对的
return _trim_outline(entries, max_items)     # 合并后整批二选一，无章节那几份的空目录被静默丢弃
```

```python
# agent/tools.py::_graph_outline_attempt
count = graph_store.scoped_entity_count([s.id for s in sources])   # 整批算，不是"这几份没有"
```

## 2. 改法：逐份判、分两组、各自出骨架、再合并

```
_mixed_outline(sources)
├── _outline_split        逐份判（目录非空 + 每份自己的覆盖率 ≥ 60%）
│   ├── 有章节 → _merge_chapter_entries   每份至少留一条，再按 coverage 补到 30
│   └── 无章节 → _graph_supplement_attempt（scope 只给这一组）
└── 合并成一份 prompt：章节块 + 图谱补充块 + 一类规则
```

两组都非空才走这条路；只有一组时**一个字节都不变**（`MINDMAP_MIXED_SKELETON=0`
是 A/B 与回滚开关，默认开）。

### 合并规则 ①：顺序——章节在前、图谱在后

依据：章节是**作者自己划的结构**，本来就该是一级分支的首选（`PLAN_PROMPT` 那句
"材料自带章节时优先采用它们"就是它）；图谱那一段的用途是"这几份没有结构，别忘了
它们"，放在章节之后、条数要求之前，作用是**把遗漏说出来**，而不是与章节争夺一级。

被否掉的写法是"按材料原始顺序穿插"：那样章节的"约占 X%"要与抽出来的概念混编，模型
分不清哪些是原文结构、哪些是抽取层的产物，而两者的可信度不同——混在一起就没法各自
打折。A/B 也支持这个顺序（见 §4：B 组的分支名同时保留了章节词与概念词）。

### 合并规则 ②：总量——两边各有硬上限，合并后不新造第三个数

| 部分 | 上限 | 依据 |
| --- | --- | --- |
| 章节 | `OUTLINE_MAX_ITEMS` = 30 | 既有口径，不动 |
| 图谱 | `GRAPH_SUPPLEMENT_MAX_ITEMS` = 8 | 与 `GRAPH_OUTLINE_MIN_ENTITIES` 同量级；实测那 20 份在图里有 **169 个带边实体**、`subgraph` 按度数取回 60 个，整段塞进提示词是 2,489 字，会把 30 条章节压成背景 |

合并后最多 38 条"方面"，与"30 章 + 20 份摘要"仍是同一量级。它只影响
`sections_expected`（两级骨架的判据），而 24 份批在 30 章时**早就 > 阈值 10**，
所以**树的形状不变**（A/B 两臂都是 3–6 条一级分支，见 §4）。

真正会改变形状的是"少章节 + 多摘要"那种批（4 章 + 8 概念 = 12 > 10）：那确实多了几块，
该分组——而不是把概念藏起来、装作只有 4 块。这条由
`tests/test_mixed_skeleton.py::test_grouping_counts_the_graph_branches_too` 钉着。

### 合并规则 ③：去重——同一个说法只留章节那一条

判据是折叠后的键（`_concept_key`：去空白与标点、折小写），**判等与互相包含**
（`碳中和` ⊂ `碳中和碳达峰`）都算重复。三个方向都做：

- 章节 ↔ 图谱：留章节。它带 `start` / `coverage`，能回到原文；抽出来的名字只剩一个词。
- 图谱内部：互相包含的只留更短（更概括）的；并且**贪心按"还能覆盖几份材料"选**，
  覆盖满了就停——同一件事的几种说法本来就不该各占一条分支。
- 章节 ↔ 章节（跨材料）：同名只留先出现的那一条（模型最后只会画一条分支，留两条等于
  白占目录额度）。去重之后若某份材料一条都不剩，它的最大一章会被重新放回来
  （`_merge_chapter_entries` 的第 ① 步先占位、② 才去重，所以这一步不会发生；
  真发生在上限被撑爆时，取"不超过 30 条"而不是"每份一条"）。

## 3. §二 的账：先量"该合并成什么样"，再动代码

24 份混批（4 章 + 20 摘要 / 73,194 字）上，改法给出的三行数字：

| --- | --- | --- |
| 章节分支 | **30** | 4 份 markdown 的 41 条目录 → 每份至少留一条 + 按 coverage 补到上限 |
| 图谱分支 | **8** | 从 60 个候选实体里贪心选（见下），覆盖 20 份里的 **15 份** |

### 4.3 ④ 耗时：新增开销在哪

`_mixed_outline` 在 24 份批上 **210–280 ms**（冷 219 / 热 282 / 热 212），其中：

- 逐份解析目录 **1 ms**（`heading_outline_by_source` 与 `_outline_entries` 同量级）；
- 其余全是一次 `scoped_entity_count` + 一次 `subgraph`（scope 只给 20 份）的 Neo4j
  往返。这与第三档（`_graph_outline_attempt`）付的是同一笔钱，而它只在"两组都有"
  的批上付——纯章节 / 纯摘要批一分钱不付。

相对 37–43 s 的整次生成，是 **+0.5% 上下**；骨架那一次从 1.8 s 到 2.0 s，多出来的
是 prompt 里那 8 行概念。**"只对 20 份取子图"没有变慢的迹象。**

## 5. 自评：「每份材料都要被至少一条分支指到」这个目标，是不是一定对？

**不是。** 它是这次修法的**检测手段**，不是**产品目标**，两者必须分开。

反例就在库里：那 20 份摘要是**一堆彼此独立**的篇目（碳中和 2 份、海绵城市/雨污分流
4 份、机器学习各类应用 5 份、财务报销 2 份、电商 1 份、大希律 1 份…）。按"每份一条
分支"切，会得到 20 条又宽又重复的一级分支；而它们真正不同的"事"只有 **6–7 件**。
4.2 那一批更明显：20 份与题无关的材料各给一条分支 = 一张 24 条一级分支的图，那不是
导图，是文件列表。

**该用的判据是「每个不同的事一条分支」，外加两条可执行的下限：**

1. **簇覆盖率**：把材料按"被哪条分支引到"聚成簇（同一条分支引到的材料算一簇），要求
   **每一簇至少有 1 条分支**，且**簇数 ≈ 分支数**——簇数明显多于分支数，说明有材料
   没被任何事代表；分支数明显多于簇数，说明同一件事被拆成了几条（该合并）。
2. **分支名必须是材料里的原词**（`faithfulness` 的逐字口径）。这条是"这一支真的长在
   材料上"的最低证据：B 组 16.7% > A 组 0.0%，差值就是它买到的全部东西。

**它怎么从产物里算出来**（都能从一张已生成的图 + 材料原文算，不需要再跑模型）：

```
簇          = 按 branch → 材料 的引用关系做连通分量（branches × sources 的 0/1 矩阵）
簇覆盖率    = 被至少一条分支引到的材料数 / 材料总数          ← 分母是"份"，不是字数
分支/簇比   = 一级分支数 / 簇数                              ← >1 说明拆细了，<1 说明漏了
忠实度      = 一级分支名（去空白标点）逐字出现在本次材料里的比例
```

"24 份里 24 份被指到"这个数在我们的实测里**两臂都没做到**（A 17–38%、B 62–67%，
主题不匹配那一批两臂都是 17%），而**这不全是模型的问题**：请求只有 6 条分支，
6 条分支最多能"指到"6 件事。把指标写成"份"会逼着实现去拆细，把指标写成"簇"才对得上
"这张图该讲几件事"。

所以修完之后我会这样陈述它能保证的东西：**没有一份材料在骨架的输入里被静默丢弃**
（有章节的进章节块，没章节的进概念块，两边都没有的在清单里有点名 + 一句规则），
**而不是**"每一份都有一条分支指向它"。

## 6. 边界与没做的事

- **入图的闸没动**。`_graph_ingest_pending` 仍然"有章节目录就不入图"——所以冷启动的
  混合批（那几份还没入过图）补不出概念，走的是 `_mixed_plain_rules`（一句"不要因为
  它们没有标题就不给位置"）。要它补，得改入图闸并付抽取的钱，那是另一件事。
- **没有新的诊断 code**：复用 `GRAPH_OUTLINE_USED` / `GRAPH_OUTLINE_UNAVAILABLE`，
  消息里报"覆盖其中 N/M 份"；跳过时的后果那句按混合批改写（"这几份没有分支指向它们"）。
  `openapi.json` / Pydantic 模型一个字节都没动。
- **两级骨架的判据没动**：只是把图谱那几条加进了 `sections_expected`。
- **主题与材料不匹配时不硬塞**（见 4.2）：模型有权把无关材料留在图外，代码只保证
  "它们被看见了"，不保证"它们被画出来了"。
