# 一级分支条数：不设限的来龙去脉，与"按偏好"那套的设计留档

这份文档回答四件事，顺序就是当初问的顺序：

1. **前端那个"默认 6"到底算不算用户显式选择** —— 核对结果是：**没有对象**，
   因为前端从来没接过这个参数；
2. `branches` 的契约值到底是多少（**5**，不是 6），以及 6 与 10 两个数各自从哪来；
3. 「首张不设限、之后按用户偏好」那套三档判据的完整设计（**已放弃，此处留档**），
   包括它为什么最终没上线；
4. `style_profile.branches` 那层画像**到底在描述什么** —— 附 54 条样本的实测分布。

第 3 节是"下次真要做分支数时该从哪里下手"的唯一入口；第 4 节是"为什么要做"的一半证据。

---

## 1. 事实核对：下拉从来没接过这个参数

原来的担心是「前端每次都发 6，那"不设限"永远不生效」。核对之后这条担心**不成立**，
而且原因比"默认值太强"更彻底：

| 查的地方 | 结果 |
| --- | --- |
| `backend/app/agent/contracts.py::AgentRunRequest` | **没有 `branches` 字段**（`goal` / `intent` / `thinking_model` / `diagram_type` / `prefs_applied` / `snapshot` / `selected_ids` / `sources` / `budget` / `deep_thinking`，到此为止） |
| `backend/openapi.json` | 全文搜 `branches`：只在 `Node` / 流程节点的 `description` 里出现，**没有 schema 字段** |
| `frontend/src/stores/options.ts` | 只有两个下拉：拆解方式（`thinking_model`）与图型（`diagram_type`）。`DIAGRAM_TYPE_OPTIONS` 是那四个值，没有第三个控件 |
| `frontend/src/api/schema.d.ts` | 由 openapi 生成，同样没有 |

**所以"用户当场选了几条"这件事今天根本不存在。** 定性因此要改：

> 不是"用户偏好与前端下拉在抢同一个数"，而是**下拉从来没有接过这个参数**。

本轮讨论里出现过"界面请求值 6""界面上选的 5"这类说法（`docs/GRAPH-SCALE.md` 第 273、
345 行的提示词引用与对照表脚注）。**那是过时表述**，指的其实是**度量脚本**的参数：

```bat
python scripts/measure_scale.py --only medium --repeat 1 --branches 16
python scripts/measure_branch_budget.py --repeat 3 --grids A,B,C --arm a
```

`measure_*.py` 的 `--branches` 会作为 `ToolCall` 的 `arguments` 传给工具，于是它出现在
提示词里、也出现在那些对照表的脚注里。**它不是界面上的东西**，别拿它当契约依据。

### 唯一"零契约成本"的显式通道

`AgentRunRequest.prefs_applied` 是 `list[str]`（`max_length=50`，自由字符串），语义是
"这一次运行实际带着哪些偏好"，落进 `runs.request.prefs_applied`，已经有两个真正的
消费者（`prefs.service._last_applied` 与 `runs` 的审计）。

它里面出现一条 `branches=6`，后端就能读到"用户当场选了几条"，**不需要加字段、不需要
重新生成 `openapi.json`、不需要动前端镜像**。而前端不发它，就是"未选"。

> 结论：**`prefs_applied` 里带 `branches=<整数>` 才算"用户当场选的"，不发就是"未选"。**
> 这条与下面第 3 节的开关无关，下一轮改分支数时照旧成立。

## 2. `branches` 的契约值：5，不是 6

```python
# backend/app/agent/tools.py::GenerateDeepArgs
branches: int = Field(default=5, ge=3, le=DEEP_MAX_BRANCHES, description="一级分支数量上限")
# backend/app/agent/tools.py::GenerateArgs   （同值同区间）
branches: int = Field(default=5, ge=3, le=DEEP_MAX_BRANCHES, ...)
DEEP_MAX_BRANCHES = 20
```

- **默认值 5**、下界 3（`MIN_BRANCHES`，少于三条不成图）、上界 20（画布承载能力）。
- 这个数是**模型自己填的工具参数**。它填的时候在一次骨架调用**之前** —— 也就是说，
  在它读到材料目录之前。所以它是"预感"，不是"判断"。

### 6 与 10 这两个数从哪来（都不是分支默认值）

| 数 | 出处 | 依据 |
| --- | --- | --- |
| **6** | `SKELETON_GROUP_MAX` | 组的可读区间 `3..6`。理由：`DETAIL_PROMPT` 对一级分支的既有要求是 3–6 条，一组超过 6 条就回到"一层横向太多" |
| **10** | `SKELETON_GROUP_THRESHOLD` | **超过 10 条才分两级**。依据两条：调色板是 8 色（`NODE_COLORS`，"一色一组"刚好一屏），而画布横向能扫完的一行也在 10 条上下 |
| **4** | `SKELETON_GROUP_TARGET` | 每组目标支数。依据："一组的子节点 3–5 个正好一屏"，20 节 ÷ 4 = 5 组，落在 `3..6` 中间 |

一句话：**6 是"一组最多几条"，10 是"多到该分组"，5 才是"一级分支默认几条"。** 三个数是
三件事，混过这一轮。

`SKELETON_GROUP_THRESHOLD` 是**结构保护**，不是分支上限：一级分支不设限之后它更重要
（松掉上限时最容易出的错是图宽到没法看），所以现行实现里它照旧生效。

### 工具参数**不进** `openapi.json`（已核实，这一条省掉很多顾虑）

`GenerateDeepArgs` / `GenerateArgs` 是 **LLM 的工具 schema**，不是 HTTP 请求体。全文搜
`backend/openapi.json` 只有 `Node` / 流程节点的 `description` 命中 `branches`，**没有一处
是 schema 字段**。所以：

- 改一个工具参数的 `description`、`default`、甚至**删掉整个字段**，都**不触发**契约变更
  （不需要重新生成 `openapi.json`、不需要同步 `frontend/src/api/schema.d.ts`）；
- 但它会改变**模型看到的东西**，所以要按"改提示词"的标准来做（一句话能改变骨架形状）。

反过来也成立：`AgentRunRequest` 的字段才进 `openapi.json`。这一轮不许动那两处，指的就是
后者——别把"工具参数"和"请求字段"混成同一件事，这是本轮最容易走偏的一步。

## 3. 已放弃的设计：「首张不设限，之后按偏好」

> **状态：放弃。** 需求后来改成"如何展开一级分支树和子树都不做限制，交给模型自由发挥，
> 但生成的节点要有引用"——**全程不设限**。下面这套是"两段式"的实现方案，留档是因为
> 它把"分支数该由谁定"的三种答案（显式 / 推断 / 谁都没说）想清楚了，下一轮还要用。
> 它曾经以 `MINDMAP_BRANCH_CAP`（默认关）的形式挂在代码里，随着现行实现落地已从
> `tools.py` 撤出；`app/prefs/style.py::branch_hint()` 这个**取数值的接口**是通用能力，
> 与语义无关，保留。

### 3.1 三档按"谁表过态"排，不按数值大小排

```
① 显式        prefs_applied 里写了 branches=<n>       → 用它，一个字都不改地写进提示词
② 偏好        style.branch_hint() 可用               → 用它的上限（p75，不是中位数）
②b 让位       材料自己数出的方面数 > ②的上限           → 回到不设限（反闭环）
③ 不设限      上面都没有                             → 给判据不给数
```

### 3.2 为什么②的上限取 p75 而不是中位数

上限取中位数 = 把"典型值"当成"最大值"。更要紧的是闭环：这一层的样本来自历史产物，而
历史产物是在"最多 N 条"这句话下长出来的。取中位数当上限，下一次的产物继续落在中位数
上，下一版画像的中位数还是它 —— 一个自我确认的回路。

`BranchHint.cap` 因此取 `Param.high`（p25–p75 区间里的 p75，`_number` 里
`statistics.quantiles(..., n=4, method="inclusive")[2]`）：它是这段分布里**真实出现过**
的条数，不是 median + 1 那种凭空加的余量。

> **留档：p75 这个取值方式为什么最后没用上。** 原因不是它不好，而是整条"按偏好当上限"
> 被放弃了（第 3 节开头）。也就是说：`p75` 是针对"上限取中位数会自我确认"这个**具体
> 缺陷**的解法，而那个缺陷本身仍然存在于"任何用历史产物去预测下一次形状"的做法里。
> 将来若重做条数控制（从 `prefs_applied` 那条通道开始，见第 1 节），这一段可以原样
> 复用：**上限取这段分布的上四分位，不取中位数**，理由与本节相同。

### 3.3 §二 那三条出路：为什么选 C 的零加字段变体

原题是"前端那个默认值要不要算显式"，三条出路：

| 方案 | 做法 | 为什么不选 |
| --- | --- | --- |
| A | 后端把"等于默认值"当"未选" | 前提不成立（前端没有这个字段）；而且"真的想要那个数"与"没动过"不可分辨 |
| B | 保留默认值作上限，只在偏好更强时覆盖 | 语义变弱成"偏好没建立时不强求"——那不是"不设限" |
| **C** | 加一个后端能读的标记，前端不发就视为未选 | **选它**，但用**已存在**的字段表达，不新增 |

**C 的变体 = `prefs_applied`**。理由：

- 它是 `list[str]`，**不进 `openapi.json`、不需要前端镜像同步** —— 这一轮的硬边界正好
  不许动那两处；
- 它的语义本来就是"这次运行实际带着哪些偏好"，一条 `branches=6` 读进去毫不勉强；
- `prefs.service._last_applied` 已经在按 `key=value` 解析同一份数组，多一个键不会让它
  出错（`list_all` 只把命中的键贴到已有的偏好行上）。

解析的三条宽容与三条不宽容（`_requested_branches` 的实现口径）：

| 宽容 | 不宽容 |
| --- | --- |
| 键大小写不敏感、允许首尾空白（人拼的字符串） | 值必须是整数，且在 `MIN_BRANCHES..DEEP_MAX_BRANCHES` 内，越界静默忽略 |
| `branches` 与 `branches.default` 都认（后者是 A 类偏好的命名习惯） | 一条里没有 `=` 不算（`partition` 后先判分隔符） |
| 同一个数组里多条时取第一条（确定性） | **不报错**：这是旁路信息，为它把整次生成判死，代价方向完全错 |

### 3.4 反闭环：为什么是"材料宽度"而不是"每 N 张放一次"

老用户用了半年、样本早就够了，那他从第 6 张图开始就永远走"偏好上限"，而偏好本身是从
前 5 张（在"最多 N 条"下长出来的）学来的。**这个回路是真的**，本机数据也是证据（见第 4 节：
中位数 5 与契约默认值 5 一字不差）。

两种打破办法，选后者：

| 办法 | 问题 |
| --- | --- |
| 每 N 张放一次（计数器） | **同一次输入**的产物取决于"这是他第几张图"：用户看到同一件事两次不同结果，而界面和日志里没有一处能解释第二次为什么变了 |
| **材料宽度判据** | 材料里有 12 章、偏好说 5 条时，这一次不设限。可解释、可复现、不需要计数器 |

`_material_width(entries, supplement, graph_entities, chapters)` 就是那个"材料自己说这次
有几个方面"的数：章节行数（含混合批里图谱补的那几条）与按章切的章数取大者。三个来源在
正常路径上互斥（图谱那一档只在章节抽不出来时接管），相加只在混合批这一个真实形态上同时
非零。

**材料只有 3 块、偏好说 5 条时照常按偏好** —— 那不是压制，上限本来就不起作用（模型自己
只会给 3 条）。所以"永远走偏好"本身不是问题，问题只在"材料比偏好宽"的那一次。

## 4. 那层画像到底在描述什么：54 条样本的分布

原假设有两条，只有一条能被数据支持：

```
① 用户真的习惯 5 条左右        → 画像在正常工作
② 模型每次都按默认值 5 写      → 画像学到的只是"模型自己的默认"
   判据：如果 5 占 15/21 条以上 → 是②
```

实测（`data/mindmaps.db`，`status='done'` 且 `candidate` 可解析，`_dedupe` 折叠后）：

| 一级分支数 | 1 | 3 | 4 | 5 | 6 | 7 | 12 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 条数（折叠后 54 条） | 2 | 11 | 8 | **23** | 7 | 2 | 1 |

- **5 占 23/54 = 42.6%**，远低于判据要的 71%（15/21）。分布里 `3/4/6/7` 都在出现，这是
  **真离散**，不是"同一个默认值被记了 15 次"。
- 结论：**"那层画像学到的只是模型自己的默认值"这个判断是错的。** 准确的说法是：
  **默认值把分布拉到了 5 附近，但画像本身有信息量。**
- 限定一（~~很可能是 `measure_*.py` 脚本 `--branches` 的产物~~ → **2026-11-28 切了，
  两个都不是脚本产物**，取证与口径见 §4.4）：`3` 是**无材料的纯主题请求**加**同一张
  三支小图被反复编辑/展开**，`12` 是同一条材料三次采样里的一次离群。真实使用确实集中在
  **4–6**，但那句话的原因不是"脚本污染"。
- 限定二：这条只否掉了"全是默认值的回声"，没有证明"它足以当上限"。见下面"为什么放弃"。

### 4.1 口径漂移：21 / 68 / 54 是三个不同时刻的数

同一个 `style_profile.branches`，在不同地方会看到三个数，而它们**都不是错的**：

| 数 | 是什么 | 从哪来 |
| --- | --- | --- |
| **21** | `style_profile` 表里 `samples` 那一列 | **上一次 `refresh()` 的快照**。面板与 `describe()` 读的就是它 |
| **68** | 库里 `status='done'` 且 `candidate` 可解析的运行条数 | `iter_observations()` 现在能读到的全部 |
| **54** | 68 条经 `_dedupe` 折叠后的条数（同形状最多两票） | 下一次 `refresh()` 会写进去的那个数 |

`read()` 是纯读、`refresh()` 才重算（见 `app/prefs/style.py` 模块头），所以**表里的数与
数据的现况可以差得很远**。踩过一次的后果很具体：拿 21 当基线去算占比，结论会与拿 54 算
出来的不一样。**引用这个数时先说清是哪一层的数。**

### 4.2 为什么放弃"按偏好当上限"——不是"画像全是噪音"

这两个结论必须分开说，否则下一个人会读成"`style.py` 不可信"，然后连另外 7 个参数
（深度 / 每层宽度 / detail 长 / label 长 / 图标 / 配色 / 图型）一起不信 —— 而那 7 个
参数各自都有独立的信息源，问题只出在 `branches` 这一个上：

> `branches` 的样本混着**模型自己的默认值**（5）与**同一句话的多次重跑**（3 那一批里
> 五条是同一个纯主题、另六条是同一张三支小图的编辑与展开），所以"用它当上限"
> **缺一个独立的信息源**。深度的中位数 4 不是任何默认值的回声，那是同一个数字在这里
> 不成立的原因。（原文此处写的是"度量脚本的参数（3、12）"——**那句话是错的**，
> 见 §4.4。）

这才是与"用户放弃按偏好"自洽的理由，而不是"数据没用"。

复现（单行，`cmd` 下已实测；`cmd` 不认反斜杠续行，写多行会直接报语法错）：

```bat
cd backend
python -c "from app.prefs import style; import collections; obs=[o for o in style.iter_observations() if o.depth>0]; kept,_=style._dedupe(obs); print(collections.Counter(o.branches for o in kept))"
```

输出：`Counter({5: 23, 3: 11, 4: 8, 6: 7, 1: 2, 7: 2, 12: 1})`（2026-11-23）。

### 4.3 这条与"用户放弃按偏好"是自洽的

不是"偏好不该存在"，而是**"用它当分支数的上限"缺一个独立的信息源**：那批样本里混着
模型自己的默认值与同一句话的多次重跑。用户放弃"按偏好"这个决定，与这条数据是自洽的——
**但理由是这个，不是"画像全是噪音"。**

### 4.4 「3 与 12 是不是脚本产物」这一刀：切了，两个都不是

这一问在台账里挂成了第 11 条，blocker 写的是"归因一行代码都没有"。实际切下来是三条
取证，其中两条是代码事实、一条是数据事实：

1. **测量脚本不写 `runs` 表。** `runs` 的写入 SQL 全在 `app/agent/runs.py`，而它的
   唯一调用方是 `app/agent/router.py`（`runs.checkpoint` / `runs.finish`）——也就是
   走 HTTP 的那条运行路径。`measure_branch_budget.py` 走的是
   `measure_scale.py::_run_once` → `registry.execute(...)`，**不经过 router**，产物留在
   进程内存里、落 jsonl 报告。`backend/scripts/` 里唯一 `import` 过 `runs` 的是
   `verify_prefs_acceptance.py`，它只调 `runs.get`（读），而且先把 `MINDMAP_DB_PATH`
   指到 `tempfile.mkdtemp()`。
   **这一条的理由不是"脚本不碰主库"**——恰恰相反，`measure_branch_budget.py` 就把
   `MINDMAP_DB_PATH` 指到 `data/mindmaps.db`（它要按 `SOURCE_IDS` 读真材料）。
   理由是**它只读那张库，不写 `runs`**。所以"脚本生成的树进了画像数据源"这条路
   在代码上不存在。
2. **`branches` 不读任何脚本产物。** `app/prefs/style.py::observe()` 的 docstring 第一句
   就是"纯函数，不读库"，`branches = len(shapes.top_branches(content))`，输入只来自
   `runs.candidate`；`_observations()` 的 `SELECT` 只有 `runs` 一张表。
3. **按 `goal` 字面归因，落不到脚本常量上。** 测量脚本的 topic 是脚本里的常量
   （`TOPIC` / `sources` 固定 UUID），而库里 `branches=3` 的样本 goal 全是界面语：
   `碳中和的主要方面`（同一句重跑）、`把「工业过程减排」这个标题改短一点`、
   `展开节点「…」，补充 3 个子节点。`、`ai学习`、`机器学习`、`rust学习路线`。
   `branches=12` 只有一条：goal `检索与召回的取舍`、带 1 份材料，而**同一个 goal 的
   另两次是 4 与 5**——脚本若真传过 `--branches 12`，三条该一起变宽。

复算（`cmd` 下实测，一行；`cmd` 不认反斜杠续行）：

```bat
cd backend
python -c "import json,sqlite3,collections;from app.prefs import style;c=sqlite3.connect('data/mindmaps.db');c.row_factory=sqlite3.Row;g={r['run_id']:(json.loads(r['request'] or '{}').get('goal'),len(json.loads(r['request'] or '{}').get('source_ids') or [])) for r in c.execute(\"select run_id,request from runs where status='done' and candidate is not null\")};obs=[o for o in style.iter_observations() if o.depth>0];kept,_=style._dedupe(obs);print(collections.Counter(o.branches for o in kept));print(*[g.get(o.run_id) for o in kept if o.branches in (3,12)],sep='\n')"
```

**★ 顺带修掉一个字段名：`runs.request` 里没有 `sources`。** 它的键是 `goal` / `intent` /
`thinking_model` / `diagram_type` / `prefs_applied` / `selected_ids` / **`source_ids`**。
台账第 11 条原先那句判据写的是"按 `runs.request` 的 `sources` 长度"，照它做取到的是
**恒 0**（这跟"度量脚本产物"无关，是那一栏自己写错了字段名）。

**所以这一问的答案是不成立，但"缺独立信息源"这个结论仍然成立——缺的不是"排除测量树"，
是"给定材料量下的条件分布"**：`branches` 报的是中位数（`_number` 取 `statistics.median`），
而 `source_ids` 为空的那一组与有材料的那一组**中位数都是 5**，所以混合分布没有把结论
拉到别处；真正没有的是"3 份材料该给几支"这类条件信息。而那个用途（拿画像当分支数上限）
已经在台账第 1 条里废弃掉了——`branches` 工具参数现在两处 `description` 都以「已废弃」
开头。用途不在，缺口就不构成待办。

## 5. 现行实现（用户改需求之后）

```
一级分支条数：代码不给数。
提示词里那一段永远是判据（NO_BRANCH_CAP_RULE），不是"最多 N 条"。
代码只守两条与内容无关的边界：MIN_BRANCHES（<3 不成图）、DEEP_MAX_BRANCHES（画布上限）。
SKELETON_SIZE_OFF 那条"请求 N 条、给了 M 条"的诊断随之撤掉——没有期望就没有落差。
SKELETON_GROUP_THRESHOLD(10) 的两级分组照旧生效：它守的是图宽，不是条数。
```

判据原文（两半缺一不可：**给几条** + **哪些不该凑一起**）：

```
按内容实际包含的方面定条数：层级多就用足，内容单薄就少给；
不要为了凑数把不同的事塞进同一支，也不要为了整齐把不同的事合成一支。
```

后半句是这次新加的：上限一松，最容易出的错从"为凑数硬拆"变成"为整齐硬合"，两个错在
同一次调用里会互相拉扯。

沿用这套判据时**别把 `branches` 那个参数加回去**：它的唯一来源是模型在读到材料之前填的
预感，而"预感当上限"正是这一段要拆掉的东西。要让规模有上界，用材料自己（章节数）或
契约常量，不要用工具参数。

### 5.1 只读核对到的三处缺口（当时的结论，**已过期，见 5.2**）

按"不设限"这个语义过了一遍现行代码，有三处是描述与行为对不上的，**本轮不改**（它们归
正在写那条路的改动）：

1. **`branches` 变成"填了不生效"的字段。** `GenerateDeepArgs.branches` /
   `GenerateArgs.branches` 仍在 schema 里（默认 5，`description` 写着"一级分支数量上限"），
   但已经没有一处拿它当上限了。仓库自己的规矩写在 `GenerateArgs` 的 docstring 里——
   *"一个永远填了没用的参数比没有这个参数更糟"*（那一段是为 `points_per_branch` /
   `max_depth` 被删时写的）。两种处置都可以：删掉字段，或把 `description` 改成它现在真正
   的用途（预估要几组）。**这两种都不触发契约变更**（工具参数不进 `openapi.json`，见 2 节）。
2. **两级分组的预判仍拿 `args.branches` 当下界。**
   `sections_expected = max(args.branches, 目录行数 + 图谱补条, 章数)`：纯主题（零材料）时
   这个数就是那个预感 5，于是**不请求两级**；而模型这时已经"不设限"，真给了 15 条，
   `_skeleton_plan` 收到的是扁平响应，压不出层级 —— 图会很宽，而 `SKELETON_GROUP_THRESHOLD`
   本来正是为这件事存在的。修法要么在"没有上限"时默认请求两级，要么把下界抬到阈值本身。
3. **没有材料时"按内容实际包含的方面定条数"没有可数的对象。** 判据假设有材料（章节行是
   它的输入）；纯主题时模型只能凭主题想象，`MIN_BRANCHES=3` 是唯一下限。这不是缺陷，
   但要知道无材料那一档的条数分布会比有材料时更散。

## 5.2 三处缺口的现状（复核，2026-11-28）

§5.1 那三条是 `e91e90d` **之前**的只读核对。今天按同样的问题重新核了一遍，结论是：
一条已经动手改完、一条的前提已经不成立、一条仍然是那样但**实测不支持改**。

| # | §5.1 当时的说法 | 现在的实际 | 处置 |
|---|---|---|---|
| ① | `branches` 变成"填了不生效"的字段 | 仍然不生效（`app/**` 里零读取），但 `description` 已经改成实话 | **已改**（见下） |
| ② | 两级分组的预判仍拿 `args.branches` 当下界 | **不成立了**：`e91e90d` 已把它从 `sections_expected` 里拿掉，现在只数材料宽度 | 无需动 |
| ③ | 纯主题时"按内容定条数"没有可数的对象 | 仍然是那样 | 不改（见 5.2.2） |

### 5.2.1 ①：改的是 `description`，不是删字段

两处字段（`GenerateArgs.branches` / `GenerateDeepArgs.branches`）的 `description`
现在是 **"已废弃：一级分支条数由内容决定，填什么都不会改变结果"**。

§5.1① 说两种处置都可以，这里选后者，判据是**故障面**而不是工作量：

- 两个参数的 `model_config` 都是 `extra="forbid"`。删字段之后，模型但凡凭旧记忆传一次
  `branches`，整次工具调用会**校验失败**——把"参数是噪音"升级成"参数是故障"。改描述不会。
- 仓库里四十余处用例与五个度量脚本仍在显式传 `branches`（它们钉的是别的行为、不读这个值）。
  删字段要连它们一起改，而那些改动不携带任何新信息。
- 两种处置都**不进 `openapi.json`**（工具参数由 `contracts/agent.py::ToolSpec.parameters`
  在运行时生成，本节 §2 已核），所以这个选择不涉及契约。

用例在 `backend/tests/test_branch_arg_deprecated.py`，三条各钉一件事：
`description` 说的是废止（且字段还在）、注册表里透出去的也是这句、以及
**`branches=3` 与 `branches=20` 的每一次模型调用输入 + content + data + 整棵树全都相同**。
最后那条是"以后谁把它接上，这里就会红"的那个提示。

### 5.2.2 ②与③：纯主题那一格，实测不支持改

② 被 `e91e90d` 改掉之后，剩下的那一格是：**纯主题（零材料）时 `sections_expected = 0`，
于是永远不请求两级**。§5.1② 给的修法是"没上限时默认请求两级，或把下界抬到阈值"。

改之前先量了两件事（两件都是可复算的，不是估的）：

1. **真实运行里纯主题的图有多宽。** `data/mindmaps.db` 的 `runs` 表：150 次产出了可数的
   一级分支，`request.sources` **全部为空**（= 真实用法几乎全是纯主题，与 §10307 那处注释
   一致）。一级分支数的分布是 4–8 为主，**最大 12，超过阈值 10 的只有 1 次（0.7%）**。
   查询口径：`select request, candidate from runs`，读 `request["sources"]` 与
   `candidate["root"]["children"]` 的长度。
2. **带材料的验收树有多宽。** `data/acc_trees/*.json` 20 棵（每棵 1 份材料）：
   4 / 5 / 5 / 5 / 5 / 5 / 5 / 4 / 4 / 6 / 5 / 6 / 4 / 4 / 7 / 7 / 6 / 7 / 6 / 6 支，
   **没有一棵超过 10**（`python scripts/_probe_thin_material_branches.py` 的第一节会把
   每棵的目录块数一起打出来）。

所以"纯主题会给出十几条一级分支"这件事，在 150 次真实运行里只发生了 1 次。而改法会让
**全部**纯主题请求都带上"这次请归成 3 组"这一段（`_group_plan_rules` 的组数由
`sections_expected` 倒推，零材料抬到阈值+1 就是 3 组），代价是：

- 覆盖面 100% 换 0.7%。模型的响应若仍只有 5–6 支，`_skeleton_plan` 会把它压平回扁平
  （`len(flat) > SKELETON_GROUP_THRESHOLD` 才保留分组），那一段提示词白付；
- 撞一条用例：`tests/test_skeleton_groups.py::test_ten_branches_change_nothing` 明写着
  "**无材料时骨架 system 仍是 `PLAN_PROMPT` + 那两句契约，一字不多**"。撞它不是意外，
  它钉的就是这个行为——但它说明这条改动不是"补一个漏判"，而是改一条被刻意选中的不变式，
  得先有"纯主题真的会宽"的证据才值得改。

**决定：不改，留触发条件。** 什么时候回来做：`runs` 里一级分支 >10 的比例超过 10%（现在是
0.7%，样本 150 次），或者有用户反馈"这张图太宽"。那时应该先看的是 `_cap_plan` 的 20 条
上限与画布排布，而不是往骨架提示词里加分组要求——因为分组要多吃一层深度。

顺带修了一处**真的悬空了**的指令（同一条链路上查出来的，与上面的判断无关）：
`_group_plan_rules` 里原来写着"用户消息里那个条数说的是二级分支的总数"，而
`_plan_ask` 早在撤掉配额时就不再往 user 里放任何条数了——那句话指不到东西。现在它自指
system 里紧挨着的那个数（"上面那个 {sections} 说的是二级分支的总数"）。
