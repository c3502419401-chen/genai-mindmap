# 视图层收起：数据完整，这一屏只画得下这么多

折叠退休之后（`7d25a85`）数据层是完整的一棵 100+ 节点的树，可它整棵摊在 1600×852 上
是**不可读的**：`fit-all` 的字号只有 1.6–3.1px。这一轮把可读性交回渲染层——
**数据一个节点不动，画布按"显示节点的数量上限"少画，每个被截断的地方留一个「+N」。**

它和折叠的区别只有一条，但它是全部：

| | 折叠（`_fold_tree`，已退休） | 收起（这一轮） |
| --- | --- | --- |
| 数据 | 子树被并成一个叶子，节点**没了** | 一个节点都不动 |
| 保存 / 导出 / 撤销栈 | 只剩下折叠产物 | 与收起之前逐字节相同 |
| 还原 | 恢复不了（`node_expand` 是重新生成一条新分支） | 一次点击 / 一个按钮 |
| 出现在哪 | 生成侧（`backend`） | 渲染层（`frontend/src/canvas/view-collapse.ts`） |

## 〇、这一轮改的是口径：从"几层"到"几个"

上一版（`d6f40efd`）按**层数**收：`显示某节点的子节点 ⟺ 子节点层号 ≤ expandDepth`。
它是**结构**口径，而产品负责人的原话是**预算**口径：

> 还是有显示节点上限，但是如果生成节点多于显示节点，就不继续在导图里面显示了，但还是有
> 生成的节点，这时候用户点击节点后就可以看到后面还有没有显示的节点，由用户决定是否展开
> 查看，然后展开之后应该还有折叠回去的选项保持界面清爽

两处都是口径问题，不是参数问题：

| | 旧（层数） | 新（数量） |
| --- | --- | --- |
| 旋钮 | `DEFAULT_EXPAND_DEPTH = 1` | `MINDMAP_VISIBLE_NODE_LIMIT = 40`（`≤0` = 不限制） |
| 截断边界 | **一整层**：第 2 层以下全无 | **一串具体的父节点**，散在同一层内 |
| 展开入口 | 节点右下角一枚「+N」 | **点节点本身**就是展开/收起，角标只是同一个动作的可点版本 |
| 回程 | 只有「收起深层」（回全部默认） | 逐个「−」+ 顶部「收起到上限」 |
| 自适应 | 按视口反推层数（`chooseExpandDepth`） | 不需要：上限是认知预算，与屏幕无关 |

层数那套还有个算术上的死结：正整数层数里 **1 与 2 之间没有第三档**——136 个节点展开
1 层是 7 个（25.6px，一屏看全但没有任何细节），展开 2 层是 25 个（8.3px，看不清）。
数量口径把这条死结拆掉了：40 个节点既不是"只剩目录"，也不是"摊满一间屋子"。

## 一、读数：上限与字号是两个问题

三棵真树从 `backend/data/mindmaps.db` 与 `runs.candidate` 原样导出（见
`frontend/tests/fixtures/real-trees.ts`），视口 1600×852，`NODE_SIZE = 180×48`、
层距 236、兄弟间距 20。

**默认上限 40**（按层铺满取前 40 个）：

| 树 | 总数 / 深度 | 收起后可见 | 外接框 | `fit-all` 字号 | `fit-width` 档 | 重叠 |
| --- | --- | --- | --- | --- | --- | --- |
| 136 节点 / 6 支 / 深 4 | 136 | **40** | 888×1884 | **5.3px** | 12px · 17 个在视野外 | 0 对 |
| 95 节点 / 4 支 / 深 3 | 95 | **40** | 888×2088 | 4.8px | 12px · 20 个在视野外 | 0 对 |
| 80 节点 / 8 支 / 深 3 | 80 | **40** | 888×1884 | 5.3px | 12px · 18 个在视野外 | 0 对 |

**第一条必须写清楚的事：40 不是"一屏看全"的界线。** `docs/LAYOUT-CLARITY.md` 那张表说的
是"节点数分档里，40–79 全部不可读"——40 是**再往上一定看不清**的分界，不是"40 就看得清"。
在 136 这棵树上，`fit-all` 达标（≥12px）需要压到 **17 个节点**：

| 上限 | 可见 | 外接框 | `fit-all` 字号 |
| --- | --- | --- | --- |
| 不限制 | 136 | 1124×6236 | 1.6px |
| 60 | 60 | 888×2768 | 3.6px |
| **40（默认）** | **40** | **888×1884** | **5.3px** |
| 30 | 30 | 888×1408 | 7.1px |
| 20 | 20 | 652×932 | 10.7px |
| 17 | 17 | 652×932 | **12.5px** |

所以默认落进 **`fit-width`**（字号 12px、纵向拖动看），不是 `fit-all`。这不是缺陷，
是两个旋钮各管一件事：

- **数量上限管认知预算**：一屏上不要出现 136 个框。拖动扫视 40 个框是读得懂的，
  拖动扫视 136 个框读不懂（75 个叶子沿竖轴摊开就是 6236px）。
- **字号由 `clarity.chooseViewMode` 那两档管**：装得下就 `fit-all`，装不下就停在 12px
  + 拖动。

宽度一直不是瓶颈（最大 888 < 1600），**高度是**——所以"少画节点"立竿见影，
"缩得更小"只会让字更小。

## 二、选哪些节点：按层铺满（BFS），不是前序（DFS）

同一个上限，两种遍历给出的"这一屏"完全不同。实测（1600×852，上限 40）：

| 树 | 前序（DFS）40 个节点 | 按层铺满（BFS）40 个节点 |
| --- | --- | --- |
| 136 / 6 支 | 一级分支只露出 **2 / 6** 支 | **6 / 6** 支全部露头 |
| 95 / 4 支 | **2 / 4** | **4 / 4** |
| 80 / 8 支 | **4 / 8** | **8 / 8** |

前序会把**第一条分支连同它整棵子树吃满预算**——那正是折叠被退休的理由（"只看到一支"，
`docs/FOLD-RETIRED.md` §1）。按层铺满则是"先根、再全部一级分支、再各自的子树"，
用户先拿到的是**目录**，这与他看思维导图的方式一致。上限压到 12 也能保住这条性质：
12 = 根 + 6 支 + 5 个更深的孩子，一支都不少。

**层内保持树序，不做"每支轮转"。** 轮转（每支各分一个再下一轮）能让边界层的深浅更对称，
但它会让"为什么这个节点的孩子显示了、那个没有"变成一条需要单独解释的规则。真正防住
"看着完整其实缺一块"的东西是**每个被截断的父节点上都必须有可见的标记**（见 §四），
不是边界层的对称性。代价是：**靠前的分支深、靠后的分支浅**（见 §六的自评）。

## 三、过滤口径：预算前缀 + 三道闸门

```
①预算前缀   按层铺满取前 limit 个节点            ← 一个**固定集合**，不是边走边扣的余额
②加法       用户点开的节点：放出它的**直接子节点**  /  全部展开：放全部
③减法       用户收起的节点：剪掉它的**整棵子树**
④可见       祖先闭合（每个画布上的节点，父链全在画布上）
```

四条各自都有一个"不这么写就会出问题"的理由：

**① 为什么是固定集合、不是余额。** 边走边扣意味着"收起 A 之后，A 省下的额度被后面的
分支顶上来"——用户点的是"少看一点"，画布上的节点数却一个都没少，只是换了一批（B 的孩子
突然冒出来）。固定前缀让收起**真的**变少，而"回到 40"由「收起到上限」一条路负责。

**② 加法只放直接子节点。** 角标写的是 `+3`，点下去就该冒 3 个。把整支放出来会让角标上
的数与画面不一致（上一版反复强调过的那条："这个数第二次就没人信"）。再深的地方照旧带
它自己的角标，用户一层一层决定。

**③ 减法按整棵子树剪。** 收起一个节点 = "这一支我这一屏不看"。只藏它的直接子节点，
孙辈仍在画布上就是**孤儿**（父链断了），布局会把它们画成一片浮空的方块。

**④ 不压缩层号。** 收起第 3 层不会让第 4 层升到第 3 层——层号是内容属性（`depth` 还决定
配色继承与详情面板的面包屑），视图层不许改它。

**只作用于树型。** 鱼骨与流程的画布树是合成出来的（虚拟根 + 每个容器一个子）：数量口径
要数内容里真实的节点，而合成根不在内容里，数出来的上限会凭空虚高一个。

**生成中的预览不收起。** 预览走的是 `agentPreview` 那条分支，根本不经过 `viewTree`
（见 `stores/mindmap.ts::renderSource` 两个出口）。数量口径下这条**结构上仍然成立**，
不需要任何特判：节点一个一个长出来的画布与加收起之前逐像素相同，`done` 落地之后才第一次
按上限收。

### 布局吃不吃得下"不规整的子树"？

层数口径收出来的形状是规整的（"前 N 层"），数量口径收出来的形状**极不规整**：
同一层里有父节点挂着 3 个孩子、紧挨着的父节点一个孩子都没有，还可能出现"父节点只剩一个
孩子、那孩子却有 10 个孩子"。`layoutTidy` 是 Reingold–Tilford 的固定尺寸变体，
它只要求输入是一棵**连通的、根可达的树**（不变量 ④），对形状没有任何假设——兄弟方向按
子树占位递归切分，父节点落在子节点区间的中点，任何形状都不会重叠。

实测三种病态形状（`right` / `down` / `both` 三个朝向各验一遍）：

| 形状 | 节点 | 外接框 | 严格重叠 |
| --- | --- | --- | --- |
| 寡妇 + 爆炸（父 1 孩子 → 那孩子 10 个孩子） | 13 | 888×660 | **0 对** |
| 梳子（20 层单链） | 20 | 4664×48 | **0 对** |
| 偏斜（第一支吃到第 5 层，其余各 1 个孩子） | 15 | 1124×388 | **0 对** |
| 真树 136 截断到 40 | 40 | 888×1884 | **0 对** |
| 真树 136 截断到 40，再点开一处 | 43 | — | **0 对** |

代价只有一个，不是重叠而是**长**：梳子形状在 `right` 下是 4664px 宽的一条，`fit-all`
字号 4px。那是"内容本身是一条链"的必然结果，与收起无关（不收起也是 4664px）。

## 四、交互：点节点 / 角标 / 两个出口

### 点节点本身会发生什么

单击一个节点，先做**既有的事**，再按它此刻的状态决定要不要改可见性：

```
选中（右侧详情区块换成它、工具条浮出来）   ← 与以前完全一样
+
这个节点还有孩子没显示  → 放出来（= 点它头上的 +N）
这个节点的孩子是用户点开的 / 全部展开给的 → 收回去
其余（叶子，或"孩子靠预算显示着"）        → 什么都不做，只选中
```

判据只有一处：`view-collapse.ts::foldActionOf`，渲染层给不给「−」角标走的也是它——
两处各判一次就会分家（角标说能收起、点节点却只选中），而那种不一致用户一眼就能看见。

**为什么"点节点 = 开合"不会让看详情变难。** 详情不需要独占这一下：

1. 单击照旧 `select`：右侧「节点详情」区块、工具条、面包屑全部照旧。
2. **叶子节点上点击没有任何附加动作**——读正文这条最常用的路径，画布一个像素都不动。
3. 只有"这里还有没显示的"或"这里是我自己摊开的"两种状态，点击才改可见性。那两种状态下
   用户点它，本来就只有一个意思："我要看这一支 / 我不要看这一支"。
4. 双击仍然是**改名**（既有能力，`beginEdit`），没有被"双击开详情"占用——这条是刻意的：
   用双击去补详情，等于让改名退到一个更隐蔽的位置。
5. Ctrl / Cmd / Shift 点（圈选区）**不改可见性**：圈着圈着让整张图重排是灾难。

### 两枚角标

| 角标 | 什么时候在 | 常驻吗 | 点了 |
| --- | --- | --- | --- |
| `+N` | 这个节点还有 N 个子节点没画出来 | **常驻**（不 hover 也在） | 展开（`toggleFold`） |
| `−` | 这个节点的子节点正显示着 | 用户自己摊开的**常驻**；预算给的随 hover / 聚焦 / 选中出现 | 收起（`collapse`） |

`+N` 必须常驻，理由见 §六：数量口径下"哪儿被截了"只由它标出来。
`−` 不必常驻：画布上到处挂减号太吵，而"收回"是一个**明确的、要动手的**意图。

`+N` 的数字是**没画出来的直接子节点数**（不是整支、不是总数），点一下当场冒这么多；
整支的规模在 `title` 与 `aria-label` 里（"这一支还有 17 个节点没画"）。

### 两个出口

```
顶部（有截断时常驻）：显示 40 / 136 个节点  [全部展开] [收起到上限]
顶部（全展开后）    ：显示全部 136 个节点              [收起到上限]
```

「全部展开」是逃生舱，也是"这棵树到底有多大"的唯一诚实答案；「收起到上限」是**一次到位
的回程**——没有它，「全部展开」就是一次性的破坏（字小到看不清，还得一个个点回去）。
「收起到上限」只在"有手动状态"时出现（展开过 / 收起过 / 全部展开过），因为默认状态本来
就在上限上，摆一个点了没反应的按钮只会让人以为坏了。

## 五、与 undo / 拖拽 / 保存导出的交互

**① 收起/展开不进撤销栈，也不置脏。** 它是视图状态，存在 store 的四个 `ref` 里
（`visibleNodeLimit` / `viewExpandedNodes` / `viewCollapsedNodes` / `viewExpandAll`），
不碰 `content`。`undoDepth` 不变、`dirty` 不变、`clientRevision` 不变。Ctrl+Z 撤的永远
是内容——用内容撤销去退视图，用户会发现"撤销一步"把他刚改的字也吃了。

**② 被藏起来的节点被 undo 恢复时：按当前口径重新算，不特判。** 视图的规则是"预算 + 闸门"，
不是"这次操作"。撤销一次删除之后如果恢复出来的那几支仍在截断之外，画的仍然是 `+N`
——但**角标上的数字会变**（`hiddenChildren` / `hiddenSubtree` 都是 computed）。

**③ "选中即可见"是硬不变式。** 选中 / 开始编辑 / 新增节点 / 从引用列表跳转，都会先把
目标节点的祖先链放进 `viewExpandedNodes`（`revealInView`）。判据从"层号 ≤ N"换成了
**"它在不在画布上"**（数量口径下没有可算的边界，唯一可靠的问法是问画布）。缺少这条，
会出现"详情面板正在说一个画布上看不见的节点"，以及"按 Tab 加了子节点、画面毫无变化"。

**④ 拖拽：这个仓库里没有。** `<VueFlow>` 写死 `nodes-draggable="false"`，`store.nodes`
里 `draggable: false`；`Node.pos` 在渲染层没有任何读者。坐标只有一个来源：`layoutDiagram`。
所以展开/收起后整棵树重排是**必然且正确**的（布局是纯计算的，没有"用户记住的位置"可保）。

**⑤ 保存 / 导出 / 导入：收起状态不落盘，也不该落盘。** 四条理由与上一版相同（`Node.collapsed`
已经有主：导入文件用它表达"源文件里这个节点是收起的"；写 `content` 会让视图动作变成内容
改动；`diffEdits` 的 `EditField` 里没有它；上限依赖"这个人一次想看几个节点"，与哪棵树无关）。
代价也一样：**刷新页面 / 换一张图，手动点开的那几支会回到上限以内。**

## 七、自评：这个口径会不会制造"看着完整其实缺了一大块"？

**会，而且比层数口径更容易。** 这是这一轮必须自己说清的一件事。

层数口径的截断边界是**一整层**：第 2 层以下全无，视觉上齐刷刷断在一行，用户能读出
"边界在层上"。数量口径的边界是**一串具体的父节点**，散在同一层内，而且**不均匀**：

- 靠前的一级分支拿到了更深的孩子（看起来"讲到了第 3 层"）；
- 靠后的分支在更浅处就断了（看起来"这一支只有 2 层"）。

用户扫一眼画布，最容易得出的错误结论正是："前面那几支讲得细，后面那几支讲得浅。"
而真相是预算在中间用完了。**这是按层铺满（§二）的代价，我选它是因为另一种代价更贵**
（前序会让 6 支里 4 支一个节点都没有）。

我做到的，与做不到的，分开说：

**做到了——"不 hover、不点"就能看见"这里被截了"：**

1. `+N` 角标**常驻**，且每枚都挂在**真正被截断的那个父节点**上。19 枚角标就是 19 处
   截断点，一枚不多一枚不少（用例按 `hiddenChildren > 0` 逐个对齐）。
2. 数量口径下所有截断点**在同一层**（BFS 的性质），所以那 19 枚角标在画布上排成**同一
   高度的一串加号**——读起来像"这一排都还有下文"，而不是"某一处有个孤零零的数字"。
3. 顶部常驻 `显示 40 / 136 个节点`：**比例**是当场可见的。只给 40 会以为树小，只给 136
   会找不到那 96 个。

**没做到——"这一支讲完了没有"仍然读不出来。** 一枚 `+3` 只能证明"这里还有 3 个直接
孩子"，它证明不了"这一支一共还有 21 个、还有两层"。整支的规模我写进了 `title` 与
`aria-label`——但那要 hover / 读屏才拿得到，恰好落在"不许 hover 才能看出被截"这条要求
之外。

所以我的判断是：**常驻层面只做到了"看得出这里有截断"，做不到"看得出这一支讲没讲完"。**
要把后者补上，下一轮该做的不是给每个父节点再加一行字（那会把画布糊满），而是**在一级
分支上挂一枚"这一支还有 N 个节点"的常驻角标**：一级分支只有 6 个、位置固定、语义干净，
而"这一支一共讲了多少"恰好是用户判断"要不要展开"的唯一依据。这个口径下的角标是
"按支统计"的，与父节点上的"按层截断"角标**是两种东西，可以并存**（一个说"这一支的
规模"，一个说"这一处断了"）。这一轮不做，理由只有一个：它需要一句概括/统计的文案
（`docs/FOLD-RETIRED.md` §5 记过一条批量概括调用的实测：1.87 秒 / 5 组），而这一轮的
承诺是"不新增调用"。

## 八、代码地图与回滚

| 位置 | 干什么 |
| --- | --- |
| `frontend/src/canvas/view-collapse.ts` | 纯函数：`viewTree()`（预算前缀 + 三道闸门）、`foldActionOf()`（点一下会发生什么）、`MINDMAP_VISIBLE_NODE_LIMIT` / `NO_NODE_LIMIT`、`countSubtree` / `depthOf` |
| `frontend/src/stores/mindmap.ts` | `renderSource` 里套 `viewTree`（**唯一入口**：`layout`、`flatNodes`、`nodes` 都吃它的输出）；四个视图 ref；`expandNodeInView` / `collapseNodeInView` / `toggleFoldInView` / `expandAllInView` / `collapseViewToCap` / `revealInView` / `resetViewCollapse` |
| `frontend/src/canvas/MindMapCanvas.vue` | `onNodeClick` 里接上 `toggleFoldInView`；`toggleFold` / `collapseFold` 两个角标入口；顶部「显示 N / M」+ 两个出口 |
| `frontend/src/canvas/MindNode.vue` | `+N`（`data-test="node-folded"`，常驻）与 `−`（`data-test="node-collapse"`，用户展开的常驻、其余 hover 显形） |

收起必须发生在 `renderSource` 而不是渲染组件里：`nodes` 与 `edges` 都从 `layout` 读坐标，
而 `layout` 吃 `source.root`。只过滤 `flatNodes` 的话，被截断的节点仍然参与 `layoutTidy`
的占位——它们照样撑开画布、照样把字号挤到 5px，只是看不见。

**回滚路径**：`store.visibleNodeLimit = 0`（或 `NO_NODE_LIMIT`）就是"不限制"，
等价于加收起之前的行为——一个节点都不藏。两种到达方式：把 `MINDMAP_VISIBLE_NODE_LIMIT`
改成 `0`（出厂即关闭），或在运行期把 `store.visibleNodeLimit` 设成 `0`。

## 九、已知边界（不要当成 bug 修）

- **40 个节点在 1600×852 上仍然过不了 `fit-all` 的 12px**（§一）。要一屏读全得把上限压到
  17 上下——那是另一个取舍（认知预算 vs 一屏看尽），这一轮选了前者。
- **一个根挂 50 支**（库里那棵 561 节点的探针树）：上限 40 只画得出根 + 39 支，
  剩下 11 支各带一枚 `+N`。真正的解法是分组标题（§七），不是把上限调大。
- **鱼骨 / 流程图不收起**：它们的节点本来就少，而合成树让"数量"这个概念在两种形状下不通用。
- **收起没有持久化位**：刷新 / 换图回到上限以内（§五 ⑤）。
- **点节点展开会重排整张图**：布局是纯计算的，坐标只有一个来源。`applyView` 带 250ms
  动画，但节点会从鼠标底下移开——这是"点节点就展开"的代价，换来的是"不用去找那枚角标"。
