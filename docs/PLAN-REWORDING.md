## 先说三处复核结论（与核对报告的差异）

这三处不影响核对报告的结论，但影响"替换句能不能直接贴"。抄进申报书之前必须先修。

**① 分档统计与实际逐条数不一致：B 是 13 项，不是 14 项；D 是 2 项，不是 1 项。**

`PLAN-VS-IMPLEMENTATION.md:43` 写「A 3 / B 14 / C 4 / D 1」，但按总表判定列逐条数：

| 判定 | 条目 | 条数 |
|---|---|---|
| A | P1、P2、P13 | 3 |
| B | P3、P4、P5、P6、P7、P8、P11、P12、P14、P15、P18、P19、P20 | 13 |
| C | P9、P10、P17、P22 | 4 |
| D | **P16**、**P21** | 2 |

3 + 13 + 4 + 2 = 22，闭合。`P16`（6.1 后端技术栈原文空白）与 `P21`（6.4 三条指标）在总表里都判 D，统计行少算了一个。这是"抄表时把 D 当成只有 P21"，不是判定错误。

→ 本文第二节按 **13 项** 逐条判，不按 14 项凑数。

**② 第四节给的向量库替换句有一处数字错位，必须修。**

原替换句写「在 **3652 节点规模下实测**单次检索 9.5–21.6 ms」。核过原始出处：`9.5–21.6 ms` 是 **1000×1024** 微基准（`OPTIMIZATION-CROSS-MAP.md:99`），全库 3652 节点那一档是 **15–60 ms**（`:102`），矩阵乘 3652×40 查询约 **15 ms**（`:141`）。把 1000 条的数字安到 3652 条规模上，评审只要点开复现脚本就对不上。✓ 已在第一节第三处改掉。

另外原句里的「复评门槛（历史节点 ≥50 万 / 单次查询 ≥500 节点 / 并发 ≥10 QPS）」，仓库里能溯源到的是**只有第一条**（`OPTIMIZATION-CROSS-MAP.md:260`：历史节点总数 ≥ 50 万，约 8000 张 60 节点的图）。后两条找不到出处，已删——**申报书里的门槛数字必须是能对上的**，多写两条等于多两个被问的点。

**③ 核对报告 5.2 建议的"首张可见节点 < 10 秒"是一条新的不可达指标，不能采用。**

建议表写「首张可见节点（`node_grow`）< 10 秒　需补测」。但 `LATENCY-BREAKDOWN.md:31` 实测「骨架 + 证据 + 结构（到第一个 `node_grow`）= **41.5 秒**」。首帧 0.1 秒之所以成立，是因为那一帧只是"已受理、进入生成"的状态提示；**第一个内容节点要比它晚 41 秒**。"<10 秒"会把一条不可达指标换成另一条，验收时同样对不上。

→ 替换句按 **首帧 / 首个节点 / 完整导图** 三段报实测值，首个节点一栏留占位、由实测填，**不预设阈值**。第三节给了可直接用的表述。

## 一、必须改的五处

### 第一处 【6.2-4，段 089】生成时间 < 3 秒

**原文**

> 压力测试优化系统响应速度（如生成思维导图时间 < 3 秒）。

**替换句（可直接贴）**

> 压力测试与性能度量：以流式传输为前提，生成延迟分三段度量并分别报 P50 / P95——首帧（服务端开始回传、界面进入"正在生成"）、首个节点（树根与一级分支落地）、完整导图（全部节点与说明落地），每段注明所用模型、并发数与节点规模。三段实测值见 6.4。

**为什么这么改**

不是"3 秒太严所以放宽"，是**原句的度量对象写错了**。"生成思维导图时间"在一句话里同时指三件时间尺度完全不同的事：界面有反应、第一支长出来、整棵树长完。生成类任务（大模型对话、长文档处理、报表导出）的行业标准做法是**把首帧延迟与完整延迟分开报**，因为两者衡量的是两种体验：前者是"系统是否在工作"，后者是"我要等多久才能用"。

用非技术评审能接住的比方：打印 200 页的标书，用户先关心"第一页什么时候出来、机器是不是卡住了"，再关心"全部打完要几分钟"。只报"全部打完 3 秒"是假承诺，只报"第一页 0.1 秒"是藏话——两个都报才是完整交代。

而且原口径**自身就矛盾**：同一件事在 6.2-4 写 3 秒、在 6.4 写 5 秒（复杂场景）。评审读到这里会先问"到底几秒"，改完这个矛盾自动消失。

**★ 第三处重复，别漏**（用户只提了两处，原文实测是三处）：

段 113（第四阶段 2026-07~10 系统测试）里的原句：

> 性能测试，确保系统响应时间满足预期（如生成思维导图时间 < 3 秒），并进行压力测试优化；

替换句：

> 性能测试，按 6.4 的三段口径度量并记录（首帧 / 首个节点 / 完整导图，各报 P50 / P95），与上一轮基线对比；压力测试，验证 1–3 路并发下的请求成功率与最长静默间隔（实测 3 路并发最长静默 25.1 秒，据此补了生成期心跳帧）✓ `FEATURES_AND_OWNERS.md:39`。

只改 6.2-4 与 6.4 而不改段 113，等于在同一份申报书里留了一个旧口径的对照物——验收方逐条对表时一定会撞到它。

### 第二处 【6.4，段 101】响应时间 < 5 秒

**原文**

> 系统响应时间 < 5 秒（复杂场景）。

**替换句（可直接贴，占位处填实测）**

> 系统响应时间分三段度量，各报 P50 / P95：首帧 < 1 秒（实测 P50 ______ 秒）；首个节点落地 ______ 秒（实测，随材料规模与外部检索冷热变化）；完整导图 P50 ______ 秒 / P95 ______ 秒（节点 ≤ ______，模型 ______，并发 ______ 路）。
>
> 不承诺"整张图在固定秒数内完成"这一绝对值。单次生成含 3–4 次模型往返，实测总耗时与节点数近似线性（≈ 节点数 × 0.35 秒，三组开关下 0.354–0.379 高度一致 ✓ `LATENCY-BREAKDOWN.md:45-53`），该系数由所用模型的输出速度决定，不由本系统决定；本系统的优化落在减少往返次数、分半并发与流式呈现上，这些已计入上表。

**三个占位分别是什么**（供实测填数，也供答辩时解释）

| 占位 | 定义 | 怎么测 | 现有可引用的数 |
|---|---|---|---|
| 首帧 | 客户端收到第一条 SSE 帧（界面可显示"正在检索/正在生成"） | 浏览器 Network 面板取 TTFB 到首帧，或服务端埋点 `run_start` | P50 0.1 秒（线上 1/2/3 路并发各 7 次）✓ `FEATURES_AND_OWNERS.md:39` |
| 首个节点 | 首个 `node_grow` 帧（树根与一级分支落地，用户第一次看见内容） | SSE 帧时间线，从请求发出算到首个 `node_grow` | 端到端实测 41.5 秒（含冷启动外部检索 14.8 秒）✓ `LATENCY-BREAKDOWN.md:31` |
| 完整导图 | 全部节点与说明落地、`done` 帧 | 同上，到 `done` | 工具级 41.0 / 72.6 秒；端到端 139.5 秒；线上压测 P50 76.5 秒 ✓ |

三个数**必须分档报**，不能只报第一个。只报"首帧 0.1 秒"是用真数字讲假故事——见第五节自评。

**为什么这么改**

首帧能承诺 < 1 秒，因为它衡量的是"系统接住了请求并开始工作"，这条路已经做到 0.1 秒；完整导图的耗时主要是模型输出量（一次 3–4 次往返、每节点约 0.35 秒），这部分随节点数增长，属于可测量、可优化、但不能给出固定上限的量。**把可承诺的与不可承诺的分开，是收紧口径，不是放宽**：原来一句"<5 秒"既不可测也不可交付；改后三段都可测、有 P50/P95、有样本量与并发数。

### 第五处 【6.1，段 076】前端技术栈 + PUML 渲染

**原文**

> 1、前端：前端使用React构建用户界面提供组件化开发模式，使用Zustand状态管理库，用于管理复杂的应用状态管理，并通过TypeScript提高代码质量，基于AI大模型的中间层实现多模态的处理，通过TailwindCSS实现流畅的交互动画和统一美观的样式布局，基于pluml-encode和viz.js 处理puml代码，以axios作为网络通信库，Zod做数据校验，确保数据的准确性和完备性。

**★ 复核意见：PUML 那半句不能单独换。** 这一句里同时有五个技术栈判断（React、Zustand、axios、Zod、pluml+viz.js），其中四个也是错的。只替换 PUML 分句，等于把 React 与 Zustand 两处留在原地——那是评审最容易问穿的地方（"你用的什么框架"一句话就破）。**替换单元必须是整段 6.1 前端。**

**替换句（整段可替换）**

> 1、前端：使用 Vue 3 构建用户界面（组合式 API + `<script setup>`），状态管理采用 Pinia，全量 TypeScript 并以 `vue-tsc` 作类型门禁，样式用 TailwindCSS v4；画布基于 `@vue-flow/core` 渲染节点与连线，节点坐标由自研 tidy-tree 算法计算（不引入通用图形布局库——单机 2C2G 上少一个依赖比省几行代码重要 ✓ `ARCHITECTURE.md:61`）；网络层用原生 `fetch` 并直接读 SSE 流；数据校验由后端 Pydantic v2 承担，前端以 OpenAPI 生成类型 + 契约校验脚本对齐，不引入运行期 schema 校验库。
>
> 2、PlantUML 采用「服务端生成 + 下载」形态：后端按图型（树 / 流程 / 鱼骨）输出 `.puml` 文本，与 Markdown / OPML / JSON 并列共四种导出格式，JSON 是唯一的无损格式（文本三格式的标题槽只有一个，节点级字段会丢 ✓ `backend/app/export/service.py:853-856`）。不在浏览器内渲染 PUML：`viz.js` 是 Graphviz 的 WASM，只接受 DOT 语法；`plantuml-encoder` 仅做 URL 压缩编码，出图依赖 PlantUML 服务端（JVM）。两者组合无法完成前端渲染。实现见 `backend/app/export/service.py`，逐字节回归用例 `tests/test_export.py::ByteIdenticalTest` ✓。

**为什么 ② 这条特别要紧**

这不是选型口味问题，是**语法层面不可能**：

- `viz.js` 是 Graphviz 编译成 WASM，输入语言是 DOT。喂它 `@startmindmap … @endmindmap`，第一行就报语法错。
- `plantuml-encoder` 做的事是把 PlantUML 源码压成一段 URL 片段（给 `plantuml-server` 用的路径参数），它本身不出图。出图那一步需要一个跑着 Java 的 PlantUML 服务端。
- 也就是说，这两个库串起来，中间缺的那个进程**恰好就是出图能力的全部**。原句等于说"用两个编码器实现一个解码器"。

仓库对此有专门记录，且把理由写在了当时 ✓ `docs/ARCHITECTURE_ADDENDUM.md:189-193`：「`plantuml-encoder` 输出的是 URL 片段…真正出图要靠 PlantUML 服务端（JVM）；`viz.js` 是 Graphviz 的 WASM，只认 DOT 语言，解析不了 PlantUML 语法。」

**申报书里写一个语法上不可能的方案，是评审最容易当场击穿的一类**——不需要跑代码，懂的人看一眼库名就知道。替换句主动写出"为什么不可能"，反而成了一个能讲清技术判断力的点。

**顺带**：`pluml-encode` 是原文的拼写错误（应为 `plantuml-encoder`），替换句已改正；这一个字母的错在评审眼里等于"没真用过"。

### 需要改的 8 项：原句 → 替换句

#### P6 【3.2.2，段 040-041】

**原文**

> AI根据内容主题自动设计导图布局（如树状图、流程图、鱼骨图），并适配颜色、图标等视觉元素。
> 研究用户偏好学习，实现个性化风格推荐。

**替换句**

> AI 根据内容主题选择图型并计算布局：树状（四种朝向）、流程（分层有向，判定节点按形状加宽）、鱼骨（六类成因斜插主骨，头部在右为几何定死）；节点按一级分支自动配色，图标按语义类别归一化生成，颜色与图标均可逐个修改（引核对 P6）。
> 风格偏好以「显式偏好 + 一致性统计」实现：用户改过的 8 项结构参数（分支数、层深、节点密度等）构成风格画像，在生成时作为排序权重与提示词偏好参与，不改变用户已确认的内容。基于模型训练的偏好学习不在本期范围。

**为什么**：原文"研究用户偏好学习，实现个性化风格推荐"读起来是"训练了一个偏好模型"，实际是显式写入 + "近三次一致才提一条建议"的规则。另外"适配颜色、图标**等**视觉元素"里那个"等"字，把所有没渲染的视觉项（主题预设、字体、主色在契约里有、界面无 ✓ 引核对 P6）都兜进去了——**把"等"删掉，只留颜色与图标，这句话就如实了**。

#### P7 【3.3.1，段 044-045】

**原文**

> 连接行业数据库（如学术论文、百科）、企业文档或用户个人知识库，自动填充或验证节点内容。
> 示例：用户输入"碳中和"，AI自动关联政策、技术路径、企业案例等分支。

**替换句**

> 接入公开学术与百科来源（中文维基、arXiv、OpenAlex、Crossref、快百科五源）与用户个人知识库（材料入库后保留 90 天、最多 200 份）；生成时按分支检索，命中内容作为节点正文的依据，节点可点击回到原文位置（引核对 P7）。
> 示例：用户输入"碳中和"，系统按政策、技术路径、企业案例方向检索公开材料，命中则落为对应分支的节点并附引用。

**为什么**：把"验证"拆成"引文逐字命中"+"不含事实判定"两句，是这一条唯一的活路。评审问"怎么保证内容对"时，主动划界比被抓出来强得多。原文的"碳中和→政策/技术路径/企业案例"例子本身靠外部检索命中，能演示但不可控——替换句加"命中则"三个字，把必然变成条件。

#### P8 【3.3.2，段 047】

**原文**

> AI识别思维导图中的逻辑矛盾、冗余节点或缺失环节，提出优化建议（如"分支A与分支B存在因果关系，建议添加连接线"）。

**替换句**

> AI 对导图做结构体检并给出建议，覆盖五类问题：单子节点、层级过深、同级重复标签、节点论断与所引原文相悖、材料中有据可查的缺失环节；建议以面板列出，附诊断原码与理由，用户逐条决定是否采纳，不自动修改画布。体检对树状图生效，流程与鱼骨图暂不支持（引核对 P8）。
> 跨分支语义关系（因果 / 引用 / 冲突四类）的数据结构已在契约中具备并可在导出中保留，界面呈现与"建议添加连接线"这类跨节点建议不在本期范围。

**为什么**：括号里那个例子是全句**唯一具体可验证的承诺**，而它做不到（`relations` 界面不渲染，用户看不到那条线，也没法删）。换成五类真做得到的检查，把做不到的降级为"契约具备、界面未做"。这一条改完，B 档里最脆的一处就补上了。

#### P12 【5.2，段 067】

**原文（两句，都在承诺"自动改"）**

> 利用 AI 持续分析用户使用习惯和思维导图结构，实时调整节点关系与布局。
> 当用户在思维导图中添加新节点时，系统能智能判断其与已有节点的逻辑联系，自动优化层级结构，使思维导图始终保持清晰、合理。

**替换句（两句都要换）**

> 系统持续分析用户的使用习惯与导图结构：使用习惯沉淀为风格画像（结构参数中位数），导图结构由结构体检主动诊断；两者共同作用于**后续生成**的参数与提示词，不改动已保存导图的结构。
> 当用户新增节点时，系统给出「该挂在哪」的位置建议：候选父节点、同类节点在历史导图中的常见位置、以及材料中与该节点相关的段落命中；建议由用户确认后应用，不自动改动已确认的结构。判断依据是父子层级位置与材料相关性，不含跨节点的因果、引用、冲突推断。

**为什么**：原文两句都在承诺自动修改，**第一句比第二句更激进**——"实时调整节点关系与布局"是无须用户动作的行为级承诺，答辩时会被问"你什么时候自动改了我的图、我怎么知道、能撤回吗"。实际设计里"检查结果永不自动应用"是**刻意的决定**（`optimization/service.py:9-18`，引核对 P12）。两句一起换，改完反而显出设计判断：不自动改动用户已确认的内容，是有理由的产品选择，不是没做。

#### P14 【5.3，段 071】

**原文（节选，原段后半为"…将无序信息转化为层次清晰、内容完整的思维导图，解决传统手动整理耗时长、易疏漏的痛点"）**

## 五、自评：改措辞与如实申报的线在哪

**先给判断：一份申报书写"响应时间 < 5 秒"而实测 41 秒，改口径本身不是粉饰——因为那句话的错不在数字，在度量对象。但如果改完之后读者仍然以为"整图 5 秒"，那就是粉饰。区别不在动词（改/不改），在改完之后还能不能被同一个实验证伪。**

给三条可操作的标准，按重要性排：

1. **替换句是否仍然带着可测的量。** 保留数字、分位数、样本量、并发数 = 如实；把这些换成形容词（"快速""实时""流畅"）= 粉饰。我的替换句里每个"<"后面都跟着一个占位或一个实测值，就是为这条。
2. **替换句是把"做不到"改成"我不承诺"，还是把"做不到"改成"做到了"。** 前者是收紧口径（"整图 N 秒"→"三段分报，不承诺绝对值"），后者是造假。这条线在语言上很细：**"不承诺整图固定秒数"可，"响应时间 < 5 秒（首帧）"不可**——后半句把限定词塞进括号，主句看上去还是原来那个承诺。
3. **替换句有没有自己交出证伪路径。** 给出复现脚本、复跑清单、"这一项未验证"的字样 = 如实。反过来，用"可选""后续""规划中"这类词把可检验的动作挡在句子外面 = 粉饰。

**"响应时间 < 5 秒 vs 实测 41 秒"这一条，按上面三条过一遍：**

- 原句错在两处：**度量对象错**（"系统响应时间"被用来指"整图完成时间"，这两个在工程上不是同一个量）和**数值乐观**（41 秒 vs 5 秒）。只要改的是第一处，就是纠错；把第二处也一起"改掉"（不报 41 秒），就是粉饰。
- 所以我给 6.4 的替换句里，**三段占位是并列的，一个都不能省**。如果只填首帧 0.1 秒、把完整导图那栏留空或删掉，那份申报书就变成了"用真数字讲假故事"——每一个数字都是真的，合起来是误导。这是我在这一条上最在意的事。
- 结论：**改口径算不算粉饰，取决于完整耗时那一栏在不在。写着 41 秒，就是如实；只写 0.1 秒，就是粉饰。**

**我给的替换句里，哪一句最接近粉饰、哪一句最接近如实：**

- **最接近如实：PUML 那句。** 它把原方案为什么不可能（`viz.js` 只认 DOT、`plantuml-encoder` 出图要 JVM）写在申报书里，等于把计划书的错公开存档，还给了可复跑的用例路径（`ByteIdenticalTest`）。它没有隐藏任何东西，反而主动暴露了自己的前身是错的。一份申报材料里出现这种句子，通常意味着作者真的动过手。

- **最接近粉饰：P19 容器化那句的"另提供可选的单机容器化方案"。「可选」这个词在这句里承担了遮蔽功能**——"可选"是真的（不接管 CD、生产走 systemd），"文件齐全"也是真的，但两个真话并排放，读起来就是"这东西能起"。而事实是从来没在真机上构建过。我必须承认：如果不写"尚未在真机完成一次完整构建与运行验证"那半句，这一句就是标准粉饰——用两个真陈述合成一个假印象，比直接说假话更难被抓住。所以替换句里那半句**是这句的承重墙，删不得**。这也说明一件事：粉饰往往不靠编造，靠省略。

- **另有一个我主动弃用的粉饰方案**：方案乙把"账号体系 + 编辑账本"拼成"协作的雏形"。那是用一个比喻把不存在的能力造出来——三个人各做各的事、数据层连"是哪个用户改的"都记不住（`actor` 只有 `user`/`agent`），这不叫雏形，叫"两件不相干的东西放在一起"。我判它不成立，不是因为它不划算，是因为它过不了第三条标准：那句"协作雏形"交不出任何能证伪它的实验——你没法设计一个实验去测"这是不是协作的雏形"。**一个不能被证伪的能力描述，就是粉饰的定义。**
