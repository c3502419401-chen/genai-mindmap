# 生成链路的边界与流式：一轮修复记录

> 记录 2026-11-07 这一轮针对「上传材料生成导图」这条链路的排查与修复。
> 所有数字都来自真机实测，测试结论取自 `python -m pytest` 与 `npm run test`。

## 一句话结论

这一轮修掉的问题里，绝大多数是同一个病：**同一个边界在两个地方各写了一份，改一处另一处不动，而且两边都不报错**。它们不是逻辑写错，而是"没有单一事实来源"。

## 起点：三个现象

用户上传一份 15 页英文论文（解析出 38036 字符），点「合并生成导图」之后：

1. 面板上只有一行红色的「未成功」，**没有任何地方说明为什么失败**；
2. 生成出来的树只有 3~4 级，而契约写着允许 8 层；
3. 节点生长只在右侧面板的一列缩进文字里，**画布上看不到**，得等生成结束再点「应用」才见得到整张图。

第 2、3 条背后还有一条没人报的现象：**带材料的生成一帧生长事件都没发过**。

## 逐项

### 一、材料被砍掉三分之二

`backend/app/agent/tools.py` 里留着 `MAX_SOURCE_CHARS = 12000`。38036 字的材料只有 31% 喂给了模型，剩下两万六千字模型根本没看见——但它仍然会为"整篇论文"写结论。

`generation` 层早就改成按 token 预算判断（`CONTEXT_TOKEN_LIMIT = 200000` + `estimate_input_tokens`），agent 工具层还守着一份字符闸。同一个概念两处各有一份，改一处另一处不会跟着动。

**修法**：预算内完整发送；超预算时按 token 预算二分找最长前缀（中英文 token 密度差四倍，同一个字符闸对两种文本松紧完全不同）。预算把系统提示词、JSON 转义开销和截断提示一起算进去。

「原文过长，已截断」的提示必须保留——模型看到半份材料却以为是全文时，会为被裁掉的结尾写引用，而那些引用在原文里匹配不上，要到校验阶段才炸，那时调用额度已经花完了。

校验引文用的 `sources` 保留完整原文，只有提示词里的副本可以裁。这个不对称是有意的：`quote` 必须逐字核对。

**实测**（同一份论文）：修复前 57 节点；修复后 98 节点、6 个一级分支，68 条引用里 45 条落在原截断点之后。

### 二、失败不留痕

三个问题叠在一起：

- `agent/service.py` 里**一行 logger 都没有**；
- `tool_end` 事件的 `ok=false` 时，面板只显示「{工具名} 未成功」，`result_summary` 里的 `code`/`message` 从不渲染；
- HTTP 日志只有一条 `POST /api/agent/runs/stream 200`——SSE 流建立成功了，失败发生在流内部。

结果是失败无法解释，只能靠复现去猜。

**修法**：后端补齐工具失败、工具超时、预算耗尽（模型调用 / 工具调用 / 墙钟三种）、上游异常、意外结束、失败次数超限的日志，带 `call_id`、工具名、`code`、`message` 与已用调用次数；只记 500 字以内的摘要，**不记**工具参数、`result.data` 和异常堆栈（它们可能夹带整份正文或整棵树）。前端在失败行下面显示 `code：message`，缺字段时回退成一句话，不渲染 `undefined`。

这条修复立刻自证了价值：后面放开深度时撞上 `OpBatch` 的 100 条上限，日志直接把 `ValidationError` 和实际条数打了出来。

### 三、深度被三处压到两级

带材料的新建走 `_generate()` → `SOURCED_DETAIL_PROMPT`，**一次调用生成整棵树，没有递归**。压深度的有三句话，一处比一处隐蔽：

| 位置 | 原文 | 后果 |
|---|---|---|
| `DETAIL_PROMPT` | 「每个可分解的分支至少 2 个要点，**目标 2-4 个**」 | 把要点写成终点 |
| `DETAIL_PROMPT` | 「每个分支**再给 2-4 个要点**」 | 直接把结构定义成根 → 分支 → 要点 |
| `THINKING_MODELS["default"]` 第 3 步 | 「一般 **2-4 层**」 | 默认思考模型必然拼进 system，等于另一处又给了一个层数区间 |

`层级不超过 8` 只是一句上限，没有任何一句在要求模型往下走，所以上限一次都没被碰到。

**修法**：把"拆到哪一层"从数字换成判据。

- 上限明确写成「可读性上限，不是要拆到的目标」，数字仍取自契约常量。
- 停止条件只有两种可判定的情况：最小可执行单元（能直接照着做），或单一概念（再拆只是换个说法重复自己）。
- 给「单一概念」一条判据：能不能分成两个并列的成分。模块、流程、表格、公式有组成和参数，不算单一概念——不定义的话模型会把「多头注意力」这种词当叶子。
- 加一句「思考方式里的步骤只决定按什么角度拆，不决定拆到哪一层」。五套思维模型里都有「每支配一个类比」，不切开会被读成「这一支写完了」。
- 四行 ❌/✅ 形态对照，例子**刻意不含任何领域内容**——写进具体事实，无来源时会被当材料抄，有来源时又不在原文里，两边都会长出凭空多出来的节点。
- 有来源时判据换成材料：原文还有更具体的表述支撑就再拆，没有就停。并点明「原文自己的分层就是依据」——标题、编号、列表项、表格的行、公式的每一步，这比让模型判断「哪句更像细节」稳定得多。

**实测**（同一份论文）：

| 版本 | 深度（含中心主题） | 节点 | 一级分支 | 每层分布 |
|---|---|---|---|---|
| 改前 | 4 | 103 | 8 | 1/8/23/71 |
| 改后 | 5 | 117~140 | 6~11 | 1/11/44/51/10、1/6/25/79/29 |

连续五次运行全部 5 层，没有一次退回 4 层。依据没松：逐节点把 label 里的数字串回原文检索，改前改后都是 0 处找不到；无引用节点从 1/103 变成 42/140，多出来的全是「结果（6）」「优化器（5.3）」这类组织性标题层，不是事实断言。

### 四、流式挂错了路径

`node_grow` 帧只在 `_generate_deep` → `ask_model` → `_GrowStream` 这条路上上报。而 `build_registry()` 在 `has_sources=True` 时会 `discard("mindmap_generate_deep")`（deep 不读材料，会产出一棵与材料无关的树还以 `ok=true` 返回，移除它是对的）。

于是流式只存在于一条「不传材料、只给主题」的路径上，**真正在用的那条完全不流式**。`_generate` 的三处 `chat_async` 一个都没传 `on_delta`。

两条路的增量提取还不能共用：deep 的响应是 `{"children":[{"label","expandable"}]}`，没有 id、位置靠调用方给的 slot 路径；`mindmap_generate` 输出完整树、自带 id。后者复用普通生成早已写好的 `parse_partial`（补括号把半截 JSON 变成可解析）与 `collect_new_nodes`（按 id 挑出真写完的节点、保序），另写一层 `id → 索引链` 的换算。

`expandable` 一律传 `null`：整树提取器补出来的空 `children` 是解析中间态，不是模型在说「这支到底了」，不能当 `false` 用。

**实测**：`node_grow` 106 帧、首帧 2.5 秒、`tool_end` 在 25.7 秒——提前 23 秒开始上屏。

### 五、画布不渲染预览

`agentPreview` 只被 `AgentPanel` 消费成一个缩进列表（最多 24 行）；画布的 `store.nodes` / `store.edges` 只从 `content.root` 算，预览根本没进布局。

**修法**：给画布加一层渲染源，三级优先级：

1. `content`（已应用的图）——最优先，用户已经打开的图不能被顶掉。
2. `candidate`（整树校验通过的完整候选）——`content` 为空时用它。
3. `agentPreview`（生长中的预览）——前两者都没有时用它。

第二级是必须的：`snapshot` 到达时预览会被清空（这是对的，不能在快照之后还挂着没校验的树），渲染源不覆盖候选的话，画布会在那一刻掉回空态占位，用户还是得点一下才看得见。

`acceptCandidate()` 一行未改——候选只进渲染源、不进 `content`。**渲染与采纳是两件事**：前者看得见，后者才写进用户的图。

预览节点没有 id，进布局前按路径派生（`preview-0-2-1`）。不用递增计数器：帧是增量到达的，计数器会随插入顺序变化，同一棵树两次渲染拿到不同 id，布局缓存和 Vue 的 key 一起抖。

可编辑性选「不可选中」（`selectable` 只对 `content` 为真、`select(id)` 只接受 `content` 里真实存在的 id）。原因不是怕麻烦：`selectedId` 会被 `runGeneration` 带进 expand 请求的 `selected_ids`，预览与候选的 id 后端根本不认识。

顺带修掉三处这次改动会引爆的隐患：

- `selectedNode` 原来只看 `flatNodes`，渲染源换成候选后可能显示一个候选节点，并给它摆出一排写 `content` 的编辑按钮。
- `deleteNode(id)` 对不在树上的 id 会走完 `applyContent`：记一步历史、`clientRevision++`、状态栏说「已删除」，实际什么都没删。
- `select(id)` 原来无条件接受画布传来的任何 id。

## 模式提炼：同一个数写两遍

| 概念 | 位置 A | 位置 B | 表现出来的后果 |
|---|---|---|---|
| 材料长度上限 | `generation` 的 token 预算 200000 | `tools.py` 的 `MAX_SOURCE_CHARS = 12000` | 三分之二材料没进模型 |
| 树深上限 | 契约 `MAX_TREE_DEPTH = 8` | `tools.py` 的 `DEEP_MAX_DEPTH = 4` | 模型想拆第 5 层时被拦，且不报错 |
| 单批操作数 | 契约 `MAX_TREE_NODES = 1000` | `OpBatch.ops` 的 `max_length = 100` | 152 个节点时抛 `ValidationError` |
| 输入字数 | 后端已删除 | 前端 `MAX_INPUT_CHARS = 20000` | 一份正常论文在界面上生成不了 |
| 深度预期 | `DETAIL_PROMPT` 的「能拆就拆」 | `THINKING_MODELS["default"]` 的「一般 2-4 层」 | 模型听具体的那个数字 |
| 流式上报点 | deep 的 `ask_model` | 主路径 `_generate`（没有） | 用户那条路一帧都不发 |

共同点：**两个值都会静默生效，谁小谁说了算，且没有任何一处会报错**。只有真机跑到边界上才暴露。

由此定下两条做法：

1. 边界只留一处定义，需要引用时直接取常量（`DEEP_MAX_DEPTH = mindmap_contract.MAX_TREE_DEPTH`）。常量改名会立刻 `AttributeError`，不会像硬写一个数那样静默用旧值。
2. 测试里也不写死数字，从常量算出来（`'字'.repeat(MAX_INPUT_CHARS - 2)`）。这次前端与后端脱节，就是因为两边各写了一个 `20000`。

## 顺手澄清的两处误判

如实记下，避免以后重复踩：

- **「放开深度会让树变深」不成立**。`max_depth` 按 root 之下算层数，旧的 4 对应树深 5 层，而实测模型自然就停在第 5 层。旧的 4 在那个主题上没有切掉任何内容。改它的理由是"两处不一致"和"换个更细的主题会被先拦住"，不是"变深了"。
- **预算从 25 涨到 80，多出来的不是深度，是宽度**。同一主题：40 次 → 159 节点 / 5 层 / 35 秒；80 次 → 295 节点 / 5 层 / 64 秒。深度由模型决定，预算决定同一层里有多少分支被展开。

## 当前边界（都是有意保留的）

| 边界 | 值 | 为什么保留 |
|---|---|---|
| 节点总数 | 1000 | 契约，画布与存储的承载上限 |
| 树深 | 8 | 契约，可读性的物理上限 |
| 单批操作 | 1000 | 与节点数对齐，保证一次提交装得下一整棵树 |
| 输出 token | 65536 | 单次调用上限，两条出口共用 |
| 单次生成时长 | 600 秒 | "卡住不动"的物理边界，不是目标值 |
| 模型调用次数 | 80 | 成本护栏。超了不等于失败：用已建好的树收尾并记诊断 |
| 上下文 token | 200000 | 实测该上限下模型仍能正确回答文末内容 |

## 遗留

- **深度到 5 层是提示词杠杆的极限**。6 条一级分支里 5 条停在第 4 层，只有「模型架构」一支到第 5 层。再往下只剩两条路——把一句话拆成数字碎片，或写死层数——都会破坏「不许造层级」和「不许写死层数」。要稳定到 6 层以上必须改调用结构（按层递归），本轮没做。
- **打开旧图后生成，画布不显示生长**。`runGeneration` 不清 `content`，所以 `content` 非空时预览与候选都不顶掉它，生长只在右侧面板可见。要改需要像 `generate()` 那样做 previous/restore，属于 `runGeneration` 的语义变更。
- **折叠还没做**。1000 节点的图摊平在画布上，可读性靠缩放。折叠做完之后，深度限制才真正可以彻底交给模型。
- **节点级 `source_refs` 没在界面上体现**，`ops` 帧前端也没消费。
