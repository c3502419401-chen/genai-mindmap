# `SuggestionKind.link` 第一版：新加的节点该挂在谁下面

> 状态：**第一版，只给建议、不自动改、还没进接口。** 产出方是
> `backend/app/optimization/link.py`，默认关（`MINDMAP_OPTIMIZATION_LINK`）。

## 一、为什么这件事排在前面

`SuggestionKind.link`（`contracts/diagnostic.py:41`）写完那天就是空位，注释写着
"补跨节点关系"，而全仓没有任何地方产出它。原因不是忘了，是**没有判据**：

```
要判"这个新节点与哪条论证线同源"，先得知道"用户把上一个新节点挂在了哪"
而 edit_events 里 add 事件一条都没有（565 条 = update 559 / style 4 / remove 2）
```

距离不在算法，在**表里缺一列**。补上 `parent_id` 之前，任何"判断逻辑联系"的算法都
是在猜——而"猜得看起来合理"正是这类功能最擅长的事。补列见
`docs/EDIT-LOG.md` 二·六。

补上之后底仍然薄：库里 `add` 零条，所以第一版拿不到"这个用户怎么挂节点"，只能靠
另外两样——**跨图历史同类节点**与**材料原文**。这两样够不够，见第四节（实测，不是
讨论）。

## 二、四样输入

| 输入 | 从哪来 | 第一次跑时的状态 |
|---|---|---|
| 新节点 label + detail | 请求里 | 有 |
| 它当前的父节点 | `parents_of(content)`（§一补的那一列同一套口径） | 有 |
| 跨图历史同类节点 | `knowledge/vector_cache` + 历史图库（`cross_map` 那套复用，不新增表） | 3652 个历史节点、1075 条已缓存 |
| 材料原文 | `library_chunks` / `chunk_vectors` | 1265 段 / 3626 条向量 |

后两样都是**可空**的：取不到就少一条依据，不是错误。这一步不能因为"历史库还空着"
就整条不出现——那正是 `cross_map` 的分层理由（`cross_map` 那一类在图库空的时候整类
不出现，`link` 不一样：它有树本身可看）。

## 三、方法论：先描述，再决定

借的是 Coco 论文 §6.1 Table 2 那条**有消融支撑**的洞察：

```
只让模型输出决定（Decision Only）  Qwen-3.5-9B  0.4832 → 0.3045
→ 先输出"这是什么 / 意图是什么"再决定，比直接判定好约 37%
```

映射到这一步：不让模型直接吐 `parent_id`，而是让它先写

```
what  这个节点讲的是什么（一句话）
line  它与哪条论证线同源（指向某个一级分支或某个历史/材料片段）
```

再写候选。**这两行不是装饰**：它们在同一次生成里排在候选前面，模型必须先写下来
才能接着写候选——这是"结构化先于决定"在单次调用里的等价形式，省掉了第二次往返
（论文那边是两次生成，成本翻倍）。

`two_stage=True` 保留了这个消融（第一段只问描述，第二段把描述当条件），
`decision_only=True` 是论文的对照组。三个模式产出形状完全相同，所以能直接比。

## 四、输出形状

```json
{
  "what": "这个节点讲的是什么（一句话）",
  "line": "它与哪条论证线同源",
  "candidates": [
    {"parent_id": "...", "label": "...", "why": "...",
     "evidence": ["node:...", "map:...", "chunk:..."]}
  ],
  "suggestion_kind": "link"
}
```

它落在 `Suggestion` 上：`kind=SuggestionKind.link`、`node_id`=新节点、
`message`=一句话人话、**`evidence`=上面那个对象的 JSON**。

`evidence` 装 JSON 而不是加字段，是硬约束：`Suggestion` 是
`ConfigDict(extra="forbid")` 且是 `/optimization/suggest` 的响应模型，给它加字段就要
重导 `openapi.json` 与 `schema.d.ts`——那两个文件正在被别人改。**为了不改契约而
把结构化载荷塞进一个自由文本字段**，与 `agent/tools.py` 把三态塞进 `data` 是同一条
取舍（那里明写着"进契约就要重导，那是另一条线的事"）。

### 证据必须能回指

每个候选的 `evidence` 只能从**这次请求里给过模型的 id** 里选：

```
node:<节点 id>              树上的节点
map:<map_id>#<标签>         历史图里的同类节点
chunk:<source_id>:<start>   材料原文的一段（按 source_id + 码点偏移跳回去）
```

解析时逐条机械校验，**不在允许集合里的一律丢弃**，并计入 `dropped_evidence`。
理由与"引文必须逐字出现在原文里"是同一条：一个指向不存在 id 的"依据"比没有依据
更坏——它看起来可查，点下去是空的。

同一个口袋里还有两处拒绝：`parent_id` 不在候选里（挂到一个不存在的父上，界面无处
可点）、`parent_id` 重复（同一个父给两个理由，用户选不了）。三个计数都进 `evidence`
的 JSON，它们是调提示词的唯一读数。

## 五、只给建议，不自动改

产出的是 `Suggestion`，而前端 `stores/structure.ts::APPLIERS` 里**没有 `link`**，
`mindmap/diagnostics.ts::APPLICABLE_KINDS` 白名单也没有它——所以界面上它只有"忽略"，
没有"应用"。这不是没接完，是唯一正确的形态：

- 改层级不可逆（撤销只救回这一次会话）；
- 论文 Appendix A 第一条 limitation 正是"用户想看到、改正、忘掉系统学到的东西"，
  作者自己把**可审阅 / 可纠正**列进 future work——我们站在他们承认没做好的那一侧。

动作层已经现成，缺的只是"应用它到底改成什么"的定义：

```
move_node + tree_invalid（环 / 层级校验）   backend/app/agent/tools.py
prefs.suggestion_accepted（合法写入来源）   backend/app/prefs/service.py
```

## 六、实测：藏节点再猜

```
cd backend && python scripts/measure_link_placement.py --per-map 2 --samples 30
            python scripts/measure_link_placement.py --analyze      # 错判分类 + 功效，不调模型
```

### 器械（先说清这个数字是怎么来的，因为下面每一条结论都依赖它）

- 从 `runs.candidate` 取 **tree** 型真图，**8 张图 × 2 个节点 = 16 个样本**
  （按图标题去重：同一主题被生成过很多次，不去重就是同一道题反复记分）；
- 每张图摘掉一个**深度 ≥ 3、带 ≥20 字说明**的节点（一级分支的父恒为中心主题，
  藏它等于送分），问模型"它该挂哪"，答案是这个节点原来的父；
- **候选顺序打乱**。`parent_choices` 按"与目标的字面重合"降序排，而真父恰恰是
  字面最像的那个——不打乱的话"每次都选第一个"就能拿 100%，那个 100% 量的是排序
  函数，不是判断力；
- 四个配置：开放集（全树里选，随机基线 `1/候选数`）/ 三选一（真父 + 2 个随机干扰，
  随机基线 `1/3`）× 先描述再决定 / 只输出决定；外加两个 **`bare`** 对照
  （剥掉跨图历史与材料，只剩这棵树）。

### 结果（deepseek-chat，16 个样本）

| 配置 | top1 | top3 | 随机基线 | 答案恰好排第一位 |
|---|---|---|---|---|
| 开放集 · 先描述再决定（历史+材料） | **14/16 = 88%** | 16/16 | 5.9% | 2/16 |
| 三选一 · 先描述再决定（历史+材料） | **15/16 = 94%** | 16/16 | 33.3% | 3/16 |
| 开放集 · **剥掉历史与材料** | 13/16 = 81% | 15/16 | 5.9% | 2/16 |
| 三选一 · **剥掉历史与材料** | 15/16 = 94% | 16/16 | 33.3% | 3/16 |
| 开放集 · 只输出决定 | 15/16 = 94% | 16/16 | 5.9% | 2/16 |
| 三选一 · 只输出决定 | 16/16 = 100% | 16/16 | 33.3% | 3/16 |

### 四个读数，每一个都改变结论

**① 远高于随机 → 这一步现在成立。** 开放集 88% vs 5.9%（14.9 倍），三选一 94% vs
33.3%（2.8 倍）。而"答案恰好排第一位"只有 2–3/16，所以这不是排序泄漏，是它在判。

**② 但撑住这个数字的不是跨图历史与材料。** 把它们全剥掉，开放集还有 81%、三选一
还有 94%。也就是说：**真正起作用的是"这棵树本身"**——真父的标题、它的子节点清单，
加上模型对概念归类的常识。历史与材料只补了 13→14 那一个（+1 个样本，在噪声里）。

这条必须写在这里，因为它是这一版最容易被读反的地方：四样输入列在一起看起来像一个
整体，实测却说其中两样（库里最贵的那两样：向量缓存、材料库）**还没证明有用**。

**③ 论文那条 37% 的增益在这里没有复现，而且是反的**（94% → 100%，
只输出决定反而略高）。原因是**天花板**：这批样本对 deepseek-chat 太简单，
38 个百分点的空间里只剩一两个样本的差别。要说清这条洞察在这个仓库上值不值，
得换更难的题（更深、兄弟更多、父节点标题更不含信息的树），而那样本现在没有。

**④ 错的那些是跨支，不是差一层。** 自动分类（`--analyze`）：

```
open/decide        n=16 完全正确=14  层级相邻/同支=0  完全跑偏=2
open/decide/bare   n=16 完全正确=13  层级相邻/同支=1  完全跑偏=2
```

两条错判都是**跨一级分支**（"抵消只处理剩余排放"被放进"碳交易"那一支，而不是
"误区"那一支）。所以 88% 是如实的，没有"放宽到相邻层就更高"这种余地。

样本：`城市垃圾分类政策`，藏起「减量化资源化无害化」（真父「政策目标与原则」）。

```json
{
  "what": "垃圾分类政策的核心目标：减量化、资源化、无害化三端并进",
  "line": "政策目标与原则（一级分支 goal）",
  "candidates": [{
    "parent_id": "goal",
    "label": "政策目标与原则",
    "why": "它讲的是政策要达成的核心目标，属于「政策目标与原则」这一支，历史图里同类节点也都挂在这里。",
    "evidence": [
      "map:run:probe-expand-on#减量化资源化无害化",
      "map:run:run-mwo9724h-wmzfehzs#减量化资源化无害化",
      "map:run:probe-expand-on3#减量化资源化无害化"

  }],

```

**这一条是"跨图历史真的起作用"的样子**：三张历史图里的同名节点都挂在「政策目标与
原则」下面，模型据此判定——`evidence` 三项全是可回指的历史图 id，没有一句"根据用户
习惯"。

样本：`碳中和三句话说清`，藏起「误区三：买碳信用就万事大吉」（真父「误区不等于
完全不排放」）。

{
  "what": "把碳中和简化为买碳信用抵消，忽视实质减排与信用质量",
  "line": "误区辨析线——与「误区不等于完全不排放」下的其他误区同源",
  "candidates": [
    {"parent_id": "e", "label": "误区不等于完全不排放",

     "evidence": ["map:run:run-mwnijov6-ergj6bk2#误区三：买碳信用就万事大吉",
                  "node:e", "node:e1", "node:e2", "node:e4"]},
    {"parent_id": "a2-2", "label": "碳信用抵消",
     "why": "节点核心讲的是碳信用抵消的局限与风险，可作为该子节点下对抵消手段的警示说明",
     "evidence": ["node:a2-2", "node:a2"]},
    {"parent_id": "d3", "label": "最后抵消：碳汇与碳移除",

候选为什么也讲得通，然后自己选。

## 七、自评：没有"这个用户的历史"，只靠跨图历史与材料，能做到多准

**准到 88%（开放集）/ 94%（三选一），但那不是跨图历史与材料的功劳。** 这两句必须
一起说，单说前一句会让人以为"再攒点历史就更准"，单说后一句会让人以为"这条路没用"。

三条限制，按对结论的影响排序：

**① 样本 16 个，8/8 与 14/16 之间没有统计差别。** 16 个样本上 88% 的 95% 置信下界
约 62%——"高于随机（5.9%）"这个判断很稳，"准确率是 88% 而不是 95%"这个判断完全不稳。

**② 题太简单，两个消融都测不出结论。** 16 个样本里模型几乎打满，于是"先描述再决定
vs 只输出决定"（论文里 0.4832 vs 0.3045）在这里只差一个样本，"有历史 vs 无历史"只差
一个样本。**要在这个仓库上判这两件事，需要更难的题**：藏更深的节点、选兄弟更多的
父节点、或者选标题里不含主题词的父节点（现在的父节点标题几乎都在替模型报答案）。

**③ 这 16 道题的正确答案本来就是唯一的**，而真实场景里"这个节点该挂哪"经常有两个
都讲得通的答案（上面那三个候选就是）。把它按唯一答案记分，是**低估**了这一步。

### 那还需要多少条真实 `add` 事件

`--analyze` 按 α=.05 / power=.8 算的配对样本量：

```
要检出 88% → 92%（+4pt）  需要 562 个样本
要检出 88% → 94%（+6pt）  需要 259 个样本
要检出 88% → 98%（+10pt） 需要 105 个样本
```

所以：**想把"这个用户的历史"这一格的增益量出来（假设它能带来 +6 个百分点），
大约需要 259 条真实 `add` 事件。** 一个每天加 3 个节点的活跃用户，那是 12 周左右；
现在的库里是 **0 条**。

在那之前，这一列的价值不在"训练"，在**可观测**：`parent_ids(map_id)` 能让"用户加的
节点挂在哪"第一次成为一条能读的行，而这件事本身就是补列的全部理由（见
`docs/EDIT-LOG.md` 二·六）。要更早拿到第一批样本，最短的路是让 `parent_id` 先在
本地跑起来——下一次有人加节点，库里就有第一行。
