# 检索评估基线（recall@k / MRR / nDCG / coverage）

一句话：**改检索之前先量一遍**。这份文档给出一套不依赖模型、不依赖人工标注的检索层
测试集与四个指标，以及一张当前基线的表。以后每次改检索，跑一条命令、把新表贴进来、
跟上表比，就知道"这次改动到底有没有变差"。

配套脚本：`backend/scripts/evaluate_retrieval.py`。用例：
`backend/tests/test_retrieval_eval.py`。

## 1. 为什么不用 ragas

`ragas` 评的是**生成质量**（faithfulness / answer relevancy / context precision），
它的输入是人工标注的 ground truth（问题 + 标准答案）。我们要的不是那个：给定一个
query，`top_k` 里到底有没有该被召回的段落——这纯粹是检索层的事，和"模型答得好不好"
是两个失效面。混在一起量，检索退化会被提示词退化掩盖。

成本差别更实际：标注一份标准答案要人，而**章节结构就是现成的标注**。一份有目录的
材料天生自带"这个标题管这几段原文"这份对应关系。所以这套东西**一个模型都不调、一条
标注都不要、一个新依赖都不装**（纯标准库 + 仓库里已有的 `heading_outline`）。

## 2. 测试集怎么造

对每份材料单独跑 `heading_outline`（`app/knowledge/service.py`，逐行扫原文、只取一级
标题、条目互不重叠），然后：

| 步骤 | 规则 |
|---|---|
| query | 章节标题原文 |
| relevant | `[start, start+coverage)`——标题行首到下一个同级标题的原文区间 |
| 每份材料条数 | 最多 8 条，按**原文顺序等距取样**（不按 coverage 取最大） |
| 排除 | 标题 < 4 字 / 章节 < 200 字 / 章节占全文 > 60% |

三条排除的理由（细节见脚本文档字符串）：

- **标题 < 4 字**：3 个汉字只切得出 2 个 bigram，BM25 的 IDF 撑不起区分度，这种 case
  会退化成"必然命中"。4 字起才有 3 个 bigram。
- **章节 < 200 字**：父块是 450–700 字切出来的，200 字以下的章节没有独立边界，命中
  它的那一块必然大部分落在章外，判定噪声大于信号。
- **章节 > 全文 60%**：这种章节本身就是"整份材料找不找得到"的弱标签，永远满分。实测
  两批材料都没撞到这条（最大单章：`docs/AGENT_PLAN.md` 16%、桌面那份 docx 48%），它是
  安全阀。

`EvalCase` 只有三个字段：`query` / `source_hash`（材料的 `sha256(text)`）/
`relevant`（**区间列表**，允许一段 case 有多段）。用指纹而不用文件名或 `Source.id`：
前者会变，后者是每次请求现生成的 uuid4。

**命中判定**：检索返回的 `EvidenceHit` 区间与 `relevant` 的交集 ≥ **命中块自身长度的
20%** 才算命中。方向选"占命中块的比例"而不是"占 relevant 的比例"——后者会把所有真
命中判掉（600 字的父块整块落在 3000 字的章内也只占 20%）。20% 被两侧夹出来：

- 下界：父块之间有 `CHUNK_OVERLAP_CHARS = 100` 的重叠，一个与章节只共享那 100 字的
  邻块，在 600 字父块上是 100/600 ≈ 17%、在 700 字上限上是 14%——都低于 20%，判为
  不命中，正是要的（那块讲的是别的事，只是尾巴搭在同一段文字上）。
- 上界：章节边界是标题行首，父块带"句首吸附"，真讲这一章的父块常有 30%–60% 落在章外；
  阈值抬到 40% 以上就开始把真命中判掉。

代价写在明处：150 字的短父块若整块就是那 100 字重叠，比值 67% 会被判成命中；但
`_merge_short` 会把 150 字以下的块并掉，真实语料里几乎不出现。

|---|---:|---:|---:|---:|

## 3. 四个指标

设某条 case 的 relevant 合并去重后总长 `L`，前 `k` 条命中依次新增覆盖的比例
`g₁…g_k`（每条只算"之前没覆盖过"的字，故 `Σgᵢ ≤ 1`）：

| 指标 | 定义 | 口径 |
|---|---|---|
| `recall@k` | `top_k` 内有没有任何一条命中（判据见上），取 case 平均 | **二值** |
| `mrr@k` | `1 / 第一条命中的名次`（没命中记 0），取 case 平均 | 名次 |
| `ndcg@k` | `Σ_{rank≤k} g_rank / log2(rank+1)`，取 case 平均；IDCG 取 1 | 折扣累加 |
| `coverage@k` | `Σ_{rank≤k} g_rank`，取 case 平均 | **比例** |

`ndcg` 的 IDCG 取 1："一条命中完全覆盖 relevant 且排第一"是可达上界（父块区间理论上
可以正好等于章节区间）。代价是"排第一但只覆盖一半"得 0.5，比常规二值 nDCG 更严。

**`recall` 与 `coverage` 的口径差异是这套东西的核心，不能只看一个**：

- `recall@k` 回答"这一章有没有被摸到"——一条命中覆盖 20% 就记满分 1；
- `coverage@k` 回答"这一章被摸到了多少"——同一条命中只记 0.2。

两者一起看才分得出"命中一段就收工"（recall 高、coverage 低）与"真把整章召回"
（两者都高）。只看 recall，会把"父块够大、随便沾一点就算命中"的退化当成进步——而
本仓库当前恰好是父块模式（`MINDMAP_PARENT_RETRIEVAL` 默认 1），这个风险是实打实的。

读数：

- **父块召回是这批材料上唯一还有区分度的开关**：`parent 0 → 1` 让 `R@1` +6.9pp
  （93.1 → 100）、`MRR@3` +3.4pp、`NDCG@10` +3.9pp、`COV@10` +5.4pp。`coverage` 的
  涨幅最小，符合预期：父块更大，命中的区间更宽，但"这一章被摸到多少"受限于名次。
- **`hybrid` 两行完全相同**：本机没有 embedding 凭证（`MINDMAP_EMBEDDING_API_KEY` /
  `DASHSCOPE_API_KEY`），`hybrid=1` 实际退成纯 BM25。这是环境事实，脚本每次会在表头
  上方打一行提示。有凭证的机器上这两行才该分开——那时重跑一遍，`--check` 会盯住它。
- **`lib=1` 与 `lib=0` 逐位相同**，且这不是"开关没生效"：`lib=1` 时请求内来源被清空、
  只靠知识库，命中带的是**持久 id**（探针验证过），区间与请求内那批逐位一致——因为库
  里就是同一批正文。这一行量的是"关掉浏览器再回来还能不能召回"，答案是能。
- **`R@3/R@5/R@10` 三列全是 100%**：见第 7 节，这是这套构造的已知天花板，不是好消息。

## 6. 怎么用

改检索（切块参数、融合权重、父块开关、查询改写……）之后：

```
cd backend
python scripts/evaluate_retrieval.py --ladder                # 1. 跑一遍，看表
python scripts/evaluate_retrieval.py --markdown -            # 2. 产出一段可贴的表格 + 基线块
python scripts/evaluate_retrieval.py --check                 # 3. 与文档里记录的基线比
```

第 3 步读的是**本文件最后那段 ```json 围栏**，退出码 1 表示有配置掉超过 **2pp**（绝对
百分点），并逐条指出是哪个配置的哪个指标（下面这段是格式示例，`↓` 那一行就是"是哪个
配置的哪个指标"的答案）：

```
基线不符（容差 2.0pp，共 2 处）：
  ↓ rag/hybrid=0 parent=1 lib=0  recall@1  100.0% → 96.6%（-3.4pp）
  ↓ ladder/title_drop  coverage@10  50.5% → 46.2%（-4.3pp）
```

三条使用纪律：

1. **配置从基线里取**，不用你记得当初开了哪些开关：`--check` 会把基线里那 8 个配置
   原样重跑一遍。要换配置集，就用 `--markdown` 重新生成一段基线。
2. **贴表要连围栏一起贴**。只贴上面那张人看的表，`--check` 读不到基线（脚本会报
   "基线文件里没有 ```json 围栏"）。
3. **别只看 recall**。当前 `R@3/5/10` 已饱和，真正有信号的是 `R@1`、`NDCG@10`、
   `COV@10` 与 `--ladder` 的后两档（见下一节）。

不接进 CI：那需要材料随仓库走（多份大文档），而 `--check` 的用途是"改完检索手动跑一下"。
它是一个能返回退出码的普通脚本，想接随时能接。

## 7. 系统性偏差：标题当 query 到底偏多少

这套测试集有一个**结构性**偏差：query 是章节标题原文，而标题就是这一章的第一行。于是
"该被召回的那段"与"query 的用词"完全重合，检索只需要做字符串匹配。真实用户的问题会
更口语、更远。

偏差有多大，可以用三条独立的量来框：

**(a) 饱和。** 29 条 case、8 个配置，`R@3/R@5/R@10` **全部 100%**，`R@1` 只在 93.1% 与
100% 两个值之间跳（唯一的落差来自 parent 开关，6.9pp）。`R@3` 以上这三列当前的**判别力
为零**：任何"k≥3 照样全中"的退化都不会在这三列上出现。还有信号的是 `R@1`（6.9pp 的可动
空间）、`NDCG@10`（43.2 → 47.1，3.9pp）与 `COV@10`（52.4 → 57.8，5.4pp）。理论上
`R@1` 的可比区间是 10.7%（随机地板）→ 100%，共 89.3pp，可这套测试集把 8 个配置全压在
了天花板上——**天花板效应本身就是偏差的量纲**：得分不能再好了，指标也就不能再告诉你
什么。

**(b) 词面黏度。** 用同一个 `wording_overlap`（query 的 bigram 落在目标原文里的比例）
量三批东西：

| query 类型 | 词面重合 |
|---|---:|
| 章节标题（= 本测试集的 query） | 100.0% |
| 标题去掉每三个字里的第三个 | 57.6% |
| 手写口语问法（4 条，对目标材料全文） | 11.1% / 30.0% / 36.4% / 57.1%，均值 **33.7%** |
| 无关中文串（噪声地板） | 0% – 22.2% |

真实问法落在 **11%–57%**（均值 34%），噪声地板在 0–22%——真实问法贴着噪声地板上沿，
而测试集钉在 100%。注意手写那几条是**对全文**量的（分母更大，重合率被抬高），所以
33.7% 还是个上限。

**(c) 距离阶梯的斜率。** 同一批 case，只换提问写法：

| 台阶 | 词面重合 | R@1 | R@3 | R@5 | R@10 | COV@10 |
|---|---:|---:|---:|---:|---:|---:|
| `title`（标题原文） | 100.0% | 100.0% | 100.0% | 100.0% | 100.0% | 57.8% |
| `title_drop`（每三字去一字） | 57.6% | 79.3% | 93.1% | 100.0% | 100.0% | 50.5% |
| `title_half`（只留前半截） | 100.0% | 86.2% | 96.6% | 100.0% | 100.0% | 51.6% |
| `body_sentence`（正文首句，长句） | 100.0% | 100.0% | 100.0% | 100.0% | 100.0% | 69.9% |

两个方向要分开读：

- **去词/换词这条轴**（`title → title_drop`）：词面重合 100% → 57.6%，`R@1` 从 100% 掉到
  **79.3%（-20.7pp）**，`R@3` -6.9pp，`COV@10` -7.3pp。只有两个点，够看方向、不够拟合
  曲线；真实问法的重合率（34%）比 57.6% 还低，所以沿这条轴**只能给方向**：真实 `R@1`
  不高于 79.3%。
- **少信息这条轴**（`title_half`）：词面重合仍是 100%（前半截是标题的连续子串），但
  `R@1` 掉到 86.2%（-13.8pp）。这说明 `wording_overlap` 只刻画"用词是否来自材料"，不
  刻画"信息量被砍掉一半"——两个偏差点彼此独立，得分别看。
- `body_sentence` 反而更好（`COV@10` 69.9%）：长 query 匹配到的块更多。它**不是**更难
  的 case（它逐字来自材料），别把它当"口语问法"读。

**结论（量化）**：基线表里的 `R@1 = 100%` 至少高估 **20.7pp**，合理上界是 **79.3%**；
下界是无信息地板 10.7%。`R@3/5/10` 的 100% 不能当作"检索已经完美"的证据，它只说明
**这批 query 太容易**。真实问法下 `R@3` 大概也不会满，但**这个测试集量不出来**。

**怎么补**（按性价比排序）：

1. **最便宜**：把 `--ladder` 的 `title_drop` / `title_half` 两行当主看板。它们对同一批
   原文区间、同样零标注，但可用空间是 `title` 行的 2–3 倍：`title` 行的 `R@1` 只能在
   6.9pp 里动（93.1 ↔ 100），这两行分别能在 20.7pp / 13.8pp 里动（100 → 79.3 / 86.2）。
   `--check` 已经把 `ladder` 一起比了——饱和的 `R@3` 抓不住的退化，这两行能抓住。
2. **最实在**：手写 20–30 条真实问法（换词、口吻、带疑问），人工标到章节号。
   `EvalCase` 的字段已经够用（`source_hash` + 手填 `relevant`），半天工作量，能把偏差
   从"至少 20pp"压到 5pp 以内。这一步没有任何自动构造能替代：**换词需要语言知识，
   而结构里没有语言知识**。
3. **不做**：用模型生成问题（LLM 改写/合成）。它会把不确定性引入尺子本身——每次重跑
   数字都会漂，与"可比的数字"这个目标直接冲突。真要用，也只能生成**一次**然后冻结成
   固定文件（等于走第 2 条），不能每次现生成。

## 8. 边界

- **不改任何检索实现**：只调用 `search_parent` / `search_sources`，`service.py` 一行未动。
- **不引入依赖**：纯标准库 + 仓库已有模块（`heading_outline`、`library.content_hash`、
  `parse_text` / `parse_bytes`）。没有装 ragas。
- **不碰前端、不碰 `RAG-DECISIONS.md`**。
- **不碰真实库**：`lib=1` 时库落在临时目录、跑完删掉，`backend/data/mindmaps.db` 不被
  任何一次评估写过。
- `--source-mode` 只是**记录**（`MINDMAP_SOURCE_MODE` 只影响正文进不进 prompt，而本
  脚本不碰生成），所以 `rag` 与 `full` 两行数字逐位相同——那恰好是"它没漏进度量"的
  证据。要验证这一点：`--source-mode rag,full`，看 16 行里成对相等。

## 9. 机器可读基线

下面这段是 `--check` 的唯一输入。它是上面第 4 节那张表的原样 JSON（多一个
`generated_at` 与每份材料的字数/章节数）——**不要手改数字，不要删围栏**。要更新基线：

## manual 套：手写真实问法（校准用）

title 套的 query 就是章节第一行、词面重合 100%，把 `R@1` 顶到了 100%——它自己考自己，至少高估 20.7pp（见上一节的阶梯实验）。

manual 套用 **28 条手写问法**，三种距离各占约三分之一，对目标区间的词面重合**均值 31.4%**（近 31–45%、中 30–47%、远 12–27%），粒度分布：整章 21 / 章内某段 5 / 跨章 2。问法长这样：`答辩那天网线断了还能讲吗`、`前端当初为什么不选 React`、`为什么空行比句末标点优先，这不是反过来了吗`。

| 配置 | case | R@1 | R@3 | R@5 | R@10 | COV@10 |
|---|---|---|---|---|---|---|
| parent=0 | 28 | **71.4%** | 85.7% | 92.9% | 96.4% | 53.4% |
| parent=1 | 28 | **67.9%** | **92.9%** | 92.9% | 92.9% | 52.7% |

### 一个反转：父块召回换的是"排第几"，不是"有没有"

**title 套上 parent 0→1 是 +6.9pp，manual 套上 `R@1` 变成 -3.5pp**（71.4% → 67.9%），但 `R@3` 是 **+7.2pp**（85.7% → 92.9%）。

解释得通：父块返回的区间大、容错高，更容易"摸到"目标章节（`R@3` 涨）；但 top-1 也更容易被一个"大而泛"的块占掉（`R@1` 跌）。单级块小、更精准，排第一更准。

所以准确的说法不是"父块召回 +6.9pp"，而是：**它把召回从"排第一"换成了"排前三"**。这个交换值不值，取决于下游看几条——只看 top1 是亏的，看 top3 是赚的。

### 怎么用

改检索时**先看 manual 套**（接近真实），title 套只作回归（保证没变差）。

```
cd backend
python scripts/evaluate_retrieval.py --suite manual   # 真实难度，看这个
python scripts/evaluate_retrieval.py --check          # 回归，只比 title 套
```

`--check` 不比 manual 套：它的绝对分数更低、波动更大，当 CI 门槛会频繁误报。

### rerank：父块丢掉的那块 top1，被重排补回来了

`MINDMAP_RERANK`（`app/knowledge/rerank.py`）接上之后的读数。测法是**纯 BM25 + 父块**
（`--hybrid 0`：当时 hybrid 那几行还没跑完，先把重排这一维单独量出来）：

```
cd backend
python scripts/evaluate_retrieval.py --suite manual --hybrid 0 --parent 1 --library 0 --rerank 0
python scripts/evaluate_retrieval.py --suite manual --hybrid 0 --parent 1 --library 0 --rerank 1
```

| 配置 | case | R@1 | R@3 | R@5 | R@10 | MRR@3 | NDCG@10 | COV@10 |
|---|---|---|---|---|---|---|---|---|
| rerank=0 parent=1 | 28 | 67.9% | 92.9% | 92.9% | 92.9% | 78.0% | 43.8% | 52.7% |
| rerank=1 parent=1 | 28 | **82.1%** | 92.9% | **96.4%** | **100.0%** | **86.9%** | **49.7%** | **60.5%** |
| 差 | | **+14.2pp** | ±0 | +3.5pp | +7.1pp | +8.9pp | +5.9pp | +7.8pp |

三件事值得单独说：

- **`R@1` +14.2pp 是这个仓库里检索层单项改动的最大一笔**（对照：`parent 0→1` 在
  title 套上是 +6.9pp、在 manual 套上 `R@1` 是 **−3.5pp**）。重排做的正是父块模式
  丢掉的那件事——"在已有的候选里把最相关的排到最前"。
- **父块召回与重排不是取舍，是可以同时拿到的**：`parent=0` 的 `R@1` 是 71.4%，
  `parent=1` 掉到 67.9%，而 `parent=1 + rerank` 是 82.1%。也就是说父块那 +7.2pp 的
  `R@3` 覆盖**不是**用 top1 精度换来的，只要补上重排这一层，两个指标可以一起涨。
- **`R@10` 从 92.9% 涨到 100% 不是重排排序排出来的，是扩池扩出来的**。原来
  `top_k=10` 只取 10 条子块候选，折父块时同一父块的多条会并成一条，实际返回往往
  不到 10 条；重排打开后候选池是 `max(top_k*4, 10) = 40` 条，折完能凑满 10 个不同
  父块。**读数要按这个拆开读**：`R@1`/`MRR` 是重排的功劳，`R@5`/`R@10` 里混着扩池
  的功劳，两者在同一次开关里。

模型选择是量出来的，不是选的：同一批候选（相关 / 部分相关 / 无关）在两个模型上

| 模型 | 相关 | 部分相关 | 无关 | 读数 |
|---|---|---|---|---|
| `qwen3-rerank` | 0.798 | 0.379 | 0.157 | 三档拉得开，默认 |
| `gte-rerank-v2` | 0.357 | 0.141 | 0.006 | 全挤在低分区，间距更小 |

`gte-rerank-v2` 的极差（0.351）看着不小，但真候选之间相邻名次的差值普遍 < 0.02，
分数挤在一起时重排的稳定性全靠稳定排序兜底，收益会缩水。所以 `DEFAULT_MODEL` 是
`qwen3-rerank`，`gte-rerank-v2` 留作可选项（`MINDMAP_RERANK_MODEL=gte-rerank-v2`）。
`gte-rerank`（不带 v2）官方公告 2026-05-30 下线，实测该账号 403 无权限。

### 对照组：换一个更小的本地 cross-encoder，收益归零

为了把"父块太粗，分数挤在一起"这个担心查实，本地跑了同一套 manual case，只把
打分器换成 `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`（117M，多语种，CPU）：

| 打分器 | R@1 | R@3 | R@10 | MRR@3 | 极差中位 | top1−top2 中位 | 单次耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 无（rerank=0） | 67.9% | 92.9% | 92.9% | 78.0% | — | — | — |
| mmarco MiniLM（本地替身） | 67.9% | 89.3% | 96.4% | 76.8% | 0.4551 | 0.2607 | 12.9s/40 条 |
| qwen3-rerank（线上默认） | **82.1%** | 92.9% | 100.0% | **86.9%** | 0.26–0.29 | — | 0.88s/23 条 |

**结论一：分数挤在一起不是父块颗粒度的锅。** 本地替身在 34–40 条父块上的极差
中位 0.4551、top1−top2 间隔中位 0.2607——比 `qwen3-rerank` 的 0.26 跨度还宽。
450–700 字的粗块没有让分布塌缩，cross-encoder 照样能在这批块上给出分明的分数。
真正决定收益的是**模型对中文长块的判别力**：同一个入口、同一批父块，
`qwen3-rerank` 给 +14.2pp，117M 的 mmarco 给 0.0pp、`MRR@3` 还掉 1.2pp。
所以"用哪个模型"这件事的量级，比"父块多粗"大得多。

**结论二：有一类查询上分数确实会挤，但原因不是颗粒度。** 27 次调用里有 **8 次
（30%）标准差 < 0.05**，且这几次的 `max` 只有 0.0075–0.0211——**整批候选被判为
"都不相关"时分数会挤在极低区**，相邻差值只有 0.001 量级，此时重排等于按噪声
排序。替身那 −3.6pp 的 `R@3` 恰好是 1 条 case（28 条里 1 条 = 3.57pp）从 top3
掉出去，与这个机制一致。它不会凭空把无关项排到前面（那些查询的 top1 本来就不
是正解），但**会消耗掉原本靠 BM25 名次偶然保住的那一条**。

复现命令（先拉模型，再跑；CPU 上整轮 5–6 分钟）：

```
python -c "from huggingface_hub import snapshot_download as d; print(d('cross-encoder/mmarco-mMiniLMv2-L12-H384-v1'))"
python scripts/measure_rerank.py --local-model <上一步的目录>
```

### 同一开关在 title 套上是**负**收益

| 配置 | case | R@1 | R@3 | MRR@3 | NDCG@10 | COV@10 |
|---|---|---|---|---|---|---|
| title rerank=0 parent=1 | 29 | 100.0% | 100.0% | 100.0% | 47.1% | 57.8% |
| title rerank=1 parent=1 | 29 | **96.6%** | 100.0% | 98.3% | 45.9% | 56.7% |
| 差 | | **−3.4pp** | ±0 | −1.7pp | −1.2pp | −1.1pp |

（命令：`--suite title --hybrid 0 --parent 1 --library 0 --rerank 1`。）

不是"title 套已饱和所以涨不动"，是**方向反过来**。机制：title 套的 query 就是
章节第一行、与目标区间词面重合 **100%**，BM25 在这种场景下已经是最优排序，没有
任何语义信号比字符串本身更准；reranker 按语义重排，会把"字面最像"的那条挤下去。

把两套放一起才看得出这个开关真正依赖什么：

| 测试集 | 词面重合 | `R@1` 变化 |
|---|---:|---:|
| title（标题当 query） | 100% | −3.4pp |
| manual（手写真实问法） | 31.4% | **+14.2pp** |

**`MINDMAP_RERANK` 的默认 1 只对"自然语言问法"成立**。将来若有调用方拿检索去做
标题定位、关键词跳章这类字面检索，应当在那里显式关掉——开着是静默的负收益
（结果照样返回，只是顺序变差）。

### 耗时

`qwen3-rerank`，候选是 450–700 字的父块：

| 候选条数 | 中位 | 最小 | 最大 |
|---:|---:|---:|---:|
| 12 | 586.6ms | 579.4ms | 929.9ms |
| 23 | 883.1ms | 580.9ms | 891.2ms |

按 5 秒检索预算算占 **12%–18%**。候选条数是 `max(top_k*4, 10)`：`top_k=3` 时 12 条、
`top_k=5` 时 20 条、`top_k=10` 时 40 条（实际条数受材料切得出多少父块限制，
上表第二行只有 23 条就是这个原因）。

无凭证时这条路的固定成本只有 TLS + 往返：对同一端点连打 6 次（401 也走完整
握手与往返）中位 **383ms** / 最小 378ms / 最大 587ms。也就是说"多一次调用"的
**网络**部分约 0.38 秒，剩余是服务端推理。

**评估脚本必须显式钉住这一维**，所以有 `--rerank 0|1`，且**默认 0**：本文件里所有
历史基线都是关着重排采的，而线上 `MINDMAP_RERANK` 已经默认开——不钉的话，同一份
配置在配了凭证的机器上会读出另一个数，`--check` 会莫名其妙地挂。这个默认值现在
有两条依据：`--check` 要基线稳定；**title 套本来就该关着重排**（开着掉 3.4pp）。
